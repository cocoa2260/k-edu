## 먼저 정할 계산 약속

벡터는 숫자를 순서대로 나열한 것이고, 행렬은 벡터를 행과 열로 쌓은 표다. Shape는 표의 크기다. 3×2는 3행 2열이며, 3개 Token에 각각 2개 숫자가 있다고 읽을 수 있다. Token은 모델이 처리하는 단위로 실제 단어 하나와 항상 일치하지 않는다.

이 강의의 벡터는 **행벡터**다. n×d 입력에 d×m 가중치를 곱하면 n×m이 된다. 곱할 때 안쪽 크기 d가 맞아야 한다. 전치(ᵀ)는 행과 열을 바꾸는 연산이다. 같은 위치끼리 더하려면 크기가 같아야 한다.

숫자는 원리를 보기 위해 직접 정한 **합성 예제**다. 실제 한국어 Tokenizer가 만든 벡터나 학습한 모델의 값이 아니다. U01은 2차원, U02는 한 Head의 2차원, U03 Multi-head와 U04 위치 예시는 별도의 4차원 예제다. 서로 다른 예제를 한 모델의 연속 실행 결과로 이어 붙이지 않는다. 계산 중에는 정밀도를 유지하고 표의 결과만 소수 넷째 자리로 반올림한다.

## K2-02.U01 · 신경망 한 층과 Activation

### 입력에 가중치를 곱하고 편향을 더한다

Forward는 주어진 입력과 현재 모델 값으로 출력을 계산하는 과정이다. Weight는 입력을 섞는 가중치, Bias는 더해 주는 값이다. 학습은 데이터와 목표를 이용해 이런 값을 조정하는 과정이고, 이번 활동에서는 고정한 값으로 Forward만 계산한다.

입력 x = [2, 1], Bias b = [-1, 0]으로 둔다. Weight W는 다음과 같다. 이 표에서는 행이 입력 성분, 열이 출력 성분이다.

| W | 출력 1 | 출력 2 |
|---|---|---|
| 입력 1의 가중치 | 1 | -1 |
| 입력 2의 가중치 | 2 | 1 |

활성화 전 값 z = xW + b를 계산한다.

| 출력 | 가중합과 Bias | 활성화 전 z | ReLU 적용 후 |
|---|---|---|---|
| 1 | 2×1 + 1×2 - 1 | 3 | 3 |
| 2 | 2×(-1) + 1×1 + 0 | -1 | 0 |

ReLU는 각 값과 0 중 큰 값을 남기는 Activation(활성화 함수)이다. 결과는 [3, 0]이다. Shape는 x 1×2, W 2×2, b는 두 출력에 더할 길이 2, 결과 1×2다.

### 활성화 함수가 필요한 이유

가중합과 Bias만 여러 번 합성하면 하나의 가중합과 Bias로 정리할 수 있다. 중간에 비선형 함수를 넣으면 그와 다른 형태의 변환을 표현할 수 있다. ReLU는 이해하기 쉬운 예시이며 모든 Transformer가 ReLU를 쓰는 것은 아니다. 실제 모델에서는 다른 활성화나 게이트 구조도 확인해야 한다.

이 계산의 음수가 ‘나쁜 의미’, 양수가 ‘좋은 의미’인 것은 아니다. 숫자 한 성분을 업무 판단이나 모델의 생각으로 곧바로 해석하지 않는다. 이 한 층의 계산만으로 언어 이해나 환불 답변 품질을 입증할 수도 없다.

**작성 활동 A:** 위 계산을 다시 하고 Bias를 [0, 0]으로 바꿨을 때를 구한다. 입력 길이가 2인데 3×2 W를 곱할 수 없는 이유를 Shape로 적는다. 행벡터 표기와 구현 도구의 Weight 저장 방향이 다를 수 있으므로 표기부터 맞춘다. [Linear](https://docs.pytorch.org/docs/stable/generated/torch.nn.Linear.html) · [ReLU 공식 정의](https://docs.pytorch.org/docs/stable/generated/torch.nn.ReLU.html)

## K2-02.U02 · Self-Attention의 계산

### Token의 표현에서 Q·K·V를 만든다

Self-Attention은 같은 입력의 각 위치에서 만든 Query와 Key의 점수를 이용해 Value를 섞는 계산이다. Query(Q)는 현재 위치의 조회 벡터, Key(K)는 비교할 벡터, Value(V)는 가중합할 정보 벡터다. 세 벡터는 별도 가중치로 만들 수 있다. 검색 DB에 저장한 문서나 검색용 Embedding과 역할을 혼동하지 않는다.

Token T1·T2·T3의 입력 X를 각각 [1, 0], [0, 1], [1, 1]로 둔다. Q=XWQ, K=XWK, V=XWV로 계산한다. 여기서는 Bias를 생략하고 WQ·WK는 2×2 단위행렬, WV는 대각선이 2와 4인 행렬이다. 단위행렬은 입력을 그대로 통과시킨다. 이 예시의 Q=K는 가중치를 그렇게 정했기 때문이며 일반적인 요구사항은 아니다.

| 위치 | 입력 X | Q | K | V |
|---|---|---|---|---|
| T1 | [1, 0] | [1, 0] | [1, 0] | [2, 0] |
| T2 | [0, 1] | [0, 1] | [0, 1] | [0, 4] |
| T3 | [1, 1] | [1, 1] | [1, 1] | [2, 4] |

X·Q·K·V는 모두 3×2다. 하나의 Head가 비교에 쓰는 Key/Query 차원 dₖ는 2다.

### T3의 Query 한 행을 끝까지 계산하기

내적은 같은 위치 성분끼리 곱해 더한 값이다. T3의 Query [1, 1]을 세 Key와 각각 비교하면 1, 1, 2다. 이를 √dₖ = √2로 나눈다. 이 스케일링은 차원이 커질 때 내적의 규모가 커지는 효과를 조절한다. 실제 학습 값의 모든 통계가 항상 같다는 주장은 아니다.

Softmax는 점수마다 지수함수를 적용한 뒤 그 합으로 나누어, 합이 1인 가중치를 만든다. 여기서는 **한 Query가 볼 수 있는 Key 방향**으로 정규화한다.

| 비교 Key | 내적 | √2로 나눈 점수 | Softmax 가중치 |
|---|---|---|---|
| T1 | 1 | 0.7071 | 0.2483 |
| T2 | 1 | 0.7071 | 0.2483 |
| T3 | 2 | 1.4142 | 0.5035 |

가중치를 Value에 곱해 더한다. 첫 성분은 약 0.2483×2 + 0.2483×0 + 0.5035×2 = **1.5035**, 둘째 성분은 약 0.2483×0 + 0.2483×4 + 0.5035×4 = **3.0070**이다. 표시값이 아닌 반올림 전 가중치로 계산한 결과다.

전체 계산은 **점수 = QKᵀ/√dₖ → 필요하면 Mask 적용 → 행별 Softmax → V와 곱하기**다. QKᵀ는 3×3, 가중치도 3×3, V는 3×2이므로 출력은 3×2다. Mask가 없는 경우에는 각 위치가 세 Key를 모두 본다. 생성용 Causal Mask는 U04에서 추가한다.

### Softmax를 적용하는 위치와 뜻

지수 계산에서 큰 수가 생기지 않도록 한 행의 최댓값을 모든 점수에서 빼고 계산할 수 있다. 모든 점수에 같은 상수를 더하거나 빼도 Softmax 가중치는 같다. 반면 점수의 크기를 곱해서 바꾸거나 √dₖ를 생략하면 일반적으로 가중치가 달라진다.

Attention의 가중치는 **현재 계산에서 어떤 V를 얼마나 섞었는가**를 보여준다. 답변의 사실성, 문서의 접근 권한, 사람에게 설명 가능한 원인을 보장하는 점수가 아니다. 다음 Token 선택 확률을 만들 때 사용하는 출력단 Softmax와도 입력·정규화 대상이 다르다. 이번에는 어휘 전체에 대한 다음 Token 확률을 계산하지 않는다.

**작성 활동 B:** T3의 계산표와 Shape를 완성하고, T2가 미래 T3를 볼 수 없어야 한다면 어느 점수를 막아야 하는지 표시한다. [원 논문의 Attention 설명](https://arxiv.org/html/1706.03762v7)

## K2-02.U03 · Transformer Block

### Multi-head는 다른 투영으로 여러 번 계산한 뒤 합친다

Head마다 Q/K/V를 만드는 가중치를 달리 두어 서로 다른 표현에서 관계를 계산할 수 있다. Head가 각각 문법·감정·사실성을 반드시 담당한다고 미리 정해진 것은 아니다.

별도의 Shape 예제로 Token 수 n=3, 모델 차원 d_model=4, Head 수 h=2, Head당 Q/K/V 차원 2를 가정한다. 이 표는 단순한 Multi-head 예시이며 모든 실제 모델의 Q Head 수와 KV Head 수가 같다는 뜻은 아니다.

| 단계 | Shape | 하는 일 |
|---|---|---|
| 입력 X | 3×4 | Token별 네 성분 |
| 각 Head의 Q/K/V | 각각 3×2 | Head별 가중치로 투영 |
| 각 Head의 점수·가중치 | 각각 3×3 | Token 사이 비교 |
| 각 Head 출력 | 각각 3×2 | Value 가중합 |
| 두 Head를 열 방향으로 연결 | 3×4 | 네 성분으로 묶기 |
| 출력 투영 W_O | 4×4 | Head 결과를 섞어 3×4 출력 만들기 |

한 Token에서 Head 1의 출력 [1, 2], Head 2의 출력 [3, 4]를 연결하면 [1, 2, 3, 4]다. 출력 투영이 첫·셋째 성분을 더해 첫 출력, 둘째·넷째를 더해 둘째 출력으로 만들고 셋째·넷째는 유지하도록 정하면 **[4, 6, 3, 4]**가 된다. 이는 연결·투영 계산만을 위한 별도 예시이며 U02의 Head가 실제로 이 값을 출력했다는 뜻은 아니다.

### Residual·LayerNorm·FFN의 책임

| 요소 | 역할 | 생략하거나 바꾸면 검토할 점 |
|---|---|---|
| Residual · 잔차 연결 | 하위 계산의 출력에 원래 입력을 더해 정보·기울기가 흐를 경로를 둔다 | 입력을 직접 전달하는 경로가 달라진다. Shape가 다르면 그대로 더할 수 없다 |
| LayerNorm | 이 예시에서는 각 Token의 특성 축에서 평균·분산으로 정규화한 뒤 학습 가능한 크기/이동 값을 적용한다 | 값의 규모와 학습 안정성 조건이 달라진다. 여러 Token의 평균을 빼는 계산으로 혼동하지 않는다 |
| FFN · Feed-Forward Network | 각 Token에 같은 가중치의 비선형 변환을 적용한다 | 표현 변환 능력이 달라진다. FFN 자체가 다른 Token을 직접 조회하는 것은 아니다 |

Residual의 작은 예로 입력 [1, 0, 1, 0]에 출력 [4, 6, 3, 4]를 더하면 [5, 6, 4, 4]다. 이것은 덧셈 예시이며 전체 Block의 완성 출력은 아니다.

LayerNorm의 별도 2차원 예시에서 입력 [1, 3]의 평균은 2, 모집단 방식 분산은 1이다. 안정화 상수 ε=0.00001, 크기 γ=[1,1], 이동 β=[0,0]이면 결과는 **[-0.999995, 0.999995]** 정도다. 분산에 ε를 더한 뒤 제곱근으로 나눈다. 실제 모델은 RMSNorm처럼 다른 정규화를 사용할 수 있다. [LayerNorm 공식 정의](https://docs.pytorch.org/docs/stable/generated/torch.nn.LayerNorm.html)

FFN은 이 예시에서 2차원 → 3차원 가중합 → ReLU → 2차원 가중합이다. [1,2]가 첫 가중합에서 [1,-1,3], ReLU에서 [1,0,3], 다음 가중합에서 [4,-3]이 되도록 정한 별도 계산을 활동지에서 추적한다. 중간 차원이 커져도 마지막은 Residual에 더할 수 있는 크기로 돌아와야 한다.

### 정규화의 위치도 모델 구조의 일부다

아래는 Dropout을 생략한 설명용 표기다. LN은 LayerNorm, MHA는 Multi-head Attention이다. 원 논문의 Post-LN 형태와 비교용 Pre-LN 형태를 구분한다. 특정 모델이 어느 형태인지 실제 사양을 확인한다.

| 형태 | Attention 하위층 | FFN 하위층 |
|---|---|---|
| Post-LN | A = LN(X + MHA(X)) | Y = LN(A + FFN(A)) |
| Pre-LN 예시 | A = X + MHA(LN(X)) | Y = A + FFN(LN(A)) |

정규화 위치·Activation·게이트·Head 구성은 모델마다 다를 수 있다. 구성 요소를 빼면 항상 즉시 오답이 된다고 단정하지 않는다. 구조와 학습 조건이 달라지므로 재학습·평가가 필요한 변경으로 다룬다. [Multi-head 공식 설명](https://docs.pytorch.org/docs/stable/generated/torch.nn.MultiheadAttention.html) · [정규화 위치를 다룬 연구](https://arxiv.org/abs/2002.04745)

**작성 활동 C:** 두 Head의 Shape, 연결·출력 투영·Residual, LayerNorm과 FFN의 작은 계산을 완성한다. 각 요소의 역할과 바꿨을 때 확인할 점을 적는다.

## K2-02.U04 · 위치 정보·구조·Mask

### 위치를 표현하는 방법

위치 표현이 없는 양방향 Self-Attention만 생각해 보자. 입력 행의 순서를 바꾸면 출력도 같은 순서로 바뀌는 성질이 있다. 그 출력을 단순 평균하면 순서 차이가 사라질 수 있다. “A가 B를 도왔다”와 “B가 A를 도왔다”의 관계를 다루려면 위치와 구조의 정보를 어떻게 넣을지 설계해야 한다.

이 설명을 ‘위치 벡터가 없으면 어떤 모델도 순서를 전혀 알 수 없다’로 확대하지 않는다. Causal Mask 같은 비대칭 구조도 위치의 단서를 줄 수 있다. 여기서는 위치 없는·Mask 없는 작은 Attention의 순서 재배열 성질을 확인한다.

| 방법 | 개념 | 이번에 확인할 범위 |
|---|---|---|
| Sinusoidal Positional Encoding | 위치별 Sin/Cos 값을 만들어 입력 표현에 더한다 | 4차원 예시의 위치 0·1 값 |
| 학습형 위치 표현 | 위치에 대응하는 벡터를 학습한다 | 위치 범위와 학습/평가 조건을 확인해야 한다는 점 |
| RoPE | 위치에 따라 Q/K의 성분 쌍을 회전시켜 내적에 상대 위치가 반영되도록 한다 | 한 2차원 성분 쌍의 단순 회전 예시 |

Sinusoidal의 별도 4차원 예시에서 위치 p는 [sin(p), cos(p), sin(p/100), cos(p/100)]이다. 위치 0은 **[0,1,0,1]**, 위치 1은 약 **[0.8415,0.5403,0.0100,1.0000]**이다. 실제 값 0.99995를 반올림해 1.0000으로 표시했다. 이 식은 원 논문의 10000 기반 공식을 d_model=4에 적용한 예다.

RoPE의 단순 회전 예시에서는 [1,0]을 90도 돌리면 [0,1]이다. 같은 방향 [1,0] 둘의 내적은 1이지만, 하나만 90도 돌리면 0이다. 둘을 같은 각도로 돌리면 내적은 유지된다. 실제 RoPE의 각도는 위치·차원별 주파수 설정으로 정하며 모든 성분을 무조건 90도 돌리는 것이 아니다. 입력에 위치 벡터를 더하는 방식과도 구분한다. [RoPE 원 논문](https://arxiv.org/abs/2104.09864)

실제 모델을 고를 때에는 **정확한 모델 저장소·revision → 구조/설정 파일 → 위치 처리 구현·확장 설정 → 해당 길이에서의 실제 평가**를 확인한다. 최대 위치 설정이나 RoPE 확장 항목이 있다는 사실만으로 그 길이의 답변 품질이 검증되지는 않는다. 이번에는 특정 배포 모델의 위치 사양이나 긴 문맥 품질을 검증하지 않았다.

### Encoder·Decoder·Cross-Attention을 구분한다

| 구조/계산 | Query의 출처 | Key·Value의 출처 | 대표적인 보기 범위 |
|---|---|---|---|
| Encoder Self-Attention | 입력 문장 | 같은 입력 문장 | 유효한 입력 위치 전체를 양방향으로 볼 수 있다 |
| Decoder의 Causal Self-Attention | 현재 출력 쪽 입력 | 같은 출력 쪽 입력 | 현재와 이전 위치를 보고 미래 위치는 막는다 |
| Encoder-Decoder의 Cross-Attention | Decoder 표현 | Encoder 출력 | 허용된 원문 위치를 조회한다. 출력 쪽 미래 차단과는 별도다 |

원 논문의 Encoder-Decoder와 Decoder-only 언어 모델을 같은 구조라고 부르지 않는다. Decoder-only 모델에는 별도 Encoder와 그 출력을 읽는 Cross-Attention이 없는 구성이 가능하다. 문서를 프롬프트에 넣었다고 그 계산이 자동으로 Cross-Attention이 되는 것은 아니다. 해당 구조에서 Self-Attention의 입력에 포함되는 경우와 구분한다.

### Padding Mask와 Causal Mask

아래 입력은 T1·T2·T3·PAD다. PAD는 길이를 맞추기 위해 넣는 자리이며 실제 내용 Token으로 조회하지 않게 한다. 표의 행은 Query, 열은 Key이고, 1은 허용, 0은 차단이다.

| Query | Encoder에서 T1/T2/T3/PAD | Causal+Padding에서 T1/T2/T3/PAD |
|---|---|---|
| T1 | 1 / 1 / 1 / 0 | 1 / 0 / 0 / 0 |
| T2 | 1 / 1 / 1 / 0 | 1 / 1 / 0 / 0 |
| T3 | 1 / 1 / 1 / 0 | 1 / 1 / 1 / 0 |

PAD 자체의 Query 출력과 학습 손실을 어떻게 제외할지는 별도로 처리한다. Key의 PAD를 막았다고 PAD Query의 출력이 자동으로 0이 된다고 가정하지 않는다.

이 강의의 계산에서는 차단할 점수를 **Softmax 전에 -∞로 처리**해 가중치를 0으로 만든다. Softmax 후 가중치를 0으로만 만들면 남은 값의 합이 1이 아니게 될 수 있다. 모든 Key를 차단한 행은 정규화할 대상이 없어 특별한 처리가 필요하다. 예제 검사기는 그런 입력을 거부한다. 라이브러리별 Boolean Mask의 참/거짓 의미도 다를 수 있으므로 API 규칙을 확인한다.

U02의 T2 Query를 Causal로 바꾸면 점수는 [0, 0.7071, -∞], 가중치는 약 **[0.3302,0.6698,0]**, 출력은 **[0.6605,2.6790]**이다. Mask 없이 T3까지 보면 출력은 [1.1978,3.2089]로 달라진다. 미래 위치를 볼 수 있으면 다음 Token 학습에서 정답 쪽 정보가 새는 문제가 생긴다.

**Causal Mask는 문서 접근 권한 검사 장치가 아니다.** 문서 B를 입력에 넣고 Mask가 있으니 안전하다고 판단하지 않는다. 허용 문서만 모델에 전달하는 시스템의 권한 경계는 별도로 구현·검증해야 한다.

**작성 활동 D:** 볼 수 있는 Token 표를 완성하고 T2의 가중합을 계산한다. 자료 전체를 읽는 분류와 앞의 내용으로 다음 Token을 생성하는 과제에 어떤 범위가 필요한지 설명한다. Cross-Attention에서 Q와 K/V의 출처도 적는다.

## K2-02.U05 · 생성과 KV Cache

### 학습에서는 정답 시퀀스를 알고 있다

다음 Token을 학습하는 단순 예에서 입력과 목표를 한 칸씩 어긋나게 둔다. BOS는 시작을 나타내는 설명용 Token이다. 실제 Token 표기는 모델에 따라 다르다.

| 위치 | 학습 입력 | 그 위치가 맞힐 목표 | 입력에서 볼 수 있는 위치 |
|---|---|---|---|
| 1 | BOS | T1 | BOS |
| 2 | T1 | T2 | BOS, T1 |
| 3 | T2 | T3 | BOS, T1, T2 |

정답 Token을 입력에 주어 학습하는 방식을 Teacher Forcing이라고 한다. 정답 시퀀스가 준비되어 있으므로 Mask로 미래를 차단한 채 여러 위치의 연산과 손실을 병렬로 계산할 수 있다. 이것이 목표 Token을 같은 위치의 입력에 노출해도 된다는 뜻은 아니다. 또한 학습의 반복 Step과 층 사이 의존성까지 사라지는 것은 아니다. [다음 Token 학습 공식 안내](https://huggingface.co/docs/transformers/tasks/language_modeling)

일반적인 자기회귀 생성에서는 앞으로 고를 Token을 아직 모르므로 선택한 Token을 다음 입력에 반영하며 이어 간다. 최적화된 다른 생성 방식까지 모두 같은 실행 일정이라고 단정하지 않고, 여기서는 기본적인 Prefill/Decode 흐름을 배운다.

### Prefill과 Decode에서 재사용하는 것

Prefill은 주어진 프롬프트를 처리해 위치별 표현과 K/V를 계산하는 단계다. 이후 Decode에서는 새 Token을 입력에 추가해 다음 Token 선택을 위한 출력을 계산한다. KV Cache는 각 층의 이전 위치 Key/Value를 저장해 재사용하는 공간이다. 모델 Weight를 바꾸거나 문서를 영구 학습한 것이 아니고, 검색 DB·대화 요약 메모리와도 다르다.

| 단계 | 이번에 처리할 입력 | 처리 후 Cache 길이 | 이 단계 출력으로 선택할 Token |
|---|---|---|---|
| Prefill | 프롬프트 T1·T2·T3 | 3 | T4 |
| 첫 Decode | 방금 선택한 T4 | 4 | T5 |
| 둘째 Decode | 방금 선택한 T5 | 5 | T6 |

여기서 T6를 선택한 뒤 멈추면 T6 자체는 아직 모델에 입력하지 않았으므로 Cache 길이는 5다. ‘생성한 Token 수’와 ‘이미 처리해서 Cache에 넣은 Token 수’를 구분한다. 실제 API가 반환하는 내부 상태의 시점은 구현을 확인한다.

Cache가 없으면 같은 과거 K/V를 다시 계산하는 낭비가 생긴다. Cache를 쓰면 새 Token의 Q/K/V를 계산하고, 새 Query가 저장된 과거 K/V와 현재 K/V를 본다. 그래도 긴 문맥을 읽는 계산·메모리 사용은 남는다. 이 강의의 단순 전체 조회 예시에서는 한 Decode Query의 점수 수가 Cache 길이에 따라 늘어난다.

재사용은 **같은 모델·같은 앞부분·같은 위치/Mask·일관된 수치/Cache 설정**이라는 조건이 필요하다. 앞의 프롬프트·모델/Adapter·위치 설정이 바뀌면 무조건 같은 Cache를 이어 쓰지 않는다. 다른 사용자나 권한의 Cache를 섞지 않는 세션 경계도 운영 시스템의 책임이다. [KV Cache 공식 설명](https://huggingface.co/docs/transformers/cache_explanation)

이번 숫자 예제에서는 U02의 합성 Attention 입력 뒤에 [2,-1], [-1,2]를 순서대로 붙인다. 과거 전체를 다시 계산한 마지막 출력과 K/V를 이어 저장한 마지막 출력을 비교한다. **위치 표현·정규화·FFN·언어 출력층이 없는 한 층 Attention 계산**의 일치 확인이며, 실제 모델의 Token 생성·속도 개선 검증은 아니다.

### KV Cache 메모리를 따로 계산한다

단순한 전체 길이 Cache를 같은 크기로 저장한다고 가정하면, K와 V의 데이터 바이트 수는 다음 곱으로 계산할 수 있다.

**2 × 동시 시퀀스 수 B × 층 수 L × 저장 Token 수 T × KV Head 수 Hkv × Head 차원 D × 성분당 바이트 S**

앞의 2는 Key와 Value 두 종류다. Query Head 수 Hq와 KV Head 수 Hkv가 다를 수 있다. GQA는 여러 Query Head가 더 적은 KV Head를 공유하는 구조의 예다. 실제 모델의 값을 확인한다. [GQA 원 논문](https://arxiv.org/abs/2305.13245)

| 가상 설정 | K/V 데이터 크기 |
|---|---|
| B=1, L=4, T=128, Hq=Hkv=4, D=8, S=2 | 65,536 byte = 64 KiB |
| 위에서 T만 256 | 131,072 byte = 128 KiB |
| 기본값에서 B만 2 | 131,072 byte = 128 KiB |
| 기본값에서 Hq=4 유지, Hkv만 1 | 16,384 byte = 16 KiB |

1 KiB는 1,024 byte다. 이 표는 실제 특정 모델 사양이나 VRAM 실측이 아니다. Weight·임시 Activation·Attention 작업 공간·메모리 할당/관리 비용은 포함하지 않았다. Sliding Window·압축/양자화·고정 크기/동적 Cache·Prefix 공유 등의 구현에 따라 실제 저장량과 계산은 달라진다.

모델 Weight를 4bit로 줄였다고 KV Cache도 자동으로 4bit가 되는 것은 아니다. 둘의 데이터 형식과 구현을 따로 확인한다. 교육생 장비에서 실행 가능성을 판단할 때는 모델 파일 크기뿐 아니라 입력/출력 길이·동시 요청·전체 실행 메모리를 확인해야 한다.

**작성 활동 E:** Teacher Forcing과 생성 흐름을 구분하고 Cache 길이를 적는다. 위 설정의 바이트 수를 계산한 뒤, 문맥 길이·동시 사용자·KV Head·자료형이 각각 어떤 영향을 주는지 설명한다. 실제 장비의 속도나 수업 가능성은 미검증으로 남긴다.
