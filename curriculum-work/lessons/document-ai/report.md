# 원문과 맞는 주장을 검토하고 보고서로 옮기기

앞 [문서 등록 수업](intake.md)에서 가상 안내를 7일에서 14일로 바꾸면 옛 검색 근거를 버려야 함을 확인했다. 이제 보고서에 쓸 문장을 정하고 그 문장이 현재 원문으로 뒷받침되는지 검토한다. **자료의 현재성 → 주장과 근거의 관계 → 특정 내용에 대한 결정 → 출력과 화면 확인**을 이어 본다.

이 수업은 고정 예제와 로컬 검토자 시연이다. LLM이 문장을 생성하거나 실제 사람이 업무를 승인한 실험으로 읽지 않는다. [연결 실습](../../practice/document-assistant/L9.md)에서 현재 승인 경계를 직접 확인하고, 기존 파일은 과거 출력 예제로 관찰한다.

## 출처가 있으면 문장이 맞을까

원문에 ‘신청 기한 7일’이 있다. 보고서의 문장이 ‘신청 기한은 30일이다’라면 원문 ID와 실제 인용문이 붙어 있어도 틀린 주장이다. Citation이 존재하는 검사, 인용 문자열이 원문에 있는 검사, 그 근거가 주장을 지지한다는 검토는 서로 다른 일이다.

이번 자동 검사는 현재 버전·권한·원본 해시·Element·인용 문자열을 확인한다. 의미 일치·조건 누락·표의 잘못된 행 연결까지 자동 판정하지 않는다. 실습의 검토자는 고정된 로컬 시연 역할이며 독립적인 교사나 실제 인증 사용자가 아니다.

| 구성 | 역할 | 예제 |
|---|---|---|
| Claim | 보고서에 실을 한 주장 | 합성 텍스트의 신청 기한은 7일이다 |
| Citation | 그 주장을 검토할 원문 연결 | txt-policy 내부 버전 1의 line-1 |
| Quote | 확인할 실제 인용 문자열 | 신청 기한 7일 |
| Locator | 원본에서 확인할 위치 | TXT 원본 1줄 또는 PDF 1쪽 사각형 |
| Review | 이 내용에 대한 검토 결정 | 승인/거부, 검토자 표기, 이유 |
| DocumentSpec | 두 출력 형식이 공유하는 내용 명세 | 제목·주장·근거·원본 해시·Parser·템플릿 버전 |

Claim ID는 문장을 대신하는 정답이 아니라 연결 키다. 같은 C1이어도 문장이 바뀌면 다시 검토해야 한다. 인용은 문서 전체 하나를 뭉뚱그려 붙이기보다 주장마다 연결한다. 한 문장이 서로 다른 사실을 섞고 있다면 각각의 주장으로 나눠 검토할 수 있게 한다.

### 같은 출처를 달아도 틀린 두 문장

가상 TXT 원문은 ‘신청 기한 7일’이다. ‘신청 기한은 7일이다’는 이 문장으로 검토할 수 있다. 반면 ‘신청 기한은 30일이다’에 같은 7일 인용을 붙이면 출처 연결은 가능해도 의미가 모순된다. ‘미사용 고객도 15000원을 낸다’는 PDF의 사용 이력 행 금액을 잘못 옮긴 다른 오류다. 원문이 존재하는가, 인용이 그대로 있는가, 조건까지 그 주장을 지지하는가를 순서대로 묻는다.

현재 prepare 함수는 실제 버전/Element·인용 존재와 신뢰할 위치를 확인한다. 7일 인용을 붙인 30일 주장도 이 자동 연결 검사만으로는 만들어질 수 있다. 검토자가 모순을 판단해 거부해야 한다. 잘못된 문장을 먼저 승인하면 현재 소프트웨어가 그 의미 오류를 대신 막아 줄 것이라고 기대하지 않는다.

## 검토 대상의 내용을 고정하기

DocumentSpec은 현재 저장소의 원본과 IR에서 출처·좌표를 읽어 만든다. 외부에서 보낸 좌표나 원본 해시를 그대로 쓰지 않는다. 같은 Claim ID라도 문장·인용·출처가 달라지면 검토 대상의 해시도 달라진다.

| 단계 | 확인할 것 | 실패하면 |
|---|---|---|
| 명세 작성 | 각 주장에 실제 원문 인용이 있는지 | 누락·불일치 거부 |
| 현재성 확인 | 내부 버전·권한·원본 해시·문서 review 상태 | 새 버전·삭제·제한·재색인 뒤 재검토 |
| 검토 기록 | 내용 해시에 연결한 승인/거부·이유 | 승인 기록이 없거나 거부면 출력 차단 |
| 임시 출력 | 같은 명세로 DOCX·PDF 작성 | 변환 실패면 최종 폴더를 만들지 않음 |
| 출력 직전 | 명세·출처·승인 상태 다시 확인 | 중간에 삭제됐다면 임시 결과 폐기 |
| 형식·화면 확인 | 두 파일 내용·한글·줄바꿈·배치 | 오류를 수정하고 다시 렌더링 |

Registry의 review 상태는 ‘검토 대상’이라는 뜻이다. 이번에 추가한 승인 기록은 특정 DocumentSpec에 대한 별도 결정이다. 문서가 review 상태라는 이유만으로 보고서 전체가 승인된 것으로 취급하지 않는다.

내용 해시는 검토자가 보았던 제목·주장·인용·위치·원본/템플릿·현재성 정보를 하나의 대상으로 묶는다. ‘승인됐던 주장 ID’를 기억하는 대신 지금 출력할 내용이 그 대상과 같은지 확인하는 것이다. 같은 ID의 문장을 7일에서 30일로 바꾸면 원문 인용을 그대로 두어도 내용 해시가 달라지고 과거 승인과 맞지 않는다.

원본이 14일로 바뀌어 새 버전이 등록되면 7일 보고서의 출처 버전도 더는 현재가 아니다. 새 버전을 parse/index/review한 뒤 인용과 문장을 다시 작성하고 새 명세를 검토해야 한다. 다른 문서의 변경까지 generation으로 감지하는 것은 이번 실습의 보수적인 선택이다. 일반 서비스의 세밀한 영향 분석이 구현됐다는 뜻은 아니다.

명세에는 템플릿 버전과 저장소 generation도 들어간다. 다른 문서가 바뀌어도 이전 명세를 거부하는 보수적인 정책이다. 템플릿 구현을 바꿀 때는 버전도 바꿔야 한다. 같은 명세 해시의 검토 결정은 한 번 저장하며 결정 정정·철회·사용자 인증 기능은 아직 구현하지 않았다.

현재 템플릿은 `kedu-evidence-report-v2`다. 저장된 초기 두 Claim 예제는 v1으로 만들었고 DOCX 입력의 구조 위치를 출력하도록 나중에 v2로 바뀌었다. 과거 v1 검토/파일은 당시 기록으로 보존한다. 그 내용을 현재 도구로 다시 출력하려면 현재 원문에서 v2 명세를 새로 만들고 검토해야 한다. 단순히 저장 JSON의 버전 이름을 고쳐 승인을 재사용하지 않는다.

## 같은 내용과 같은 화면은 다르다

기존 출력 실험은 하나의 DocumentSpec에서 공통 문단 목록을 만든 뒤 Word 문단/스타일과 PDF 문단으로 각각 출력했다. [python-docx 공식 예제](https://python-docx.readthedocs.io/en/latest/user/quickstart.html)의 문단·제목 스타일 API를 사용하고 PDF는 ReportLab으로 작성한다. 두 파일의 픽셀 배치가 같아야 하는 요구는 없지만, 주장·인용·위치·원본 해시는 같아야 한다.

[예제 DOCX](../../practice/document-assistant/backend/data/report-v1/evidence-report.docx)와 [예제 PDF](../../practice/document-assistant/backend/data/report-v1/evidence-report.pdf)를 열면 PDF 원문을 인용한 C1과 TXT를 인용한 C2를 볼 수 있다. 두 파일 모두 교육용 합성 자료이며 독립 업무 승인이나 실제 환불 정책이 아님을 표시했다.

| 검사 | 이번 실제 확인 | 이 검사로 알 수 없는 것 |
|---|---|---|
| 구조 | DOCX에 제목/본문/주장/인용/위치가 저장됨 | 화면에서 글자가 보이는지 |
| 내용 | DOCX의 16개 문단이 직접 PDF와 DOCX 렌더링 PDF에 모두 존재 | 의미가 정답인지 |
| 화면 | 최종 DOCX 1쪽과 PDF 1쪽의 한글·배치·해시 확인 | 다른 Word 버전·교육생 PC의 동일한 표시 |
| 경계 | 승인 전·원문 변경/삭제·인용/좌표 변조·변환 실패 거부 | 인증·동시 발행·배포 후 회수 |

첫 DOCX 렌더링은 한글이 화면에서 빠지고 기본 스타일의 파란 선이 남았다. 저장된 문자열과 직접 생성한 PDF만 읽었으면 놓쳤을 문제다. 렌더러가 임시 사용자 디렉터리를 쓰므로 글꼴을 시스템에서 찾을 수 있게 준비하고, Word의 테마 글꼴·제목 테두리 잔여 설정을 제거한 뒤 다시 렌더링했다. 당시 최종 두 파일은 한글과 내용이 정상적으로 보였다. 이번 설명 정비에서 새 DOCX/PDF를 생성·렌더링한 결과와 구분한다.

DOCX의 한글 글꼴은 파일에 내장하지 않았다. 열어 볼 장비에는 Noto Sans KR이나 호환 글꼴이 필요하다. PDF에는 사용한 글꼴 부분을 포함했다. 글꼴 라이선스는 [원본 자료 안내](../../practice/document-assistant/backend/data/document-v1/FONT-OFL.txt)에 있다.

출력 과정은 임시 폴더에서 시작한다. 파일을 다 만든 뒤 다시 원문/승인을 검사하고 통과하면 최종 폴더로 옮긴다. 중간에 원문이 삭제되거나 변환이 실패하면 최종 폴더를 남기지 않는다. 이 전후 검사는 실패 범위를 줄이지만 DB와 파일시스템을 묶은 동시 발행/취소의 완전한 원자성은 아니다. 이미 외부로 복사한 파일을 자동 회수하지도 않는다.

## 교육생이 확인할 네 가지 사례

| 사례 | 해야 할 판단 | 제출할 증거 |
|---|---|---|
| 원문 7일·주장 30일 | 실제 인용이 있어도 의미 불일치로 거부 | 해당 Claim·인용·거부 이유 |
| 승인 뒤 문장 변경 | 과거 승인 해시를 재사용하지 않음 | 수정 전후 내용과 출력 거부 |
| 승인 뒤 원문 삭제/권한 제한 | 이전 문맥이 있어도 재조회에서 차단 | 현재 상태와 최종 폴더 미생성 |
| 파일 생성 성공·화면 한글 누락 | 내용 검사와 화면 검사를 나눠 수행 | 렌더링 전후와 수정 원인 |

강사는 Claim마다 원문 조건과 표의 관계를 직접 확인한다. 문자열 일치가 있어도 중요한 예외가 빠졌다면 승인하지 않는다. 자동 검사를 통과했어도 독립 검토를 하지 않았으면 그 상태를 그대로 기록한다.

**확인 질문**

1. 원문 7일을 정확히 인용한 30일 주장이 자동 연결 검사를 통과할 수 있는 이유와 검토자가 해야 할 판단은 무엇인가?
2. 같은 Claim ID라도 문장·인용·출처/버전·템플릿이 바뀌면 왜 과거 승인을 재사용하면 안 되는가? 문서 review 상태와 보고서 approve는 같은가?
3. DOCX/PDF의 저장·텍스트 검사만으로 배포 가능하다고 할 수 있는가? 새 원본 삭제와 이미 배포한 파일의 회수는 어떤 차이가 있는가?

## 여기까지의 범위

기존 실험에서 실제 PDF/TXT → IR → 두 Claim과 두 Citation → 고정 검토 결정 → DOCX/PDF 출력과 화면 검사를 실행했다. LLM으로 새 문장을 생성하거나 실제 사용자의 승인을 받은 실험은 아니다. 과거 RAG/Agent/LoRA 품질 보류도 유지한다.

단일 로컬 CLI 실습이며 DB와 파일시스템에 걸친 동시 발행·취소의 원자성, 이미 배포한 파일의 회수, 인증·감사·보안 보관은 미완료다. 보고서를 만든 뒤 원본이 삭제돼도 외부에 복사한 파일이 자동으로 사라지지는 않는다. 실제 서비스에는 발행/회수와 보관 정책이 필요하다.

[실습](../../practice/document-assistant/L9.md)에서 현재 명세 작성/승인 경계·고정 검토·내용 변경/출처 무효화를 확인한다. [강사용 해설](teacher-guide.md)을 함께 사용한다. 다음에는 Provider 기능/예산, React/Streaming, 다중 형식·최종 평가의 설명 정비가 이어진다.
