# 문서를 다시 올리거나 지웠을 때 근거도 바뀌는가

K2-14.U01~U02 · L9 첫 묶음. 선수는 L8 문서 입력과 K2-11 역할·전달 계약이다. L9 전체 여섯 단원 중 **형식·원본·공통 문서 구조, 문서 상태·권한·삭제**를 먼저 다룬다. 보고서·Provider·React/Streaming·최종 평가는 다음 묶음이다.

이 강의 다음에는 [실제 결과](../../reports/KEDU-PRODUCTION-013/RESULT.md)를 읽으면 된다. 실행 담당자는 [L9 안내](../../practice/document-assistant/L9.md)를 추가로 본다. 본문에 실행 코드나 JSON을 넣지 않았다.

## U01 · 형식·원본·공통 문서 구조

같은 환불 안내라도 PDF는 페이지의 어느 영역인지, 텍스트 파일은 몇 번째 줄인지 찾아야 한다. 두 형식을 억지로 같은 페이지 좌표로 바꾸면 존재하지 않는 출처가 생긴다. 먼저 문서 내용의 공통 구조를 만들고 원본으로 돌아갈 정보는 형식에 맞게 보존한다.

| 계층 | 역할 | 이번 구현 |
|---|---|---|
| 원본 | 실제 입력 바이트 | 읽은 시점의 사본과 SHA256을 SQLite에 보존 |
| DocumentRecord | 문서의 현재 상태 | ID·내부 버전·권한·제목·형식·상태 |
| DocumentElement | 추출한 구성 요소 | 문단/텍스트 줄/표, 고유 ID, 내용·행렬·Locator |
| IR | 형식 사이의 중간 표현 | 원본 해시·Parser 버전·형식·Element 목록 |
| Chunk | 검색에 사용할 부분 | 비어 있지 않은 Element 텍스트와 문서/버전/Element ID |
| Locator | 원본에서 다시 볼 위치 | PDF 물리 페이지·영역, TXT 실제 줄 번호 |

SHA256은 바이트 변경을 식별하는 값이다. 내용이 옳다거나 최신 정책이라는 뜻은 아니다. 같은 파일명도 바이트가 다르면 다른 입력이며, 같은 바이트를 새 요청으로 등록하면 이 실습에서는 새 내부 버전이 된다. 외부의 ‘v1’ 같은 표시는 등록 요청의 정보이고 내부 버전은 저장소가 1, 2처럼 발급한다.

문서 전체를 하나의 문자열로 만드는 대신 Element ID를 둔다. 예를 들어 PDF 1쪽의 세 번째 텍스트 영역은 그 페이지와 사각형을 가리키고, TXT의 세 번째 줄은 원본 줄 번호를 가리킨다. 빈 줄을 없애 검색해도 원래 줄 번호는 유지한다. 표는 행렬로 남기되 그 전체를 일반 문단으로 위장하지 않는다.

### 확장자가 다르면 무엇이 다른가

| 형식 | 이해할 구조 | 이번 지원·확인 |
|---|---|---|
| PDF | 페이지·텍스트/이미지·영역·표 | L8 추출기를 재사용. 저장된 디지털 합성 PDF 실행 |
| UTF-8 TXT | 문자 인코딩·물리 줄 | 실제 실행. BOM 허용, 잘못된 UTF-8·NUL·빈 내용 거부 |
| DOCX | 압축 패키지 안의 본문·스타일·관계 등 | 이번 Registry는 거부. 어댑터·문단/표 Locator 미구현 |
| HWPX | XML 기반 문서와 관련 자원 | 이번 Registry는 거부. 패키지/구역/문단 어댑터 미구현 |
| HWP | 바이너리 문서 형식 | 이번 Registry는 거부. 변환기·의존 환경 미검증 |

[한컴 공식 안내](https://www.hancom.co.kr/support/faqCenter/faq/detail/2784)는 HWP와 XML 기반 HWPX를 구분한다. 파일의 확장자만 고친다고 변환되는 것은 아니다. [python-docx 공식 안내](https://python-docx.readthedocs.io/en/latest/user/documents.html)도 문서의 본문 외 스타일·머리말 같은 부분이 따로 있음을 설명한다. 어느 라이브러리가 파일을 연다는 사실과 그 안의 모든 내용을 추출했다는 사실은 구분한다.

현재 두 형식만 실행했다. 세 형식 이상 확장이라는 최종 목표를 완료로 세지 않는다. L9의 PDF 스캔 경로는 L8의 OCR 언어 데이터 준비가 추가로 필요하며 이번에는 다시 실행하지 않았다. HWPX를 ZIP/XML로 읽는 짧은 예제를 만들었다는 이유로 표·그림·수식·읽기 순서까지 지원한다고 표시하지 않는다.

### 무엇을 검색에 넣고 무엇을 보존할까

이번 검색은 텍스트 Element의 문자열 포함 검사다. 벡터 검색·BM25·순위 모델을 새로 검증하지 않았다. L3~L8의 LocalIndex를 바꾸지 않고 문서 상태에 따른 노출 여부를 확인하는 별도 저장소를 사용했다. PDF 표는 IR에 행렬로 보존하지만 표 자체의 검색·질문 해석은 추가 작업이다. 기존 텍스트 줄에 표의 글자가 나타날 수 있어도 행·열 조건을 이해했다는 증거는 아니다.

검색 결과의 문장을 외부에서 바꿔 보내도 문맥을 만들 때는 저장소의 현재 원문 Element를 다시 읽는다. Caller가 보낸 좌표도 원본 좌표를 대신하지 못한다. 다만 이 저장소가 내주는 바이트 사본은 업로드 때의 원본이며, 사용자 PC의 파일이 이후 수정되는 것을 계속 감시하는 서비스는 아니다.

**실습:** PDF의 영수증 문장과 TXT의 금액 문장을 찾고, 각각 문서 ID·내부 버전·원본 해시·Element·Locator를 연결한다. PDF 좌표를 TXT에도 넣으면 왜 잘못인지 설명한다. 제출물은 원본 → Record → IR → Chunk → 원본 위치의 연결표와 지원/미지원 표다.

## U02 · 문서 상태·권한·삭제

파일이 존재해도 검색에 나와서는 안 되는 때가 있다. 업로드 직후에는 추출하지 않았고, 추출 직후에는 검색 준비가 안 됐을 수 있다. 버전이 바뀌면 이전 결과는 현재 근거가 아니며, 권한이 막히거나 삭제된 문서는 이미 가져온 검색 결과에서도 다시 확인해야 한다.

| 상태/행동 | 저장소의 동작 | 검색 가능 여부 |
|---|---|---|
| uploaded | 크기·지원 형식·등록 권한 확인 후 원본 사본 저장 | 불가 |
| parsed | 원본을 IR로 변환, 해시 확인 | 불가 |
| indexed | 텍스트 Element를 검색용 목록에 반영 | 가능. 검토 완료라는 뜻 아님 |
| review | 검토 대상으로 표시 | 가능. 문맥에 검토 필요 표시 유지 |
| 새 버전 | 내부 버전 증가·이전 Chunk 즉시 제거 | 새 버전 재처리 전까지 불가 |
| restricted | 권한 변경·현재 Chunk 제거 | 불가 |
| deleted | 원본·IR·제목·해시·Chunk 비우고 ID/버전의 삭제 흔적 보존 | 불가, 같은 ID 재등록 거부 |

review는 승인 상태가 아니다. 이번 경로에는 최종 승인·보고서 발행 기능이 없다. 자료를 검토하기 위해 검색할 수 있는 것과 승인된 답변을 사용자에게 발행하는 것은 구분한다. 후속 U03에서 승인 기준과 Claim별 근거를 연결한다.

### 같은 요청을 두 번 보내면

네트워크가 끊기면 사용자는 같은 업로드 버튼을 다시 누를 수 있다. 요청 키를 쓰면 같은 요청을 재전송했는지 확인할 수 있다. 이번에는 키와 함께 문서 ID·외부 버전·제목·권한·형식·원본 해시의 지문을 저장한다.

같은 키·같은 입력이면 새 버전 없이 현재 상태를 반환한다. 같은 키로 내용을 바꾸면 충돌로 거부한다. 새 키로 같은 바이트를 보내면 명시적인 새 등록으로 보고 버전을 증가시킨다. 바이트 중복 제거와 요청 중복 방지는 서로 다른 정책이다. 제목만 바뀌어도 같은 요청 키를 재사용하면 충돌한다.

중요한 예외가 있다. 과거 버전의 요청을 다시 보내거나 이미 삭제·제한된 문서의 요청을 재전송했을 때 ‘전에는 성공했으니까 성공’이라고 되돌리면 자료가 부활할 수 있다. 따라서 요청 키가 맞아도 현재 문서의 버전·권한·삭제 상태를 확인해 거부한다.

### 이전 검색 결과를 언제 버릴까

저장소 변경 때 전체 generation을 증가시킨다. 검색할 때의 generation과 문맥을 만들 때의 값이 다르면 다시 검색하게 한다. 한 문서만 바뀌어도 이전 선택 전체를 거부하는 보수적인 실습 정책이다. 이후 ID·버전·권한·현재 상태·Element를 다시 확인하고 저장된 텍스트를 사용한다.

실제 실행에서는 금액을 검색한 뒤 새 버전을 올렸다. 이전 선택은 거부됐고 새 버전은 다시 추출·색인하기 전까지 노출되지 않았다. 권한 제한 후에는 해당 문서가 검색에서 사라졌고, 삭제 후 저장소를 다시 열어도 원문과 IR이 비어 있었다.

### 실패와 삭제의 범위

Parsing이 실패하면 문서 상태는 uploaded에 머물고 검색에 들어가지 않는다. 이번에는 실패 이력을 가진 작업 Queue·재시도 Worker·여러 작업자의 동시 처리까지 만들지 않았다. [SQLite 문서](https://docs.python.org/3/library/sqlite3.html)의 트랜잭션 API를 사용해 한 등록의 원본·버전·Chunk 무효화·요청 키를 함께 반영하지만, 이 검증은 단일 로컬 CLI 흐름에 한정한다.

삭제는 현재 저장소의 원본/IR/검색 내용 제거다. 업로드한 사람의 파일·다른 디렉터리·DB 백업·파일시스템의 삭제 전 바이트까지 지우는 보안 삭제를 뜻하지 않는다. 요청 키의 지문과 ID/버전 삭제 흔적은 재전송 부활 방지를 위해 남긴다. 보관 기간과 백업 정책은 실제 서비스에서 별도로 정해야 한다.

권한도 고정 staff 역할과 신뢰한 등록 정보로 검사한다. 웹에서 사용자가 보낸 ‘staff’를 그대로 믿는 인증 시스템이 아니다. 실제 인증·조직 권한·감사·백업 관리 없이 이 코드를 업로드 서비스로 공개하지 않는다.

**실습:** 같은 요청 재전송, 같은 키/다른 내용, 새 버전, 권한 제한, 삭제, 저장소 재시작의 여섯 상황을 비교한다. 제출물은 각 상황의 내부 버전·상태·검색 결과·이전 문맥 사용 가능 여부 표다. 강사는 삭제된 원문이 재등장하지 않는지, 검토 상태를 승인으로 오해하지 않는지 확인한다.

## 다음 연결

U01~U02의 자료와 실제 PDF/TXT·로컬 상태 검사를 작성했다. 독립 강사/교육생 검증은 남아 있다. 다음 U03~U06에서는 Claim별 Citation과 검토·DOCX/PDF 보고서, Provider/예산, React/Streaming, 다중 형식·최종 평가를 이어 붙인다. 기존 RAG/Agent/LoRA 품질 보류는 이 구현으로 해소되지 않는다.
