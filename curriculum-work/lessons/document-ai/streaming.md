# 조금 보이는 답변과 완료된 답변을 구분하기

답변 일부로 ‘신청 기한은 7일’이 보인 순간 연결이 끊겼다. 아직 뒤에 조건이나 오류가 올 수 있는데 이 문장을 완료된 답변으로 사용해도 될까? 또 취소한 옛 실행의 응답이 늦게 도착해 새 실행 화면을 바꾸면 어떻게 막을까?

앞 [Provider 수업](provider.md)의 최종 생성 판정 다음에 **바이트 수신 → SSE 이벤트 → 실행별 상태 → 부분/확정 표시**를 붙인다. [화면 실행 안내](../../practice/document-assistant/stream-ui/README.md)와 [연결 실습](../../practice/document-assistant/L9.md)에서 직접 확인한다. 전송 완료·답변의 의미 검토·업무 승인을 구분한다.

이번에는 실행 가능한 React 화면과 로컬 Python HTTP 서버를 추가했다. 기존 React 강의 원문과 FastAPI API는 보존했다. 새 서버는 별도 Router에서 완성된 고정 답변을 먼저 받은 뒤 나누어 전송한다. **실제 HTTP Streaming은 실행했지만 모델이 Token을 생성하는 즉시 보내는 경로는 아니다.**

## 네트워크에서 도착하는 조각은 이벤트가 아니다

서버가 한 번에 쓴 문장이 브라우저에도 그대로 한 번에 도착한다는 보장은 없다. 한글 글자 중간의 UTF-8 바이트가 잘리거나, 한 조각에 여러 이벤트가 들어올 수 있다. 따라서 수신 조각마다 문자열을 독립적으로 바꾸고 JSON을 읽으면 안 된다.

| 처리 층 | 해야 할 일 | 이번 확인 |
|---|---|---|
| 바이트 해독 | 여러 조각 사이의 미완성 UTF-8 보존 | 한글·이모지의 모든 2분할 위치와 1바이트 조각 검사 |
| SSE 프레임 | 줄·빈 줄·여러 data 줄을 모아 이벤트 완성 | LF·CRLF·CR, 주석, 여러 이벤트와 여러 data 줄 |
| 앱 계약 | JSON·실행 ID·연속 번호·이벤트 종류 확인 | 다른 ID·누락/중복 번호·잘못된 최종 답변 거부 |
| 화면 상태 | 부분 응답과 완료 판정 구분 | 최종 성공 전에는 answer를 확정하지 않음 |

이번 구현은 [SSE 표준](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)의 UTF-8·줄바꿈·data 프레이밍을 따르는 제한된 Parser다. id/retry 재연결 기능은 구현하지 않았다. 일반 SSE의 EOF 처리와 별개로, 이 앱은 프레임이 잘렸거나 최종 판정 없이 EOF가 오면 실패로 취급한다.

예를 들어 ‘한’은 UTF-8에서 3바이트 ED 95 9C다. 앞 조각이 ED 95에서 끝나면 아직 글자가 완성되지 않았다. TextDecoder가 이 상태를 다음 조각까지 보관한 뒤 9C와 합쳐야 한다. 글자 하나가 도착했다고 JSON도 끝난 것은 아니다. 줄과 빈 줄을 모아 SSE 프레임을 완성한 뒤 data의 JSON을 해석한다.

네트워크 조각은 Transport의 단위이고, SSE 이벤트는 프로토콜의 단위이며, 모델 Token은 Tokenizer의 단위다. 화면에 글자가 조금씩 보인다는 사실만으로 모델 Token Streaming이나 체감 생성 속도를 검증했다고 부르지 않는다.

## 최종 판정을 별도로 보내기

이번 이벤트 계약에는 시작, 부분 텍스트, 오류, 최종 판정이 있다. 모든 이벤트는 같은 실행 ID와 연속 번호를 가진다. 같은 문장을 요청해도 실행마다 ID가 달라 과거 결과를 구분할 수 있다.

| 이벤트 | 역할 | 화면에서의 의미 |
|---|---|---|
| start | 고정 실습 응답이라는 시작 정보 | 대기에서 수신 중으로 이동 |
| delta | 이어 붙일 부분 텍스트 | 아직 최종 답변이 아님 |
| error | 서버가 알려 준 오류 | 이후 성공 확정 금지, 최종 실패 확인 |
| final | 완료·실패·예산/시간/기능/출력 상한·취소 판정 | 성공일 때만 누적 문장과 최종 답변을 비교해 확정 |

아래는 **이벤트 계약 설명용 입력 예**다. 실제 모델 출력 기록이 아니며 명령으로 실행하는 코드도 아니다. 각 빈 줄은 SSE 이벤트 하나의 끝이다. id는 실행을 구분하고 seq는 그 실행 안에서 0부터 이어지는 번호다.

```text
event: start
data: {"id":"demo","seq":0,"fixture":true}

event: delta
data: {"id":"demo","seq":1,"text":"신청 기한은 7일"}

event: final
data: {"id":"demo","seq":2,"status":"completed","answer":"신청 기한은 7일"}

```

start 뒤에는 수신 중이고 answer는 아직 비어 있다. delta 뒤에는 draft만 쌓이며 answer는 여전히 비어 있다. 마지막 final이 completed이고 그 답변이 누적 draft와 같을 때만 answer를 확정한다. start/delta 두 이벤트만 정상 도착했어도 연결이 끝나면 이 앱은 missing_final 실패다. 중간 프레임이 잘리지 않았다는 것과 과제가 완료됐다는 것은 다른 검사다.

성공 final의 답변이 누적한 delta와 다르면 거부한다. 비성공 final에는 답변을 확정하지 않는다. 최초 유효한 최종 판정이 도착하면 이 실행의 수신을 닫고 이후 데이터로 결과를 바꾸지 않는다. 이 정책은 끝없이 열린 연결을 기다리지 않기 위한 앱 규칙이며 이후 모든 바이트를 검증했다는 뜻은 아니다.

화면은 ‘전송 완료’라고 표시한다. 이는 프로토콜이 정상 종료됐다는 뜻이지 답변의 사실·근거·업무 승인이 맞다는 뜻이 아니다. 앞 보고서 수업의 근거 검토와 승인 결정을 생략할 수 없다.

## React에서 실행을 구분하기

화면 상태에는 실행 ID, 현재 단계, 부분 문장, 확정 답변, 마지막 번호, 오류와 취소 확인이 있다. 수신 함수는 React와 분리해 Node 검사와 브라우저가 같은 코드를 사용한다. React는 이 상태를 그린다.

[React Effect 문서](https://react.dev/reference/react/useEffect)는 외부 연결과 정리 절차를 설명한다. 이 화면은 실행 버튼에서 요청을 시작하며, 정리 때 수신을 중단하고 실행 세대를 바꿔 늦게 도착한 결과가 현재 화면을 수정하지 못하게 한다. 개발 모드의 Effect 추가 실행을 모델의 추가 요청으로 연결하면 안 된다.

동시에 실행할 수 있는 요청은 화면당 하나다. 시작하면 조건 선택과 시작 버튼을 잠그고 취소 버튼을 켠다. 완료·실패·취소 뒤에는 새 실행이 가능하다. 새 실행은 부분 문장도 초기화한다. 자동 재연결·자동 재호출은 하지 않는다.

### 늦은 취소 확인이 새 결과를 덮어쓰는 경우

느린 응답을 취소한 뒤 곧바로 새 실행을 시작할 수 있다. 이전 취소 접수 응답이 늦게 도착해도 새 실행의 완료 상태를 취소로 바꾸면 안 된다. 이번 브라우저 검사에서는 취소 접수 응답을 일부러 늦추고 새 정상 실행을 완료시켰다. 실행 세대가 달라 이전 확인이 새 화면을 덮어쓰지 않았다.

이를 시간 순서로 보자. 실행 A를 취소하면 A의 부분 문장은 남겨도 확정 answer는 비운다. 곧 실행 B를 시작하면 새 ID와 새 실행 세대를 만들고 화면을 초기화한다. 뒤늦게 A의 취소 접수가 도착했을 때 현재 세대는 B이므로 화면을 바꾸지 않는다. 요청 ID 검사는 잘못된 이벤트를, 실행 세대 검사는 옛 비동기 콜백을 막는 서로 다른 경계다.

취소 버튼은 브라우저 수신을 중단하고 실습 서버에 취소를 요청한다. 서버는 고정 응답 전송 루프에서 취소 플래그를 확인해 종료한다. 화면의 ‘서버가 취소 요청을 접수했습니다’는 요청 접수 확인이다. 실제 GPU/CPU 모델 계산을 강제로 중단했다는 뜻이 아니다. 서버 접수를 확인하지 못했으면 그 상태도 화면에 표시한다.

## 부분 문장을 남기되 정답으로 확정하지 않기

연결이 끊기면 사용자는 이미 보인 문장을 완성된 답변으로 착각할 수 있다. 이번 화면은 부분 문장을 남기면서 ‘최종 답변으로 사용할 수 없다’고 표시하고 확정 answer는 비운다. 오류·시간 초과·취소 모두 같은 원칙이다.

| 직접 실행할 상황 | 기대할 결과 | 이번 실제 관찰 |
|---|---|---|
| 정상 전송 | 한글 문장을 누적한 뒤 최종 성공 | 전송 완료, 7일 문장 확정 |
| 오류 응답 | 일부 내용이 보여도 실패 | 한국어 오류 설명, 확정 답변 없음 |
| 중간 연결 종료 | 최종 판정/프레임 부재를 감지 | 연결 종료 안내, 부분 응답 표시 |
| 기능 미지원 | Router의 비성공 판정을 화면에 연결 | 지원 경로가 없다는 설명 |
| 시간 한도 | 일부 문장 뒤 시간 초과 판정 | 부분 응답 사용 불가 표시 |
| 느린 응답 취소 | 수신 중단·서버 접수 구분 | 수신 취소, 서버 루프의 취소 상태 확인 |

서버는 이벤트 바이트를 한글 중간에서도 나누어 쓴다. 하지만 실제 TCP/브라우저가 조각을 합칠 수 있으므로 브라우저에서 모든 UTF-8 분할 위치를 강제로 관측했다고 주장하지 않는다. 분할 경계의 완전한 확인은 별도 Parser 검사로 수행했다.

## 화면과 브라우저에서 확인할 것

기존 화면 검증은 데스크톱 1120×900과 모바일 크기 390×844에서 직접 열어 확인했다. 한글·상태·취소 안내를 읽을 수 있었고 390px에서 가로 넘침이 없었다. 모바일 크기 에뮬레이션이며 실제 스마트폰·Safari·Firefox 검증은 아니다.

문장에 HTML처럼 생긴 내용이 있어도 React 텍스트로 표시하고 실행하지 않는지 검사했다. 이 사례 하나가 모든 XSS 방어를 보장하지는 않는다. 이번 화면은 원문을 HTML로 해석하거나 Markdown을 렌더링하지 않는다.

접근성 측면에서는 선택 항목의 label, 버튼 활성 상태, 상태 안내, 오류 알림, 응답 영역의 busy 표시를 넣었다. 독립 스크린리더 사용자 평가나 전체 접근성 감사는 아직 수행하지 않았다.

화면의 DOM 문자열과 상태 검사가 통과해도 글꼴이 없으면 한글이 네모로 보일 수 있다. 설치/실행할 브라우저에서 한글 지원 글꼴이 선택되는지와 실제 화면을 따로 확인한다. 개발 환경의 자동 검사 성공을 교육생 PC 표시 품질로 확대하지 않는다.

**제출물:** 여섯 상황의 서버 최종 상태·화면 상태·확정 답변 유무를 표로 정리한다. 이어 취소 직후 재실행 사례에서 실행 ID가 다른 이유를 설명한다. 강사는 끊긴 문장을 성공으로 표시하지 않는지, 서버의 접수와 실제 모델 중단을 혼동하지 않는지, 단순 전송 완료를 의미적 정답으로 부르지 않는지 확인한다.

**확인 질문**

1. UTF-8 바이트 조각·SSE 이벤트·모델 Token은 어떤 단위인가? 한 조각마다 독립 JSON 파싱을 하면 왜 위험한가?
2. delta의 내용이 그럴듯해도 final 없이 연결이 끝나면 answer를 확정할 수 있는가? 전송 완료는 의미 승인인가?
3. A 취소 직후 B를 시작한 뒤 A의 취소 접수가 늦게 오면 어떤 실행 상태만 바뀌어야 하는가? 접수 확인은 모델 강제 중단인가?
