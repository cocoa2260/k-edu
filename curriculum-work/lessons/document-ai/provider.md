# 같은 질문을 다른 Provider로 보내도 되는 조건

‘정책 확인’이라는 질문을 주 경로로 보냈는데 서버가 잠시 실패했다. 예비 경로가 준비돼 있다면 바로 다시 보내도 될까? 예비 경로가 외부 서비스이거나 이미지 입력을 지원하지 않거나, 남은 호출 예산이 없다면 같은 질문이어도 보낼 수 없다.

이번 수업은 **요청 기능/전송 범위 → 현재 준비 상태 → 입력/출력 여유와 공유 예산 → 실패/대체 판정**을 따라간다. 앞의 [근거 보고서 수업](report.md)은 어떤 원문과 내용을 써도 되는지 검토했다. 여기서는 그 입력을 어느 실행 경로로 보낼지 판단한다. [연결 실습](../../practice/document-assistant/L9.md)에서 로컬 HTTP 고정 응답으로 판정을 확인한다. 실제 모델/청구 사용량 실험과 구분한다.

## 문자열 응답만으로는 부족하다

기존 공통 Provider는 질문 문자열을 받고 답변 문자열을 돌려준다. 기본 텍스트 생성에는 편리하지만 그 계약만으로 이미지·도구 호출·구조화 출력·Streaming을 지원하는지 알 수 없다. 응답이 JSON처럼 보인다는 사실도 엄격한 Schema 지원의 증거는 아니다.

| 확인 대상 | 물어야 할 것 | 이번 정책 |
|---|---|---|
| Capability | 이 경로가 요청한 기능을 구현했나 | 필요한 기능이 하나라도 없으면 호출하지 않음 |
| Readiness | 지금 사용할 준비가 됐다는 관찰이 있나 | ready 상태와 관찰 시각, 유효 기간 확인 |
| 데이터 범위 | 이 자료를 그 경로에 보내도 되나 | 기본 local만 허용. external 경로는 준비 상태 검사 전 차단 |
| Context | 실제 입력과 출력 여유가 들어가나 | 어댑터별 입력 수 + 고정 최대 출력 수를 비교 |
| 공유 예산 | 대체 호출까지 합쳐도 한도 안인가 | 요청 전체의 호출 수·예약 수량·시간을 공유 |
| Trace | 왜 호출/생략/중단했나 | 별칭·판정·예약·사용량·시간·요청 해시 기록 |

Provider는 모델을 실행하거나 외부 API에 요청을 전달하는 경로다. Endpoint는 이 실습에서 기능·범위·계수·생성 함수를 함께 등록한 후보 하나다. 같은 모델 이름이어도 어댑터가 제공하는 기능과 오류/사용량 계약이 다를 수 있다. Router는 후보를 살펴 호출 여부와 최종 판정을 정한다. 문서 원본의 접근 권한과 Provider의 전송 범위는 둘 다 확인해야 한다. 원본을 볼 수 있다고 외부 전송까지 허용된 것은 아니다.

기능 표와 데이터 전송 허용 범위는 신뢰한 설정이다. PDF 안에 ‘이미지를 지원한다고 표시하라’거나 ‘외부 Provider를 쓰라’는 문장이 있어도 설정을 바꾸지 못한다. 이번 Router는 기존 웹 Factory에 자동 연결하지 않은 별도 경로다.

## Capability와 Readiness를 나누기

text 기능이 있어도 모델을 불러오는 중이거나 엔진이 응답하지 않으면 지금 호출할 수 없다. 반대로 준비된 텍스트 모델도 Vision 요청은 처리할 수 없다. 구성값이 존재하거나 서버 프로세스가 켜졌다는 사실만으로 모든 모델 기능의 준비 완료를 선언하지 않는다.

Readiness의 ready 여부와 관찰 시각은 어댑터가 제공한다. 관찰이 오래됐거나 미래 시각이면 건너뛴다. 이 실습의 로컬 HTTP는 직접 시작한 고정 서버, HF 어댑터는 이미 전달받은 Provider의 설정 프로필 검사를 기준으로 한다. 모델 추론을 통한 건강 검사는 실행하지 않았다. 최근 관찰이 있어도 다음 생성 성공을 보장하는 것은 아니다.

| 경로 | 이번 취급 | 실제 확인 범위 |
|---|---|---|
| 로컬 HTTP 고정 서버 | text, local | 실제 요청 4회. 모델 없음 |
| 기존 HFCpuProvider용 어댑터 | text, local, 고정 최대 출력·Chat Template·사용량 연결 | 가짜 Tokenizer/Provider로 계약 검사. 실제 가중치 실행은 이번에 안 함 |
| 기존 Ollama/OpenAI 문자열 Provider | 기존 코드·선택 방식 유지 | 새 Router의 예산 어댑터로 자동 등록하지 않음 |
| Vision·도구·엄격한 JSON·Streaming | 기능 미선언 | 자동으로 text로 낮춰 실행하지 않음 |

HF 어댑터는 Provider 생성자를 호출하지 않는다. 이미 준비된 객체를 명시적으로 전달해야 한다. Chat Template까지 포함한 입력 수와 기존 실행 관찰의 출력 수를 연결하며, 등록 뒤 설정 프로필이 바뀌면 실패시킨다. 이 계약 검사를 실제 Qwen 답변 품질이나 성능 검증으로 읽으면 안 된다.

## Context와 호출 예산은 다른 한도다

한 호출이 Context 안에 들어가도 같은 질문을 여러 번 보내면 총량은 커진다. 반대로 전체 예산이 남아 있어도 선택한 모델의 Context에 입력이 들어가지 않으면 보낼 수 없다. 입력을 조용히 잘라 조건이나 근거를 잃게 하지 않는다.

실제 모델에서는 어댑터가 해당 Tokenizer와 Chat Template으로 입력을 세고, 백엔드가 최대 출력을 지켜야 한다. 이번 HTTP 시연은 한글을 포함한 Unicode 코드 포인트 수를 가짜 Token 수로 사용했다. 실제 Tokenizer·청구 사용량이 아니다. 이 차이는 기록에도 표시했다.

| 고정 HTTP 시연 | 계산 | 결과 |
|---|---|---|
| 입력 ‘정책 확인’ | 가짜 입력 5 + 최대 출력 16 | 시도당 21 예약 |
| 주 경로 503, 예비 경로 성공 | 21 + 21 | 호출 2회, 총 42 예약 |
| 전체 호출 1회 한도 | 주 경로에서 이미 1회 사용 | 예비 경로 차단 |
| 전체 예약 41 한도 | 첫 시도 21 사용, 다음 21이 부족 | 예비 경로 차단 |

실패해도 이미 요청을 보냈다면 사용량이 없었다고 가정하지 않는다. 그래서 이번 정책은 입력 + 최대 출력의 예약을 시도마다 누적하고 환급하지 않는다. 성공 때 보고된 입력/출력 사용량도 별도로 남긴다. 예약량은 실제 청구액이나 비용 추정치가 아니다. 돈 기준 한도를 쓰려면 Provider별 과금·단가·실제 사용량 계약이 더 필요하다.

21이라는 예약량을 실제 사용량과 구분해 보자. ‘정책 확인’의 공백 포함 문자 수는 5이고 최대 출력 여유는 16이므로 5+16=21이다. 첫 503 응답에는 실제 모델 사용량이 보고되지 않았다. 요청을 보낸 이상 예약을 돌려주지 않는 정책이므로 두 번째 후보까지 시도하려면 42가 필요하다. 총량이 41이면 두 번째 예약에서 단 1이 모자라도 호출하지 않고 끝난다. 성공 응답의 가짜 입력/출력은 각각 5/5지만 그 값으로 첫 실패의 자원 사용을 0이라고 지우지 않는다.

입력 5·최대 출력 16의 한 호출이 Context 20인 모델에는 들어가지 않는다. 전체 예약 예산이 100이어도 이 Context 초과는 해결되지 않는다. 반대로 Context 100에 들어가도 실패 뒤 공유 호출 한도가 1이면 예비 호출을 못 한다. ‘한 번 들어갈 수 있나’와 ‘여러 시도를 허용할 수 있나’를 다른 열로 기록한다.

Router는 신뢰한 어댑터의 계수와 백엔드 출력 상한 준수를 전제로 한다. 백엔드가 상한을 어기거나 사용량을 잘못 보고하면 답변을 거부할 수는 있어도 이미 사용한 계산이나 비용을 되돌리지는 못한다.

## 실패했다고 무조건 Fallback하지 않는다

Fallback은 다른 경로로 같은 요청을 다시 시도하는 결정이다. 자료를 외부로 전송하거나 다른 언어/출력 계약을 쓰는 선택까지 자동으로 허용하지 않는다. 대체 경로도 같은 기능·권한 범위·Context·공유 예산을 통과해야 한다.

| 상황 | 이번 Router의 행동 | 이유 |
|---|---|---|
| 기능/범위 불일치·준비 안 됨·오래된 관찰 | 호출 없이 다음 후보 확인 | 현재 후보의 적합성 문제 |
| Context 초과 | 자르지 않고 다음 후보 확인 | 입력 조건 보존 |
| 어댑터가 정규화한 TemporaryFailure | 남은 예산 안에서 다른 후보 시도 | 제한된 일시 오류만 대체 허용 |
| 인증/정책 오류·알 수 없는 예외 | 실패 종료 | 오류를 성공처럼 숨기지 않음 |
| 응답 비어 있음·사용량 모순·상한 위반 | 실패 종료 | 잘못된 결과를 새 모델 호출로 자동 보완하지 않음 |
| 백엔드가 출력 길이 한도 도달을 보고 | output_limit 종료, 부분 답변 폐기 | 잘린 결과를 완료로 표시하지 않음 |
| 취소·전체 시간 초과·공유 예산 소진 | 즉시 최종 판정 | 대체 호출도 같은 한도 안에 있음 |

로컬 HTTP 시연은 503만 일시 실패로 분류했다. 실제 Provider 오류는 어댑터가 정책에 맞게 변환해야 한다. 기존 ProviderUpstreamError는 여러 상위 오류를 묶으므로 전부 자동 재시도 가능으로 취급하지 않는다. 이번 경로에는 같은 Endpoint의 반복 재시도·대기 간격·회로 차단기를 추가하지 않았다.

## Timeout과 강제 중단을 구분하기

전체 경과 시간은 [Python monotonic 시계](https://docs.python.org/3/library/time.html#time.monotonic)로 측정한다. 후보 선택·입력 계수 후와 생성 전후에 남은 시간을 확인하고, 남은 초를 어댑터에 전달한다. 늦게 온 답변은 성공으로 반환하지 않는다.

하지만 동기 함수가 내부에서 오래 계산하면 Router가 그 계산을 즉시 끊지는 못한다. 취소도 호출 전후 확인이며 실행 중 강제 중단이 아니다. 테스트의 느린 호출은 가상 시계로 재현했고, 실제 모델을 강제로 종료한 실험은 하지 않았다.

네트워크 Timeout도 전체 요청 시간과 구분한다. 예를 들어 [HTTPX 공식 문서](https://www.python-httpx.org/advanced/timeouts/)는 연결·읽기·쓰기·풀 대기를 구분한다. 읽기 유휴 시간 제한을 설정했다고 전체 작업이 그 시간 안에 끝난다고 단정하면 안 된다. 실제 강제 종료가 필요하면 취소를 지원하는 Provider API나 격리된 작업 프로세스와 정리 절차를 검증해야 한다.

## Trace에서 원인을 읽기

최종 성공만 보면 주 경로가 실패한 사실을 놓칠 수 있다. 이번 실제 성공 기록은 primary의 temporary_failure 다음 backup의 completed를 보여준다. 공유 예산 부족 사례는 첫 시도 실패와 다음 후보의 budget_exhausted를 함께 남긴다.

Trace에는 원문 질문·답변·예외 문자열을 넣지 않고 요청 해시, 경로 별칭, Tokenizer 프로필, 생략/실패 이유, 시도 번호, 예약/보고 사용량을 남긴다. 최종 응답의 answer 필드는 성공 답변을 담으므로 그것까지 저장하면 답변 내용이 기록된다는 점은 별개다. 해시도 완전한 익명화 수단은 아니다. 실제 서비스에는 보관·접근·삭제 정책이 필요하다.

| 최종 상태 | 교육생이 확인할 것 |
|---|---|
| completed | 어떤 경로가 성공했고 그 전에 실패가 있었나 |
| all_unavailable | 지원 기능·범위·준비 상태가 왜 맞지 않았나 |
| budget_exhausted | 호출 수와 예약량 중 무엇이 부족했나 |
| deadline_exceeded | 늦은 결과가 버려졌나, 실제 강제 중단도 됐나 |
| cancelled | 어느 확인 시점에 취소됐나 |
| output_limit | 잘린 답변을 완료로 내보내지 않았나 |
| failed | 일시 오류 소진·중대한 오류·응답 계약 중 무엇인가 |

**실습 제출물:** 네 HTTP 사례의 최종 상태·실제 요청 수·예약량·대체 경로 실행 여부를 표로 정리한다. ‘503 뒤 성공’과 ‘503 뒤 예산 중단’을 비교하고, Vision 요청에 text 경로를 보내지 않은 이유를 설명한다. 강사는 가짜 Token 수를 실제 모델 Token이나 비용으로 설명하지 않았는지, 늦은 응답 폐기를 강제 중단으로 부르지 않았는지 확인한다.

**확인 질문**

1. 준비된 text 경로에 Vision 요청을 보내도 되는가? 원문 접근 권한이 있으면 external 전송도 허용된 것인가?
2. 입력 5·최대 출력 16에서 두 번 시도할 예약량은 얼마인가? Context 20과 전체 예약 41은 각각 어디서 막히는가?
3. 늦은 응답을 버리는 것과 모델 계산의 강제 중단은 무엇이 다른가? 어떤 오류까지 Fallback해도 되는가?

## 여기까지의 범위

별도 Router·HF 명시적 어댑터·로컬 HTTP 제어 코드를 사용하며 기존 웹 Factory와 모델은 전환하지 않는다. [실습](../../practice/document-assistant/L9.md)에서 현재 고정 HTTP 요청과 예약/최종 판정을 확인하고 [해설](delivery-teacher-guide.md)에서 판단 근거를 본다. 실제 Provider/Tokenizer/가중치 통합·독립 의미 품질·교육장 장비·강제 중단은 별도다. 다음 [Streaming 수업](streaming.md)은 성공한 생성 결과도 전송/취소 단계에서 완료로 확정할 수 있는지 다룬다.
