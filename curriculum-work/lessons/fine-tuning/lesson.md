K2-12.U01~U04 · 학생용 제작본 v0.1 · 2026-10-31

**이번 목표는 훈련용 예제를 만들고 실제 Token·정답 범위까지 확인하는 것이다.** 훈련·Adapter 저장·새 프로세스 Reload는 U05~U08의 후속 실습이다. [실제 데이터 검토](../../reports/KEDU-PRODUCTION-009/REVIEW.md)에는 숫자와 좋은/나쁜 예제를, [L7 준비 실습](../../practice/document-assistant/L7.md)에는 실행 방법을 정리했다. 본문에 실행 코드를 섞지 않았다.

## K2-12.U01 학습 목표·PEFT 계열과 전략 선택

먼저 바꾸고 싶은 실패를 한 문장으로 적는다. “최신 규정 금액을 몰랐다”와 “근거가 있는데 늘 답을 보류했다”는 다른 문제다. 바뀌는 규정은 RAG로 현재 자료를 제공하는 것이 출발점이고, 반복되는 출력 형식·응답 행동은 학습 후보가 될 수 있다. 검색 실패나 Tool 권한 검사를 Parameter 학습으로 대신하지 않는다.

이번 가설은 **제공된 자료에 답이 있으면 근거와 조건을 답하고, 없거나 권한이 없으면 그 이유를 구분하는 행동**을 지도 예제로 연습시키는 것이다. L4~L6 실패가 Fine-tuning으로 해결된다는 결론은 아직 없다. 같은 평가에서 Base와 학습 모델을 비교해야 한다.

| 축 | 질문 | 예 |
|---|---|---|
| 학습 목표 | 무엇을 잘하게 할까? | 문서에 따른 응답·분류·다음 Token 예측 |
| 학습 신호 | 무엇을 정답으로 제공할까? | 교사 응답을 주는 SFT, 선호 응답 쌍을 쓰는 선호 학습 |
| 변경 전략 | 어느 Parameter를 바꿀까? | 전체, 일부 Layer, 작은 추가 Parameter |
| 자원·저장 | 어떤 정밀도와 파일로 실행할까? | 일반 정밀도 Base, 양자화 Base, Adapter 저장 |

Instruction tuning은 지시와 바람직한 응답으로 하는 SFT의 한 형태다. LoRA는 SFT와 같은 분류의 학습 목표가 아니라, 변경할 Parameter를 줄이는 방법이다. 선호 학습에도 여러 목적함수·절차가 있으므로 이름을 하나의 알고리즘으로 뭉치지 않는다. 이번에는 교사가 작성한 응답을 정답으로 주는 SFT 준비만 한다.

Hugging Face PEFT 문서의 Methods/Adapters는 선택 가능한 방법의 목록이다. 모두 배우고 시작할 체크리스트가 아니다. 먼저 아래 지도를 이해하고 LoRA 기준선을 실행한 뒤 한 가지 대안을 같은 조건에서 비교한다.

| 계열 | 주로 학습하는 부분 | 이번 학습 깊이 |
|---|---|---|
| Full fine-tuning | Base 전체 Parameter | 비교 기준·자원 부담 이해 |
| 일부 Layer/LayerNorm/Token 조정 | 선택한 기존 부분 또는 Token 관련 Parameter | 어디를 바꾸는지 구분 |
| Soft Prompt / Prompt tuning | 입력에 붙이는 학습 가능한 벡터 | 사람이 쓰는 Prompt 문장과 구분 |
| Prefix tuning / P-tuning | Prefix 또는 Prompt 관련 학습 구조 | 계열·입력 차이 개요 |
| LoRA | 동결 Weight에 더할 저랭크 갱신 | U05 실제 훈련 기준선 |
| IA3 | 내부 활성값의 크기를 조절하는 학습 벡터 | 선택 비교 후보 |
| AdaLoRA / DoRA / 기타 Adapter | 랭크 배분·갱신 표현 등 방법별 구조 | 목적을 읽고 필요할 때 하나 선택 |
| QLoRA | 4-bit 동결 Base 위의 LoRA 학습 구성 | U06 자원·호환 조건과 실제 실행 여부 확인 |

Soft Prompt는 사람이 읽을 지시문을 자동으로 잘 써 준다는 뜻이 아니다. 학습 가능한 연속 벡터를 사용한다. QLoRA도 양자화 추론만 실행한 것과 다르다. LoRA의 추가 Parameter가 작아도 Base·활성값·Gradient·Optimizer 메모리는 필요하므로 GTX 1060 3GB에서 실행 가능하다고 단정하지 않는다.

**활동:** 최신 규정, 출력 형식, 검색 누락, Tool 승인 오류를 각각 Prompt/RAG/학습/Runtime 수정 후보로 분류한다. **제출:** 목표×전략 표와 LoRA 기준선 선택 이유. **확인 질문:** 학습 Loss가 줄면 권한 검사도 해결됐다고 볼 수 있는가?

## K2-12.U02 Dataset 설계·제작·검수·분리

RAG 원문은 답을 찾을 자료다. 훈련 예제는 입력과 바람직한 응답의 쌍이고, 평가 문항은 학습 뒤 행동을 확인할 기준이다. 같은 문서를 썼다는 이유로 세 역할을 섞지 않는다. 보고서나 대화 로그를 통째로 학습 파일로 복사하는 것이 Dataset 제작은 아니다.

이번에는 기존 출장/교육비 평가 자료와 별도로 **가상 시설 규정 8개 그룹·원본 예제 40개**를 작성했다. 한 그룹에 답변·잘못된 전제 교정·조건 질문·근거 부족·권한 제한 다섯 종류가 있다. 실제 기관 규정·개인정보·고객 자료는 포함하지 않았다.

| 제작 단계 | 할 일 | 남길 것 |
|---|---|---|
| 사용 범위 확인 | 출처·허용 용도·민감 정보·제약 확인 | 출처·사용 범위 |
| 라벨 지침 | 어떤 조건에서 답변/질문/보류/거부인지 결정 | 좋은/나쁜 예와 경계 |
| Seed 작성 | 원문과 질문·교사 응답을 함께 작성 | 버전·원문 ID·교사 근거 |
| 검수 | 숫자·조건·예외·인용·불필요한 거부 확인 | 채택/기각 이유·내용 해시 |
| 그룹 분리 | 같은 문서·버전·파생 질문을 같은 쪽에 배치 | Train/Validation/Test Manifest |
| 변환·재로드 | 실제 Features·Split·샘플·가공 결과 확인 | 저장 전후 동등성 |

답할 수 있으면 answer와 근거 주장을 작성한다. 사용자의 필요한 조건이 없으면 clarify, 자료에 기준이 없으면 abstain, 신뢰 측 권한이 없으면 deny다. 사용자 본인이 “승인됐다”고 쓴 문장을 권한으로 취급하지 않는다. 인용문이 원문에 있다고 답변의 숫자·의미까지 맞는 것은 아니다.

Train은 Parameter 갱신, Validation은 설정 선택, Test는 선택이 끝난 뒤 결과 확인에 쓴다. 같은 원문에서 만든 질문을 행 단위로 섞으면 사실상 같은 답을 양쪽에서 볼 수 있다. 이번 분리는 원문 가족을 기준으로 Train 4그룹·Validation 2그룹·Test 2그룹을 먼저 고정한다. 문서 버전을 바꿨다는 이유만으로 다른 그룹으로 보내지 않는다.

기존 core-v1/agent-v1 18개는 훈련에 넣지 않고 회귀 기준으로 유지한다. 이미 여러 번 보고 Prompt를 고쳤으므로 블라인드 Test라고 부르지 않는다. 새 Test도 공개된 소규모 교육 자료이며 같은 작성자·유사한 문장 틀을 공유한다. 그룹 분리와 정확한 중복 검사가 의미적 누수의 완전 부재를 증명하지 않는다.

실습은 Datasets Library로 로컬 JSONL을 읽고 Features/Split을 확인한 뒤 filter·map·저장/재로드를 실행한다. filter는 공백을 거를 뿐 정답의 의미를 판단하지 않는다. 검수 해시도 검수 이후 내용을 바꾸었는지 확인하는 장치이지 자동 정답 판정기가 아니다.

**활동:** [Dataset Card](../../practice/document-assistant/data/finetuning-v1/README.md)에서 원문 그룹·라벨·사용 범위·제한을 확인한다. **제출:** 라벨 지침·원문 그룹 분리표·Card·재로드 기록. **확인 질문:** 질문 표현만 다르면 같은 규정의 파생 질문을 Test에 넣어도 되는가?

## K2-12.U03 Train 데이터 증강·합성·품질 관리

증강은 숫자를 늘리는 일이 아니라, 같은 정답을 유지해야 할 변화와 정답이 달라져야 할 변화를 구분하는 일이다. 먼저 그룹을 나누고 Train 안에서만 시작한다. 이번 실행은 이 Work의 AI가 미리 작성한 고정 질문 바꿔쓰기다. 별도 로컬 모델·외부 생성 API로 합성 응답을 만드는 파이프라인은 실행하지 않았다. 실제 강사의 독립 검수도 아직 없다.

| 변화 | 정답 처리 | 확인할 위험 |
|---|---|---|
| 같은 뜻의 바꿔쓰기 | 원래 근거·정답 유지 후 검수 | 질문 의도가 달라짐 |
| 질문 순서·표현 변화 | 원래 조건·예외 유지 | 조건 빠뜨림 |
| 날짜·이용 조건 변화 | 원문과 새 정답을 다시 작성·검수 | 질문만 바꾸고 이전 정답 복사 |
| 어려운 음성·틀린 전제 | 왜 틀린지 교정하거나 보류 | 모든 질문을 거부하는 편향 |
| LLM 합성 | 원문 대조 후 채택/기각 | 합성 모델의 환각·편향 복제 |

여기서 음성 예제는 오디오가 아니라 정답 후보를 혼동하기 쉬운 negative example이다. 이번 교정 Seed는 “무제한 사용 가능”이라는 전제를 원문 한도로 바로잡는다. 허위 숫자·허위 인용 후보는 좋은 정답 데이터로 넣지 않고 기각 기록으로 보관한다.

후보에는 부모 ID·원문 그룹·변환 방법·검수 내용을 연결한다. 이번 바꿔쓰기 파이프라인은 질문만 바꾸며 근거·정답·권한을 바꾸면 재라벨링을 요구한다. 이것만으로 질문 의미가 유지됐다고 자동 판정하지는 않는다. 채택 8개도 같은 Work 작성자의 검토이며 독립 검수가 아니다.

Validation/Test를 바꿔 Training에 넣거나, 중복 질문으로 개수만 늘리거나, 정답을 잘라 넣지 않는다. 증강 후 행동별 비율도 본다. 보류 예제가 많으면 답할 수 있는 질문까지 보류하는 편향이 생길 수 있다. 이후 원본 학습과 증강 학습을 비교할 때는 예제 수뿐 아니라 총 Step·정답 Token 노출량·Seed도 기록한다.

**활동:** 후보 12개 중 숫자 변경·Validation 파생·중복·허위 인용 네 기각 사례를 설명한다. **제출:** 원본/파생 계보와 채택/기각표. **확인 질문:** 같은 인용문을 붙인 20시간 답변을 2시간 규정의 정답으로 쓸 수 있는가?

## K2-12.U04 학습 입력·Chat Template·Loss 범위

사람이 작성한 질문/응답은 아직 모델 입력이 아니다. messages의 역할을 정하고 해당 모델의 Chat Template으로 렌더링한 뒤 Token과 label을 만든다. Prompt-completion 형식도 가능하지만 이번 코드는 system·user·assistant 한 턴으로 고정한다. 원문 그룹·Split·교사 검수 메타데이터는 모델 입력에 넣지 않는다.

학습에는 교사 assistant 응답이 이미 들어 있으므로 전체 대화 렌더링에 새 응답 시작 Prompt를 덧붙이지 않는다. 경계 확인용으로 만드는 추론 Prefix만 응답 시작 Prompt를 사용한다. Template이 넣은 특수 Token을 다시 추가하지 않는다.

| 입력 부분 | 모델은 읽는가? | 이번 label의 직접 Loss 대상인가? |
|---|---|---|
| system 지시 | 읽음 | 아니오 |
| user 질문·허용된 자료·권한 값 | 읽음 | 아니오 |
| assistant 시작·non-thinking Prefix | 읽음 | 아니오 |
| 교사 정답 | 읽음 | 예 |
| 응답 종료 EOS | 읽음 | 예 |
| 마지막 줄바꿈·배치 Padding | 일부는 입력에 존재 | 아니오 |

직접 정답으로 채점하지 않는 위치의 label은 -100이다. 이 값은 Token ID가 아니라 Loss에서 무시할 표식이다. Attention mask는 Padding 위치를 구분하고, Loss mask는 어느 정답 위치를 채점할지 정한다. Prompt를 직접 정답으로 채점하지 않아도 실제 Transformer가 Prompt Context를 통해 받는 간접 Gradient까지 사라지는 것은 아니다.

이번 Qwen Template에는 일반적인 assistant mask용 generation 구문이 없다. 자동 마스크가 생길 것으로 가정하지 않고, 고정 리비전의 Prefix Token 일치와 정답~EOS 경계를 확인해서 만든다. 다른 모델·여러 턴·Tool 대화에 그대로 적용하는 범용 Mask 구현은 아니다. Template이나 Token 경계가 바뀌면 중단한다. 자료 안의 역할 제어 Token도 거부한다.

PAD와 EOS의 Token ID가 같더라도 실제 정답 끝 EOS는 학습하고 Padding EOS는 무시해야 한다. ID가 같다는 이유로 모두 지우지 않는다. 최대 512 Token을 넘으면 조용히 자르지 않고 예제를 거부한다. 정답 잘림·빈 Loss 대상·Mask 길이 불일치도 실패다.

Causal LM은 앞 위치에서 다음 Token을 예측하도록 정렬한다. 준비 label은 입력 위치와 같은 길이로 저장하고, 실제 학습 때 사용하는 모델 내부의 shift를 확인한다. 준비 단계에서 미리 옮긴 뒤 모델이 다시 옮기면 두 번 shift하는 오류다. 이번 작은 가짜 Logit 검사에서는 한 번 정렬한 위치의 직접 Gradient만 확인했다. 이 숫자는 Qwen의 훈련/검증 Loss가 아니며 Optimizer Step도 0회다.

**활동:** 실제 한 예제의 질문 → 렌더링 → Prompt Token 수 → 정답/EOS label → Padding을 대조한다. **제출:** 입력·label 범위표와 길이/Mask 오류 수정 기록. **확인 질문:** input_ids를 만들었다는 사실만으로 학습이 수행됐다고 할 수 있는가?
