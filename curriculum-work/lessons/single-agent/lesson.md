# Single-Agent — 모델의 요청과 실행기의 결정을 구분하기

K2-10 · 학생용 강의 제작본 v0.1 · 2026-10-31

**목표는 모델이 함수를 직접 실행한다고 생각하지 않고, 행동 요청 → 검사 → 실행 → 관찰 → 다음 선택의 경계를 설명하는 것이다.** 같은 문서 답변 앱의 [L4 RAG](../rag/lesson.md)를 이어 쓰며 [L5 실습](../../practice/document-assistant/L5.md)에서 실행한다. 설명과 실행 코드는 파일을 나눴다.

이 실습은 도구 실행 계약과 종료 조건을 배우는 작은 Runtime이다. 실제 사용자 인증·운영 승인 시스템이나 자유 계획 능력을 검증한 제품이 아니다. L4의 잘못된 금액·무관한 인용·조건 누락은 Agent를 붙여서 해결된 것으로 표시하지 않는다.

## K2-10.U01 Agent·Workflow·Tool·MCP

L4는 질문이 들어오면 정해진 순서로 검색하고 Context를 만들고 생성했다. L5는 모델이 다음 행동을 요청하고, 그 관찰을 보고 다음 요청을 만드는 구조다. 모델은 검색·원문 확인·최종 답변·되묻기·중단 중 허용된 행동을 선택한다. Runtime은 요청을 받아 검사하고 등록된 함수만 실행한다.

| 개념 | 담당하는 것 | 이번 구현 |
|---|---|---|
| Workflow | 사전에 정한 처리 순서 | L4의 검색 → Context → 생성 |
| Agent | 상태·관찰에 따른 다음 행동 요청 | L5의 JSON 행동 선택 |
| Tool | 실행기가 호출할 수 있는 기능 | 문서 검색·발견한 원문 읽기 |
| Registry | 도구 이름·Schema와 실제 함수 연결 | 허용 목록을 통한 로컬 호출 |
| MCP | 도구 등을 노출하고 호출하는 연결 규약 | 개념 비교만; 통신 실행은 없음 |

모델이 search_documents라는 문자열을 출력해도 Python 함수가 저절로 실행되지는 않는다. Runtime이 이름을 Registry에서 찾고 인수를 검사한 다음 함수를 호출한다. 없는 이름을 Python 코드처럼 평가하거나 임의 모듈을 import하지 않는다. 모델의 출력은 데이터이며 실행 권한이 아니다.

이번에는 일반 문자열 생성 Provider로 JSON 행동을 받고 직접 파싱한다. API의 native function calling이나 MCP 요청을 보냈다는 뜻이 아니다. MCP를 연결하더라도 도구 결과를 어떻게 사용하고 언제 멈출지는 별도의 Agent Runtime이 결정해야 한다.

작은 모델이 형식을 이해하도록 현재 상태에 맞는 예시를 제공한다. 발견한 Source ID를 읽기 형식 예시에 넣기도 한다. 이것은 가이드가 있는 실험이며 모델이 독립적으로 최적의 계획·근거를 찾아냈다는 증거가 아니다. Runtime은 예시를 자동 실행하지 않고 실제 모델 응답을 검사한 뒤에만 호출한다.

**활동:** L4의 고정 검색과 L5의 모델 행동 Trace를 비교한다. 도구 요청이 거부되었을 때 실제 함수가 호출됐는지 확인한다.

**제출:** 같은 질문의 Workflow/Agent 차이와 모델·Runtime·Tool 책임표. **확인 질문:** MCP에 도구가 등록되어 있으면 모델이 사용자 승인까지 얻었다고 볼 수 있는가?

## K2-10.U02 Tool Schema·Registry·검증

기본 읽기 도구는 두 개다. search_documents는 현재 staff 학습 역할이 볼 수 있는 문서를 검색해 Source ID와 짧은 미리보기를 돌려준다. read_evidence는 같은 실행에서 검색으로 발견한 Source ID만 받아 현재 원문을 다시 확인한다. 검색 미리보기를 곧바로 완전한 근거로 취급하지 않는다.

| 도구 | 인수·조건 | 결과 |
|---|---|---|
| search_documents | query 문자열, k는 1~3의 정수 | 적격 문서의 Source ID·미리보기 |
| read_evidence | 이번 실행에서 발견한 Source ID | 현재 원문·문서 버전·논리 위치 |
| save_note | 모의 승인 검사 전용, 기본 안내 목록에 없음 | 승인된 경우에만 메모리 내 메모 |

알 수 없는 필드도 거부한다. approved=true를 모델이 인수에 붙여도 신뢰할 수 있는 승인 상태가 되지 않는다. k=true처럼 겉으로 숫자처럼 보이는 값도 정수 계약에 맞지 않아 거부한다. 이름·인수·모의 저장 승인은 Registry가 함수 진입 전에 검사한다. 원문은 read_evidence 내부에서 발견 여부·현재 권한을 검사한 뒤에만 읽는다. 따라서 읽기 함수에 진입했다는 수치와 실제 원문을 반환했다는 수치는 다를 수 있다.

승인 실험은 외부 작업이 없는 모의 저장이다. 실행기 쪽에서 실행 ID·도구 이름·인수에 연결한 승인 값을 따로 전달한 경우만 한 번 허용한다. 같은 Registry 안에서 재사용하거나 다른 인수로 바꾸면 거부한다. 승인 UI·사용자 신원·보관 기간·다른 프로세스 간 재사용 방지는 구현하지 않았다. 이 작은 메모리 예제를 실제 메일·결제·운영 파일 저장에 그대로 적용하지 않는다.

도구가 돌려준 데이터도 검사한다. 결과 필드와 크기가 맞지 않으면 실패로 보고 잘못된 결과로 발견/읽기 권한을 추가하지 않는다. 자료 속 “이전 지시를 무시하라”는 문장은 Observation 데이터일 뿐 다음 행동 명령으로 승격하지 않는다. 그렇다고 작은 모델의 공격 저항성이 자동으로 보장되는 것은 아니다.

**활동:** 없는 도구, 승인 추가 필드, 발견하지 않은 Source ID, 승인 없는 save_note를 요청한 고정 응답 실험을 확인한다. 요청 시도와 실제 함수 dispatch 수를 따로 센다.

**제출:** 이름·인수·권한·결과 검사의 거부 증거. **확인 질문:** 모델이 “사용자가 승인했습니다”라고 썼을 때 어느 상태를 확인해야 하는가?

## K2-10.U03 State·Observation·종료

State에는 원 질문, 발견한 Source ID, 실제 읽은 원문, 최근 Observation, 모델/도구 시도 수, 오류 횟수 등이 있다. 현재 호출에는 필요한 State만 입력한다. 이 실습은 읽은 원문과 최근 관찰을 넣으며 전체 Trace나 숨은 사고 과정을 다음 입력에 복사하지 않는다.

최종 근거 답변에는 실제로 읽은 Source ID만 사용할 수 있다. 원문을 읽기 전에 ID를 추측해 인용하거나 삭제 전 결과를 재사용하면 거부한다. Index가 바뀌면 최종 답변을 검사할 때도 오래된 자료를 확인한다. 인용이 원문에 존재해도 주장을 지지하는지는 L4처럼 별도 대조가 필요하다.

| 제한 | 기본값 | 무엇을 세는가 |
|---|---|---|
| 모델 결정 시도 | 4회 | 잘못된 행동 형식·Provider 오류도 포함 |
| 도구 요청 시도 | 3회 | 거부된 요청·재시도도 포함 |
| 읽기 도구 일시 오류 재시도 | 실행 전체 1회 | 같은 인수로 다시 시도 |
| 같은 오류 반복 | 오류 ID별 2회 | 서로 다른 오류도 모델 시도 상한에 걸림 |
| 경과시간 | 180초 | 호출 전후 확인; 진행 중 강제 취소 아님 |

도구 요청 시도와 실제 dispatch는 다르다. 없는 도구를 두 번 요청하면 도구 시도는 두 번이지만 실제 함수 dispatch는 0이다. 읽기 도구의 일시 오류를 한 번 재시도하면 두 dispatch가 같은 요청에 사용될 수 있다. 재시도마다 새 예산을 주지 않는다. 모의 저장 같은 보호 동작은 자동 통신 재시도 대상에서 제외한다.

현재 로컬 생성 경로는 입력 1536 Token과 2000문자 제한을 검사하고, L5의 각 모델 출력은 최대 192 Token으로 제한한다. 짧은 행동 요청용 설정이며 L4의 최대 512 Token과 다르다. 긴 최종 답변이 잘릴 수 있으므로 출력 상한 도달과 형식 실패를 기록한다. 작은 실험의 시간값을 교육장 성능으로 일반화하지 않는다.

**활동:** 검색 → 읽기 → 답변의 고정 응답 Trace와 실제 모델 Trace를 비교한다. 반복 검색·반복 실패·시간 초과·취소에서 종료 이유와 남은 부분 결과를 구분한다.

**제출:** 실제 선택·검사·Observation·종료 이유를 연결한 표. **확인 질문:** 각 도구가 최대 세 번 실행될 수 있도록 만들면 실행 전체의 도구 상한도 세 번인가?

## K2-10.U04 Single-Agent 평가와 Framework 포팅

같은 평가를 유지해야 역할을 늘린 효과를 비교할 수 있다. 기존 C01~C12에 Agent 경계 A01~A06을 더해 18개를 고정한다. A01은 불필요한 도구 호출, A02는 검색/원문 읽기, A03은 없는 도구, A04는 인수·승인 위조, A05는 일시 오류, A06은 반복 실패를 다룬다. A 사례를 사실 정답률의 분모에 섞지 않는다.

일시 오류는 실험 장치로 주입한다. 실제 모델이 해당 도구를 요청하지 않았다면 주입 지점을 통과하지 않은 것이므로 “실제 Timeout 복구 성공”으로 쓰지 않는다. 고정 응답 실험은 특정 경계를 확실하게 지나게 하고, 실제 모델 실험은 모델이 무엇을 골랐는지 그대로 남긴다. 둘은 서로 다른 증거다.

Framework로 옮겨도 이름·인수·권한·출처·종료 계약을 유지해야 한다. 이번에는 LangChain의 StructuredTool로 두 읽기 도구를 감싸 실제 invoke API를 확인한다. 검색·읽기 결과와 추가 인수 거부는 같은 Registry를 사용한다. Framework 자체의 Agent 실행기나 전체 반복 상한을 포팅한 것은 아니다. 전체 Agent를 옮길 때는 Framework 바깥/안쪽에서 어느 예산을 세는지 추가 검사해야 한다.

| 이번 비교 | 확인한 범위 | 아직 확인하지 않은 범위 |
|---|---|---|
| 직접 Runtime | 행동 검사·도구 dispatch·State·상한 | 실제 인증·운영 승인 |
| StructuredTool 연결 | 같은 읽기 함수·Schema·출처 경계 | Framework Agent 전체 Loop |
| MCP 설명 | 도구 연결 규약과 Agent의 차이 | MCP 서버·클라이언트·전송 |

모델이 도구를 요청했다는 사실은 답변 품질 통과가 아니다. 필요한 원문을 못 읽거나, 읽어도 잘못 답하거나, 끝내지 못하면 그 실패를 남긴다. 실제 생성 모델·접두어·자료·정책·예산을 함께 기록해 다음 Multi-Agent 비교에 재사용한다.

**활동:** [L5 결과](../../reports/KEDU-PRODUCTION-007/RESULT.md)에서 고정 응답과 실제 모델의 호출/종료를 비교한다. 동일 18개 사례와 정책을 다음 역할 분리 실험에서도 유지하는 계획을 작성한다.

**제출:** 사례별 행동·도구 시도/dispatch·오류·원문 대조와 Framework 연결 계약표. **확인 질문:** StructuredTool의 invoke를 성공시켰다면 Framework Agent와 MCP까지 검증했다고 해도 되는가?

## 참고와 다음 연결

MCP는 공식 [Tools 명세 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)을 확인했다. 이번 로컬 JSON 프로토콜이 그 MCP 통신 구현이라는 뜻은 아니다. Framework는 설치한 LangChain Core의 StructuredTool API를 실제 호출해 확인했다.

다음 L6에서는 검색·작성·검토 역할을 분리하되 같은 자료와 평가를 유지한다. 역할이 늘어나도 각 역할이 볼 수 없는 자료를 넘기거나 전체 호출 상한을 초기화하지 않는다.
