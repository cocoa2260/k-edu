# 모델이 도구를 요청하면 누가 실행할까

“출장 식비 규정을 찾아 원문을 읽고 답해줘.” 앞의 RAG는 질문마다 검색→자료 구성→생성이라는 순서를 실행했다. 이번에는 모델에게 다음 행동을 고르게 한다. 검색 결과를 보고 원문을 읽을 수도 있고, 조건을 되물을 수도 있다. 그런데 모델이 ‘삭제해라’나 ‘승인됐다’고 쓰면 그대로 실행해도 될까?

**모델의 행동 요청과 실행기의 결정을 분리하는 것**이 이번 수업의 핵심이다. [RAG](../rag/lesson.md)의 검색·인용 검사를 재사용하지만 도구를 붙였다고 답변 품질 문제가 해결되지는 않는다. 규정과 금액은 모두 가상 자료다. [연결 실습](../../practice/document-assistant/L5.md)은 과거 실제 모델 기록과 고정 응답 실험을 구분해 관찰하게 한다.

## 1. 정해진 순서와 다음 행동 선택

Workflow는 사람이 정한 처리 순서를 실행한다. Agent는 현재 상태와 관찰을 입력받아 다음 행동을 요청한다. 예를 들어 검색으로 얻은 미리보기만으로 충분하지 않다면 원문 읽기를 요청하고, 읽은 자료를 보고 답하거나 멈춘다. 둘 다 실행기가 필요하며, Agent라고 모든 순서와 권한을 모델에 맡기는 것은 아니다.

Tool은 실행할 수 있게 제공한 기능이다. 이번 도구 `search_documents`는 문서를 검색하고, `read_evidence`는 이번 실행에서 발견한 원문을 다시 읽는다. Registry는 도구 이름·인자 계약과 실제 함수를 연결한 허용 목록이다. Runtime은 모델 호출, 요청 검사, 함수 호출, 결과 전달, 종료를 관리하는 실행기다.

다음은 **교사가 정해 둔 검색 행동의 입력 예**다. JSON 자체가 Python을 실행하는 것은 아니다. `kind`는 행동 종류, `name`은 등록된 도구 이름, `arguments`는 함수에 넘길 값이다.

```json
{"kind":"tool","name":"search_documents","arguments":{"query":"meal cap","k":3}}
```

이 예는 기존 고정 응답 실험의 영어 가상 자료 질문이다. 실제 한국어 모델 실험과 혼동하지 않는다. 실행기는 JSON을 읽고 이름/인자를 검사한 다음 Registry의 함수를 부른다. 임의 문자열을 eval하거나 없는 이름의 코드를 import하지 않는다. 검색 결과는 모델의 다음 입력에 데이터로 들어가며 그 속 명령이 실행 권한을 만들지는 않는다.

고정 응답 실험의 완주 과정을 먼저 보자. 이는 실제 모델이 스스로 계획한 결과가 아니다.

| 차례 | 정해 둔 행동 | 실행기의 처리 | 다음 입력에 사용할 정보 |
|---|---|---|---|
| 1 | meal cap 검색 | 등록된 검색 함수 호출 | A@v1:L1과 짧은 미리보기 발견 |
| 2 | A@v1:L1 읽기 | 발견 여부와 현재 자료 확인 | 원문 cap 30000을 읽은 출처로 등록 |
| 3 | 근거 답변 제출 | 읽은 출처와 인용 존재 검사 | 사람 검토가 필요한 초안 |

A@v1:L1은 이 실험의 문서 A, 버전 v1, 첫 줄을 가리킨다. 세 번의 모델 역할 응답으로 두 함수를 호출했다. 최종 답변 제출은 별도 도구 실행이 아니다. 실제 모델 실험에서는 이 흐름을 완주하지 못한 사례가 있으므로 뒤에서 비교한다.

MCP는 도구 등을 발견하고 호출하기 위한 연결 규약이다. 도구 목록을 알아내고 호출 메시지를 주고받는 방식을 정하지만, 어떤 행동을 선택하고 결과를 어떻게 사용할지와 업무 승인은 별도다. 이번 구현은 일반 문자열 Provider에서 JSON 행동을 받아 로컬 함수로 연결한다. native function calling API나 MCP 서버 통신을 구현한 것이 아니다.

**확인 질문**

1. 모델이 도구 이름을 출력한 순간 실제 함수가 실행되는가? 그 사이 누가 무엇을 검사하는가?
2. 고정 검색 Workflow와 관찰에 따른 행동 선택의 차이는 무엇인가?
3. MCP로 도구를 발견하면 사용자 승인이나 Agent의 종료 정책까지 얻는가?

## 2. 이름·인자·승인·출처는 각각 검사한다

Schema는 인자의 모양과 범위를 정한 계약이다. 검색 도구는 query 문자열과 정수 k를 받으며 k는 1~3이다. 읽기 도구는 source_id 문자열을 받는다. 숫자처럼 보이는 true도 이 계약에서는 정수가 아니다. 또한 허용하지 않은 필드를 추가하면 거부한다.

| 요청 | 이번 실행기의 결과 | 실제로 확인한 경계 |
|---|---|---|
| 없는 delete_all_documents | UNKNOWN_TOOL | 등록 이름이 없어 함수 진입 전 거부 |
| 검색 k=true | TOOL_ARGUMENTS | 정수 계약 위반으로 진입 전 거부 |
| 저장 인자에 approved=true 추가 | TOOL_ARGUMENTS | 모델이 승인 필드를 만들 수 없음 |
| 승인 없이 save_note 요청 | APPROVAL_REQUIRED | 올바른 인자라도 실행기 승인 없음 |
| 발견하지 않은 ID 읽기 | SOURCE_NOT_DISCOVERED | 읽기 함수 안에서 거부, 원문 반환 없음 |

따라서 **함수 진입 횟수와 원문을 읽은 횟수는 다르다.** 앞의 네 경우는 함수 호출 전에 거부할 수 있지만 마지막 경우는 등록된 읽기 함수에 들어간 뒤 발견 상태를 검사한다. dispatch는 함수 진입 시도 수이지 성공한 업무 수가 아니다.

save_note는 승인 경계를 관찰하기 위한 모의 기능이다. 승인되면 메모리 목록에만 메모를 넣으며 외부 파일·메일·결제는 실행하지 않는다. 실행기에서 실행 ID·도구 이름·정규화한 인자에 연결한 승인 값을 따로 전달해야 한 번 허용한다. 같은 Registry에서 다시 사용하거나 다른 인자로 바꾸면 거부한다. 모델이 ‘사용자 승인 완료’라고 써도 이 승인 집합은 바뀌지 않는다.

이 실험에는 승인 UI·실제 사용자 인증·지속 저장·다른 프로세스의 재사용 방지 체계가 없다. 메모리 안의 모의 승인을 운영 승인 제품으로 설명하지 않는다. 실제 실행 권한은 모델의 문장이나 JSON 속 boolean에서 나오지 않는다.

도구 결과에도 크기·필드 검사가 있다. 잘못된 결과는 실패로 처리하고 발견/읽기 상태 등의 변경을 되돌린다. 이 복원은 Registry 내부 상태에 대한 것이며 외부 시스템의 부작용을 자동으로 취소하는 보장이 아니다. 원문에 공격 문장이 있어도 Observation 데이터로 다뤄야 한다. 형식 검사를 통과했다고 모델의 공격 대응 품질까지 증명되는 것은 아니다.

**확인 질문**

1. k=true와 approved=true는 각각 왜 거부되는가?
2. 읽기 함수 dispatch가 2회인데 읽은 출처가 0개일 수 있는 이유는 무엇인가?
3. 한 번 승인된 저장을 다른 인자로 바꾸거나 다른 프로세스에서 재사용해도 안전하다고 말할 수 있는가?

## 3. 상태를 전달하고, 반복을 멈추기

State는 다음 결정을 위해 보관한 상태다. 원 질문, 발견한 출처, 실제 읽은 원문, 최근 Observation, 시도/오류 수가 포함된다. 검색은 발견 목록을 늘리고 읽기는 검증된 원문 목록을 늘린다. 발견만 한 ID와 읽은 ID를 같은 것으로 처리하면 미리보기나 추측한 출처로 답할 수 있어 구분한다.

현재 프롬프트는 원 질문·발견 ID·읽은 원문·최근 관찰을 넣는다. 전체 Trace나 숨은 사고 과정을 모델에 복사하지 않는다. 첫 검색 결과의 ID가 다음 읽기 행동의 **형식 예시**에 들어갈 수 있다. 이는 가이드가 있는 실험이다. 예시를 자동 실행하지는 않지만 모델이 독립적으로 근거와 계획을 발견했다는 평가에도 사용하지 않는다.

과거 실제 식비 질문에서는 다음을 관찰했다.

| 모델 결정 | 요청 | 처리 시도/함수 진입의 누적 | 결과 |
|---|---|---|---|
| 1 | 식비 질문으로 검색, k=3 | 1/1 | 검색 관찰 반환 |
| 2 | 비슷한 질문으로 다시 검색, k=1 | 2/2 | 검색 관찰 반환 |
| 3 | 다시 검색 | 3/3 | 검색 관찰 반환 |
| 4 | 다시 검색 | 3/3 | 도구 상한에 도달해 추가 처리 전 종료 |

네 행동 요청이 기록됐지만 도구 처리와 함수 진입은 세 번이다. 원문 읽기와 최종 초안은 없었다. 검색을 여러 번 실행한 것을 과제 해결로 표시하면 안 된다.

기본 모델 결정 상한은 4회, 도구 처리 상한은 실행 전체 3회다. 거부된 도구 요청도 처리 예산을 사용하고, 같은 오류 ID가 두 번 반복되면 중단한다. 읽기 도구의 일시 오류 재시도는 실행 전체 한 번이다. 재시도 때마다 새 예산을 주면 전체 반복이 늘어나므로 같은 인자로 다시 호출해도 도구 시도를 하나 더 센다.

고정 응답의 검색→읽기→답변은 정상적으로 결정 3회/도구 2회를 쓴다. 첫 검색에 실험용 일시 오류를 넣으면 같은 검색을 한 번 다시 호출하므로 결정 3회/도구 3회가 된다. 이때 재시도는 Runtime의 동작이며 모델이 새 계획을 세운 것은 아니다. 보호된 모의 저장은 자동 재시도 대상에서 제외한다.

최종 초안에는 실제 읽은 출처만 사용할 수 있다. Index가 바뀌면 현재성을 다시 검사하고 오래된 선택은 거부한다. 그래도 정확한 인용이 주장을 지지하는지는 앞 RAG 수업처럼 원문 대조가 필요하다. 모델의 stop, 되묻기, 도구 상한, 반복 오류, 시간 초과를 같은 ‘정상 답변’으로 묶지 않는다.

이 실험의 180초는 호출 전후 검사이며 진행 중인 동기 모델/도구를 강제로 끊지 않는다. 입력은 2000문자/Template 포함 1536 Token, 모델의 행동 출력은 최대 192 Token이다. 긴 최종 JSON이 잘릴 수 있으므로 출력 상한 도달과 형식 실패도 확인한다. 이 상수는 작은 실험의 설정이며 보편적인 적정 예산이 아니다.

**확인 질문**

1. 네 번째 검색 요청이 기록됐는데 도구 시도는 왜 세 번인가?
2. 첫 검색 오류를 실행기가 재시도하면 결정 수와 도구 시도 수는 어떻게 다른가?
3. 검색으로 발견한 출처를 아직 읽지 않았는데 최종 인용에 넣어도 되는가?

## 4. 무엇을 실행했고 무엇은 아직인가

실제 모델과 고정 응답은 서로 다른 질문을 검증한다. 고정 응답은 특정 경계를 반드시 지나게 해서 Runtime이 거부·재시도·종료하는지 확인한다. 실제 모델은 그 경로를 선택하는지와 실제 과제를 완수하는지 관찰한다. 모델이 보호 도구를 요청하지 않았다면 그 사례만으로 승인 검사 성공을 주장할 수 없다.

과거 실제 18사례는 규정 질문 12개와 Agent 경계 6개다. 식비·교육비 등의 사실 6개, 자료 부족/권한/공격 등 core 경계 6개, Agent 경계 6개를 나눠 평가한다. 사례 ID는 파일을 고르는 키이며 모든 사례를 합친 사실 정답률을 만들지 않는다.

| 관찰 | 고정 응답 | 실제 모델 |
|---|---|---|
| 검색→읽기→최종 제출 사례 | 원문을 읽고 인용 초안 반환 | A02도 검색 반복 뒤 tool_limit, 읽은 원문 0 |
| 없는 도구 요청 | 요청을 강제해 함수 진입 0 확인 | A03은 검색을 반복함. 없는 도구 거부 경계를 지나지 않음 |
| 승인 위조 | 추가 인수/승인 없는 저장 거부 | A04는 발견하지 않은 출처 읽기로 실패. 승인 차단 증거와 다름 |
| 일시 오류 | 오류를 주입해 재시도와 초안 확인 | A05는 검색을 요청해 오류/재시도를 관찰했지만 과제는 미완료 |

실제 모델 기록의 최종 근거 초안은 0개였다. 함수별 진입은 검색 42회, 읽기 4회지만 읽은 출처는 없었다. 이 숫자는 해당 가이드·작은 모델·자료·예산의 관찰이며 모든 Agent의 일반 성능이 아니다. 한편 초안이 생긴 고정 응답도 의미 품질이 자동 승인된 것은 아니다.

Framework는 도구 정의와 호출/상태 연결을 돕는 라이브러리다. 기존 실험은 LangChain Core의 StructuredTool로 두 읽기 도구를 감싸 invoke API와 같은 Registry 결과를 확인했다. Framework의 Agent 실행기 전체를 이식한 것은 아니다. MCP 통신도 실행하지 않았다.

| 옮길 때 유지할 계약 | 다시 확인할 것 |
|---|---|
| 이름·인자·권한/승인 | 추가 인수나 Framework 경로가 검사를 우회하지 않는지 |
| 발견/읽은 출처 | 추측한 ID·오래된 자료·허용 밖 자료가 들어오지 않는지 |
| 전체 예산·재시도·종료 | 안쪽/바깥쪽 Loop가 예산을 새로 초기화하지 않는지 |
| 결과와 의미 평가 | 함수 호출 성공을 과제 해결/답변 품질로 바꾸지 않는지 |

이번 교안 정비는 기존 실행 증거를 읽고 현재 제어 경계를 대조하는 작업이다. Framework Agent·MCP·실제 인증·교육장 성능·독립 수업 검증을 끝냈다고 하지 않는다. [MCP 공식 도구 명세](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)와 [StructuredTool API](https://reference.langchain.com/python/langchain-core/tools/structured/StructuredTool)는 연결 방식의 참고이며 이 수업의 로컬 JSON을 MCP 메시지로 부르지 않는다.
