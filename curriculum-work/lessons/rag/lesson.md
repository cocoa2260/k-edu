# 근거를 제시하는 RAG — 검색에서 답변 검토까지

K2-09 · 학생용 강의 제작본 v0.1 · 2026-10-31

**목표는 검색과 생성을 연결하고, 답변의 각 주장이 실제 원문에서 뒷받침되는지 확인하는 것이다.** [L3 검색](../../practice/document-assistant/L3.md)과 [L2 Harness](../harness/lesson.md)를 같은 앱에서 이어 쓴다. 실행 코드·실험용 입력·운영 기록은 별도 파일에 있다.

이번에는 실제 E5 검색 모델과 Qwen3-0.6B 생성 모델을 CPU에서 실행한다. 검색 결과가 있거나 출력 검사를 통과했다는 사실만으로 답변이 맞다고 판단하지 않는다. 결과는 사람이 확인해야 하는 초안이다. 가상 문서의 금액·규정을 실제 기관 정책으로 사용하지 않는다.

## K2-09.U01 Offline과 Online의 연결

RAG는 필요한 자료를 검색해 생성 모델의 입력에 넣는 구성이다. 자료를 준비하는 작업과 사용자의 질문을 처리하는 작업을 나눠야 어디서 잘못됐는지 알 수 있다. Offline은 여기서 사전 자료 처리라는 뜻이며 인터넷을 끈 실행만을 뜻하지 않는다.

| 구간 | 하는 일 | 이번 산출물 |
|---|---|---|
| 사전 자료 처리 | 원문 식별·Chunk·Embedding·Metadata 저장 | L3의 SQLite Index와 Manifest |
| 질문 처리 | 입력 검사·적격 필터·검색 | 질문과 검색 순위·Source ID |
| Context 구성 | 현재 버전 재확인·자료를 입력으로 조립 | 실제 전달한 자료·입력 해시 |
| 생성 | 고정 모델·Template·예산으로 호출 | 원응답·Token 수·시도 기록 |
| 검사·검토 | 구조·출처·부분 인용 검사 후 의미 대조 | 초안 또는 실패 종료·사례별 검토 |

검색에는 L3의 Hybrid를 기본으로 사용한다. 질문·가용 문서 조건을 고정하고 상위 3개 Chunk를 가져온다. L1의 사례별 수동 문서 선택이나 평가 정답 목록으로 대체하지 않는다. 모델의 답변을 받기 전후로 Index 변경 번호와 현재 자료를 확인한다. 갱신·삭제가 일어났다면 이전 선택으로 생성한 답변을 그대로 반환하지 않는다.

생성 모델은 고정 리비전의 Qwen3-0.6B이고 이번 환경에서는 CPU float32로 실행한다. Chat Template를 적용한 실제 입력 Token을 세고 입력 1536·신규 출력 최대 512라는 학습용 예산을 둔다. enable_thinking은 끄고 비교 조건을 고정하기 위해 Greedy 생성을 사용한다. 이것이 모델의 권장 품질 설정을 최적화한 결과라는 뜻은 아니다.

L2의 공통 호출 상한·재시도·한 번의 출력 보완을 재사용한다. 검색 실패, Context 조립/예산 실패, 생성 또는 출력 실패를 구분해 기록한다. 시간 상한은 동기 호출 전후 검사이며 진행 중인 CPU 생성을 정확히 그 시각에 끊는 장치가 아니다.

**활동:** [L4 실습](../../practice/document-assistant/L4.md)에서 한 사례의 질문 → 검색 Chunk → 실제 입력 → 모델 원응답 → 검사 → 초안을 연결한다. 모델에 평가 정답이 들어가지 않았는지도 확인한다.

**제출:** 원문에서 답변까지의 실행 추적표. **확인 질문:** 원문을 갱신하고 Index를 바꾸지 않았다면 어느 구간의 결과를 신뢰할 수 없는가?

## K2-09.U02 Chunk 구조와 Query Rewrite

문서 ID를 찾았어도 답에 필요한 문장이 빠질 수 있다. L3의 C09에서는 교육비 문서가 검색됐지만, 상위 Chunk가 두 번째 줄이면 지원 상한·신청 기한이 있는 첫 줄이 Context에 없을 수 있다. 문서 단위 Recall과 답변에 필요한 문장 회수는 다른 검사다.

Chunk를 바꿀 때는 제목·표 구조·규정의 조건과 예외를 보존한다. 고정 길이로만 나누면 “지급한다”와 “지급하지 않는다” 또는 금액과 예외가 서로 다른 조각으로 갈릴 수 있다. 이번 비교에서는 검색된 줄과 같은 문서의 앞뒤 한 줄을 확장한다. 권한·현행·가용 문서 조건은 유지하며 정답 문서 ID를 골라 넣지 않는다. 실제 입력을 다시 검사해 문자·Token 예산을 넘으면 중단한다.

Query Rewrite는 검색용 질문을 바꾸는 것이다. 생성 모델에 전달할 원래 사용자 질문과 구분해서 기록한다. 이번 C07 비교는 원래 질문을 유지하고 검색 질의만 “국내 당일 출장 식비 규정 상한 조건”으로 바꾼다. 공격 메모의 숫자를 따라가는 검색과 규정 중심 검색이 어떻게 달라지는지 확인한다. 정답 금액을 질의에 넣어 결과를 맞추지 않는다. 자동 Rewrite 모델은 구현하지 않았고 교사가 지정한 비교 조건이다.

| 비교 | 유지하는 것 | 바꾸는 것 |
|---|---|---|
| C07 검색 질의 | 원 질문·문서·모델·출력 지시 | 검색용 표현 |
| C09 인접 줄 | 원 질문·질의·검색 방식·모델 | Context에 포함할 인접 줄 |
| 출력 지시 v1/v2 | 질문·검색·자료·모델·검사기 | 답변 상태·주장 인용을 요구하는 지시 |

한 번에 검색 질의·Chunk·Prompt를 모두 바꾸고 어느 하나가 개선 원인이라고 결론 내리지 않는다. 필요한 근거를 더 넣어도 생성이 정확해지는지는 실제 답변으로 다시 확인한다.

**활동:** 비교 기록에서 검색 결과와 실제 Context를 대조한다. 필요한 문장은 생겼는데 모델이 여전히 보류하거나 잘못 답한 사례가 있는지도 본다.

**제출:** 변경 전후 Chunk/질의·입력 길이·원응답과 한 조건만 바꾼 기록. **확인 질문:** 검색된 문서 ID가 맞아도 답을 만들 수 없는 이유는 무엇인가?

## K2-09.U03 Grounding·Citation·응답 보류

Grounding은 답변이 제공한 근거와 연결되는 성질을 확인하는 일이다. Citation은 그 근거를 찾을 수 있게 표시한다. 문서 ID 하나를 적는 것에서 더 나아가, 어느 버전의 어느 줄인지와 그 줄에서 가져온 정확한 부분 인용을 주장별로 기록한다.

이번 출력은 상태, 답변, 주장 목록으로 구성한다. 각 주장은 주장 문장·Source ID·부분 인용을 갖는다. 실행기는 Source ID가 이번 Context에 있었는지, 부분 인용이 해당 원문 줄에 실제로 포함되는지를 검사한다. 모델이 없는 문서를 만들거나 인용문 자체를 바꾸면 실패 ID로 한 번 보완하게 하고 같은 검사를 다시 실행한다.

| 확인 단계 | 자동 확인 여부 | 놓칠 수 있는 것 |
|---|---|---|
| 출력 필드·자료형·빈 값 | 확인 | 의미상 모순 |
| 제공한 Source ID | 확인 | 해당 문서가 믿을 만한 규정인지 |
| 부분 인용의 원문 존재 | 확인 | 인용이 주장을 뒷받침하는지 |
| 주장과 근거의 의미 일치 | 별도 원문 대조 | 숫자·조건·예외·부정 표현 |
| 전체 답변의 누락·적절성 | 별도 사례 평가 | 근거 없는 요약·필수 조건 누락 |

“상한은 50000원”이라는 주장 옆에 실제 원문의 “30000원” 문장을 붙이면 Source ID·원문 존재 검사는 통과할 수 있다. 그래서 초안을 자동 승인하지 않는다. 공격 메모의 문장을 정확히 인용한 경우도 그 문장이 기관 규정이 되는 것은 아니다.

자료 부족은 필요한 근거가 없는 상황이다. 추가 질문은 조건이 불명확한 상황이고, 권한 밖 자료는 제공할 수 없는 상황이다. 상태 이름만 맞추는 것도 충분하지 않다. 실제 v1 실행에서는 금액을 답하면서 상태를 자료 부족으로 표시하고 주장 목록을 비운 사례가 있었다. 구조 검사는 통과했지만 올바른 보류나 근거 답변으로 평가할 수 없다.

**활동:** 읽기용 실행 기록에서 주장 옆 출처 링크를 열고 숫자·조건·예외를 대조한다. 본문이 사실을 주장하는데 claims에는 빠진 내용이 있는지도 확인한다. C03·C04·C06·C12의 보류·되묻기·거부를 구분한다.

**제출:** 주장별 근거 대조표와 보류/거부 이유. **확인 질문:** 인용문이 원문에 존재한다는 사실만으로 그 주장이 참이라고 할 수 있는가?

## K2-09.U04 검색 실패와 생성 실패의 평가

오류 원인을 나누면 보완할 위치가 보인다. 필요한 원문이 검색 후보에 없으면 검색 표현·질의·필터·Index를 확인한다. 후보에는 있지만 Context에 빠졌다면 Chunk·확장·예산을 본다. 충분한 근거가 입력됐는데 모델이 다른 값을 말하거나 근거를 생략하면 생성 지시·모델·설정을 본다. 마지막으로 자동 검사가 통과시킨 의미 오류도 따로 남긴다.

| 원인 구간 | 점검 질문 |
|---|---|
| 자료/Index | 원문·버전·권한·삭제가 현재 상태인가? |
| 검색 | 필요한 문장이나 문서가 후보에 있는가? |
| Context | 생성 모델에 실제 전달한 원문에 필요한 조건이 있는가? |
| 생성 | 원문에 없는 값·명령을 따르거나 중요한 조건을 빠뜨렸는가? |
| 검사/평가 | ID·형식 통과를 사실성 통과로 바꾸지 않았는가? |

같은 12개 사례를 유지한다. 정상 사실 6개와 경계 행동 6개를 섞어 하나의 정답률로 만들지 않는다. 최초 출력과 보완 후 출력을 구분하고, 실패 종료를 정상 답변으로 바꾸지 않는다. 이 작업의 원문 대조는 같은 Work 세션의 검토이며 독립 강사·교육생 검증과 구별한다.

출력 지시 v1/v2 비교는 C01에서 관찰한 상태/근거 문제를 출발점으로 한다. v2에서 올바른 Source ID·부분 인용을 얻어도 금액만 말하고 사전 승인이나 식사 제공 예외를 빠뜨리면 완전한 답변이 아니다. 개선과 남은 실패를 함께 기록하고 수업용 분석 사례로 사용한다.

**활동:** 한 실패를 골라 원인 구간, 변경한 조건, 같은 사례의 재실행, 남은 오류를 적는다. 모델을 더 크게 바꾸기 전에 실제 입력과 인용을 먼저 확인한다.

**제출:** 사례별 검색/Context/생성/검사 결과와 개선·회귀·채택 이유. **확인 질문:** 모든 출력이 JSON 검사에 통과했다면 RAG 검증이 완료됐다고 말할 수 있는가?
