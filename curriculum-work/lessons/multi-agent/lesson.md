# Multi-Agent — 역할·정보 전달·전체 예산을 함께 나누기

K2-11 · 학생용 강의 제작본 v0.1 · 2026-10-31

**목표는 같은 모델을 여러 번 부르는 것을 넘어, 역할마다 볼 정보와 선택할 행동·도구·종료 책임을 구분하는 것이다.** [L5 Single-Agent](../single-agent/lesson.md)를 이어 쓰고 [L6 실습](../../practice/document-assistant/L6.md)에서 같은 18개 사례를 비교한다. 실행 코드는 별도 파일에 있다.

이번에는 한 Qwen CPU 모델을 검색·작성·검토 역할로 순차 호출한다. 동시에 여러 모델을 올리는 구조가 아니다. 역할 Runtime과 경계 검사, 실제 모델의 과제 완료를 구분한다. L4/L5의 답변 품질 문제는 역할 이름을 늘려 해결된 것으로 처리하지 않는다.

## K2-11.U01 역할 분리가 필요한 문제

Single-Agent가 짧은 질문을 한 번 검색해 답할 수 있다면 역할을 늘리는 비용이 더 클 수 있다. 역할 분리는 검색과 작성의 목표가 다르거나, 작성자가 빠뜨린 조건·근거를 별도 검토할 필요가 있을 때 검토한다. 역할이 늘면 호출·지연·전달 오류도 늘 수 있다.

| 구성 | 장점으로 기대하는 것 | 추가로 생기는 비용·실패 |
|---|---|---|
| 고정 RAG | 정해진 단계·원인 추적 | 상황에 따른 추가 선택 제한 |
| Single-Agent | 같은 State에서 다음 행동 선택 | 반복 검색·혼합된 목표·종료 실패 |
| 역할 분리 | 검색·작성·검토의 목표·입력·도구 분리 | 잘못된 전달·중복 호출·검토자의 오류 |

같은 모델 가중치를 사용해도 입력과 허용 행동·권한·State가 실제로 달라야 한다. 이름만 researcher/writer/reviewer로 바꾸고 모든 문서·대화·도구를 공유하면 책임과 정보 경계가 흐려진다. 이번 Orchestrator는 모델 관리자가 아니라 역할 전환과 예산을 적용하는 일반 코드다. 각 역할은 그 안에서 도구·전달·보완·중단을 선택한다.

한 역할이 충분한 근거가 있는데도 되묻거나 일찍 중단하면 호출 수는 줄 수 있다. 이것을 비용 효율이나 품질 개선으로 바로 평가하지 않는다. 먼저 원래 과제를 끝냈는지 확인한다. 같은 실패를 역할마다 반복하는 것도 협업의 성공이 아니다.

**활동:** 같은 사례를 L5와 L6에서 비교하고 기대한 분리 효과·실제 종료·추가 비용을 따로 적는다. 단순 인사 A01에 여러 역할이 필요한지도 판단한다.

**제출:** Single/Multi 선택 이유와 기대 효과·실패 가능성 표. **확인 질문:** 호출 수가 절반으로 줄었는데 답변 없이 끝났다면 개선으로 볼 수 있는가?

## K2-11.U02 역할별 상태·Tool·입출력

| 역할 | 목표·볼 정보 | 허용 행동·도구 | 넘기는 것 |
|---|---|---|---|
| 검색 담당 | 원 질문·가용 자료·검색/읽기 상태 | 검색·원문 읽기·되묻기·근거 전달·중단 | 실제 읽은 근거 ID·부족 정보 코드 |
| 작성 담당 | 원 질문·검증된 근거·보완 요청 | 받은 원문 읽기·초안·근거 요청·되묻기·중단 | 답변·주장·부분 인용 |
| 검토 담당 | 원 질문·초안·해당 근거·실패 ID | 원문 읽기·인용 검사·통과/보완/기각·중단 | 판정·정해진 실패 ID·검토 의견 |

작성·검토 담당에게 검색 권한을 자동으로 주지 않는다. 원문 읽기도 전달받은 ID 안에서만 허용한다. 검색 담당이 어떤 문서를 볼 수 있다는 이유만으로 작성 담당도 볼 수 있는 것은 아니다. 존재하는 Source ID라도 받는 역할의 범위 밖이면 전달을 거부한다.

Handoff는 역할 사이에 넘길 실행 자료다. 실행 ID·질문 ID·송신/수신 역할·원문 버전·근거 ID·실패 ID·예산 사용량을 기록한다. 이 중 역할·권한·예산은 Runtime이 만든다. 모델이 출력한 승인 값이나 예산 0이라는 주장으로 바꾸지 않는다.

전달할 원문은 모델이 쓴 요약을 믿고 복사하지 않는다. Runtime이 허용된 ID로 현재 저장소에서 다시 읽는다. 자유로운 요약문에는 받는 역할이 볼 수 없는 내용이 섞일 수 있으므로, 검색 담당의 부족 정보도 NO_EVIDENCE·NEED_MORE_CONTEXT·CONDITION_UNCLEAR 코드로 제한한다. 모델 출력의 임의 문자열을 권한 검사의 대체물로 쓰지 않는다.

각 역할은 전체 대화 기록을 받지 않는다. 작성 담당은 검증된 근거와 필요한 보완 내용, 검토 담당은 초안·근거·기존 실패만 받는다. 이전 역할의 내부 지시나 숨은 사고 과정을 전달하는 구조가 아니다. 문서 갱신·삭제가 생기면 다음 모델 입력 전에도 원문 적격성을 다시 확인한다.

**활동:** M01에서 실제로 존재하고 검색 담당이 읽은 근거를 작성 담당에게 허용하지 않았을 때, 작성 모델을 호출하기 전에 차단되는지 본다. 예산 스냅샷이 모델 입력이 아니라 Runtime의 실제 누적값인지 확인한다.

**제출:** 세 역할의 실행 계약·Handoff·수신 범위 차단 증거. **확인 질문:** 문서 ID만 걸러 내고 모델이 쓴 자유로운 요약은 그대로 넘기면 어떤 문제가 남는가?

## K2-11.U03 검토와 한 번의 보완

작성 담당은 근거가 부족하면 검색 담당에게 추가 근거를 요청할 수 있다. 검토 담당은 주장·인용·조건을 확인해 통과·한 번 보완·기각을 선택한다. 이 두 보완은 실행 전체의 같은 한 번 예산을 공유한다. 역할을 바꾸어 예산을 새로 시작하지 않는다.

| 요청 | 다음 동작 | 상한 |
|---|---|---|
| 작성자의 근거 요청 | 검색 역할 재진입 | 기존 역할 호출 수 유지·공통 보완 1회 사용 |
| 검토자의 보완 요청 | 작성 역할 재진입 | 같은 보완 1회 사용·실패 ID 유지 |
| 잘못된 전달/출력 수정 | 같은 역할에서 재검사 | 같은 보완 예산 사용 |
| 같은 실패의 반복 | 부분 초안과 최종 전달 분리 후 종료 | 반복 보완 금지 |

예를 들어 M02에서는 빈 근거 전달 → 작성자의 추가 근거 요청 → 검색·읽기·재전달 → 작성 → 검토를 실행한다. 처음 검색 역할을 한 번 호출했다면 재진입할 때 그 한 번을 지우지 않는다. M03은 검토 반려 뒤 초안을 다시 썼어도 같은 실패가 남으면 최종 답변으로 내보내지 않는다.

검토자도 같은 작은 모델이므로 틀릴 수 있다. 다른 Context에서 검토한 것과 독립된 사람의 평가를 받았다는 것은 다르다. 모델의 pass는 승인 권한이 아니라 의견이다. Runtime은 Source ID와 부분 인용을 다시 확인하되 의미적 뒷받침은 별도 원문 대조로 남긴다. 모델 검토를 통과한 결과도 사람이 봐야 하는 초안이다.

실험 중 검토 역할이 JSON을 Markdown 코드 블록으로 감싸 반환한 경우가 있었다. 이번 파서는 응답 전체가 정확히 하나의 JSON 블록인 경우만 포장을 벗기고 같은 Schema 검사를 적용한다. Python 블록·앞뒤 설명·JSON 여러 개를 추출하거나 실행하지 않는다. Markdown 포장, JSON 데이터, 실제 실행을 혼동하지 않는다.

**활동:** M02/M03의 호출 수·보완 수·실패 ID를 따라간다. 검토자가 통과라고 말해도 Runtime의 승인 상태가 false인지 본다.

**제출:** 판정 → 보완 요청 → 동일 검사 → 최종 전달/중단 기록. **확인 질문:** 작성자가 보완을 한 번 쓴 뒤 검토자가 새 보완을 요청하면 어떤 예산을 확인해야 하는가?

## K2-11.U04 실패 전파와 동일 조건 비교

이번 기본 상한은 전체 모델 호출 8회·도구 처리 6회, 역할별 검색 4회·작성 2회·검토 3회다. 합이 9라고 전체 모델 호출을 9번 할 수 있는 것은 아니다. 전체와 역할 상한 중 먼저 닿은 제한을 적용한다. 일시 오류 재시도도 실행 전체 한 번이고 실제 호출 예산에 포함한다.

240초는 호출 전후에 확인하는 경과시간 제한이다. 진행 중 모델을 정확히 그 시각에 끊는 보장이 아니다. 호출 도중 늦게 도착한 출력은 다음 역할에 넘기지 않는다. 실패한 초안은 partial_draft로 따로 남기고 정상 전달용 draft로 바꾸지 않는다.

비교 질문은 L5와 같은 C01~C12·A01~A06, 총 18개다. 정상 사실 6개와 core 경계 6개, Agent 경계 6개는 따로 본다. M01~M04는 Handoff 경계 검사이며 품질 분모에 더하지 않는다. 같은 모델·자료라도 예산과 역할 Prompt가 바뀌므로 결과 차이를 역할 수 하나의 효과로 단정하지 않는다.

| 비교할 것 | 주의할 점 |
|---|---|
| 답변·행동 품질 | 호출 성공과 과제 완료 구분 |
| 모델·도구 호출 수 | 보완·재시도·모든 역할 합산 |
| 지연 | 모델 적재와 질문 처리 구분·실험 환경 한계 |
| 역할 도달 여부 | 앞 역할 실패 시 뒤 역할을 실행한 것으로 쓰지 않음 |
| 개별 역할 확인 | 검증된 입력으로 따로 호출한 Probe와 통합 성공 구분 |

앞 역할에서 중단되면 전체 실행에서 작성·검토가 호출되지 않을 수 있다. 이때 별도 Role Probe로 각 역할의 실제 모델 입출력을 확인할 수 있지만, Runtime이 준비한 근거로 역할을 따로 시험한 것임을 표시한다. 실제 검색자가 넘긴 근거로 세 역할을 완주했다고 쓰지 않는다.

**활동:** [실제 비교 검토](../../reports/KEDU-PRODUCTION-008/REVIEW.md)에서 역할별 도달·종료·남은 실패를 확인한다. M04의 역할 오류·전체 호출 소진·늦은 출력이 전체 작업을 멈추는지도 본다.

**제출:** 같은 18개 사례의 Single/Multi 결과·호출·지연과 별도 4개 경계 검사. **확인 질문:** 작성/검토 Probe가 성공했다면 통합 실행도 성공했다고 할 수 있는가?
