# Harness와 Loop — 호출을 실행·검사하고 멈추는 구조

K2-06 · 학생용 강의 제작본 v0.1 · 2026-10-31

**목표는 모델을 여러 번 부르는 것이 아니라, 무엇 때문에 다시 부르고 언제 멈췄는지 설명하는 것이다.** [Prompt](../prompt/lesson.md)·[Context](../context/lesson.md)의 입력과 가상 자료를 그대로 이어 쓴다. [L2 실습 안내](../../practice/document-assistant/L2.md)를 옆에 열면 된다. 실행 코드는 별도 Python 파일에 있다.

이번 제작에서는 고정 응답과 오류를 주입하는 실습을 실제 실행했다. 모델은 실행하지 않았다. 따라서 아래의 성공은 호출 제어와 구조 검사의 성공이며, 답변 품질이나 공격 저항성의 성공률이 아니다.

## K2-06.U01 Harness의 최소 책임

Harness는 모델 호출을 감싸는 실행기다. 모델이 답을 생성하는 동안, 실행기는 입력을 준비하고 Provider를 부르고 출력을 검사하고 상태와 종료 이유를 기록한다. 모델을 바꾸어도 이 책임은 앱에 남는다. 현재 Provider 인터페이스는 문자열을 받아 문자열을 반환한다. 여기에 호출 관리를 덧붙이며 기존 대화 API는 유지한다.

이번 실행기는 L1의 사례 ID와 비교 조건을 받아 같은 준비 함수를 사용한다. 그 뒤 출력 계약을 붙이고 2000문자 입력 제한을 다시 확인한다. L1 입력이 제한 안에 들어갔어도 계약·보완 지시를 추가하면 넘을 수 있으므로 최종 입력을 검사한다. 공백 질문 C10과 알 수 없는 사례는 호출 전에 거부한다.

| 책임 | 이번 구현의 행동 | 사람이 확인할 지점 |
|---|---|---|
| 준비 | 가상 자료·수동 선택·출력 계약 결합 | 질문/자료/평가 정답의 분리 |
| 호출 | 주입한 Provider의 generate 호출 | 실제 모델인지 고정 응답인지 |
| 검사 | 출력 필드·자료 ID 확인 | 사실·조건·예외는 별도 평가 |
| 상태 | 시도·재시도·보완 횟수 유지 | 총 호출 상한이 공유되는지 |
| 기록 | 순번·실패 ID·입출력 해시·종료 이유 | 원문·Key가 기록에 새지 않는지 |
| 종료 | 초안 반환 또는 실패 종료 | 실패를 정상 답변으로 바꾸지 않는지 |

Trace는 실행 경로를 설명하는 기록이다. 모델의 숨은 사고 과정을 기록하는 것이 아니다. 기본 Trace에는 원문 대신 해시를 남긴다. 해시는 실행 간 입력의 동일성을 비교하는 용도이며 암호화나 재현용 원문 보관을 대신하지 않는다. 재현하려면 코드·자료 버전·설정과 접근을 제한한 입력 원본이 별도로 필요하다.

**활동:** L2 데모의 valid_shape를 열어 준비 → 호출 → 검사 → 종료를 찾는다. 각 사건의 담당자를 모델/실행기/사람 중 하나로 표시한다. provider가 scripted-fixture이고 model이 no-model-executed인 것도 확인한다.

**제출:** 책임 분담표와 Trace 네 단계 설명. **확인 질문:** Provider가 같은 형식의 문자열을 돌려주면 사실 검사도 끝났다고 할 수 있는가?

## K2-06.U02 오류·재시도·반복의 다른 목적

시간 초과는 답변 내용을 평가하기 전에 통신에서 생긴 실패다. 이번 실행기는 연결 실패와 시간 초과에만 같은 입력으로 한 번 재시도한다. 모델이 입력을 처리했으나 응답이 늦게 도착한 경우에도 다시 요청할 수 있으므로 시도 횟수는 비용·중복 실행과 연결된다. 이 실습은 부작용이 없는 답변 생성만 대상으로 한다. 결제·메일 전송 같은 작업에는 동일 정책을 그대로 적용하지 않는다.

응답이 도착했는데 계약에 맞지 않으면 실패 ID를 붙여 보완을 요청한다. 이때 입력이 달라지므로 통신 재시도와 구분한다. 후보를 여러 개 생성해 집계하는 Self-Consistency, 사람이 버전을 비교해 개선하는 작업도 목적과 예산이 다르다. 이번 실행기는 후보 집계를 구현하지 않았다.

| 종류 | 시작 조건 | 바뀌는 것 | 이번 상한·종료 |
|---|---|---|---|
| 통신 재시도 | 연결 실패·시간 초과 | 입력 유지 | 실행 전체에서 1회, 반복 실패 시 종료 |
| 형식/ID 보완 | 응답 구조 또는 제공 ID 검사 실패 | 실패 ID 안내 추가 | 실행 전체에서 1회, 같은 실패 반복 시 종료 |
| 후보 집계 | 여러 후보를 비교한다는 사전 계획 | 생성 후보 | 이번 범위 밖 |
| 품질 개선 | 고정 평가에서 오류·회귀 발견 | Prompt/Context/설정의 특정 버전 | 사람이 채택·복구 결정 |

재시도 1회와 보완 1회는 각각 새 예산을 발급하지 않는다. 최초 호출을 포함해 총 3회가 공통 상한이다. 예를 들어 시간 초과 → 형식 오류 → 올바른 구조는 3회다. 형식 오류 → 시간 초과 → 형식 오류라면 답변 없이 멈춘다. 원격 상태 오류와 Provider 응답 해석 오류는 이번 정책에서는 즉시 종료한다. 모든 오류가 일시 오류라는 가정을 하지 않는다.

**활동:** timeout_then_success, repair_then_success, global_three_calls를 비교한다. 재시도에서는 두 입력 해시가 같은지, 보완에서는 달라지는지 확인한다.

**제출:** 시작 조건·입력 변화·상한·종료 표. **확인 질문:** 보완 호출이 시간 초과하면 재시도 횟수를 다시 0으로 초기화해도 되는가?

## K2-06.U03 검증 실패와 제한된 보완

이번 출력 계약은 상태, 답변, 근거 ID 배열의 세 항목이다. 상태는 답변·자료 부족·추가 질문·거부 중 하나다. 답변은 공백일 수 없고, 답변 상태에는 근거 ID가 필요하다. 허용하지 않은 추가 필드와 중복 ID를 거부한다. 인용 ID는 이번 입력에 제공한 문서 목록 안에 있어야 한다.

검사는 두 층이다. 첫 층은 필드·자료형·빈 값·길이 등 구조 검사다. 둘째 층은 인용 ID가 제공 목록에 있는지 확인한다. 두 층을 통과해도 인용 문장이 주장을 뒷받침하는지, 현행 규정을 선택했는지, 금액·조건·예외가 맞는지는 알 수 없다. DOC-A를 인용하며 식비 999999원이라고 쓴 고정 응답도 이 검사에는 통과한다. 데모에서 이 한계를 직접 관찰한다.

| 실패 ID | 발견한 것 | 보완에 주는 정보 |
|---|---|---|
| OUTPUT_CONTRACT | JSON/필드/자료형/빈 답변 등 계약 실패 | 원래 질문·자료·출력 계약을 유지하라는 안내 |
| CITATION_NOT_SUPPLIED | 제공하지 않은 문서를 인용 | 제공 ID만 사용하도록 계약 보완 |
| OUTPUT_SIZE_OR_TYPE | 응답 크기 또는 문자열 형식 실패 | 같은 출력 계약 보완 |

보완 입력에는 실패 ID만 추가한다. 모델의 잘못된 응답 전문과 평가용 정답·채점 기준을 다시 넣지 않는다. 실패한 응답에 공격 지시가 들어 있어도 다음 입력으로 그대로 복사하지 않는다. 보완 뒤에는 처음과 같은 검사기를 다시 실행한다. 실패하면 답변을 반환하지 않고 종료한다.

지나치게 긴 응답은 수신한 뒤 거부한다. 이 검사가 생성 중 출력 Token이나 과금을 제한하는 것은 아니다. 현재 Provider 계약에는 사용량과 출력 상한 전달이 없어서 Token·비용 기록은 미확인으로 남긴다. 문자 제한도 Token 예산 검증을 대신하지 않는다.

**활동:** repair_then_success에서 실패 ID와 보완 후 검사를 연결한다. restricted_citation에서 DOC-R을 두 번 제시해도 초안을 얻지 못하는지 본다. wrong_fact_shape_passes에서는 사람이 어느 원문 조건과 비교해야 하는지 적는다.

**제출:** 실패 → 변경 부분 → 동일 검사 → 종료 Trace와 별도 사실 채점표. **확인 질문:** 올바른 문서 ID 하나가 있다고 해서 근거가 맞다고 판단하면 어떤 오류를 놓치는가?

## K2-06.U04 버전 간 개선과 회귀

한 사례가 좋아졌다는 이유로 새 버전을 채택하면 다른 사례의 실패를 놓칠 수 있다. 비교할 때 사례 집합·자료 버전·모델·설정을 고정하고 변경한 조건을 하나씩 기록한다. 구조 통과, 사실·조건 일치, 자료 부족 대응, 제한 자료 처리, 호출 수·지연은 다른 지표다. 단일 점수로 섞기 전에 실패의 영향을 본다.

이번 데모는 동일 C01~C12에 고정 출력 A/B를 주입한다. A에서는 C01/C02의 구조가 실패하고 B에서는 통과한다. 대신 B는 C07에 승인 필드를 추가해 실패한다. C10은 양쪽 모두 입력 거부다. 이는 모델이나 Prompt의 개선 관찰이 아니라, 비교 도구가 개선과 회귀를 모두 남기는지 확인하는 실험이다. 더 많은 형식 통과만 보고 B를 자동 채택하지 않는다.

실제 모델 비교는 L1의 사람 채점 기준을 이어받는다. 정상 사실 6개와 경계 행동 6개를 분리하고, 초안이 반환되어도 금액·조건·예외·근거를 원문과 대조한다. 보완으로 성공한 사례는 최초 응답 성공과 따로 기록한다. 실제 생성·사람 채점이 없으면 품질 칸은 비워 둔다.

**활동:** 비교 기록에서 개선 C01/C02와 회귀 C07을 찾아 채택 보류 이유를 쓴다. 이어서 L1 사례별 채점표에 버전·시도 수·보완 여부·종료 이유 칸을 추가한다.

**제출:** 고정 변수, 변경점, 개선/회귀 ID, 채택 또는 복구 이유. **확인 질문:** 구조 통과 건수가 늘었는데 승인 위조 필드가 생겼다면 어떤 결정을 내릴 것인가?

## K2-06.U05 승인·중단·관찰의 신뢰 경계

모델의 “승인됐다”는 문장은 권한 증거가 아니다. 실행기는 모델 출력에서 호출 상한·취소 여부·승인 상태를 읽지 않는다. 상한은 호출자 설정, 취소는 실행기 바깥에서 전달한 신호를 사용한다. 이번 앱은 외부 작업 도구 자체가 없으며 승인 상태는 항상 미승인이다. 승인 저장소·사용자 인증·승인 후 작업 실행은 이후 Agent 단계의 과제다.

forged_approval은 승인 필드를 추가한 고정 응답을 거부한다. 이 결과는 그 출력 필드를 처리하지 않는다는 증거다. 실제 사용자 권한 체계가 구현되었거나 Prompt Injection 전체를 막았다는 뜻은 아니다. L1의 staff 역시 고정 학습용 역할이며 인증받은 사용자 신원은 아니다.

이번 실행기의 기본 경과시간 상한은 90초다. 동기 호출 사이와 응답 직후에 확인한다. 호출 도중에는 중단시킬 수 없고, 늦게 도착한 결과는 버린다. 따라서 실제 벽시계 실행시간이 90초를 넘을 수 있다. Provider의 별도 HTTP 제한도 전체 작업의 강제 취소와 같지 않다. 취소 신호 역시 호출 전후에 확인한다. 테스트는 가짜 시계로 이 경계를 확인했으며 90초를 실제 기다린 성능 측정이 아니다.

Trace에는 실행기가 관찰한 사건만 기록한다. 고정 응답의 API 시도를 실제 모델 추론 횟수로 표시하지 않는다. 실패 메시지 전문·원문 자료·비밀 값을 기본 Trace에 복사하지 않는다. 실제 운영에서는 접근 제어·보관 기간·삭제·민감 내용 처리도 따로 설계해야 한다.

**활동:** forged_approval, repeated_invalid와 시간·취소 테스트를 확인한다. 모델이 바꿀 수 있는 출력과 실행기가 소유한 상태를 나누고, 늦은 정상 응답을 반환하지 않는 이유를 설명한다.

**제출:** 승인 위조·반복 실패·총 호출 상한·취소/시간 경계 증거. **확인 질문:** 호출 전 90초 제한을 검사했다는 사실만으로 진행 중인 요청을 90초에 중단한다고 말할 수 있는가?

## 제출과 다음 연결

[L2 안내](../../practice/document-assistant/L2.md)의 제출표를 사용한다. 현재 제작 검증은 고정 응답을 통한 제어 흐름과 기존 앱 회귀까지다. 실제 모델 정상·보완·안전 종료 관찰과 사실 채점은 미완료다.

다음 K2-07/K2-08의 L3에서는 수동 문서 선택을 검색용 표현과 Index로 확장한다. L2 검사기는 검색 결과의 출처를 이어받되 ID 존재만으로 근거 타당성을 판정하지 않는다.
