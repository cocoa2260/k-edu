# Vector Search와 Index 운영 — 찾고, 걸러 내고, 갱신하기

K2-08 · 학생용 강의 제작본 v0.1 · 2026-10-31

**목표는 검색 결과가 어떤 원문·버전에서 왔는지 추적하고, 오래되거나 허용되지 않은 결과를 다음 입력에 넘기지 않는 것이다.** [Embedding 강의](../embedding/lesson.md)와 [L3 실습](../../practice/document-assistant/L3.md)의 같은 자료를 사용한다.

기본 실습은 SQLite에 작은 Index를 저장하고 모든 적격 벡터를 비교하는 Exact 검색이다. 선택 실습의 HNSW·IVF는 별도로 만든 합성 벡터를 사용한다. 두 실험의 결과를 섞지 않는다.

## K2-08.U01 문서·Vector·Metadata의 계약

Vector는 검색 표현이지 원문 그 자체가 아니다. 질문의 근거를 보여 주려면 Chunk 본문과 원문 위치가 필요하고, 현행 여부와 권한을 판단하려면 Metadata가 필요하다. 같은 문서라도 버전이 바뀌면 내용과 벡터를 함께 갱신해야 한다.

이번에는 가상 문서의 비어 있지 않은 줄을 하나의 Chunk로 만든다. 문서 제목과 줄 본문을 함께 인코딩한다. 검색 결과 본문은 해당 줄이며 문서 ID·버전·문서 내부 줄 번호·내용 해시를 함께 보존한다. 한 줄 안에 조건과 예외가 함께 있는 작은 학습 자료이므로 겹침 없이 나눴다. PDF·표·긴 문서에서도 이 정책이 적합하다는 결론은 아니다.

| 기록 | 역할 | 이번 예 |
|---|---|---|
| 문서 ID·버전 | 원문 식별과 갱신 단위 | DOC-A / v1 |
| Chunk ID | 문서 내부 조각 식별 | DOC-A@v1:L1 |
| 본문·내용 해시 | 원문 대조와 변경 감지 | 문서 내부 첫 줄과 전체 본문 해시 |
| Vector | 후보 순위 계산 | 고정 E5 설정의 384개 실수 |
| 권한·현행·삭제 | 검색 적격 조건 | staff / current / deleted |
| Profile·Generation | 표현 호환성과 검색 시점 | 설정 해시·Index 변경 번호 |

source_locator는 SQLite 문서 레코드의 ID·버전·내부 줄을 가리키는 논리 위치다. origin_path는 최초 입력 JSON의 출처이며 JSON 파일의 물리적 행 번호를 뜻하지 않는다. 갱신 실험의 새 버전은 임시 SQLite에만 존재하므로 원본 JSON을 열면 여전히 v1이다. 새 버전의 근거는 해당 실험 Index와 관찰 기록에서 확인한다.

**활동:** C01의 첫 검색 결과를 원본 DOC-A 첫 줄과 대조하고 Manifest의 버전·해시·Chunk 정책을 찾는다. Vector만 보관했을 때 사라지는 정보를 적는다.

**제출:** Index 레코드와 원문 추적표. **확인 질문:** 벡터 차원과 문서 ID만 저장했다면 답의 근거 문장을 나중에 정확히 재현할 수 있는가?

## K2-08.U02 Exact Search와 ANN

Exact 검색은 같은 적격 집합의 모든 벡터를 정해진 거리로 비교한다. 여기서 Exact는 “이 거리 기준의 상위 결과를 빠뜨리지 않는다”는 뜻이다. 의미적으로 올바른 문서나 사실이 맞는 답을 보장하지 않는다. L3의 Dense 검색도 모든 벡터를 비교했지만 C07의 필요한 문서를 놓쳤다. 이는 근사 탐색 누락이 아니라 표현과 순위의 문제다.

ANN은 비교할 위치를 줄여 근접한 후보를 빠르게 찾으려는 방법이다. 검색 설정에 따라 Exact 상위 결과 일부를 놓칠 수 있다. 그래서 같은 벡터·질문·거리·k를 고정한 Exact 결과를 기준으로 누락과 지연을 측정한다. 문서 회수율과 “Exact 이웃을 얼마나 되찾았는가”는 다른 평가다.

선택 실습은 정규화한 32차원 합성 벡터 4096개와 질문 벡터 128개를 쓴다. Exact 상위 10개를 정답 이웃으로 정하고 ANN의 상위 10개와 겹친 비율을 평균한다. 이 값은 한국어 의미 검색 점수가 아니다. 지연은 모델 인코딩·Index 구축을 제외한 따뜻한 검색 5회 배치의 중앙값이며 교육장 동시 접속 성능이 아니다.

**활동:** 선택 실습의 Exact·HNSW·IVF 기록에서 같은 k와 거리를 확인한다. 검색 폭을 늘렸을 때 이웃 회수와 지연이 어떻게 변했는지 표로 적는다. 작은 자료에서는 ANN이 항상 더 빠르지 않다는 것도 본다.

**제출:** 같은 질의의 Exact/ANN 결과·누락 ID·배치 지연 표. **확인 질문:** Exact 이웃 회수율이 100%라면 질문의 정답 문서를 100% 찾았다는 뜻인가?

## K2-08.U03 HNSW·IVF의 탐색

HNSW는 여러 층의 이웃 연결 그래프를 따라 후보를 좁힌다. M은 연결 수와 관련되고 efConstruction은 구축 시 탐색 폭, efSearch는 검색 시 탐색 폭과 관련된다. 폭을 늘리면 더 많은 후보를 살펴볼 수 있지만 계산·메모리·구축 비용도 함께 고려해야 한다. 모든 데이터에서 같은 설정이 최선인 것은 아니다.

IVF는 벡터 공간을 여러 구역으로 나누고 각 벡터를 해당 구역 목록에 배치한다. 질의에 가까운 일부 구역을 고른 다음 그 안의 벡터를 비교한다. nlist는 구역 수, nprobe는 검색할 구역 수다. 구역을 나누는 학습에는 실제 분포를 대표하는 벡터가 필요하다. nprobe만 늘려도 애초 표현이 부적절한 문제를 해결하지는 못한다.

| 방식 | 이번 고정 설정 | 바꿔 보는 설정 |
|---|---|---|
| HNSWFlat | M=8, efConstruction=40 | efSearch 8 → 64 |
| IVFFlat | nlist=64 | nprobe 1 → 16 → 64 |

이번 IVFFlat은 선택한 구역 안에서는 원래 벡터로 계산한다. 모든 64개 구역을 검색하면 이 실험의 Exact 이웃 회수율이 1이 됐다. 이것을 모든 IVF 변형·압축 설정에 일반화하지 않는다. HNSW에서는 efSearch를 늘려도 이 실험에서 회수율이 1에 도달하지 않았다.

이번에 사용하는 FAISS HNSW는 벡터 삭제를 지원하지 않는다. 따라서 기본 SQLite Exact Index에서 확인한 삭제 동작을 HNSW 삭제 검증으로 표시하지 않는다. 실제 HNSW 운영에는 삭제 표식·조회 시 제외·주기적 재구축 등 별도 정책과 검사가 필요하다.

**활동:** 한 질의가 어느 그래프 이웃 또는 어떤 구역을 살펴볼지 말로 설명하고, 실제 기록의 검색 폭/누락을 연결한다. 선택 도구는 최종 이웃 ID를 기록하며 내부 그래프 이동 경로 전체를 수집하지 않는다는 범위도 적는다.

**제출:** 두 방식의 탐색 설명과 설정 변화 예상/관찰 비교. **확인 질문:** nprobe를 늘리는 일과 임베딩 모델을 바꾸는 일은 각각 어느 문제를 바꾸는가?

## K2-08.U04 Filter·갱신·삭제·재색인

권한 밖 문서를 전체 Top-k에서 고른 뒤 마지막에 빼면 허용 문서가 이미 후보에서 밀릴 수 있다. 이번 Exact 검색은 staff·현행·미삭제 조건과 해당 사례의 가용 문서 목록을 먼저 적용하고 순위를 계산한다. DOC-R과 DOC-A-OLD는 저장되어 있어도 결과와 Context에 포함하지 않는다. staff는 학습용 고정 역할이고 실제 사용자 인증은 구현하지 않았다. SQLite 파일 자체에는 제한 자료도 있어 신뢰하는 로컬 저장소로 취급한다.

갱신은 문서 본문·버전·Chunk·벡터를 함께 바꾼다. 먼저 새 표현을 만드는 데 실패하면 기존 데이터를 유지하고, 성공하면 하나의 저장 트랜잭션에서 바꾼다. Index의 변경 번호도 증가시킨다. 삭제는 Chunk 벡터를 제거하고 본문·제목을 비운 삭제 표식을 남긴다. 이는 검색에 더 이상 나타나지 않는다는 검사이며 디스크 잔여 데이터·백업까지 안전하게 지웠다는 증거가 아니다.

검색 직후에도 문서는 바뀔 수 있다. 이번 Context 준비는 검색 당시 변경 번호와 현재 번호가 다르면 거부하고 재검색하게 한다. 본문도 검색 결과에 들어 있던 문자열을 믿지 않고 저장소에서 다시 읽고 권한·현행·삭제·해시를 검사한다. 아주 작은 단일 프로세스 실습의 규칙이며 여러 서버·동시 변경의 완전한 일관성 보장은 별도 설계 대상이다.

실제 갱신 실험에서는 임시 Index의 DOC-A를 v2 시험값 35000원으로 바꾸고 이전 v1 선택을 거부했다. 새 검색의 Context가 v2를 반영하는지 확인한 뒤 DOC-A를 삭제하고 삭제 전 선택도 거부했다. 이후 모든 적격 Chunk를 검색해도 DOC-A가 결과와 Context에 없었다. 원본 가상 규정 파일의 30000원은 변경하지 않았다.

재색인은 원본으로부터 새 설정의 벡터·Index를 다시 만드는 것이다. 이번에는 Token 상한 설정 변경에 따른 재사용 거부와 별도 Index 재구축을 실제 확인했다. 다른 가중치 모델로 전환한 실험은 아직 없으므로 그 검증까지 끝났다고 하지 않는다.

**활동:** 갱신 전 검색 → 갱신 → 오래된 Context 거부 → 재검색 → 삭제 → 오래된 Context 거부의 기록을 읽는다. C12의 가용 목록 제한 실험과 실제 삭제 실험을 구분한다.

**제출:** 권한 밖·구버전·갱신·삭제·설정 불일치의 배제 증거. **확인 질문:** 검색 결과를 저장해 두었다가 며칠 뒤 그대로 모델에 넣으면 어떤 검사를 놓치게 되는가?
