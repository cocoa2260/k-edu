# L6 실습 — 세 역할의 선택과 전달 경계 확인

**[Multi-Agent 강의](../../lessons/multi-agent/lesson.md) → [실제 비교 검토](../../reports/KEDU-PRODUCTION-008/REVIEW.md)를 먼저 본다.** JSON 전체를 읽을 필요는 없다. 실행 코드와 운영 기록은 따로 있다.

같은 Qwen CPU 모델을 순차 호출한다. 검색·작성·검토는 가중치가 다른 세 모델이나 독립 서버가 아니다. 역할별 입력·도구·행동과 Runtime의 전체 예산을 분리한 구성이다.

## 1. 환경과 실행

L5의 Linux x86_64 Python 3.12 CPU 환경과 모델 캐시를 그대로 사용한다. 새 패키지나 유료 API는 필요하지 않다. 아래는 backend 폴더에서 **입력할 명령**이며 관찰 결과 예시가 아니다.

| 목적 | 입력할 명령 |
|---|---|
| 기존·새 경계 검사 | `python -m pytest -q` |
| 고정 응답 M01~M04와 정상 경로 | `python -m tools.multi_fixture_lab --output l6-fixtures.json` |
| 실제 모델의 한 사례 | `python -m tools.multi_lab --output l6-multi --cases C01` |
| 같은 설정으로 18개·별도 역할 확인 이어가기 | `python -m tools.multi_lab --resume --output l6-multi --role-probes` |

기본 실행은 모델 캐시만 읽는다. 캐시가 없을 때만 최초 download 옵션을 사용한다. 이전 결과를 덮어쓰지 않고 완료 사례를 재사용한다. 기록한 코드·자료·모델 설정이 바뀌면 새 폴더를 쓴다.

모델은 입력 1536 Token·출력 최대 192 Token, 입력은 2000문자 제한도 적용한다. 중요한 원문을 몰래 자르지 않고 초과하면 중단한다. 교육생 GPU·다른 운영체제·동시 수업 실행은 검증하지 않았다.

## 2. 결과 읽기

| 기록 | 볼 것 |
|---|---|
| role_model_called / role_action | 실제로 호출한 역할과 선택한 행동 |
| role_tool_observed | 허용된 도구의 실제 결과 |
| handoff_validated | 역할·질문·원문 버전·근거 ID·Runtime 예산 스냅샷 |
| repair_consumed / evidence_requested | 공통 보완 예산을 쓴 지점 |
| model_review | 모델의 검토 의견; 사용자 승인 아님 |
| stopped | 전체 종료 이유 |

전달 근거는 실제로 읽은 Source ID여야 하고 받는 역할의 범위에도 있어야 한다. 작성/검토는 받은 ID 밖의 원문을 읽을 수 없다. 원문은 Runtime이 저장소에서 다시 확인한다. 모델이 쓴 자유 요약이나 전체 대화 로그를 그대로 전달하지 않는다.

budget의 models/tools/repairs/retries와 역할별 roles를 함께 본다. 재진입해도 누적값을 유지한다. 8회 전체 모델 상한과 역할 4/2/3 상한은 새 예산을 각각 주는 방식이 아니다.

## 3. Single/Multi 비교

core-v1·agent-v1의 같은 18개를 쓴다. L5와 같은 자료·모델 리비전·생성 설정으로 비교한다. 다만 Single은 모델 4회·도구 3회·180초, Multi는 모델 8회·도구 6회·240초라 예산이 다르다. 호출·품질 차이를 역할 분리 하나만의 효과로 표현하지 않는다.

모델 적재는 질문 처리 시간과 따로 기록한다. L5에서 별도 적재 시간을 기록하지 않은 부분은 0으로 채우지 않는다. CPU 실험 지연을 교육장 성능으로 일반화하지 않는다.

| 사례 | Single 종료/호출 | Multi 종료/역할별 호출 | 원문·초안·검토 | 남은 오류 |
|---|---|---|---|---|
| 각 C/A 사례 | 실제 L5 기록 | 실제 L6 기록 | 실제 도달한 단계만 | 원문 대조 |

역할이 되묻거나 조기에 중단해 모델 호출이 줄어도 과제 완료가 아니라면 효율 향상으로 보지 않는다. L4/L5 답변 품질 문제는 자동으로 해결된 것이 아니다.

## 4. Handoff 경계 4개

| 사례 | 확인할 것 |
|---|---|
| M01 | 검색자가 아는 근거라도 수신 역할 범위 밖이면 전달 거부 |
| M02 | 작성자의 한 번 추가 근거 요청·역할 호출 수와 전체 보완 수 유지 |
| M03 | 검토 반려 후 같은 실패 반복 시 부분 초안만 남기고 중단 |
| M04 | 역할 일시 오류·전체 모델 예산·경과시간 소진 시 전체 중단 |

이 네 개는 고정 응답과 가짜 시계/오류로 경계를 확실히 통과하는 검사다. 실제 모델의 품질 사례로 합산하지 않는다. 실제 240초를 기다린 장애 성능 시험도 아니다.

## 5. 별도 Role Probe와 제출

writer-probe/reviewer-probe는 Runtime이 검증된 근거와 초안을 준비해서 해당 역할을 따로 호출한 결과다. 실제 연구자에게서 전달받아 전체 과제를 성공시킨 결과가 아니다. 모델 원응답과 실제 입력·해시를 남기며 어떤 역할이 유효한 행동을 냈는지 확인한다.

응답 전체가 하나의 JSON 코드 블록이면 포장만 제거하고 같은 역할 Schema를 검사한다. Python 코드나 앞뒤 설명·JSON 여러 개는 실행·추출하지 않는다. 원응답은 기술 기록에 보존한다.

제출물은 Single/Multi 선택 이유, 세 역할의 계약과 Context, 실제 Handoff·예산 Trace, 한 번 보완과 반복 실패의 종료, 같은 18개 비교와 M01~M04의 별도 결과다. 모델의 pass는 근거·의미를 자동 승인하지 않으며 최종 결과도 사람이 검토해야 한다.
