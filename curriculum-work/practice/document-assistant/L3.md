# L3 실습 — 실제 Embedding·검색·Index 변경 확인

**[Embedding 강의](../../lessons/embedding/lesson.md) → [Index 운영 강의](../../lessons/vector-index/lesson.md) → 이 실습 순서로 보면 된다.** 기술 기록을 전부 읽지 않아도 강의를 따라갈 수 있다. 실행 코드는 Backend의 retrieval과 tools 폴더에 있다.

L1의 가상 문서 6개·공통 질문 12개를 재사용한다. 실제 검색용 모델을 CPU에서 실행하며 답변 생성·유료 API 호출은 하지 않는다. 이 환경은 Linux x86_64 / Python 3.12 CPU에서 검증했고 GTX 1060 3GB·Windows·macOS·교육장 동시 실행은 검증하지 않았다.

## 1. 환경 준비

backend 폴더에서 별도 가상환경을 만든 뒤 사용한다. 기존 L0~L2 환경을 덮어쓸 필요는 없다. 아래는 **터미널에 입력할 명령**이며 출력 예시가 아니다. 모델 파일과 CPU 패키지를 내려받을 디스크·네트워크가 필요하다. 모델은 약 1.18억 Parameter라 다운로드 없이 즉시 실행되는 데모가 아니다.

| 순서·목적 | 입력할 명령 |
|---|---|
| 검증된 Linux CPU PyTorch 설치 | `python -m pip install torch==2.15.0+cpu --index-url https://download.pytorch.org/whl/cpu` |
| 기존 앱과 검색 의존성 설치 | `python -m pip install -r requirements-retrieval.txt` |
| 경계·기존 앱 회귀 검사 | `python -m pytest -q` |
| 최초 고정 모델 다운로드와 검색 실행 | `python -m tools.retrieval_lab --download --output l3-run-01` |
| 캐시만 사용해 다시 실행 | `python -m tools.retrieval_lab --output l3-run-02` |

출력 폴더가 이미 있으면 덮어쓰지 않는다. 캐시가 준비되지 않은 기본 실행은 실패하며 고정 응답으로 자동 전환하지 않는다. 프록시·TLS 검증을 끄지 않는다. 다른 운영체제에서는 해당 플랫폼의 CPU 설치 방법을 따로 확인해야 한다.

모델 ID·리비전·접두어·Pooling·정규화·차원은 [encoder.py](backend/retrieval/encoder.py)에 고정돼 있다. 실제 읽은 가중치로 Embedding을 만들고 본문·벡터·Metadata를 SQLite에 저장한다. 모델의 512 Token을 넘으면 조용히 자르지 않고 오류로 중단한다.

## 2. 출력에서 볼 것

| 파일·항목 | 역할 | 먼저 볼 부분 |
|---|---|---|
| observed.json의 metrics | 실제 검색 평가 요약 | 방식별 8개 사례의 문서 회수 비율 |
| observed.json의 cases | 같은 12개 사례 × 3개 방식 | C07·C08·C09와 경계 사례 |
| manifest_before_mutation | 최초 자료·모델·Chunk 설정 | 총 11 Chunk와 적격 9 Chunk |
| lifecycle | 실제 갱신·삭제와 오래된 선택 거부 | Context의 버전과 삭제 후 ID |
| migration | 설정 변경·재사용 거부·새 Index | 512 → 128 Token 상한 변경 |
| index.sqlite | 갱신·삭제 실험 뒤의 실제 저장소 | 마지막에는 DOC-A가 삭제됨 |
| rebuilt.sqlite | 원본 v1 자료로 새로 만든 저장소 | 새 설정, 원본 DOC-A 다시 존재 |

index.sqlite가 마지막 삭제 상태인 것은 정상이다. 최초 검색 결과와 삭제 후 저장소 상태를 같은 시점으로 취급하지 않는다. 원본 documents-v1.json은 변경하지 않는다. 갱신 시험값 35000원을 원본 규정이나 모델의 답변으로 표시하지 않는다.

Context 준비는 검색된 Chunk를 다시 읽어 주는 단계까지다. 이번에는 이것을 모델에 보내지 않는다. L2 Harness와 생성 Provider를 결합한 전체 실행은 L4에서 만든다. 기존 /ai/chat·/ai/prepare는 변경하지 않았고 새 검색 API·UI도 추가하지 않았다.

## 3. 검색 평가

검색 입력에는 질문과 적격 문서만 전달한다. 평가용 [retrieval-v1.json](data/retrieval-v1.json)의 정답 문서 ID는 나중에 결과와 비교한다. L1의 정답·채점 기준을 검색에 넣어 결과를 맞추지 않는다.

| 확인 대상 | 본인이 남길 기록 |
|---|---|
| C01·C02 | 필요한 규정과 실제 상위 Chunk |
| C07 | 공격 메모 순위와 현행 규정 누락 여부 |
| C08 | 바꿔 말한 질문의 실제 결과; 어느 방식이 유리했는지 |
| C09 | DOC-A/DOC-B 모두 필요한 이유와 부분 회수 |
| C03 | 결과가 있어도 숙박비 금액 근거가 없는 이유 |
| C06 | DOC-R 본문이 결과·Context에 없는지 |
| C10 | 검색 인코딩 전에 공백 입력 거부 |
| C12 | 가용 목록에 없는 DOC-A 배제; 실제 삭제 실험과 구분 |

지표는 상위 3개 Chunk 안에 필요한 문서가 포함된 비율이며 답변 정답률이 아니다. 같은 문서의 여러 Chunk가 상위를 차지할 수도 있다. 다음 실험으로 문서 중복 제한이나 Reranker를 추가한다면 이번 결과와 구분해 버전을 기록한다. 현재 학습된 Reranker는 없다.

## 4. Index 경계 검사

기본 검색은 권한·현행·삭제·가용 자료 조건을 먼저 적용한다. staff는 학습용 역할이고 실제 인증이 아니다. SQLite 파일에는 제한 자료도 저장되므로 파일을 일반 사용자에게 직접 공개하는 구조가 아니다.

갱신·삭제 전에 받은 선택은 변경 번호가 달라지면 Context 준비에서 거부된다. 새 검색으로 현재 레코드를 읽는다. 모델 설정이 다르면 같은 차원이어도 기존 Index를 열지 못한다. 이번 실제 재색인은 같은 모델의 Token 상한 변경이며 다른 가중치 모델로의 전환 실험은 미실행이다.

삭제는 검색 가능한 레코드·벡터의 제거 검사다. 디스크 잔여·백업·로그·다른 프로세스의 캐시까지 지웠다는 뜻은 아니다. 동시에 여러 요청이 갱신하는 운영 환경도 이번 작은 단일 프로세스 검증 범위 밖이다.

## 5. 선택 실습 — Exact·HNSW·IVF

| 목적 | 입력할 명령 |
|---|---|
| 선택 비교 패키지 설치 | `python -m pip install -r requirements-ann.txt` |
| 합성 벡터 비교 기록 생성 | `python -m tools.ann_lab --output ann-observed.json` |

32차원 합성 벡터 4096개와 질의 128개를 사용한다. 이 벡터는 언어 모델로 만든 것이 아니다. Exact의 상위 10개를 기준으로 HNSW·IVF의 이웃 회수율과 검색 배치 지연을 비교한다. 계산 예는 vector_math에 있고 첫 질의의 이웃 ID도 함께 남긴다. 내부 그래프 경로를 시각화한 도구는 아니다.

지연은 인코딩·학습·구축을 제외하고 따뜻한 검색을 다섯 번 실행한 중앙값이다. 문서 검색 성능이나 동시 사용자 수로 해석하지 않는다. 이번 HNSW에서 SQLite의 삭제 동작을 확인한 것으로 주장하지 않는다.

## 제출·완료 조건

네 종류의 표현 비교표, 질문-정답 문서와 검색 결과표, 작은 벡터 계산표, 모델 교체/복구 계획, Index 원문 추적표, Exact/ANN 비교표, HNSW/IVF 탐색 설명, 권한·갱신·삭제 증거를 제출한다.

이 제작 환경에서는 실제 CPU Embedding·검색과 캐시 재실행을 확인했다. 학생 본인의 실행 기록과 혼동하지 않는다. L0~L2의 실제 답변 생성과 L4의 실제 RAG·근거 채점, 교육장·UI 검증은 여전히 남아 있다.
