# L5 실습 — 모델의 도구 요청을 검사하고 실행하기

**[Single-Agent 강의](../../lessons/single-agent/lesson.md) → [실제 실행 검토](../../reports/KEDU-PRODUCTION-007/REVIEW.md)를 먼저 보면 된다.** 코드와 JSON은 직접 실행하거나 기술 검토할 때 선택해서 읽는다.

같은 E5 검색·SQLite Index·Qwen CPU 모델을 사용한다. core-v1 12개에 agent-v1 6개를 더한 18개가 다음 Single/Multi 비교 기준이다. 실제 모델의 행동과 오류를 직접 넣은 고정 응답 실험은 나눠서 기록한다.

## 1. 환경과 실행

L3/L4와 같은 Linux x86_64 Python 3.12 CPU 패키지를 사용하되 Framework 연결 확인을 위해 별도 가상환경을 권장한다. 먼저 [L3](L3.md)의 CPU PyTorch를 설치하고 아래를 실행한다. 모델 파일 캐시는 재사용할 수 있다. 다른 운영체제·교육생 GPU·동시 수업 성능은 검증하지 않았다.

다음 표는 **터미널에 입력할 명령**이다. backend 폴더에서 실행한다. 프로그램 출력 예시가 아니다.

| 목적 | 입력할 명령 |
|---|---|
| L5와 Framework 연결 패키지 | `python -m pip install -r requirements-agent.txt` |
| 기존·새 경계 검사 | `python -m pytest -q` |
| 모델 없이 경계·StructuredTool API 실행 | `python -m tools.agent_fixture_lab --output l5-fixtures.json` |
| 실제 모델로 한 사례 | `python -m tools.agent_lab --output l5-single --cases A02` |
| 같은 설정으로 18개 이어서 실행 | `python -m tools.agent_lab --resume --output l5-single` |

캐시가 없으면 최초 한 번 download 옵션을 붙여 고정 모델을 내려받는다. 기본 실행은 캐시만 읽으며 유료 API로 전환하지 않는다. 결과 폴더·파일을 덮어쓰지 않고, resume은 완료 사례를 재사용한다. 기록한 코드·자료·모델 설정이 바뀌면 새 폴더를 사용한다.

## 2. 실제 모델 결과에서 볼 것

| 항목 | 의미 |
|---|---|
| action_selected | 모델이 실제 출력하고 파싱을 통과한 행동 |
| failure | 행동 형식·도구·인수·출처 등 실패 ID |
| tool_started | 검사에 들어가는 도구 요청 시도 |
| tool_dispatches | 이름·인수·승인 검사 뒤 실제 함수 호출 시도 |
| tool_observed | 검사를 통과한 도구 결과 |
| stopped | 모델 중단·최종 초안·실패·상한의 종료 이유 |

모델이 잘못된 JSON을 쓰면 action_selected가 없을 수 있다. 도구 이름을 적어도 검사에서 거부하면 dispatch는 0이다. Framework API를 테스트한 사실과 실제 모델이 도구를 선택한 사실도 구분한다.

tool_attempts는 도구 처리 예산에 들어온 시도를 센다. 상한에 도달한 뒤 모델이 추가로 낸 요청은 action_selected에는 보이지만 처리 시도/dispatch는 늘지 않는다. 재시도는 새 처리 시도로 센다.

dispatch는 등록 함수에 진입한 시도다. read_evidence 내부에서 발견하지 않은 ID를 거부하면 dispatch는 있어도 읽은 원문은 0개다. 실제 검색 결과·원문은 검사를 통과한 tool_observed에서 확인한다.

현재 프롬프트는 상태에 맞는 행동 형식 예시를 준다. 검색 결과의 첫 Source ID가 읽기 예시에 쓰일 수 있어 독립적인 계획 능력의 평가로 해석하지 않는다. 예시는 자동 실행되지 않고 실제 모델 응답만 Runtime에 전달된다. 검색/읽기 후 현재 입력에는 실제 읽은 원문과 최근 Observation을 넣는다.

## 3. 공통 18개 사례

core-v1의 질문·정답 기준은 바꾸지 않는다. A01만 단순 인사 응답을 허용하는 교사 정의 정책을 사용하고, 나머지는 근거 없는 직접 응답을 허용하지 않는다. 모델 출력의 승인·정책 필드는 이 설정을 바꿀 수 없다.

| 사례 | 점검할 경계 |
|---|---|
| C01~C12 | 기존 규정 질문·자료 부족·공격·제한·공백·가용 문서 |
| A01 | 필요 없는 검색 없이 단순 응답하는지 |
| A02 | 실제 모델이 검색 → 원문 읽기를 요청하는지 |
| A03 | 없는 도구를 실행하지 않는지 |
| A04 | 승인 추가 인수·승인 없는 저장을 거부하는지 |
| A05 | 첫 검색에 주입한 일시 오류를 허용 범위에서만 재시도하는지 |
| A06 | 같은 실패나 반복 호출을 멈추는지 |

A05에서 실제 모델이 검색을 요청하지 않으면 fault_injected는 false다. 이를 실제 복구 성공으로 기록하지 않는다. 고정 응답 실험은 같은 경계를 확실히 지나도록 구성한다. 그 도구 결과를 실제 모델 성능으로 합산하지 않는다.

## 4. Schema·승인·출처 실험

고정 응답 기록에는 이름/인수 거부, 승인 없는 모의 저장 거부, 한 번의 읽기 재시도, 반복 호출 상한, 승인된 메모리 저장의 재사용 거부가 있다. 승인 모의 값은 실행기에서 생성한 것으로 사용자 승인 UI를 실행한 것이 아니다. 메모는 메모리에만 남고 외부 작업은 하지 않는다.

StructuredTool 연결은 두 읽기 도구의 실제 invoke를 확인한다. 같은 Registry 결과와 비교하고 추가 approved 인수를 거부한다. 원격 추적을 끄고 HTTP 요청 가드로 실행했다. Framework Agent 전체·MCP 연결·실제 인증을 완료한 결과는 아니다.

## 5. 제출과 평가

| 사례 | 실제 모델 행동 | 도구 시도/dispatch | 읽은 출처 | 최종 답변 또는 종료 | 의미·조건·예외 검토 |
|---|---|---|---|---|---|
| 각각의 C/A 사례 | 실제 관찰 | 별도 기록 | 실제 Source ID | 실제 관찰 | 원문 대조 |

정상 사실 6개, core 경계 행동 6개, Agent 경계 6개를 분리한다. 최종 초안의 인용이 원문에 있어도 의미가 틀릴 수 있고, 도구를 읽었어도 답변까지 못 가면 완료가 아니다. L4의 품질 문제를 해결됐다고 표시하지 않는다.

모델 결정 최대 4회·도구 요청 최대 3회·읽기 도구 재시도 실행 전체 1회·같은 오류 ID 두 번이라는 상한을 확인한다. 180초는 호출 전후 검사이며 진행 중 호출을 강제로 끊지 않는다. 각 모델 출력은 최대 192 Token이라 잘림도 확인한다.

제출물은 Workflow/Agent 비교, Registry 거부 증거, 실제 행동·Observation Trace, 같은 18개 사례의 단계별 결과, Framework 연결 범위와 남은 검증이다. 작성 자료와 실행 경로 검증을 수업·서비스 품질 승인으로 바꾸지 않는다.
