# L2 실습 — 실패를 기록하고 제한 안에서 종료하기

**읽는 순서: [Harness 강의](../../lessons/harness/lesson.md) → 이 안내 → 필요할 때만 [실행 결과](../../reports/KEDU-PRODUCTION-004/RESULT.md).** JSON 운영 기록을 전부 읽을 필요는 없다.

기존 L0 앱과 L1의 가상 문서·12개 사례·비교 조건을 사용한다. 학습 목표는 통신 재시도와 출력 보완을 구분하고, 같은 검사로 재확인하며, 상한에서 멈춘 증거를 남기는 것이다. 실제 기관 규정·실제 모델 응답을 제공한 실습이 아니다.

## 1. 실행 준비

[Backend 안내](backend/README.md)의 Python 3.12 가상환경과 패키지를 사용하고 backend 폴더에서 실행한다. 아래 표는 **터미널에 입력할 명령**이다. 프로그램 출력 예시가 아니다. 이번 도구에는 실제 Provider를 선택하는 옵션이 없고 API Key도 필요 없다.

| 목적 | 입력할 명령 |
|---|---|
| 기존 L0/L1과 L2 검사 | `python -m pytest -q` |
| 새 고정 응답 실험 기록 생성 | `python -m tools.harness_demo --output l2-observed.json` |

기록 파일이 이미 있으면 덮어쓰지 않고 실패한다. 재실행할 때는 l2-observed-02.json처럼 새 이름을 사용한다. 응답·오류 목록은 [harness_demo.py](backend/tools/harness_demo.py)에 있으며 실제 제어는 [harness.py](backend/app/harness.py)가 수행한다. 같은 앱의 Provider 인터페이스를 재사용하고 /ai/chat, /ai/prepare 계약은 바꾸지 않는다. 이번 묶음에서 새 웹 API나 React 화면은 추가하지 않았다.

## 2. 기록 읽기

먼저 증거 종류가 고정 응답 실행이고 실제 모델 호출이 0인지 확인한다. scenarios에는 각 실험 결과, regression에는 같은 12개 사례의 고정 출력 A/B 비교가 있다. 각 실험의 trace만 펼쳐 다음 순서로 읽으면 된다.

| 기록 | 뜻 |
|---|---|
| prepared | L1 자료 선택과 최종 입력 해시 |
| call_started | Provider 호출 시도와 입력 해시 |
| transport_failed / retry_scheduled | 통신 실패와 같은 입력의 재시도 |
| output_checked / repair_scheduled | 출력 검사 실패 ID와 한 번의 보완 |
| stopped | 초안 반환 또는 실패 종료 이유 |

결과의 draft_needs_review는 사람이 확인해야 할 초안이다. stopped는 실패·상한·취소 등의 종료이며 draft가 비어 있다. 원문 답변·자료는 기본 Trace에 없고 해시는 내용을 복원하지 못한다. 현재 예제에서는 가상 초안이 결과의 draft에 남지만 실제 민감 답변을 그대로 공유하는 방식으로 확대하지 않는다.

## 3. 경계 실험

| 실험 이름 | 비교할 것 | 제출할 관찰 |
|---|---|---|
| valid_shape | 최초 응답 구조 통과 | 1회 호출과 사람 검토 상태 |
| timeout_then_success | 같은 입력의 재시도 | 두 입력 해시의 동일성 |
| repair_then_success | 실패 ID 안내로 형식 보완 | 변경된 해시·동일 검사 재실행 |
| repeated_invalid | 보완 후에도 실패 | 초안 없이 종료·총 2회 |
| global_three_calls | 재시도와 보완의 공통 예산 | 합계 3회, 내부 예산 초기화 없음 |
| retry_exhausted | 통신 실패 반복 | 재시도 상한 종료 |
| upstream_terminal | 원격 상태 오류 | 보완 없이 즉시 종료 |
| restricted_citation | DOC-R 인용 | 제공하지 않은 ID 거부 |
| forged_approval | 승인 필드 추가 | 계약 거부·실행 승인 없음 |
| wrong_fact_shape_passes | 형식만 맞는 틀린 금액 | 구조 통과와 사실 실패의 차이 |

위 표는 확인할 항목이다. 실제 이 제작 환경의 관찰값은 [결과 보고서](../../reports/KEDU-PRODUCTION-004/RESULT.md)에 따로 있다. 제출할 때는 본인이 실행한 기록의 값과 파일명을 적는다.

시간과 취소는 [테스트](backend/tests/test_harness.py)에서 가짜 시계·취소 신호로 주입한다. 경과시간 검사와 진행 중 호출 강제 취소를 혼동하지 않는다. 프로세스 중단·분산 취소·실제 장애 서버의 시간 측정은 이번 검증에 포함하지 않았다.

## 4. 같은 사례로 회귀 찾기

regression의 A/B는 사람이 지정한 고정 출력 버전이다. C01/C02의 구조 통과와 C07의 회귀를 함께 찾아 채택 여부를 설명한다. C10의 공백 입력 거부를 답변 오답으로 세지 않는다. 이 실험을 Prompt 성능 향상이나 모델 정답률로 발표하지 않는다.

실제 모델 비교용으로는 아래 빈 표를 사례별로 복제한다. L1의 사실·조건·예외·근거 채점 기준을 사용한다. 정상 사실 6개와 경계 행동 6개는 분리한다. 미실행 칸에는 숫자나 예상 정답을 채우지 않는다.

| 사례 | 자료/모델/설정 버전 | 변경 조건 | 최초 구조 통과 | 보완 후 구조 통과 | 사람의 사실·근거/행동 채점 | 시도 수·지연·종료 이유 | 채택/복구 이유 |
|---|---|---|---|---|---|---|---|
| C01~C12 각각 | 미실행 | 미실행 | 미실행 | 미실행 | 미실행 | 미실행 | 미실행 |

## 5. 완료 조건과 남은 단계

이번 코드의 기본 상한은 Provider 시도 3회, 통신 재시도 1회, 보완 1회이며 재시도·보완 예산은 실행 전체가 공유한다. 90초는 호출 사이에 확인하는 경과시간 제한이다. 출력 크기 검사도 수신 뒤 적용한다. Token·비용 상한이나 진행 중 호출의 강제 취소는 구현하지 않았다.

수업 제출은 책임 분담표, 반복 종류별 정책표, 실패·보완·재검사 Trace, 회귀 비교·채택 이유, 승인/중단 경계 설명이다. 형식 통과와 사실 검토를 구분하면 고정 응답 단계의 학습 목표를 확인할 수 있다.

L2의 실제 모델 Gate는 별개다. 준비된 로컬 모델 경로에서 정상·형식 보완·안전 종료를 관찰하고 사람 채점을 남겨야 한다. 현재는 미실행이며 데모가 자동으로 이 Gate를 통과시키지 않는다. 유료 API를 자동으로 호출하는 단계도 아니다.
