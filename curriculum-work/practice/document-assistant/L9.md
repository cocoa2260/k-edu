# 문서를 등록하고 현재 근거로 보고서 준비하기

[문서 입력·상태 강의](../../lessons/document-ai/intake.md)와 [근거 보고서 강의](../../lessons/document-ai/report.md)를 읽고 진행한다. 아래는 문서 도우미 통합의 앞 세 단원에 해당한다. Provider·React/Streaming·최종 평가 안내는 뒤에 별도로 보존한다.

## 준비와 실제 실행 범위

모든 명령은 `practice/document-assistant/backend`에서 입력한다. Python 3.12의 기존 환경에 `python -m pip install -r requirements-document.txt -r requirements-report.txt`로 고정 PDF·DOCX 의존성을 준비한다. 새 임시 실습에는 모델 Weight·GPU·한글 OCR 데이터·외부 API가 필요 없다.

`tools.document_ai_steps`의 intake/lifecycle/review는 **현재 코드와 원본 자료를 사용하는 실행**이다. 임시 SQLite·TXT를 만들고 끝나면 정리한다. 기존 자료/DB를 덮어쓰지 않고, DOCX/PDF 파일 생성·LLM 호출·독립 승인도 수행하지 않는다. history는 **저장 기록 읽기**다. 실습 전에 무엇이 달라질지 예상하고 실행 뒤 이유를 설명한다.

## 1. 같은 내용과 형식에 맞는 원문 위치

다음은 **실행 명령**이다. 실제 PDF/단순 DOCX와 임시 TXT를 읽어 IR로 바꾸고 검색 문맥을 확인한다. TXT에는 기한 문장·빈 줄·금액 문장이 있다. 금액의 원문 줄 번호가 2일지 3일지 먼저 예상한다.

```bash
python -m tools.document_ai_steps --mode intake
```

현재 예제의 예상 Element 수는 PDF 11/TXT 2/DOCX 16이다. 이 숫자를 외우는 대신 무엇을 센 것인지 본다. PDF는 텍스트 블록과 별도 표, TXT는 비어 있지 않은 원문 줄, DOCX는 본문 문단·표/셀 구조를 보존한다. parse 직후에는 대상 문서의 검색 결과가 0이고 index 뒤에 문맥이 나온다.

TXT 금액의 Locator는 원본 3줄, PDF 영수증 문장은 물리 1쪽의 영역, DOCX 금액은 본문 블록 6의 표 1·행 3·열 3이다. DOCX에 가짜 PDF 페이지를 붙이지 않는다. PDF 문맥에는 두 열의 문장이 합쳐진 한계가 남으며 DOCX 금액 셀도 숫자만 검색했다고 조건/머리글 관계를 이해한 것은 아니다.

원본 파일은 [디지털 PDF](backend/data/document-v1/digital.pdf)와 [단순 DOCX](backend/data/multiformat-v1/policy.docx)다. 현재 DOCX 지원은 단순 문단과 병합 없는 직사각 표의 좁은 범위다. HWP/HWPX는 거부한다. 최초 Registry 실험의 PDF/TXT 두 형식 기록과 이후 추가된 현재 기능을 구분한다. 스캔 OCR는 이 활동에서 실행하지 않는다.

제출은 원본/내부 버전/IR Element/검색 문장/Locator의 연결표와 형식별 지원 한계다.

## 2. 재전송·새 버전·권한·삭제 비교

첫 업로드의 기한은 7일이다. 같은 요청을 다시 보내면 버전이 늘어날지, PC 파일만 14일로 고치면 저장소도 바뀔지 예상한다. 아래는 **실행 명령**이다.

```bash
python -m tools.document_ai_steps --mode lifecycle
```

같은 키·같은 입력은 replayed=True이고 버전 1이다. 호출자가 검색 결과 문장을 ‘변조한 문장’으로 고쳐도 context는 저장된 금액 원문을 가져온다. PC 파일을 14일로 바꿔도 등록 사본은 7일이다. 같은 키로 바뀐 입력을 등록하면 충돌하고, 새 키면 버전 2·uploaded가 된다.

새 버전 등록 직후에는 검색이 비고 옛 문맥은 Stale selection으로 거부된다. parse/index/review를 다시 거친 다음 14일 문장을 확인한다. 권한을 restricted로 바꾸면 검색에서 사라지고 옛 요청 재전송도 거부된다. 삭제 후 DB를 다시 열어도 state=deleted·source=None·ir=None이며 같은 ID를 새 요청으로 등록할 수 없다.

코드가 기록한 현재 상태와 과거 selection의 사용 가능 여부를 나눠 적는다. 삭제는 임시 저장소 안의 자료 제거이며 사용자 PC 원본·백업·외부 사본의 보안 삭제가 아니다. 같은 요청 재전송을 위한 지문과 삭제 흔적은 남는다. staff는 고정 신뢰 측 시연 역할이며 실제 사용자 인증으로 취급하지 않는다.

제출은 재전송/입력 변경/새 버전/제한/삭제/재시작의 버전·상태·검색·옛 문맥 결과와 이유다.

## 3. 인용이 있어도 틀린 주장을 거부하기

원문은 ‘신청 기한 7일’이다. 보고서의 문장을 30일이라고 쓰면서 같은 인용을 달면 어디서 막혀야 할지 예상한다. 아래는 **실행 명령**이다.

```bash
python -m tools.document_ai_steps --mode review
```

문서가 indexed일 때는 보고서 명세를 만들 수 없고 review로 표시한 뒤 prepare가 가능하다. 그러나 이것만으로 출력은 허용되지 않는다. 승인 전 export는 차단되며 최종 폴더 존재는 False다. 이 거부는 실제 출력 함수의 승인 검사에서 일어나고 문서 렌더링은 실행되지 않는다.

7일 인용+30일 주장은 자동 연결 검사로 명세가 만들어질 수 있다. 도구 안의 고정 검토자가 ‘7일 근거는 30일을 지지하지 않음’이라는 이유로 reject를 기록한다. 올바른 7일 명세에는 별도의 approve를 기록하지만 실제 사람의 업무 승인이 아니다. 학생도 원문과 주장·조건을 대조해 결정 이유를 적는다.

승인한 명세의 문장을 바꾸면 내용 해시가 달라 과거 승인과 맞지 않는다. 같은 파일을 새 요청으로 등록해 버전만 늘려도 옛 출처는 무효다. 문서가 review 상태라는 것, 특정 내용의 approve가 있다는 것, 그 내용이 **현재** 원문과 맞는 것은 각각 확인해야 한다.

제출은 7일/30일 주장의 인용·의미 판단, 승인 전/문장 변경/출처 새 버전의 차단 이유다. “자동 검사가 통과해서 승인했다”는 이유로 의미 검토를 대신하지 않는다.

## 4. 과거 출력 파일과 현재 템플릿 구분

아래는 **저장 기록을 읽는 실행 명령**이다. 새 문서 출력·재승인은 아니다.

```bash
python -m tools.document_ai_steps --mode history
```

초기 두 Claim의 명세·검토는 템플릿 v1, 현재 템플릿은 v2다. 저장 내용 해시와 검토 연결이 True여도 과거 명세를 현재 승인으로 쓸 수 있다는 뜻은 아니다. DOCX Locator 지원을 더한 현재 템플릿으로 새 출력하려면 원문에서 명세를 새로 준비하고 검토해야 한다.

[기존 DOCX](backend/data/report-v1/evidence-report.docx)와 [기존 PDF](backend/data/report-v1/evidence-report.pdf)를 열어 주장 두 개·인용·원본 위치·해시를 확인한다. 두 파일은 같은 명세의 내용을 다른 형식으로 출력한 과거 예제다. 픽셀 배치가 동일해야 하는 요구는 없지만 주장의 내용과 근거는 같아야 한다.

DOCX의 문단/XML에 한글이 있어도 화면에서 빠질 수 있다. Word/렌더러가 찾는 Noto Sans KR 또는 호환 글꼴을 확인한다. PDF에는 당시 사용한 글꼴 일부가 들어 있지만 DOCX에는 글꼴을 내장하지 않았다. 내용 검사와 모든 페이지의 화면 대조를 분리한다. 현재 장비에서 렌더링하지 않았다면 과거 화면 확인 기록을 본 것으로만 남긴다.

제출은 한 주장에 대한 문장/인용/위치 연결과 저장·텍스트·화면 검사의 차이, 현재 실행과 과거 관찰의 구분이다. [강사용 해설](../../lessons/document-ai/teacher-guide.md)을 함께 본다.

## 선택 실행과 출력·검사 경로

아래 표는 **실행할 명령**이다. 모든 output은 새 폴더이며 기존 실험을 덮어쓰지 않는다. registry_lab는 초기 PDF/TXT 순차 실험을 재현하는 도구라 출력의 remaining 문구에는 당시 미구현 사항이 들어 있다. 현재 DOCX 지원 판단은 위 지원 범위와 현재 코드로 한다.

| 목적 | backend에서 입력할 명령 |
|---|---|
| 기존 PDF/TXT 상태 실험을 새 폴더에 저장 | `python -m tools.registry_lab --output l9-registry-new` |
| 현재 상태·요청/삭제 경계 검사 | `python -m unittest discover -s registry_tests -v` |
| 현재 명세·검토/출력 차단 검사 | `python -m unittest discover -s report_tests -v` |
| 실제 DOCX/PDF 출력 | `python -m tools.report_lab --output l9-report-new --font assets-l8-new/NotoSansKR-Regular.ttf` |

실제 출력에는 앞 PDF 실습에서 준비한 글꼴이 필요하다. 없다면 [PDF/OCR 실습의 자산 준비](L8.md)를 따른다. 글꼴 경로를 실제 파일로 맞추고 출력 뒤 DOCX를 렌더링해 모든 페이지를 확인한다. 라이브러리가 저장에 성공했다는 사실만으로 화면을 확인했다고 보고하지 않는다. 단위 검사의 렌더링 실패/중간 삭제는 모의 경계 검사이며 실제 Office/ReportLab 화면 검사와 다르다.

출력 도구는 현재 v2 명세를 준비하고 고정 검토 결정을 기록한다. 이는 로컬 교육용 시연이며 실제 사용자의 승인 절차가 아니다. 생성된 artifacts 아래 document-spec.json은 공통 내용, review.json은 그 내용 해시에 묶인 결정, evidence-report.docx/pdf는 출력이다. 모델 생성 문장과 혼동하지 않는다.

임시 출력 뒤 원문/승인을 다시 확인하고 통과하면 최종 폴더로 옮긴다. 중간 삭제나 변환 실패는 최종 폴더 생성을 막지만 DB/파일시스템의 동시 발행·취소 전체 원자성, 이미 복사한 보고서의 회수까지 구현한 것은 아니다. 실제 인증·동시 Worker·보관/백업/보안 삭제·일반 문서 품질·독립 수업/업무 채택과 기존 모델 품질 보류는 남아 있다.

## U04 Provider 제어

[Provider 강의](../../lessons/document-ai/provider.md) → [결과](../../reports/KEDU-PRODUCTION-015/RESULT.md)를 읽는다. tools.provider_lab를 모듈로 실행하고 새 output 디렉터리를 지정한다. 정확한 CLI는 [실행 파일](backend/tools/provider_lab.py) 첫 설명을 본다. 로컬 127.0.0.1 임시 포트의 표준 라이브러리 HTTP 서버가 필요하다. 모델 다운로드·유료 API·새 Python 패키지는 필요하지 않다.

router_tests는 표준 unittest discover로 실행한다. Registry/보고서 회귀는 각각 registry_tests/report_tests를 지정한다. 실제 결과의 Token 수는 Unicode 코드 포인트 기반 Fixture이며 실제 모델 Token이 아니다.

app/provider_router.py는 기존 웹 Factory에 연결되지 않은 별도 경로다. hf_cpu_endpoint는 이미 준비한 HFCpuProvider 객체를 명시적으로 받아 Chat Template·고정 출력 상한·프로필/사용량을 연결한다. 이번 검사는 가짜 Provider 계약이며 실제 HF 가중치 실행은 아니다. 기존 문자열 Provider를 그대로 예산 지원 경로라고 등록하지 않는다. 실제 Token 계수·출력 상한·오류 분류·준비 상태를 보장하는 어댑터가 필요하다.

Timeout/취소는 동기 호출 전후 검사이고 강제 중단은 미구현이다. Trace는 질문/예외 원문을 제외하지만 최종 응답 answer를 저장하면 답변 내용이 남는다는 점은 별개다. Provider/모델 전환·실제 외부 전송·React/Streaming·금액 예산·독립 수업은 이번 범위가 아니다.

## U05 React와 SSE

[Streaming 강의](../../lessons/document-ai/streaming.md) → [결과](../../reports/KEDU-PRODUCTION-016/RESULT.md)를 읽는다. [실행 화면 안내](stream-ui/README.md)에 설치·빌드·로컬 서버·검사 순서를 적었다. 기존 FastAPI API에 자동 연결하지 않고 별도 loopback 서버에서 U04 Router의 고정 답변을 SSE로 나눈다. 실제 모델 Token Streaming은 미검증이다.

공통 Parser를 Node와 React가 함께 사용한다. 최종 판정 없이 끝나면 실패, 취소 뒤에는 부분 응답을 확정하지 않는다. 실제 Chromium에서 취소/새 실행의 늦은 확인 경합·오류·중간 종료·기능 거부·시간 한도와 모바일 크기를 확인했다. 실제 사용자 인증·운영 Proxy·다른 브라우저·교실 장비는 미검증이다.

## U06 다중 형식과 채택 기준

[최종 평가 강의](../../lessons/document-ai/evaluation.md) → [결과](../../reports/KEDU-PRODUCTION-017/RESULT.md)를 읽는다. [자료 안내](backend/data/multiformat-v1/README.md)의 저장된 PDF/TXT/DOCX 원본과 정답을 사용한다. requirements-report.txt 환경을 재사용한다. Backend에서 tools.multiformat_lab에 새 output 폴더와 NotoSansKR-Regular.ttf를 지정한다. 정확한 CLI는 [실행 파일](backend/tools/multiformat_lab.py) 첫 설명에 있다.

DOCX Parser는 표와 문단의 좁은 입력 범위만 지원한다. docx_ingest.py를 Registry에 추가했고 DOCX 구조적 위치를 보고서에 표시하도록 템플릿을 v2로 올렸다. 이전 명세는 새 템플릿 승인으로 재사용하지 않는다. HWP/HWPX는 계속 거부한다.

multiformat_tests의 표준 unittest와 기존 Registry/보고서/Router/HTTP-SSE 회귀를 실행한다. 입력 재생성이 필요할 때만 tools.multiformat_specimen을 사용한다. 저장된 원본 해시가 기준이며 생성 메타데이터 차이를 조용히 대입하지 않는다.

렌더링에는 임시 HOME에서도 보이는 글꼴 경로가 필요하다. 이번에는 작업 폴더의 글꼴을 지정한 FONTCONFIG_FILE을 render_docx.py에 전달했다. 화면과 문단 비교를 함께 확인한다. 기존 FastAPI·React·모델을 전환한 통합은 아니며 독립 품질/수업/운영 채택은 보류다.
