5. 한 단원의 실제 실습 코드는 학생이 이전 단원에서 작성한 코드 위에 **추가·교체**한다. 후속 기능이 구현된 전체 소스를 미리 지급하지 않는다.

7. Transformer 전체 재강의, Fine-tuning/LoRA, OCR/Multimodal, Document AI의 고급 확장 기능은 본과정 필수 경로를 막지 않는 **심화 자료**로 별도 보존한다.
8. 실습 전용 테스트 결과와 실제 모델 호출 성공, 답변의 사실적 정확성, 수업 완료 판정은 서로 다르게 기록한다.

## 2. 최종 폴더 위치 및 상위 구조

### 2.1 GitHub에 새로 만들 위치 — *설계안*

기존 파일들을 움직이거나 덮어쓰지 않고, 원본과 구분되는 수업용 패키지를 새로 만든다.

```text
k-edu/
├── academy/
│   └── 00. 교육과정(curriculum)/
│       ├── 00. Phase1_Theoretical/         # 기존 Phase1 — 변경 없음
│       ├── 01. Phase2_AI/                  # 기존 Phase2 13개 주제 — 원본 보존
│       ├── 02. 실습/                        # 기존 실습 구현 — 원본 보존
│       └── 03. Phase2_AI_수업용/            # [신규] 학생에게 제공할 유일한 본과정 패키지
│           ├── README.md                  # 패키지 사용 안내: Obsidian·VS Code 실행 위치
│           ├── 교안/                      # Obsidian에서 열 Vault 폴더
│           └── 실습앱/                    # 11단원 내내 같은 React/FastAPI 앱
└── curriculum-work/
    ├── plans/phase2-ai/                   # EDU-01·03·04·05·06 설계·승인 이력
    └── teacher/phase2-ai/                 # [향후] 강사 전용 해설·기준 완성본·수업 점검
```

- `03. Phase2_AI_수업용/`의 번호는 **기존 저장소에서 수업 패키지의 위치를 구분하기 위한 폴더 정렬**이며, 학생 교안에는 작업 ID로 제시하지 않는다.
- 학생에게 내려주는 폴더는 원칙적으로 `03. Phase2_AI_수업용/` 하나다. 강사용 정답과 연구·분석 보고서는 학생 배포물에 섞지 않는다.
- 학생은 **Obsidian에서 `교안/`을 Vault로 열고**, VS Code/터미널에서 옆의 **`실습앱/`을 한 번 열어 계속 사용**한다. 두 프로그램은 같은 패키지 안에 있으나 목적이 달라 경로를 찾기 쉽다.
- `실습앱/`은 Obsidian Vault **바깥**에 둔다. 이 때문에 교안에서 소스 파일을 Obsidian 내부 링크로 직접 클릭하도록 강제하지 않으며, 편집할 파일 경로를 코드 표기로 명확히 안내한다. Obsidian에는 Markdown 강의·이미지만 보이므로 Node 모듈 및 Python 환경 파일이 사이드바를 어지럽히지 않는다.

### 2.2 Obsidian 학생용 교안 — *설계상 확정할 파일명*

`교안/` 안에서는 **한 단원당 반드시 하나의 주 교안**을 제공한다. 이론과 실습을 다른 문서에 분리하지 않는다.

```text
03. Phase2_AI_수업용/
├── README.md
├── 교안/
│   ├── 시작하기.md
│   ├── 01. LLM 심화와 AI 프로젝트 출발.md
│   ├── 02. Prompt & Context Engineering.md
│   ├── 03. AI 실행 관리(Harness).md
│   ├── 04. 문서 수집·전처리·Chunking.md
│   ├── 05. Embedding.md
│   ├── 06. Vector DB & Retrieval.md
│   ├── 07. RAG 구축.md
│   ├── 08. Tool Calling.md
│   ├── 09. Single-Agent 구축.md
│   ├── 10. Multi-Agent 구축.md
│   ├── 11. 서비스 통합 및 최종 검증.md
│   ├── 이미지/                           # 교안 그림·도식. 실제 그림이 생길 때 추가
│   └── 심화/                             # 필수 학습 경로에서 분리
│       ├── Transformer와 LLM 내부 구조.md
│       ├── Fine-tuning과 LoRA.md
│       ├── OCR과 멀티모달 문서 처리.md
│       └── Document AI 확장.md
└── 실습앱/
    └── ...                               # 아래 2.3 참조
```

**파일 수:** 본과정은 `시작하기` 1개 + 단원 교안 **11개 = 12개의 핵심 Markdown**으로 이동한다. 심화 4개는 본과정 탐색을 방해하지 않는 별도 경로에 둔다. `이미지/` 아래 실제 첨부 수는 미정이고, 관련된 이미지가 없다면 빈 폴더를 억지로 Git에 생성하지 않는다.

- 각 단원은 Obsidian 좌측 파일 탐색기에서 01 → 11 순으로 정렬된다.
- `시작하기.md`에는 전체 순서, 최종 프로젝트 목표, 첫 앱 실행 위치, 편집 도구, 첫 단원으로 가는 링크만 넣는다. 별도의 중복 `목차.md`, `이론.md`, `실습.md`, `정답.md`를 무더기로 만들지 않는다.
- 단원별 그림은 `교안/이미지/`에 두고, 사용처를 알아보기 쉬운 의미 있는 이름을 붙인다. 과도한 내부 번호 대신 `문서-검색-생성-흐름.png`처럼 명명한다.
- 11개 주요 파일명과 단원명은 EDU-04 승인된 명칭을 유지했다. 필요시 학생에게 보이는 **문서 내 소제목**을 쉽게 풀어 쓸 수 있다.

### 2.3 학생이 계속 수정할 *단 하나의* 실습 앱 — 최종 목표 파일 지도

아래는 **모든 단원이 끝났을 때 목표로 하는 파일 지도**이다. 01단원 시작 시에는 `main.py`·Provider·React Chat 화면 등 **최소 시작본만 존재**하며, 뒤 단계의 `rag.py`, `agent.py`, `multi_agent.py` 등을 미리 배포하지 않는다. 구현 시점·파일별 변경을 결정하는 기준은 승인된 EDU-05다.

```text
실습앱/
├── README.md                     # 최초 실행, 환경 설정, 현재 구현된 기능만 기재
├── backend/
│   ├── requirements.txt
│   ├── .env.example             # 실제 비밀키·암호·토큰 기록 금지
│   ├── app/
│   │   ├── main.py              # FastAPI 실행, HTTP API
│   │   ├── schemas.py           # 요청·응답 데이터 구조
│   │   ├── service.py           # 기존 AI Provider 호출 서비스
│   │   ├── providers/           # 기존 Provider 경계/설정
│   │   ├── assistant_service.py  # 요청/모드 연결 (02단원부터)
│   │   ├── prompting.py         # Prompt·Context (02단원)
│   │   ├── harness.py           # 응답 검사·재시도·중단 (03단원)
│   │   ├── documents.py         # 문서 읽기·Chunking (04단원)
│   │   ├── rag.py               # 검색 기반 답변 (07단원)
│   │   ├── tools_registry.py    # 검증된 도구 실행 (08단원)
│   │   ├── agent.py             # Single-Agent (09단원)
│   │   └── multi_agent.py       # Multi-Agent (10단원)
│   ├── retrieval/
│   │   ├── encoder.py           # 실제 Embedding (05단원)
│   │   └── index.py             # 벡터 저장·검색 (06단원)
│   ├── data/
│   │   ├── fixtures/            # 시작부터 쓰는 가상 규정/질문 입력 샘플
│   │   ├── sources/             # 04단원에 추가할 동일 규정의 TXT/MD 원문
│   │   ├── catalog.json         # 04단원부터 문서 버전·현행·접근 범위
│   │   └── cases.json           # 과정 전체에서 비교할 가상 질문
│   ├── local_data/              # 생성된 Chunk·SQLite Index. Git 반영 제외
│   ├── tools/                   # 추가 확인이 필요한 경우 동일 앱 모듈을 호출하는 실행 도구
│   └── tests/                   # 각 단원에서 기능·회귀 검사를 누적
└── frontend/
    ├── package.json
    ├── index.html
    └── src/
        ├── App.jsx              # 같은 질문 입력/결과 화면을 끝까지 확장
        ├── api.js               # 공통 HTTP 요청 처리
        └── style.css
```

- 01단원부터 `backend/`와 `frontend/`는 **동시에 존재**한다. 11단원에서 새로운 React 프로젝트를 만들지 않는다.
- `data/fixtures/`는 시작부터 쓰는 **고정 자료**, `data/sources/`는 그 자료와 같은 규정을 나중에 **원문·단락 형태로 직접 처리하는 학습용 자료**다. 서로 다른 교육 사례로 바꾸지 않는다.
- `local_data/`, `.env`, `.venv/`, `node_modules/`, 캐시와 개인 모델 다운로드는 버전관리/학생 배포에 포함하지 않는다. 단, 재생성에 필요한 입력 자료와 명령은 보관한다.
- 기존 GitHub 참조 구현의 일부 모듈 이름은 이 구조와 같아도 **학생 시작본에 존재한다는 의미가 아니다**. EDU-07/08에서 실제 기초 파일과 추가 파일을 확인한다.
- 하나의 앱을 수정하면서 단원별로 Commit할 수는 있지만, `단원-완성본-01/`, `실습2-새프로젝트/` 같은 중복 프로젝트 폴더는 만들지 않는다.

| 10. Multi-Agent 구축 | 검색·작성·검토 역할 및 전달 | `multi_agent.py`, 공통 응답·UI | 역할 간 자료 전달과 최종 검토 |

### 각 교안에 *딱 한 번씩* 들어갈 필수 흐름

교안이 너무 많은 문서로 분리되지 않도록 아래 내용은 **각 단원의 본문 하나에 순서대로** 수록한다.

1. **이번에 만들 것:** 이전 단원에서 무엇이 동작했고 이번에 무엇이 새로 가능한지.
2. **개념 이해:** 처음 배우는 용어의 필요성 → 쉬운 정의 → 실제 데이터 흐름 → 적용 위치 → 자주 하는 오해. Phase1이나 앞 단원 내용은 짧은 연결 문장으로만.
3. **실습 시작 상태:** 지금 존재해야 할 파일과 실행 상태, 누락 시 어디서 확인할지.
4. **파일별 직접 작성:** 새 파일이면 **붙여넣어 실행 가능한 전체 코드**, 기존 파일이면 **수정 전 확인 위치·정확한 교체 범위와 수정 후 코드**. 숨긴 함수나 `...`로 필수 코드를 생략하지 않는다.
5. **실행하기:** 터미널을 여는 위치, 실행 명령, 입력값, 모델/설정 의존사항. 학생이 코드만 넣고 무엇을 실행할지 모르는 일이 없어야 한다.
6. **직접 확인:** 실제 브라우저/API/터미널에서 확인할 것과 예상되는 관찰. *예시 출력·과거 로그·이번 환경의 실측*을 구분한다.
7. **문제 해결:** 흔한 설치·모델 연결·문서·자료 권한·오류를 학생이 순서대로 검사하도록 안내한다.
8. **단원 마무리:** 이번 기능 확인 + 기존 기능 최소 회귀 확인 + 다음 단원에 유지할 파일·데이터.

이론의 양은 개념 난이도에 맞추어 충분히 작성한다. **한 파일 안에 있다는 이유로 이론을 한두 문단으로 축약하지 않는다.** 오히려 실행 직전에 필요한 이론을 붙여 학생이 즉시 코드와 연결하게 한다. 실제 함수/코드 책임을 모르는 상태에서 복사만 하게 만들지 않는다.

## 4. 학생의 실제 수업 동선

### 4.1 첫 수업

1. GitHub에서 `03. Phase2_AI_수업용/` 패키지를 준비한다.
2. Obsidian에서 `교안/` 폴더를 Vault로 열고 `시작하기.md`를 읽는다.
3. VS Code에서 **바로 옆 `실습앱/` 폴더 하나만** 연다.
4. `01. LLM 심화와 AI 프로젝트 출발.md`의 안내를 따라 Backend·Frontend를 실행한다.
5. 첫 Chat 화면이 뜨면 다음 단원으로 넘어갈 준비가 된 것이다. 실제 모델 경로가 실패하면 완료로 표시하지 않고 원인을 기록한다.

### 4.2 다음 단원의 공통 진행

```text
Obsidian에서 현재 단원 열기
    ↓
이전에 만든 기능 확인
    ↓
새 개념 이해 → 이번에 추가할 파일 확인
    ↓
같은 실습앱에서 코드 추가·교체
    ↓
터미널·브라우저에서 새 기능 실행
    ↓
이전 기능도 여전히 동작하는지 확인
    ↓
현재 단원 맨 아래의 ‘다음 단원’ 링크 클릭
```

**같은 문서/질문 재사용 방식:** 예를 들어 교육비·출장 규정을 기반으로 Prompt 입력 → 문서 조각 → Embedding → 검색 → RAG 근거 → Agent 실행 차이를 관찰한다. 같은 예제는 비교 기준으로 재사용하지만, *매번 같은 설명을 처음부터 반복하지 않는다*. 새 기능이 만든 **새 출력**이 무엇인지 강조한다.

### 4.3 다음/이전 단원 링크 — Obsidian과 GitHub에서 함께 열리게

학생용 교안 내부 링크는 가능하면 **표준 Markdown 상대 링크**를 사용한다. 단원 Markdown 파일명은 Vault 안에서 유일하고, 외부 네트워크·기존 원본 경로를 전제로 하지 않는다.

```markdown
[이전 단원: 문서 수집·전처리·Chunking](<04. 문서 수집·전처리·Chunking.md>)
[다음 단원: Vector DB & Retrieval](<06. Vector DB & Retrieval.md>)

![문서를 검색하고 답을 만드는 흐름](<이미지/문서-검색-생성-흐름.png>)
```

- 같은 Vault 내부 파일끼리만 Markdown 링크한다. 이미지 경로는 그 Markdown 파일에서 상대 경로로 쓴다.
- Python/React 파일은 `실습앱/backend/app/main.py` 등 **패키지 기준 경로 표기**로 안내하며, Obsidian Vault 바깥 소스를 `[[...]]` 링크로 강제로 열지 않는다.
- 필요하면 Markdown 본문에서 `실습앱/` 위치를 설명하고 VS Code의 파일 탐색기로 열도록 안내한다. GitHub 웹에서 코드 링크를 열어야 하는 별도 강사용 매핑과 혼동하지 않는다.
- 시작하기·11단원에 없는 '다음 단원' 링크를 만들지 않는다. 중간 단원의 이전/다음 연결은 실제 존재하는 파일명만 이용한다.
- 파일을 새 위치로 복사할 때 기존 `02. 실습/document-assistant/L3~L6`가 참조하던 과거 보고서 상대경로는 **그대로 이식하지 않는다**. 새 교안은 자기 패키지 안의 경로만 사용한다.

## 6. 강사·설계 산출물과 학생 자료의 분리

- 학생 배포: `academy/.../03. Phase2_AI_수업용/` 안의 **`교안/` + `실습앱/`**. 시작 교안과 그 시점까지 학생이 작성해야 할 코드만 기준으로 제공하며, 후속 완성본이 학생 시작본에 섞이지 않게 한다.
- 설계·승인 이력: 기존 `curriculum-work/plans/phase2-ai/`. 파일명 `EDU-...`은 **관리 문서**에만 허용하며 학생용 파일에는 넣지 않는다.
- 강사용: `curriculum-work/teacher/phase2-ai/`에 수업 지도/정답 해설/모델 운영 메모/완성본과 재현 증거를 보관하도록 설계한다. 실제 내용은 EDU-22~23 이후 작성한다.
- 기능 테스트: 학생 앱의 `backend/tests/` 등 해당 앱 디렉터리에 추가. 강사용 '완성본'과 코드 조각을 학생용 앱과 섞지 않는다.
- 테스트를 쉽게 하려고 강사 완성본을 전체 학생용 패키지에 먼저 복사하거나, 단원마다 `실습앱-완성`, `실습앱-중간`을 잔뜩 만드는 행위를 피한다. 내부 자동 검증에 필요하면 브랜치/Commit 또는 강사용 별도 위치에서 재현한다.
- 동일 저장소 안에 강사용 폴더가 있으므로 **접근 통제나 비공개 보장**을 의미하지 않는다. 학생 배포는 필요한 폴더만 추출·제공하는 방식이며, 비공개 정답 관리가 필요하다면 별도 권한 저장소를 사용해야 한다.

### 7.1 기계적으로 검증할 최소 조건(추후 검사기 구현)

- `교안/시작하기.md` 및 단원 교안 11개의 존재와 단원 번호 정렬 순서
- 단원별 Markdown 상대 링크의 목적 파일 존재 여부, 이미지 파일 존재 여부
- 단원 제목 고유성 및 내부 단계/검사 약호 패턴이 학생 교안 텍스트에 들어가지 않았는지
- 단원별 사용한 `실습앱/` 코드 파일이 그 단원까지의 실제 작업 트리에 존재하는지
- 각 단원에서 요구하는 신규 코드가 새 시작본에 이미 포함되어 있지 않은지
- 모든 단원 문서에서 “이번 결과”, “실행하기”, “다음 단원” 흐름이 보이는지
- Markdown 인용·코드 펜스가 올바르게 닫혔는지

위 목록은 **검수 규칙 설계**이지 지금 검사를 통과했다는 기록은 아니다.
