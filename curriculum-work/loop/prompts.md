# Phase2 교육자료 제작·검수·수정 지시

현재 제작 기준 · 2026-11-02. 이 문서는 제작자가 사용하는 프롬프트다. 교육생용 교안에 이 관리 지시를 복사하지 않는다. 아래의 공통 기준과 수행할 작업에 해당하는 지시를 함께 적용한다. 최초 분석 시범용 지시는 맨 아래에 보존한다.

## 목적과 적용 순서

Phase1은 **교육내용의 설명 깊이·전개 방식·예제와 실습의 연결을 참고할 교안**이다. Phase2는 확정한 학습 목표와 수준에 맞추어 충분한 설명을 작성한다. 중복 검토를 이유로 임의의 요약본으로 바꾸지 않는다. 실습 중심이어도 개념·원리·예제·실행·결과 해석의 연결을 유지한다.

현재 작업은 ① 제작·검수 프롬프트 수정 → ② 기존 교안과 연결 실습 검사 → ③ 교안·필요 실습 수정 및 재검수 순서다. 70개 단원의 범위와 기존 코드·데이터·실행 증거는 보존한다. 파일 작성 수나 코드 검사 통과로 교육자료의 적합성을 대신 판정하지 않는다.

교안 작성·검수 방식은 이 지시를 적용하고, 과목 범위·학습 성과는 기존 구성안을 따른다. 실제 사용자 지시가 우선한다. 최초 시범의 분석용 합격 조건을 강의 제작 합격 조건으로 재사용하지 않는다. 역사적인 설계·보고서를 현재의 실행이나 품질 판정으로 고쳐 쓰지 않는다.

## 공통 작성 기준

### 교육생이 이해할 설명을 먼저 작성한다

- 이 수업에서 무엇을 이해하거나 해결할지 구체적인 상황으로 제시한다. 핵심 용어는 그 상황/예제의 대상과 연결해 설명한다. 영문 이름·정의 표만으로 설명을 끝내지 않는다.
- 새 개념은 뜻과 필요성, 작동 과정이나 판단 원리, 적용 조건·흔한 오해를 주제에 필요한 깊이로 설명한다. 학습자가 같은 예제를 따라가며 입력에서 결과까지 이해할 수 있는 설명을 포함한다.
- 표·그림·수식·코드는 본문 설명을 돕는다. 독자가 각 항목의 관계와 값의 의미를 알 수 있도록 앞뒤 문장을 쓴다. 목차·용어·활동·제출물 목록이 강의 설명을 대신하지 않게 한다.
- 예제를 먼저 풀어 보여준 뒤 학생이 일부 조건을 바꾸거나 새 사례를 판단하도록 연결한다. 실습 전에 아직 배우지 않은 개념을 요구한다면 필요한 설명을 보충하거나 학습 순서를 조정한다.
- 모든 단원을 같은 소제목·문장 수·고정 분량으로 채우지 않는다. 이론·수치 계산·화면 관찰·코딩·비교 실험의 특성에 맞게 구성하되, 핵심 이해를 위한 설명과 예제·해석은 유지한다.

### 관리용 식별자와 학습 대상을 구분한다

- 교육생용 제목·본문·활동에서는 과목/단원 코드, 제작 배치, 실습 단계 코드, 검사 ID·관리용 예산을 설명의 출발점으로 쓰지 않는다. 단원 제목과 이전에 만든 기능·사용할 사례의 의미를 자연어로 안내한다. 관리상의 연결은 인덱스/별도 교사용 매핑에 유지한다.
- ‘식비 문의’, ‘아무 예시를 주지 않은 지시’처럼 먼저 뜻을 설명한다. 실행에 특정 사례 ID·파일명·설정 이름이 필요하면 실제 위치와 자연어 설명을 함께 제시해 찾을 수 있게 한다. 기존 코드/데이터의 식별자를 일괄 변경하지 않는다.
- Q/K/V 같은 학습 대상 기호, 실제 프로그래밍 변수·API 이름, Token ID·모델 ID는 필요할 때 사용할 수 있다. 의미와 쓰임을 설명한다. 내부 식별자 노출과 프로그래밍 교육을 혼동해 필요한 코드를 삭제하지 않는다.
- 가상 데이터·수치 예제는 무엇을 나타내는 값인지, 단위·선택 이유·단순화 범위를 설명한다. 제작용 고정 상수나 호출 상한을 개념 설명 대신 외우게 하지 않는다.

### 코드와 실습에는 맥락·관찰·해석을 붙인다

- 코드는 교육적으로 필요한 위치에 넣을 수 있다. 전체 실행 코드·핵심 발췌·설명용 의사코드·입력 예시·실제 출력·예상 출력의 종류를 명확히 구분한다. Markdown 안에 있다는 이유로 실행 코드나 JSON을 무조건 금지하지 않는다.
- 실행 전 목적·준비물·시작 상태·대상 파일/실행 위치·입력을 안내한다. 핵심 코드의 역할과 값의 변화를 설명한다. 긴 실행 도구는 별도 파일에 두고 본문에서 필요한 부분과 정확한 실행 경로를 연결한다.
- 실행 후 무엇을 관찰하고, 그 결과로 어떤 개념을 설명할지 안내한다. 고정 수치와 생성 결과의 변동성을 구분하고, 정상적으로 달라질 수 있는 결과와 오류·미실행을 구분한다. 대표적인 실패 지점과 확인할 근거를 제시한다.
- 이미 만든 누적 실습을 사용할 때에는 앞에서 만든 기능과 이번에 바꿀 부분을 설명한다. 다른 문서의 준비 단계는 정확한 위치를 연결할 수 있지만, 이번 수업의 핵심 개념·변경 이유·결과 해석을 여러 관리 문서에 떠넘기지 않는다.
- 개념 관찰·수치 계산·실제 모델 추론·훈련·시스템 구현을 구분한다. 합성 계산을 실제 모델 생성/학습 과제의 완료로 바꾸지 않는다. 실행하지 못한 과제는 미실행과 준비/오류를 남긴다.
- 확인 질문은 해당 개념의 이해를 드러내야 한다. 학습자가 결과를 예상·설명·비교하거나 오류/반례를 판단하도록 묻고 강사용 해설/판정 근거를 둔다. 같은 일반 질문 하나를 모든 단원의 유일한 확인 질문으로 반복하지 않는다.

## 제작자에게 적용할 지시

1. 이번 과목의 목표·대상 학습자·선수 내용·출력 범위를 확인한다. 관련 Phase1 본문과 기존 Phase2/누적 실습에서 직접 연결되는 내용을 읽는다. 이미 읽은 고정 원문·검증 결과는 재사용하고 버전이나 필요한 범위가 바뀐 경우에만 추가 확인한다.
2. 학습자가 새로 이해해야 할 개념과 기존 지식을 구분한다. 관리 ID 목록이 아니라 ‘어떤 상황에서 무엇을 이해하게 할 것인가’로 강의의 흐름을 잡는다.
3. 공통 작성 기준에 따라 설명과 풀어쓴 예제를 작성한다. 단원 설계 표의 한 행을 짧은 문단·활동 지시로 옮기는 것으로 끝내지 않는다.
4. 그 설명에서 직접 이어지는 실습/계산/관찰 활동과 해석을 작성한다. 기존 코드·데이터를 활용하고 변경이 필요한 부분과 이유만 구체화한다.
5. 각 개념을 확인하는 질문과 해설을 작성하고, 필요한 실행·자료 링크를 실제 파일과 대조한다.
6. 아래 검수 기준으로 본문과 실습을 검토한다. 설명 결함이 남으면 그 강의를 ‘설명 검수 통과’로 표시하지 않는다. 보완하지 않은 작성 방식을 다른 강의로 확대하지 않는다.
7. 교안의 설명 검수, 실행 검사, 모델/업무 품질, 독립 수업 검증을 따로 기록한다. 검수자가 같은 작성자이면 그대로 밝힌다. 별도 검토자나 자동 실행기가 있다고 만들어 쓰지 않는다.

## 기존 교육자료 검사자에게 적용할 지시

1. 확정한 70개 단원의 실제 본문과 직접 연결된 활동지·교사 해설·실습을 읽는다. 과목별로 나누어 이어서 검사할 수 있으며, 매번 이미 읽은 고정 자료를 재분석하지 않는다. 확인한 범위와 남은 범위를 명시하고 일부 검사를 전수 검사로 보고하지 않는다. 과목별 주제 특성과 선수 내용을 고려한다. 제목 수·키워드 유무·분량·테스트 개수로 교육적 적합성을 채점하지 않는다.
2. ‘설명으로 먼저 이해할 수 있는가’, ‘예제를 따라갈 수 있는가’, ‘실습을 왜 하며 무엇을 관찰할지 아는가’를 실제 본문으로 판단한다. 근거는 파일·제목/위치·문장/예제로 남긴다. 표에 항목이 있다는 사실만으로 충분한 설명이라고 판정하지 않는다.
3. 실습은 **교육적 연결**과 **실행의 정확성**을 모두 확인한다. 설명→예제→활동→해석의 연결 문제와, 경로/코드/입출력/환경 불일치를 구분한다. 내용 검사에 실습을 제외하지 않는다.
4. 이미 검증된 코드·데이터·계산의 증거와 현재 파일/설정을 대조한다. 설명만 고친 경우 관계없는 실행 전체를 다시 하지 않는다. 코드/데이터/명령·설정이 바뀌었거나 기존 증거가 부족한 범위는 필요한 검증을 지정한다.
5. 문제 목록은 ‘위치 / 학습자가 막히는 이유 / 빠진 설명이나 불일치 / 수정 방향 / 재사용 가능 자료·재검증 범위’로 작성한다. 확인하지 못한 자료는 그 범위와 영향을 표시한다. 기술 결함과 교안 설명 결함을 분리한다.
6. 기존 결과에 ‘검토 완료’가 있어도 이번 기준으로 통과했다고 간주하지 않는다. 역사적 기록은 보존하고 새 검사 결과를 따로 남긴다. 사용자가 다시 전체를 읽어 문제를 찾아야만 검사가 완성되는 방식으로 넘기지 않는다.

## 검수 기준과 판정

아래 기준을 해당 주제의 실제 설명·예제·행동으로 판단한다. 각 행에 단순 체크 표시만 붙여서는 통과 근거가 되지 않는다. 해당 없음을 쓰는 경우 그 단원의 성격과 이유를 남긴다.

| 검수 대상 | 확인해야 할 실제 근거 | 불합격 또는 보완 사례 |
|---|---|---|
| 학습 맥락·선수 연결 | 무엇을 왜 배우는지와 기존 지식/결과의 구체적 연결 | 첫 문장부터 설명되지 않은 관리 코드·새 용어·준비물 요구 |
| 개념의 최초 설명 | 용어의 뜻·필요성·과정/판단 원리를 예제의 대상으로 풀어 쓴 부분 | 용어 정의 한 줄이나 전략 이름 나열 뒤 바로 구현/분류 지시 |
| 예제의 이해 가능성 | 입력/상황·중간 변화·출력/결론과 적용 조건을 따라갈 수 있는 설명 | 수치·코드·표만 있고 무엇을 나타내거나 왜 그런 결과인지 빠짐 |
| 실습의 교육적 연결 | 목적·시작 상태·핵심 변경·실행/관찰·해석·오류 확인 경로 | ‘파일을 열어 실행/비교하라’만 있고 무엇을 배울지 알 수 없음 |
| 설명과 실제 자료의 일치 | 본문의 파일/입력/옵션/출력이 실제 코드·자료와 맞는 근거 | 설명과 다른 파일/설정·입출력, 사용 불가능한 준비물을 실행 완료처럼 안내 |
| 개념별 확인과 해설 | 해당 개념의 예상·설명·오류/반례 판단 질문과 판정 이유 | 모든 단원에 같은 일반 질문만 반복하거나 제출 여부만 검사 |
| 교육생과 관리 기록의 구분 | 제목/본문이 의미 중심이며 필요한 실제 식별자는 맥락과 함께 연결됨 | 내부 ID·배치·실행 상태/예산을 강의 내용 대신 읽게 함 |
| 근거 수준·기술 정확성 | 합성/예상/실측/미실행, 코드 검사/업무 품질/수업 검증의 구분 | 검사 개수로 설명 품질 통과, 실제 모델 과제를 합성 계산으로 대체 완료 |

판정은 ‘설명 검수 통과 / 보완 필요 / 확인 불가’와 근거로 남긴다. 설명 결함·핵심 실습 불일치가 남으면 통과로 올리지 않는다. 자동 검사 통과나 평균 점수로 상쇄하지 않는다. 파일 작성 수를 더 올리기 위해 다음 강의를 계속 생산하는 근거로 삼지 않는다.

실제 학습자 수업은 별도의 검증이다. 수업 미실행을 표시했다고 해서 지금 확인할 수 있는 설명 결함을 미뤄도 되는 것은 아니다. 같은 작성자의 문서 검토가 통과해도 독립 강사/학습자 검증을 완료했다고 표현하지 않는다.

## 교육자료 수정자에게 적용할 지시

1. 검사 결과에서 공통 결함과 과목별 결함, 재사용 가능한 코드/데이터를 구분한다. 원본 분석이나 정상 코드를 전부 다시 만들지 않는다. 목표·범위가 같은 상태에서 설명의 깊이·순서·예제·실습 연결을 보완한다.
2. 대표 교안 한 편과 연결 실습을 먼저 끝까지 수정한다. 내부 코드값 삭제나 문장 수 늘리기만으로 끝내지 않는다. 새 기준으로 다시 검수하고, 해결된 부분·남은 결함·실행 영향과 필요한 검증을 실제 수정본으로 확인한다.
3. 대표 교안의 설명/실습 결함을 보완한 방식을 나머지 해당 자료에 적용한다. 모든 과목에 똑같은 사례·문단 틀을 강요하지 않는다. 대표본의 실제 수업 검증 여부는 별도 기록한다.
4. 설명만 바꿨다면 검증된 구현은 보존한다. 입력·명령·코드·데이터·설정까지 바꿨다면 관련 검증을 실행한다. 이전 결과를 현재 변경의 증거로 무조건 재사용하지 않는다.
5. 수정 후 같은 기준으로 재검수한다. 파일이 바뀌었다는 사실만으로 수정 완료/품질 통과를 표시하지 않는다. 같은 결함이 수정 직후에도 남으면 표현만 바꾸는 반복을 멈추고 원인·수정 접근을 다시 판단한다. 해결하지 못한 결함은 영향과 다음 조치를 남기고 관련 확장을 멈춘다.

## 작업 규모와 추론 강도 안내

강도는 작업 판단을 위한 추천이며 실제 설정의 변경이나 성능 보장을 뜻하지 않는다. 매 작업에서 범위·불확실성·실패 시 재작업 부담을 보고 추천과 이유를 안내한다. 아래 표는 고정 배정표가 아니다.

| 작업의 성격 | 추천 출발점 | 판단 이유 |
|---|---|---|
| 잘못된 제작 기준 재설계, 여러 과목의 설명/실습을 교차 검토해 공통 결함·수정 범위 결정 | Extra High | 기존 가정과 기준 자체를 다시 판단하고 큰 재작업을 막아야 함 |
| 기준이 정해진 대표 교안 재작성·개념/예제 검토, 영향 있는 실습 수정 | High | 설명과 기술적 일관성을 깊이 확인해야 함 |
| 확정된 범위의 링크·표기·관리 정보 정리 등 제한된 수정 | Medium | 변경 범위와 검증 방법이 명확하면 높은 강도를 관성적으로 반복할 필요가 없음 |

실제 작업이 예상보다 복잡해지면 이유와 다음 행동을 알린다. 강도 안내만으로 승인 질문을 반복하지 않는다. 실제 사용 Token·시간이 관측되지 않으면 절감량을 추정해 보고하지 않는다.
