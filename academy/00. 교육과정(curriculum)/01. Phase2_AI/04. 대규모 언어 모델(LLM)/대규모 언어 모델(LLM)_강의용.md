
# 04. 대규모 언어 모델(LLM)

> 과목 단위 안내. 아래에는 기존 Unit별 상세 강의를 보존한다. 실행하지 않은 예제는 검증 완료로 표시하지 않는다.

## 개요

언어 모델의 학습 단계, 생성 설정, 문맥과 앱 기억을 구분한다.

## 학습 목표

Pre-training·Instruction Tuning·Alignment·Decoding과 Context/Memory/Retrieval을 설명한다.

## Why

문장 완성 능력과 지시 수행 능력은 같은 학습 성과가 아니다.

## Concept

Context Window는 모델 입력 한계이고 지속 기억은 애플리케이션 설계다.

## Architecture

입력 문맥 구성→모델 생성→출력 검증, 장기 정보는 별도 저장·검색한다.

## Example

Pre-trained 모델이 지시를 잘 따르지 않을 때 후속 학습과 평가를 고른다.

## Practice

동일 Prompt에서 생성 설정을 바꿔 변동을 관찰하고 평가 기준을 기록한다.

## Summary

언어 모델의 학습 단계, 생성 설정, 문맥과 앱 기억을 구분한다.

## 실무 팁

학습 단계와 앱의 검색·기억 전략을 따로 기록한다.

## 주의사항

한 모델의 관찰 결과를 모든 Reasoning Model에 일반화하지 않는다.

```text
Transformer

Autoregressive Language Modeling
   ↓

   └─ Monitoring
```

## ① 문제 이해 (Why)

### 왜 Transformer 다음에 LLM을 배우는가?

Transformer를 공부한 후 가장 많이 나오는 질문이 있습니다.

> "Transformer를 만들었는데 왜 갑자기 ChatGPT가 나온 거죠?"

좋은 질문입니다.

Transformer는 **엔진**입니다.

LLM은 그 엔진을 이용하여 만든 **거대한 자동차**입니다.

자동차 엔진이 있다고

자동차가 되는 것은 아닙니다.

엔진

↓

차체

↓

바퀴

↓

수천 개의 부품

↓

자동차

가 되어야 합니다.

Transformer도 같습니다.

Transformer만 있다고 ChatGPT가 되는 것이 아닙니다.

엄청난 양의 데이터를 학습해야

LLM이 됩니다.

---

### AI는 언제부터 "대화"를 하기 시작했을까?

예전의 AI는

하나의 문제만 해결했습니다.

예를 들어

번역 AI

↓

번역만

요약 AI

↓

요약만

질문 답변 AI

↓

질문만

각각 따로 만들었습니다.

---

그러던 어느 날

연구자들은

생각했습니다.

> "언어 자체를 배우게 하면 어떨까?"

그러면

번역도 하고

요약도 하고

질문도 하고

글도 쓰고

코드도 만들 수 있습니다.

이것이

LLM의 시작입니다.

## ② 개념 이해 (Concept)

### LLM이란?

LLM은

Large Language Model

입니다.

단어를 하나씩 살펴보겠습니다.

---

### Large

크다.

무엇이 클까요?

많은 사람들이

데이터만 많다고 생각합니다.

하지만

LLM의 Large는

여러 의미를 포함합니다.

- 학습 데이터가 많다.
    
- 파라미터가 많다.
    
- 연산량이 크다.
    
- 모델 규모가 크다.
    

즉,

"거대한 언어 모델"

이라는 뜻입니다.

---

### Language

언어를 학습합니다.

여기서 중요한 것은

언어 = 한국어

가 아닙니다.

컴퓨터가 이해하는

모든 기호입니다.

예를 들어

- 한국어
    
- 영어
    
- 일본어
    
- 코드
    
- 수식
    
- HTML
    
- SQL
    
- Markdown
    

모두 언어입니다.

그래서

코드도 생성할 수 있습니다.

---

### Model

모델은

학습된 결과입니다.

학생으로 비유하면

```text
학생

↓

공부

↓

시험
```

시험을 치른 후

학습을 통해 조정된 Parameter와 모델 구조가

학습된 모델을 이룹니다. Parameter는 데이터베이스처럼 문장을 그대로 조회하는 기억장이 아니지만, 학습 데이터의 패턴과 일부 정보를 내부적으로 표현하며 특정 학습 문장을 암기하거나 재현하는 경우도 있습니다.

즉,

LLM은

엄청난 양의 언어를 학습한 결과입니다.

## 한 문장으로 정의하면

> **LLM은 대규모 언어 데이터로 학습하여 언어를 처리하는 모델입니다. 이 강의에서 중심적으로 다루는 생성형 LLM은 Transformer의 Decoder 구조를 사용해 이전 문맥을 조건으로 다음 Token의 확률 분포를 예측합니다.**

이 정의 하나가

이번 학습에서 가장 중요합니다.

## Token이란?

여기서 매우 중요한 개념이 등장합니다.

많은 사람들이

LLM이

단어를 예측한다고 생각합니다.

사실은

**Token**을 예측합니다.

예를 들어

```text
ChatGPT
```

는

한 개의 Token일 수도 있고

여러 Token으로

나뉠 수도 있습니다.

한국어도

하나의 단어가

여러 Token이 될 수 있습니다.

즉,

LLM은

단어가 아니라

Token을 처리합니다.

> Token은 이후 커리큘럼에서 더 자세히 다루지만, 지금은 **모델이 처리하는 기본 언어 단위**라고 이해하면 충분합니다.

## Parameter란?

또 하나의 핵심 개념입니다.

파라미터는

모델이 학습한

수많은 숫자입니다.

예를 들어

```text
철수

↓

사람

↓

학생

↓

학교
```

이런 관계들이

수많은 숫자로

저장되어 있습니다.

이 숫자들이

바로

Parameter입니다.

---

### 비유

학생의 뇌를 생각해봅시다.

공부를 많이 하면

지식이 많아집니다.

LLM도

파라미터가

많아질수록

더 많은 패턴을

표현할 수 있습니다.

하지만 **파라미터가 많다고 항상 더 좋은 모델이 되는 것은 아닙니다.** 학습 데이터의 품질, 학습 방법, 모델 구조, 추론 기법 등이 함께 중요합니다.

## Parameter, 학습된 정보, Context는 같은 것이 아니다

LLM을 처음 배울 때 가장 많이 생기는 오해 중 하나는 다음입니다.

> "모델이 알고 있는 정보는 어디에 저장되어 있나요? 데이터베이스가 모델 안에 있나요?"

일반적인 LLM은 학습 문장을 그대로 검색하는 Database처럼 동작하지 않습니다. 학습 과정에서 데이터의 패턴이 **Parameter의 값과 내부 표현에 분산되어 반영**됩니다.

```text
Training Data
   ↓
학습
   ↓
Parameter 변화
   ↓
모델의 언어·지식·문제 해결 패턴에 영향
```

반면 사용자가 지금 입력한 질문이나 검색된 문서는 Parameter를 다시 학습시키는 것이 아닙니다.

```text
[학습된 Parameter]
모델이 학습을 통해 가진 능력과 패턴

[현재 Context]
System Prompt + User Prompt + 대화 기록 + 검색 문서 + Tool 결과

[외부 Memory / Database]
애플리케이션이 별도로 저장한 정보
→ 필요할 때 검색
→ Context에 넣어야 모델이 직접 활용
```

따라서 세 가지를 구분합니다.

| 구분 | 의미 | 모델 호출 때의 역할 |
|---|---|---|
| Parameter | 학습을 통해 조정된 모델 내부 값 | 모델의 기본 능력과 행동에 영향 |
| Context | 현재 요청에 직접 전달된 정보 | 이번 답변 계산에 직접 사용 |
| External Memory / DB | 애플리케이션이 별도로 저장한 정보 | 검색 후 Context에 넣어야 사용 가능 |

이 구분은 뒤의 [[RAG]], [[Agent]], [[Fine-tuning]]을 이해할 때 계속 사용합니다.

## 왜 LLM은 생각하는 것처럼 보일까?

여기서 가장 많이 오해하는 부분입니다.

현재 LLM이 사람과 같은 의식이나 주관적 경험을 가진다고 가정할 근거는 없습니다.

LLM은 학습 과정에서 언어 속의 **패턴, 문맥, 관계**를 매우 정교하게 학습합니다.

그래서 문제를 해결하는 과정이 사람의 추론처럼 보일 수 있습니다.

예를 들어

```text
2 + 2 =
```

를 답할 수 있는 이유도

수많은 수학 표현과 규칙을

학습했기 때문입니다.

이러한 능력은 대규모 데이터와 학습 목표, Transformer 구조, 학습 후 조정, 추론 시 계산이 함께 만든 결과입니다. 이를 단순히 “문장을 많이 외웠기 때문”이나 반대로 “사람과 똑같이 생각하기 때문” 중 하나로만 설명해서는 안 됩니다. 모델이 어떤 방식으로 내부 추론 능력을 형성하고 사용하는지는 계속 연구되는 주제입니다.

## ④ 관계 이해 (Relation)

이제 지금까지 배운 내용을

모두 연결해보겠습니다.

```text
AI

↓

머신러닝

↓

딥러닝

↓

Transformer

↓

LLM

↓

ChatGPT
```

조금 더 내부를 보면

```text
LLM

│

├── Token

├── Embedding

├── Transformer Block

├── Parameter

├── Pre-training

└── Next Token Prediction
```

여기서 앞으로의 커리큘럼과 연결하면,

- **Prompt Engineering**은 LLM이 더 좋은 토큰을 생성하도록 입력을 설계하는 기술입니다.
    
- **Embedding**은 토큰을 의미를 가진 벡터로 변환하는 기술입니다.
    
- **RAG**는 LLM이 학습하지 않은 최신 정보를 외부에서 가져와 활용하도록 돕습니다.
    
- **Agent**는 LLM이 도구를 사용하고 여러 작업을 계획·실행하도록 확장한 형태입니다.

## ⑤ 적용 예시 (Example / Application)

LLM은 하나의 모델로 매우 다양한 작업을 수행할 수 있습니다.

|작업|어떻게 가능한가?|
|---|---|
|대화|이전 문맥을 기반으로 다음 토큰 생성|
|번역|입력 언어를 이해하고 다른 언어로 생성|
|문서 요약|핵심 내용을 유지하며 새로운 문장 생성|
|코드 작성|프로그래밍 언어 패턴을 학습해 코드 생성|
|질의응답|질문 문맥에 맞는 응답 생성|
|문서 작성|문맥을 유지하며 긴 글 생성|

핵심은 **모든 작업이 결국 "다음 토큰 예측"이라는 하나의 원리에서 출발한다는 점**입니다.

## ⑥ 핵심 정리 (Summary)

이번 Unit에서 반드시 기억해야 할 핵심은 다음과 같습니다.

1. **LLM은 Transformer를 기반으로 한 대규모 언어 모델**입니다.
    
2. LLM의 핵심 학습 목표는 **다음 토큰을 예측하는 것**입니다.
    
3. LLM은 검색엔진이 아니라, 학습된 패턴을 바탕으로 확률적으로 다음 토큰을 생성합니다.
    
4. **Pre-training**은 방대한 언어 데이터를 이용해 언어의 패턴을 학습하는 과정입니다.
    
5. **파라미터는 학습된 지식 자체가 아니라, 그 지식을 표현하는 수많은 숫자(가중치)**입니다.
    
6. ChatGPT와 같은 서비스는 LLM 위에 대화 인터페이스, 안전성, 도구 사용 등의 기능을 추가한 응용 시스템입니다.

## ① 문제 이해 (Why)

### LLM은 태어날 때부터 똑똑할까?

당연히 아닙니다.

많은 사람들이 ChatGPT를 보면

> "원래부터 모든 걸 알고 있었나?"

라고 생각합니다.

하지만 실제로는 그렇지 않습니다.

처음 만들어진 LLM은 거의 **아무것도 모르는 상태**입니다.

예를 들어,

갓 태어난 아이를 생각해 봅시다.

처음부터

- 한국어를 하지 못하고
    
- 수학도 모르고
    
- 역사도 모릅니다.
    

하지만 수년 동안

- 책을 읽고
    
- 대화를 하고
    
- 경험을 쌓으면서
    

언어를 배우게 됩니다.

LLM도 거의 같은 과정을 거칩니다.

---

### 그런데 사람과 다른 점이 하나 있다.

사람은

```
경험

↓

언어 습득

↓

지식 축적
```

입니다.

LLM은

```
텍스트 데이터

↓

패턴 학습

↓

언어 모델
```

입니다.

즉,

LLM은 세상을 직접 경험하지 않습니다.

**텍스트 속에 담긴 세상의 패턴**을 학습합니다.

이 차이가 매우 중요합니다.

## ② 개념 이해 (Concept)

### 이 강의에서 다루는 생성형 LLM의 기본 학습 목표

놀랍게도

Autoregressive 생성형 LLM의 Pre-training 목표는 매우 단순하게 표현할 수 있습니다.

> **이전 Token들이 주어졌을 때 다음 Token의 확률을 높여라.**

끝입니다.

예를 들어

```
대한민국의 수도는
```

다음에는

```
서울
```

이 올 가능성이 매우 높습니다.

모델은

이 정답을 맞히려고 합니다.

---

### 이 과정을 방대한 데이터에 대해 매우 많이 반복합니다.

LLM은

한 문제를 푸는 것이 아닙니다.

```
오늘은

↓

날씨가

↓

좋다

↓

.

```

모든 위치에서

다음 Token을 맞히는 연습을 합니다.

예를 들어

```
오늘은

↓

?

```

정답

```
날씨가
```

다음에는

```
오늘은 날씨가

↓

?
```

정답

```
좋다
```

계속 반복합니다.

## ③ 구조와 원리 (Architecture / Principle)

이제 실제 학습 과정을 살펴보겠습니다.

---

## Step 1. Tokenization

먼저 문장을 Token으로 나눕니다.

예를 들어

```
나는 오늘 학교에 갔다.
```

↓

```
나는

오늘

학교에

갔다

.
```

처럼 나눌 수도 있습니다.

실제로는 모델마다 사용하는 **Tokenizer**가 다르며, 한국어는 조사와 어미 때문에 하나의 단어가 여러 Token으로 분리되기도 합니다.

즉,

LLM은

문장이 아니라

Token을 봅니다.

---

## Step 2. Embedding

이제

각 Token을

숫자로 바꿉니다.

```
학교

↓

[0.31, -0.55, 1.22 ...]
```

이 숫자들은

수백~수천 차원의 벡터입니다.

이제부터

컴퓨터는

숫자만 계산합니다.

---

## Step 3. Transformer

이 숫자들이

Transformer에 들어갑니다.

```
Token

↓

Embedding

↓

Transformer

↓

새로운 표현
```

여기서

Attention은 문장 안의 Token들이 서로 어떤 관계를 가지는지 계산합니다.

그래서 모델은 앞뒤 문맥을 반영한 표현을 만들 수 있습니다.

---

## Step 4. 다음 Token 예측

Transformer는

모든 Token에 대해

다음 Token의 확률을 계산합니다.

예를 들어

```
나는 커피를
```

↓

```
마셨다

70%

좋아한다

20%

샀다

5%

...
```

---

## 그런데 처음에는...

처음 모델은

거의 랜덤하게 예측합니다.

예를 들어

```
나는 커피를
```

↓

```
자동차

15%

바나나

12%

학교

9%

...
```

엉망입니다.

당연히 틀립니다.

---

## Loss(손실)

그래서

정답과

예측을 비교합니다.

```
정답

마셨다
```

예측

```
자동차
```

엄청 틀렸습니다.

그러면

Loss가 커집니다.

---

### Loss란?

Loss는

한 문장으로

> **얼마나 틀렸는지를 나타내는 값**

입니다.

```
정답

↓

예측

↓

차이 계산

↓

Loss
```

Loss가

작을수록

잘 맞춘 것입니다.

---

## Step 5. Backpropagation

이제

모델이 스스로 생각하는 것은 아닙니다.

Loss를 기준으로 어떤 Parameter를 얼마나 수정해야 할지 계산합니다.

그래서

수십억 개의

Parameter를

조금씩 수정합니다.

이 과정을

Backpropagation

(역전파)

라고 합니다.

---

### 비유

학생이

시험을 봅니다.

```
시험

↓

틀림

↓

오답노트

↓

다시 공부

↓

다음 시험
```

입니다.

LLM도

완전히 같습니다.

```
예측

↓

Loss

↓

Parameter 수정

↓

다시 예측
```

---

## Parameter는 어떻게 바뀔까?

예를 들어

Parameter가

```
0.12
```

였는데

조금 수정해서

```
0.13
```

으로 바뀝니다.

이런 수정이

수십억 개의 Parameter에서

동시에 일어납니다.

그리고

이 과정을 방대한 데이터에 대해 매우 많이 반복합니다.

이때 바뀌는 것은 개발자가 작성한 Python 소스 문장이 아니라 모델의 Weight·Bias 같은 **Parameter 값**이다. 작은 PyTorch 학습 예제라면 `Gradient 초기화 → Forward → Loss → Backward → Optimizer Step`을 반복하며 그 변화를 확인할 수 있다.

`model.train()`과 `model.eval()`은 Dropout처럼 학습·평가에서 다르게 동작하는 Layer의 **모드**를 정할 뿐 학습이나 추론을 자동 실행하지 않는다. `no_grad()`는 Gradient 기록을 끄는 별도 설정이며, 실제 Training은 Forward·Loss·Backward·Optimizer Step 같은 학습 절차가 있어야 한다. 각 함수의 소스 구현은 Study에서 다룬다.

정리하면

```
예측

↓

틀림

↓

Loss 계산

↓

Parameter 수정

↓

다시 예측
```

입니다.

이 과정을 방대한 데이터에 대해 매우 많이 반복합니다.

---

## Epoch란?

데이터를

한 번

끝까지 학습한 것을

Epoch라고 합니다.

예를 들어

100만 개 문서가 있다면

```
100만 개 읽음

↓

Epoch 1
```

다시

100만 개 읽으면

```
Epoch 2
```

입니다.

다만 **현대 LLM의 대규모 사전학습에서는 전통적인 의미의 Epoch를 여러 번 반복하지 않는 경우도 많습니다.** 데이터 규모가 워낙 크기 때문에 전체 데이터를 한 번 또는 일부만 통과하며 학습하는 전략도 사용됩니다.

---

## 학습이 끝나면?

수없이 반복한 뒤

모델은

```
오늘은

↓

날씨가
```

같은

언어 패턴을

매우 잘 예측하게 됩니다.

이것이

Pre-training입니다.

## ⑤ 적용 예시 (Example / Application)

이 학습 과정은 GPT 계열과 같은 Autoregressive 생성형 LLM의 기본 원리입니다. BERT 계열은 가려진 Token을 예측하는 Masked Language Modeling을 사용하고, Encoder–Decoder 모델은 입력을 조건으로 출력 Sequence를 학습하는 등 구조와 목표가 다를 수 있습니다.

- 일반 대화 모델
    
- 코드 생성 모델
    
- 번역 모델
    
- 문서 요약 모델
    
- 수학 문제 해결 모델
    

이 강의에서 다루는 생성형 모델들은 **다음 Token 예측**을 중심으로 학습하지만, 모든 언어 모델을 이 한 목표로 정의하지는 않습니다.

모델마다 다른 것은

- 학습 데이터
    
- 모델 크기
    
- 학습 방법
    
- 추가 튜닝
    

입니다.

2. 문장은 **Token → Embedding → Transformer** 순으로 처리됩니다.
    
3. 모델은 예측과 정답의 차이를 **Loss**로 계산합니다.

5. 이 과정을 방대한 데이터에 대해 반복하면서 언어의 패턴을 학습합니다.
    
6. LLM은 검색엔진처럼 저장 문장을 그대로 조회하는 방식이 아니라 **수많은 Parameter에 언어의 통계적·문맥적 패턴을 분산해 표현**합니다. 다만 학습 데이터의 일부를 암기하거나 재현할 가능성은 별도로 관리해야 합니다.

## 학습 심화: 한 가지 중요한 오해 바로잡기

여기까지 배우면 많은 사람이 이렇게 말합니다.

> **"결국 LLM은 다음 단어만 맞추는 거네? 그런데 어떻게 추론(Reasoning)이나 문제 해결도 하지?"**

이 질문은 현대 LLM을 이해하는 가장 중요한 질문 중 하나입니다.

다음 Token을 잘 예측하려면 문법, 문맥, 사실 관계, 코드와 문제 풀이 패턴을 내부 표현에 반영해야 합니다. 규모, 데이터, 학습 방법과 추론 방식이 결합되면서 일부 문제에서 여러 단계의 계산과 일반화 능력이 나타납니다. 그러나 생성한 풀이가 항상 실제 내부 계산을 충실히 설명하는 것은 아니며, 모든 문제에서 안정적인 논리 추론을 보장하지도 않습니다.

이 질문은 다음 주제인 **Prompt Engineering**과 이후 **Reasoning 모델**, **RAG**, **Agent**를 이해하는 핵심 연결고리가 됩니다. 앞으로의 학습에서는 "다음 토큰 예측"이라는 단순한 원리 위에서 어떻게 복잡한 AI 시스템이 만들어지는지를 단계적으로 이어서 살펴보겠습니다.


# [학습] 대규모 언어 모델(LLM, Large Language Model) (Unit 2 보강 학습 - 왜 Pre-training만으로는 ChatGPT가 되지 않을까?)

지금까지 우리는 LLM이 어떻게 학습되는지 배웠습니다.

LLM은 방대한 텍스트를 학습하면서

```text
다음 Token을 맞히는 능력
```

을 키웁니다.

이 과정을

**Pre-training**

이라고 했습니다.

그런데 여기서 중요한 질문이 생깁니다.

> Pre-training만 하면 바로 ChatGPT처럼 대화할 수 있을까요?

정답은

**아닙니다.**

---

## Pre-training 모델은 말을 잘 이어가지만, 지시를 잘 따르지는 못한다

Pre-training이 끝난 모델은

문장을 이어 쓰는 능력은 뛰어납니다.

예를 들어

```text
대한민국의 수도는
```

이라고 입력하면

```text
서울
```

을 예측할 수 있습니다.

하지만 사용자가 원하는 것은 단순히 문장을 이어 쓰는 것이 아닙니다.

사용자는 AI에게 이렇게 말합니다.

```text
이 문서를 요약해줘.

이 코드를 수정해줘.

이 내용을 초등학생도 이해할 수 있게 설명해줘.

표로 정리해줘.
```

이것은 단순한 문장 이어 쓰기가 아니라

**지시를 이해하고 따르는 능력**입니다.

---

## 그래서 Instruction Tuning이 등장했다

Instruction Tuning은 한 문장으로 말하면

> **사람의 지시와 그에 맞는 답변 예시를 학습시켜, 모델이 지시를 잘 따르도록 만드는 과정**

입니다.

예를 들어 학습 데이터는 이런 형태를 가질 수 있습니다.

```text
Instruction:
다음 문장을 영어로 번역하세요.

Input:
안녕하세요. 만나서 반갑습니다.

Output:
Hello. Nice to meet you.
```

또는

```text
Instruction:
다음 내용을 세 줄로 요약하세요.

Input:
긴 문서 내용...

Output:
핵심 요약 1
핵심 요약 2
핵심 요약 3
```

모델은 이런 데이터를 학습하면서

```text
사용자의 요청

↓

요청에 맞는 답변 형식

↓

적절한 응답
```

의 패턴을 익히게 됩니다.

---

## Pre-training과 Instruction Tuning의 차이

둘의 차이를 정리하면 다음과 같습니다.

|구분|목적|
|---|---|
|Pre-training|언어의 패턴을 학습한다|
|Instruction Tuning|사람의 지시를 따르는 방법을 학습한다|

비유하면,

Pre-training은

```text
책을 많이 읽은 사람
```

을 만드는 과정입니다.

Instruction Tuning은

```text
질문을 받았을 때 어떻게 대답해야 하는지 훈련받은 사람
```

을 만드는 과정입니다.

책을 많이 읽었다고 해서

항상 좋은 선생님이 되는 것은 아닙니다.

마찬가지로 LLM도

Pre-training만으로는

사용자의 의도에 맞게 답변하는 능력이 부족할 수 있습니다.

---

## 그런데 지시를 따른다고 항상 좋은 답변일까?

Instruction Tuning을 하면

모델은 사용자의 지시를 더 잘 따르게 됩니다.

하지만 아직 문제가 남아 있습니다.

예를 들어 사용자가 묻습니다.

```text
건강에 위험할 수 있는 행동을 추천해줘.
```

또는

```text
사실이 아닌 내용을 그럴듯하게 써줘.
```

모델이 단순히 지시만 잘 따른다면

위험하거나 부정확한 답변을 할 수 있습니다.

즉,

AI에게 필요한 것은

단순히

```text
지시를 따르는 능력
```

만이 아닙니다.

사람이 보기에

```text
도움이 되고

정확하며

안전한 답변
```

을 생성하는 능력도 필요합니다.

---

## Post-training은 하나의 방법 이름이 아니다

Pre-training이 끝난 뒤 서비스 목적에 맞게 모델의 행동을 조정하는 단계를 넓게 **Post-training**이라고 부를 수 있습니다.

여기에는 하나의 고정된 방법만 있는 것이 아닙니다.

```text
Pre-training Model
      ↓
Supervised Fine-Tuning / Instruction Tuning
      ↓
Preference Data를 이용한 추가 조정
      ├─ 고전적인 RLHF 흐름
      ├─ DPO 같은 Direct Preference Optimization
      └─ 그 밖의 다양한 후속 학습 방법
      ↓
Evaluation / Safety Evaluation
      ↓
배포 가능한 모델
```

따라서 다음을 같은 말로 쓰면 안 됩니다.

```text
Post-training ≠ Instruction Tuning ≠ RLHF ≠ Alignment
```

- **Post-training**: Pre-training 이후의 후속 조정 전체를 가리키는 넓은 표현
- **Instruction Tuning / SFT**: 지시와 모범 응답 예시를 이용하는 지도 학습
- **RLHF**: 인간 선호 피드백을 보상 신호로 활용하는 대표적 강화학습 기반 방식
- **DPO 등**: 선호 쌍을 사용하지만 별도 Reward Model/PPO 없이 직접 최적화할 수 있는 방법
- **Alignment**: 특정 알고리즘 이름이 아니라 모델 행동을 사람의 목적·정책·제약과 맞추려는 더 넓은 목표와 평가 관점

---

## 그래서 RLHF가 등장했다

RLHF는

**Reinforcement Learning from Human Feedback**

입니다.

한 문장으로 말하면

> **사람의 피드백을 이용해, 모델이 더 좋은 답변을 선호하도록 학습시키는 방법**

입니다.

여기서 핵심은

사람이 직접

```text
이 답변이 더 좋다.
```

라고 판단해준다는 점입니다.

---

## RLHF는 어떤 흐름으로 진행될까?

먼저 **고전적인 RLHF 흐름**을 이해합니다. InstructGPT 연구에서 널리 알려진 형태는 다음과 같습니다.

```text
① Pre-trained Model
        ↓
② 사람의 Demonstration 수집
        ↓
③ Supervised Fine-Tuning(SFT)
        ↓
④ 여러 Model Response 생성
        ↓
⑤ 사람이 Response의 선호 순위를 비교
        ↓
⑥ Preference를 예측하는 Reward Model 학습
        ↓
⑦ Reward가 높아지는 방향으로 Policy Model을 RL로 추가 조정
        ↓
⑧ Evaluation
```

여기서 반드시 알아둘 점이 있습니다.

> **이 흐름은 RLHF의 대표적인 교육용 예시이지, 모든 현대 LLM의 Post-training이 정확히 이 절차를 사용한다는 뜻은 아닙니다.**

Preference 데이터를 사용하는 방식에는 RLHF 외에도 DPO와 같은 다른 최적화 방법이 있습니다. 실제 상용 모델의 전체 학습 Recipe는 공개되지 않는 경우도 많으므로, 강의에서는 공개된 연구와 확인 가능한 범위만 구분해서 설명합니다.

### A/B 응답 선택은 RLHF와 같은 것인가?

예를 들어 모델이 하나의 질문에 대해 다음 두 답변을 만들었다고 하겠습니다.

```text
질문:
AI를 초등학생에게 설명해줘.

답변 A:
AI는 인공신경망과 통계적 패턴을 기반으로...

답변 B:
AI는 컴퓨터가 여러 예시를 보고 문제를 풀도록 만든 기술이야.
```

사람이 B를 더 좋다고 선택하면 **Preference Data**가 될 수 있습니다.

그러나 다음 두 문장은 다릅니다.

```text
사람이 A/B를 비교했다.              → 선호도 데이터가 만들어질 수 있음
현재 대화 중 모델 Parameter가 바뀌었다. → 일반적으로 그렇게 이해하면 안 됨
```

실제 모델 개선에 사용하려면 데이터 수집, 정책에 따른 사용 허가, 정제, 학습, Evaluation, 새로운 모델 배포 같은 별도 과정이 필요합니다. 특정 제품에서 사용자의 피드백을 실제로 어떻게 사용하는지는 그 제품의 현재 데이터 정책을 확인해야 합니다.


예를 들어 모델이 하나의 질문에 대해 여러 답변을 생성합니다.

```text
질문:
AI를 초등학생에게 설명해줘.

답변 A:
AI는 인공신경망과 통계적 패턴을 기반으로...

답변 B:
AI는 컴퓨터가 사람처럼 문제를 풀도록 만든 기술이야.
```

사람은 두 답변을 비교합니다.

초등학생 대상이라면

답변 B가 더 적절할 수 있습니다.

그러면 모델은

```text
이런 상황에서는 답변 B 같은 방식이 더 좋다.
```

는 방향으로 조정됩니다.

---

### 수업 질문: 두 응답 중 하나를 고르는 피드백은 언제 학습이 되는가

사람이 답변 A와 B를 비교해 더 나은 쪽을 선택하면 **선호도 데이터**를 만들 수 있다. 이것은 RLHF에서 사용할 수 있는 피드백 형태와 닮았다. 그러나 화면에서 한 번 선택했다고 **현재 응답 중인 모델의 Parameter가 즉시 바뀌는 것은 아니다**. 실제 개선에는 데이터 수집·허가·정제, 학습·평가, 새 모델 배포가 필요하다. 특정 제품의 피드백이 실제로 어떤 용도로 쓰이는지는 그 제품의 현재 데이터 정책을 확인해야 한다.

```text
Pre-training: 대규모 데이터에서 언어 패턴을 학습
Post-training: 지시를 따르고 원하는 행동을 하도록 후속 조정
  ├─ 예: 지도된 Instruction Tuning
  └─ 예: 선호도 데이터를 사용하는 여러 조정 방법 중 RLHF
```

**Post-training 전체 = RLHF**는 아니다. 학습 방법이 달라도 목표·데이터·평가를 구분해 설명해야 한다. 학생이 “RLHF가 곧 사용자의 모든 실시간 피드백”이라고 이해하지 않도록 이 경계를 먼저 확인한다.

## Alignment란 무엇인가?

여기서 중요한 개념이 하나 더 등장합니다.

바로

**Alignment**

입니다.

Alignment는 한 문장으로 말하면

> **AI의 답변 방향을 사람의 의도와 가치에 맞추는 과정**

입니다.

LLM은 기본적으로

다음 Token을 예측하는 모델입니다.

하지만 실제 서비스에서는

단순히 그럴듯한 Token을 생성하는 것만으로는 부족합니다.

AI는

- 사용자의 의도를 이해해야 하고
    
- 사실에 기반해야 하며
    
- 위험한 요청에는 조심해야 하고
    
- 필요한 경우 모른다고 말할 수 있어야 합니다.
    

이처럼 모델의 행동을 사람에게 유용한 방향으로 맞추는 것이

Alignment입니다.

---

### 수업 질문: Alignment는 개념인가, 소스에서 구현하는가

Alignment는 모델의 행동을 사람의 목적과 제약에 맞추려는 **목표와 평가 관점**이다. 실제 구현은 한 줄의 “Alignment 함수”가 아니라 여러 층에 걸친다.

| 층 | 대표 수단 | 책임 |
|---|---|---|
| 모델 학습 | Instruction Tuning, 선호도 기반 조정, 안전성 평가 | 모델을 개발·배포하는 쪽 |
| 애플리케이션 | 입력·출력 검증, 근거 확인, 권한, 사람 승인 | AI 서비스를 만드는 쪽 |
| 운영 | 실패 관찰, 평가 데이터, 수정·중단 절차 | 서비스 운영 팀 |

서비스의 System Prompt는 모델에 원하는 행동을 전달하지만 **보안 경계나 접근 권한 자체를 대신하지 않는다**. RAG를 붙여도 모든 답변이 근거에 맞는다고 자동 보장되지 않는다. 중요한 서비스 결과는 모델 행동과 별개로 검증·승인해야 한다.

### 추가 연결: Reasoning Model은 LLM과 어떤 관계인가

일부 LLM 시스템은 어려운 문제를 풀 때 더 많은 추론 계산이나 단계적 검토를 사용하도록 설계된다. 이를 설명할 때 “Reasoning Model”이라는 제품·학습 범주가 쓰일 수 있지만, 별도의 AI 계층이 Transformer/LLM과 무관하게 생긴 것은 아니다. 모델마다 출력 방식과 API 옵션이 다를 수 있으므로 **모든 모델에 동일한 Chain-of-Thought Prompt를 강제하는 규칙**으로 가르치지 않는다. 학생은 먼저 `학습된 모델`, `요청 Context`, `추론 시 계산`, `최종 출력`을 구분한다.

## ChatGPT는 하나의 LLM만 의미하지 않는다

많은 사람들이

ChatGPT를

```text
LLM 하나
```

라고 생각합니다.

하지만 실제 서비스 관점에서는

ChatGPT는 보통 다음 요소들이 결합된 시스템입니다.

```text
Pre-trained LLM

↓

Instruction Tuning

↓

RLHF / Alignment

↓

Safety System

↓

Prompt 처리

↓

Tool 사용

↓

사용자 인터페이스
```

즉,

ChatGPT는 단순히 Pre-training된 모델이 아니라,

사람이 실제로 사용할 수 있도록 여러 단계의 조정과 시스템이 더해진 AI 서비스입니다.

---

## 핵심 흐름 다시 정리

LLM이 실제 대화형 AI가 되는 과정은 다음과 같이 이해할 수 있습니다.

```text
Pre-training
언어 패턴 학습

↓

Instruction Tuning
지시 따르기 학습

↓

RLHF
사람이 선호하는 답변 방향 학습

↓

Alignment
사람의 의도와 안전성에 맞게 조정

↓

ChatGPT 같은 대화형 AI 서비스
```

이 흐름을 이해하면

"LLM은 그냥 다음 Token을 예측하는데 왜 대화를 잘할까?"

라는 질문에 더 정확히 답할 수 있습니다.

LLM은 다음 Token 예측 능력을 기반으로 하지만,

그 위에

## Logit에서 실제 Token이 선택되기까지

Transformer가 직접 최종 문장을 한 번에 고르는 것은 아닙니다. 한 생성 Step을 단순화하면 다음과 같습니다.

```text
현재 Token Sequence
      ↓
Transformer Forward Pass
      ↓
Vocabulary 각 Token의 Logit
      ↓
Temperature 등으로 Logit 조정
      ↓
Softmax
      ↓
확률 분포
      ↓
Top-k / Top-p 같은 후보 제한(사용하는 경우)
      ↓
Greedy 또는 Sampling 등으로 다음 Token 1개 선택
      ↓
선택한 Token을 입력 뒤에 추가
      ↓
다음 Step 반복
```

### Logit이란?

Logit은 Softmax를 적용하기 전의 **원시 점수**입니다.

```text
Token A  logit 8.1
Token B  logit 7.2
Token C  logit 3.0
```

이 값 자체가 바로 확률은 아닙니다. Softmax를 거쳐 전체 합이 1인 확률 분포로 변환합니다.

### Temperature는 Decoding 방식인가?

엄밀히 말하면 Temperature는 `Greedy`, `Sampling`, `Beam Search`처럼 **후보를 최종 선택하는 알고리즘 이름과는 역할이 다릅니다.** Temperature는 Logit/확률 분포가 얼마나 뾰족하거나 평평해지는지 조정하는 값입니다.

```text
낮은 Temperature
→ 높은 점수 후보에 더 강하게 집중

높은 Temperature
→ 낮은 점수 후보도 상대적으로 선택될 가능성이 커짐
```

그 뒤 Top-k/Top-p로 후보를 제한할 수 있고, Sampling을 사용한다면 남은 후보 중 **확률에 따라 Token 하나**를 뽑습니다.

---

### 수업 질문: Greedy와 Sampling은 무엇이 다른가

다음 Token 후보가 `A: 50%`, `B: 30%`, `C: 20%`라고 하자. **Greedy Decoding**은 이 시점의 최대 확률 `A`를 고른다. **Sampling**은 후보의 확률에 따라 추출한다. `Top-k=2`라면 `C`를 제외하고 A/B 안에서 추출한다. 남은 확률을 다시 정규화하면 A는 `0.5/0.8=0.625`, B는 `0.3/0.8=0.375`다. `Top-p=0.8`은 확률이 높은 순서로 누적합이 0.8 이상이 될 때까지 후보를 남기므로 이 예에서는 A/B가 남는다. 다른 분포에서는 남는 후보 수가 달라진다.

| 요소 | 하는 일 | 이 예시 |
|---|---|---|
| Greedy | 후보 중 최대 확률을 선택 | A |
| Temperature | Logit에서 만들어지는 확률 분포의 뾰족함을 조정 | 후보 확률 자체가 바뀔 수 있음 |
| Top-k | 상위 k개 후보로 제한 | k=2면 A/B |
| Top-p | 누적 확률 p 이상이 되는 최소 후보 집합으로 제한 | p=0.8이면 A/B |
| Sampling | 남은 후보에서 확률적으로 추출 | A 또는 B |

Temperature는 별개의 Token 선택 알고리즘이라기보다 **분포 조정 값**이다. `Temperature=0`을 Greedy와 동일하게 취급할 수 있는지, Top-k/Top-p를 함께 쓸 수 있는지는 실제 Provider·API 구현을 확인한다. 값이 낮다고 사실성이 보장되지 않는다. 또한 여기의 **LLM Sampling Top-k**는 Vector DB에서 가까운 문서 **k개를 찾는 Retrieval Top-k**와 전혀 다른 단계다.

생성은 `Transformer의 Logit → (Temperature로 조절한) 확률 → Top-k/Top-p 후보 제한 → 남은 후보 중 한 Token Sampling`의 순서로 이해한다. 선택을 매 Token마다 반복한다. `Top-k=1`은 매번 최고 후보만 남겨 다양성이 사라지지만, `Top-k>1` 뒤 Sampling은 낮은 확률 후보를 막으면서 표현의 선택지를 남긴다. **Beam Search**는 여러 생성 경로를 유지해 점수를 비교하는 별도 방식이며, 여기의 한 Token Sampling과 구분한다.

## Context Window

여기서 또 중요한 개념이 나옵니다.

모델은 한 요청에서 처리할 수 있는 Token 수에 한계가 있습니다.

이를

Context Window

라고 합니다.

예를 들어 어떤 모델의 공식 사양이 128K Context라면 시스템 지시, 사용자 입력, 대화 기록, Tool 결과와 생성 중인 출력 등이 그 예산을 함께 사용할 수 있습니다. 입력과 출력의 세부 한도는 모델과 API마다 다르므로 공식 문서를 확인해야 합니다.

한도를 넘겼을 때 앞부분을 자동으로 버리는지, 요청을 거부하는지, 입력을 잘라내는지는 애플리케이션과 API 구현에 따라 다릅니다. 중요한 내용을 임의로 잃지 않도록 요약, 검색, Chunking, 명시적인 Truncation 정책을 설계해야 합니다.

---

### 수업 질문: Context 예산을 누가 관리하는가

Context Window는 한 요청의 작업 공간에 가깝다. System/User 메시지, 포함한 대화 History, 검색한 문서, Tool Result, 생성할 Output 등이 이 공간을 공유할 수 있다. 아래 숫자는 특정 모델 사양이 아닌 **설계 연습용 예시**다.

```text
가정한 총 예산 10,000 Token
System 지시            1,000
현재 질문              1,000
대화 History           3,000
검색 문서/Tool Result   3,000
출력용 예상 공간       2,000
-----------------------------
합계                  10,000
```

검색 결과가 1,000 Token 늘면 어디를 줄일지 애플리케이션이 결정해야 한다. API가 오류를 반환할 수도, 설정에 따라 일부를 자를 수도 있으므로 **모델이 중요한 것만 알아서 기억해 준다**고 가정하지 않는다. 정책은 최근 대화 유지, 오래된 대화 요약, 권한에 맞는 문서 검색, 중복 Tool Result 제거, 명시적 Truncation 중에서 정한다. 무엇을 버렸는지 추적할 수 있어야 한다.

## Context Window를 넘지 않도록 누가 관리하는가?

핵심은 다음 한 문장입니다.

> **모델이 중요한 내용을 알아서 영구 기억해 주는 것이 아니라, 애플리케이션이 다음 요청에 무엇을 넣을지 관리해야 합니다.**

예를 들어 설계상 다음과 같은 Context 예산을 잡았다고 하겠습니다.

```text
총 Context 예산        128K
System / 정책            2K
최근 대화                20K
검색 문서                80K
Tool Result              10K
출력용 여유              16K
-----------------------------
합계                    128K
```

여기서 검색 문서가 더 길어진다고 해서 모델이 자동으로 "가장 중요한 20K만 골라 기억"한다고 가정하면 안 됩니다. 제품/API 설정에 따라 오류가 날 수도 있고, 일부 입력이 잘릴 수도 있으며, 애플리케이션이 직접 줄여야 할 수도 있습니다.

### 일반적인 Context 관리 정책

```text
항상 우선 보존
- System / Developer 수준의 핵심 정책
- 현재 사용자 질문
- 답변 생성에 필요한 출력 여유

상황에 따라 축약
- 오래된 대화 → 요약
- 긴 문서 → Chunking + Retrieval
- 중복 Tool Result → 제거
- 이미 해결된 세부 과정 → 요약 또는 제외
```

### 문서 전체를 넣는 것과 RAG의 차이

```text
긴 Context 방식
질문 + 문서 전체
→ 한 번에 많은 내용을 넣음

Retrieval 방식
문서 전체를 외부에 저장
→ 질문과 관련된 Chunk 검색
→ 관련 근거만 Context에 삽입
```

둘 중 하나가 언제나 정답은 아닙니다. 문서 크기, 변경 주기, 권한, 비용, 지연시간, 근거 확인 필요성을 함께 보고 설계합니다.

사용자의 질문,

시스템 지시문이

모두 Context Window 안에 들어갑니다.

```text
System Prompt

+

User Prompt

+

이전 대화

+

참고 문서

↓

Context Window
```

LLM은 이 범위 안의 정보를 참고해서

다음 Token을 생성합니다.

즉,

Context Window는

**현재 작업을 위한 작업 공간**

에 가깝습니다.

---

## Memory는 장기 기억에 가깝다

반면 Memory는

현재 입력창에 들어와 있지 않아도

사용자나 작업에 관한 정보를

나중에 다시 활용할 수 있도록 저장하는 개념입니다.

예를 들어

사용자가 이전에

```text
나는 Markdown 형식의 강의 자료를 선호한다.
```

라고 알려주었다면,

나중에 새로운 대화에서도

그 선호를 반영할 수 있습니다.

이것은 단순한 Context Window와 다릅니다.

---

## Parameter / Context / Memory / Retrieval의 차이

이 네 개를 한 번에 구분하면 뒤의 RAG와 Agent가 쉬워집니다.

| 개념 | 어디에 있는가 | 어떻게 모델이 사용하게 되는가 |
|---|---|---|
| Parameter | 모델 내부의 학습된 값 | Inference 때 모델 계산 자체에 사용 |
| Context | 현재 요청에 포함된 Token | 이번 Forward Pass에서 직접 사용 |
| External Memory | DB 등에 별도로 저장된 사용자/업무 정보 | 조회 후 Context에 다시 넣어야 사용 |
| Retrieval | 외부 문서에서 관련 정보를 찾는 과정 | 찾은 결과를 Context에 넣어 사용 |

```text
학습된 Parameter
        +
현재 Context
        +
필요하면 Retrieval로 가져온 외부 정보
        +
필요하면 Memory에서 불러온 정보
        ↓
LLM Inference
        ↓
Response
```

**Memory와 Retrieval은 모델 자체의 영구 기억 장치가 아니라 애플리케이션에서 설계하는 기능**이라는 점이 중요합니다.

---

## 둘의 차이

|구분|Context Window|Memory|
|---|---|---|
|성격|현재 입력 범위|장기 저장 정보|
|목적|지금 답변 생성|이후 대화나 작업에 재사용|
|유지 기간|현재 대화나 입력 범위 중심|시스템 설계에 따라 장기 유지 가능|
|예시|지금 넣은 문서, 지금까지의 대화|사용자 선호, 프로젝트 규칙, 반복 업무 정보|

---

## 왜 이 차이가 중요할까?

LLM을 사용할 때

많은 사람이 이렇게 말합니다.

> "지난번에 말했는데 왜 기억 못 하지?"

이유는 간단합니다.

그 정보가 현재 Context Window 안에 없거나,

Memory로 저장되어 있지 않기 때문입니다.

LLM은 사람처럼 모든 대화를 자동으로 기억하는 존재가 아닙니다.

현재 입력으로 제공된 정보,

또는 시스템이 별도로 저장한 Memory만 활용할 수 있습니다.

---

## 기업 AI에서는 Memory를 어떻게 사용할까?

기업 AI 시스템에서는 Memory를 매우 조심해서 설계해야 합니다.

예를 들어

AI 비서가 다음 정보를 기억한다면 유용합니다.

```text
사용자의 직무

자주 사용하는 문서 형식

선호하는 보고서 스타일

담당 프로젝트

반복 업무 패턴
```

하지만 민감한 정보는 무조건 저장하면 안 됩니다.

예를 들어

```text
개인정보

인사 평가

급여 정보

계약상 비밀

고객 민감 정보
```

등은

보안 정책에 따라 엄격하게 관리해야 합니다.

즉,

Memory는 편리한 기능이지만,

동시에 보안과 개인정보 보호가 매우 중요한 영역입니다.

---

## Context Window가 커지면 RAG가 필요 없을까?

또 하나의 중요한 질문이 있습니다.

> Context Window가 아주 커지면 RAG는 필요 없지 않을까요?

겉으로는 그럴듯해 보입니다.

하지만 실제로는 그렇지 않습니다.

Context Window가 커져도

모든 회사 문서,

모든 최신 정보,

모든 데이터베이스 내용을

매번 Prompt에 넣는 것은 비효율적입니다.

RAG는 필요한 정보만 검색해서

Context Window 안에 넣어주는 기술입니다.

즉,

```text
RAG

=

필요한 정보를 골라서 Context에 넣는 기술
```

입니다.

Context Window가 커질수록 더 많은 정보를 넣을 수는 있지만,

여전히

**무엇을 넣을지 선택하는 과정**

은 필요합니다.

그 역할을 하는 것이 RAG입니다.

---

## 정리하면

LLM이 답변을 생성할 때는

세 가지 정보가 함께 작동할 수 있습니다.

```text
현재 질문

+

Context Window 안의 정보

+

Memory 또는 외부 검색 정보
```

이 중에서

Context Window는 현재 답변의 작업 공간이고,

Memory는 장기적으로 재사용되는 정보이며,

RAG는 필요한 외부 지식을 검색해서 Context에 넣는 방법입니다.

---

## 다음 학습과의 연결

이제 우리는 LLM이

현재 입력만 보는 것이 아니라,

Context Window,

Memory,

RAG 같은 구조와 연결될 때

더 강력한 AI 서비스가 된다는 것을 이해했습니다.

이 흐름은 이후

Prompt Engineering,

RAG,

Agent에서 계속 이어집니다.

Prompt Engineering은

Context를 잘 설계하는 기술이고,

RAG는

필요한 정보를 Context에 넣는 기술이며,

Agent는

Memory와 Tool을 활용해 여러 작업을 수행하는 시스템입니다.

## Hallucination

또 하나의 중요한 개념입니다.

LLM은

모든 질문에

답하려고 합니다.

하지만

학습하지 않은 내용도

예측합니다.

그러면

사실처럼

틀린 내용을

말할 수 있습니다.

이를

Hallucination

이라고 합니다.

---

### 왜 발생할까?

LLM은

검색기가 아니라

예측기입니다.

즉,

```text
모르겠다

↓

예측
```

하는 경우가 있습니다.

그래서

없는 논문,

없는 법,

없는 URL,

없는 사람을

만들어낼 수도 있습니다.

이것이

Hallucination입니다.

> 현대 AI 서비스는 검색, RAG, 도구 사용 등을 결합하여 이러한 문제를 줄이려 하지만, 원리적으로 LLM만으로는 Hallucination 가능성이 완전히 사라지지는 않습니다.

실제 AI 서비스에서는 생성 방식을 목적에 따라 다르게 조절합니다.

|---|---|

## ⑥ 핵심 정리 (Summary)

이번 Unit에서 반드시 기억해야 할 핵심은 다음과 같습니다.

1. **학습(Training)**과 **사용(Inference)**은 목적과 계산 방식이 구분됩니다.
    
2. 답변 생성은 **Tokenization → Embedding → Transformer → Next Token Prediction → Sampling**의 반복입니다.
    
3. **Temperature**는 답변의 다양성을 조절합니다.
    
4. **Top-k**는 후보 개수를 제한하고, **Top-p**는 누적 확률을 기준으로 후보를 제한합니다.
    
5. **Context Window**는 한 요청에서 모델이 처리할 수 있는 Token 범위이며, 일반적으로 입력뿐 아니라 생성 중인 출력도 이 예산에 영향을 줍니다. 정확한 한도는 모델의 공식 사양을 확인해야 합니다.
    
6. **Hallucination**은 LLM이 예측 기반으로 답을 생성하기 때문에 발생할 수 있는 현상입니다.
    
7. **Memory**는 현재 Context Window 밖의 정보를 이후 작업에 재사용하기 위한 장기 저장 개념입니다.
    
8. **RAG**는 필요한 외부 정보를 검색해 Context Window 안에 넣어주는 방식입니다.

# [보강 학습] LLM을 “말을 잘하는 모델”이 아니라 평가 가능한 시스템으로 보기

LLM은 다음 Token을 예측하는 과정을 반복해 자연스러운 문장을 만듭니다. 그러나 실제 서비스에서는 문장이 자연스럽다는 사실만으로 충분하지 않습니다. 회사 규정을 묻는 질문에는 정확한 근거가 필요하고, 정보 추출 결과는 정해진 형식이어야 하며, 많은 사용자가 동시에 접속해도 허용 가능한 시간과 비용 안에서 응답해야 합니다.

이번 보강에서는 Tokenizer, 학습과 Alignment의 연결, 평가, 환각과 불확실성, 추론 비용을 하나의 흐름으로 살펴봅니다.

## 1. Tokenizer는 단순히 문장을 띄어쓰기로 나누지 않는다

LLM은 문자열을 직접 처리하지 않고 Token ID의 나열을 처리합니다. 이때 문자열을 Token으로 나누고 ID로 바꾸는 도구가 **Tokenizer**입니다.

```text
"생성형 AI를 공부합니다"
→ Tokenizer
→ 여러 개의 Token
→ 각 Token의 ID
→ Embedding
→ Transformer
```

Token은 단어 하나와 정확히 일치하지 않을 수 있습니다. 자주 등장하는 단어나 문자열은 하나의 Token이 될 수 있고, 드물거나 긴 표현은 여러 조각으로 나뉠 수 있습니다. 같은 문장이라도 모델마다 사용하는 Tokenizer가 다르면 Token 수가 달라질 수 있습니다.

이 차이는 세 가지에 영향을 줍니다.

1. **Context 사용량:** 같은 내용이 더 많은 Token으로 나뉘면 Context Window를 더 많이 차지합니다.
2. **비용:** API가 입력·출력 Token 수를 기준으로 과금한다면 표현 방식과 언어에 따라 비용이 달라질 수 있습니다.
3. **처리 품질:** 도메인 약어, 코드, 숫자, 특정 언어가 지나치게 잘게 나뉘면 모델이 패턴을 배우고 생성하기 더 어려울 수 있습니다.

따라서 “한국어를 지원한다”는 설명만 보지 말고, 실제 회사 문서와 약어가 어떻게 Tokenize되는지 확인하는 것이 좋습니다. Token 수가 적다고 무조건 더 좋은 모델은 아니지만, 품질·Context·비용을 함께 평가하는 중요한 단서가 됩니다.

## 2. Pre-training에서 서비스용 LLM까지

LLM이 만들어지는 과정을 다시 연결하면 다음과 같습니다.

```text
Pre-training
방대한 데이터에서 다음 Token 예측
→ 언어와 지식의 넓은 패턴 학습

Supervised Fine-Tuning(SFT)
질문과 모범 답변 예시 학습
→ 지시를 따르는 형식과 행동 학습

Preference Optimization / Alignment
사람 또는 정책이 선호하는 답변 방향 반영
→ 유용성·안전성·대화 품질 조정

Evaluation
업무 품질·안전·비용·속도 확인

Deployment and Monitoring
실제 사용자 입력에서 성능 변화와 실패 관찰
```

RLHF는 사람이 비교한 선호 데이터를 이용하고 강화학습을 포함할 수 있는 대표적인 Alignment 흐름입니다. DPO는 선호되는 답변과 그렇지 않은 답변의 쌍을 이용해 모델을 직접 최적화하는 별도의 방법입니다. DPO를 RLHF 전체와 완전히 같은 말이나 모든 RLHF를 대체하는 하나의 정답으로 설명하면 안 됩니다.

Alignment도 사실을 새로 보장하는 과정은 아닙니다. 모델이 더 친절하고 안전해 보이게 답할 수는 있지만, 존재하지 않는 회사 규정을 정확히 알게 되는 것은 아닙니다. 외부의 최신 지식은 RAG로 제공하고, 결과가 맞는지는 별도의 Evaluation으로 확인해야 합니다.

## 3. LLM 평가는 한 점수로 끝나지 않는다

“좋은 LLM인가?”라는 질문은 너무 넓습니다. 목적에 따라 여러 층으로 나누어야 합니다.

### 정답 품질

- 질문에 맞는 내용을 답했는가?
- 중요한 사실이 정확한가?
- 필요한 항목을 빠뜨리지 않았는가?
- 주어진 근거와 모순되지 않는가?

### 형식 품질

- 요청한 JSON이나 표 구조를 지켰는가?
- 필수 필드와 데이터 타입이 맞는가?
- 길이, 언어, 금지 표현 같은 제약을 지켰는가?

### 안전과 보안

- 개인정보나 비밀 정보를 노출하지 않는가?
- 유해하거나 권한 밖인 요청을 적절히 처리하는가?
- 외부 문서의 악성 지시를 시스템 명령처럼 따르지 않는가?

### 운영 품질

- 응답 시간이 목표 범위 안에 있는가?
- 요청 한 건과 전체 사용량의 비용은 얼마인가?
- 동시 요청이 늘어도 안정적으로 동작하는가?
- 실패율과 재시도율은 어느 정도인가?

공개 Benchmark는 일반 능력을 비교하는 출발점으로 쓸 수 있지만, 실제 회사의 약어와 문서 형식, 사용자 질문, 위험 조건을 모두 반영하지는 못합니다. 또한 평가 문제가 학습 데이터에 포함된 **Benchmark Contamination** 가능성도 고려해야 합니다.

실무에서는 실제 업무를 대표하는 질문과 기대 결과를 모은 평가 Dataset을 만듭니다. 정답이 하나인 추출 작업은 필드 정확도처럼 자동 평가할 수 있고, 요약이나 설명처럼 정답이 여러 개인 작업은 기준표를 이용한 사람 평가와 모델 기반 평가를 함께 사용할 수 있습니다. 모델이 모델을 평가하는 `LLM-as-a-Judge`는 확장성이 좋지만 편향과 일관성 문제를 가질 수 있으므로 중요한 판단을 전부 맡기지 않습니다.

## 4. 환각과 불확실성은 어떻게 다른가?

LLM은 그럴듯한 다음 Token을 생성합니다. 이 목표는 “모든 문장이 현실의 사실인지 확인하라”는 목표와 같지 않습니다. 질문에 필요한 지식이 없거나 입력이 모호해도 문장을 계속 완성할 수 있기 때문에 사실과 다른 내용을 자신 있게 말하는 **Hallucination**이 발생할 수 있습니다.

환각을 줄이는 방법은 하나가 아닙니다.

```text
질문이 모호함
→ 추가 질문

최신·사내 지식이 필요함
→ RAG와 출처 제공

정해진 데이터만 추출해야 함
→ Structured Output와 Schema 검증

근거가 부족함
→ 답변 보류 또는 불확실성 표시

영향이 큰 결정
→ 사람의 검토와 승인
```

“모르겠습니다”라고 말하도록 Prompt에 한 줄 쓰는 것만으로 환각이 사라지지는 않습니다. 검색 결과가 실제 질문을 뒷받침하는지, 인용한 문장이 답변의 주장과 일치하는지, 모델이 근거 밖의 내용을 추가하지 않았는지 평가해야 합니다.

모델이 출력한 확률을 사람이 느끼는 확신과 그대로 동일시해서도 안 됩니다. 다음 Token의 확률이 높다는 것은 현재 문맥에서 그 Token이 선택될 가능성이 높다는 뜻이지, 완성된 주장이 현실에서 참일 확률을 직접 의미하지 않습니다.

## 5. Context Window와 외부 Memory

Context Window는 현재 요청에서 모델이 한 번에 처리할 수 있는 Token 범위입니다. 시스템 지시, 사용자 질문, 대화 기록, 검색 문서, Tool 결과, 생성 중인 답변이 모두 이 공간을 사용합니다.

외부 Memory는 정보를 별도의 저장소에 보관했다가 필요한 시점에 다시 검색해 Context로 넣는 애플리케이션 기능입니다. 모델 내부에 영구 기억이 생긴다는 뜻이 아닙니다.

```text
Context Window
현재 계산에 직접 들어간 제한된 작업 공간

External Memory
DB·VectorDB 등에 저장된 정보
→ 필요한 내용을 검색
→ Context에 다시 넣어야 모델이 사용 가능
```

Memory를 설계할 때는 무엇을 저장할지뿐 아니라 사용자 동의, 보관 기간, 삭제, 권한, 잘못된 기억의 수정도 함께 설계해야 합니다.

### 개념 경계: Context, 외부 Memory, Retrieval

| 개념 | 어디에 있는가 | 다음 요청에 자동으로 남는가? |
|---|---|---|
| Context Window | 지금 모델 호출에 전달된 Token 범위 | 요청을 다시 구성하지 않으면 자동 보장되지 않음 |
| 애플리케이션 Memory | Database 등에 저장한 대화 요약·사용자 상태 | 저장과 권한 규칙에 따라 다시 읽어야 함 |
| Retrieval | 외부 자료에서 관련 항목을 찾아 선택 | 찾은 항목을 이번 요청 Context에 넣어야 활용 가능 |

긴 Context와 RAG는 항상 서로를 대체하지 않는다. 자료의 양·변경 주기·권한·근거 확인 요구에 따라 무엇을 직접 넣고 무엇을 검색할지 결정한다.

## 6. 응답 시간과 비용은 어디에서 생기는가?

LLM 요청의 시간은 크게 입력을 처리하는 단계와 출력을 생성하는 단계로 나누어 생각할 수 있습니다.

### Prefill

시스템 Prompt, 질문, 대화 기록, 검색 문서 등 입력 Token 전체를 처리합니다. 입력이 길어질수록 첫 Token이 나오기 전 시간이 길어질 수 있습니다.

### Decode

출력 Token을 하나씩 생성합니다. 출력이 길수록 전체 응답 시간이 늘어납니다. KV Cache가 이전 계산을 재사용하지만 생성 자체는 기본적으로 순차적입니다.

사용자가 느끼는 품질에는 첫 글자가 보이기까지의 시간과 답변이 끝날 때까지의 시간이 모두 중요합니다. **Streaming**은 생성된 Token을 즉시 전송하여 체감 대기 시간을 줄이지만, 전체 계산량 자체를 없애는 것은 아닙니다.

여러 요청을 묶어 계산하는 **Batching**은 처리량을 높일 수 있지만 개별 요청이 Batch를 기다리면 지연시간이 증가할 수 있습니다. Production 환경에서는 요청 도착에 따라 실행 중인 Batch에 새 요청을 효율적으로 편성하는 방식도 사용합니다.

비용과 지연시간에 영향을 주는 대표 요소는 다음과 같습니다.

- 모델 크기와 추론 방식
- 입력 Token 수
- 출력 Token 수
- 동시 요청 수
- Tool과 검색 호출 횟수
- 재시도와 실패율
- 직접 운영할 경우 GPU 사용량과 가동률

따라서 비용 최적화는 무조건 가장 작은 모델을 쓰는 일이 아닙니다. 쉬운 작업은 작은 모델, 복잡하거나 위험한 작업은 더 강한 모델로 보내는 Routing, 불필요한 Context 제거, 출력 길이 제한, Cache, 비동기 처리 등을 업무 품질과 함께 설계합니다.

## Document AI 요청 하나를 평가해 보기

사용자가 “출장 규정에서 해외 숙박비 한도를 찾아 표로 정리해 줘”라고 요청했습니다.

```text
1. Tokenizer
질문과 검색 문서를 Token으로 변환

2. Context 구성
시스템 지시 + 사용자 질문 + 권한이 확인된 규정 Chunk

3. 생성
LLM이 근거를 이용해 표 생성

4. 형식 검증
국가, 등급, 통화, 금액 필드가 Schema와 일치하는지 확인

5. 근거 검증
각 금액이 인용한 규정 문장에 실제로 존재하는지 확인

6. 운영 측정
지연시간, Token 수, 비용, 실패와 재시도 기록

7. 사용자 검토
중요한 결재에 쓰기 전 원문 링크로 최종 확인
```

이렇게 보면 LLM의 자연스러운 문장 생성은 전체 품질 중 한 부분입니다. 모델 평가, 검색 평가, 형식 검증, 권한, 운영 지표가 함께 있어야 신뢰할 수 있는 서비스가 됩니다.

## Practice — Post-training, Decoding, Context 설명하기

- **실습 목표:** RLHF/Alignment, Greedy/Sampling, Context/Memory/Retrieval을 서로 다른 층으로 설명한다.
- **실습 환경:** 이 문서의 A/B/C 확률표와 10,000 Token 예산표. 실행 코드 불필요.
- **실습 절차:** A/B 선호도 선택이 현재 모델을 즉시 바꾸는지 답하고, `Top-k=2`의 재정규화 확률을 계산한다. Tool Result가 1,000 Token 추가될 때 어떤 Context 정책을 쓸지 적는다.
- **예상 결과:** 선호도 선택은 학습 데이터 후보이며 즉시 Parameter 변경이 아니다. Top-k=2일 때 A/B는 0.625/0.375다. Context 초과는 애플리케이션 정책으로 관리한다.
- **실습 확인:** Temperature와 Top-k를 같은 종류의 연산이라고 쓰지 않았는지, Vector Search Top-k를 LLM Decoding과 혼동하지 않았는지 확인한다.
- **응용 과제:** 원문 근거가 필요한 문서 QA에서 긴 Context만 사용할 때와 Retrieval을 사용할 때의 비용·권한·근거 확인 차이를 비교한다.

## 보강 핵심 정리

1. Tokenizer는 문자열을 모델이 처리할 Token ID로 바꾸며 Context 사용량과 비용에도 영향을 준다.
2. Pre-training, SFT, Alignment는 서로 다른 목적을 가지며 Alignment가 사실 정확성을 자동 보장하지는 않는다.
3. LLM 평가는 정답·형식·안전·운영 품질을 나누어 실제 업무 데이터로 수행해야 한다.
4. 환각은 다음 Token 생성 목표와 사실 검증 목표가 같지 않기 때문에 발생할 수 있다.
5. Context Window는 현재 작업 공간이고 외부 Memory는 검색 후 다시 Context에 넣어야 사용할 수 있는 저장소다.
6. 입력 길이, 출력 길이, 모델 크기, 동시 요청, Tool 호출이 지연시간과 비용에 영향을 준다.

## 전체 과목 마무리

여기까지 학습했다면 LLM을 다음과 같이 하나의 흐름으로 설명할 수 있어야 합니다.

```text
① 방대한 텍스트를 수집한다.
        ↓
② Token으로 분리한다.
        ↓
③ Embedding으로 숫자 벡터로 변환한다.
        ↓
④ Transformer가 문맥을 이해한다.
        ↓
⑤ 다음 Token을 예측한다.
        ↓
⑥ Loss를 계산하고 Backpropagation으로 파라미터를 수정한다.
        ↓
⑦ 이 과정을 방대한 데이터에 대해 반복하여 LLM을 완성한다.
        ↓
⑧ 사용자가 질문하면 학습은 하지 않고 추론(Inference)만 수행한다.
        ↓
⑨ Sampling 전략을 이용해 다음 Token을 하나씩 생성한다.
        ↓
⑩ 원하는 종료 조건에 도달할 때까지 반복하여 최종 답변을 만든다.
```

이 흐름을 이해하면 "LLM은 어떻게 만들어지고, 어떻게 답변을 생성하는가?"를 원리 수준에서 설명할 수 있습니다.

다음 커리큘럼인 **Prompt Engineering**에서는 이 LLM의 동작 원리를 바탕으로, **왜 프롬프트에 따라 답변 품질이 달라지는지**, 그리고 **LLM이 더 정확한 추론과 출력을 하도록 입력을 설계하는 원리**를 학습하게 됩니다.
