# 역할을 나눌 때 자료와 책임은 어떻게 넘길까

“출장 식비 규정을 찾아 상한과 조건을 설명해줘.” 앞의 Single-Agent는 검색을 반복하다 끝나기도 했다. 검색에 집중하는 역할, 답을 쓰는 역할, 빠진 조건을 확인하는 역할로 나누면 해결될까? 역할을 늘리면 목표를 분리할 수 있지만, 전달 중 근거가 빠지거나 같은 실패를 반복할 수도 있다.

**이번에는 한 요청이 역할 사이를 이동하는 과정과 전체 작업의 종료 책임을 배운다.** [Single-Agent](<../01. Single-Agent/강의용.md>)의 도구·출처 검사를 재사용한다. 같은 Qwen CPU 모델을 역할별로 순차 호출하며 동시에 세 모델을 올리거나 서로 다른 서버가 대화하는 구성은 아니다. 가상 규정과 금액을 실제 기관 정책으로 사용하지 않는다.

[연결 실습](<../../../02. 실습/document-assistant/L6.md>)에서는 먼저 완주하는 고정 응답으로 구조를 이해하고, 실제 모델 기록에서 어떤 단계까지 도달했는지 비교한다. 아래 고정 예제를 모델의 계획/작성 능력으로 표시하지 않는다.

## 1. 역할 이름보다 목표·정보·행동을 나누기

RAG는 정해진 검색→Context→생성을 실행했다. Single-Agent는 같은 상태에서 다음 행동을 고른다. 이번 구성은 그 선택을 검색·작성·검토 역할로 나눈다. 검색 담당은 근거를 찾고, 작성 담당은 받은 근거로 초안을 만들고, 검토 담당은 질문과 초안·근거를 대조한다.

이름만 바꾸고 같은 전체 대화·자료·도구를 모두 주면 무엇을 분리했는지 설명하기 어렵다. 역할별 목적뿐 아니라 볼 정보와 허용 행동도 달라야 한다. 짧은 인사나 단순 조회라면 역할을 늘리는 호출·지연·전달 비용이 이득보다 클 수 있다.

이번 Orchestrator는 역할 전환과 정책을 적용하는 일반 실행 코드다. 모델 관리자 한 명이 나머지 모델의 권한을 마음대로 정하는 구조가 아니다. 검색 역할은 검색/읽기/전달/되묻기를 고르고, 작성자는 초안이나 근거 추가 요청을, 검토자는 통과/보완/기각을 고른다. 어떤 역할로 넘어갈 수 있는지는 실행기가 통제한다.

### 한 요청의 정상 경로를 먼저 따라가기

다음은 **가상 영어 규정 cap 30000과 교사가 정해 둔 행동**을 사용하는 기존 Control 실험이다. A@v1:L1은 문서 A의 v1 첫 줄이다.

| 모델 역할 호출 | 행동 | 도구/전달과 다음 상태 |
|---|---|---|
| 검색 1 | meal 검색 요청 | 실행기가 검색. ID와 미리보기 발견 |
| 검색 2 | A@v1:L1 원문 읽기 | 현재 원문을 읽은 출처로 등록 |
| 검색 3 | 읽은 ID를 작성자에게 전달 요청 | 실행기가 출처와 수신 범위 확인 후 원문 전달 |
| 작성 1 | cap 30000 근거 초안 제출 | 출처/부분 인용 검사 후 검토자로 전달 |
| 검토 1 | pass 의견 | 실행기가 전달 경계 확인. 사람 검토용 초안 반환 |

전체 모델 역할 응답은 5번, 도구 처리는 검색·읽기의 2번이다. 전달 검증은 도구 호출이나 새 모델 호출과 다른 실행기 작업이다. 역할별로 같은 모델을 불러도 카운터를 따로 세어 어느 단계가 비용을 썼는지 본다.

이 경로에서 검토의 pass도 사람의 승인이나 의미 품질 보증은 아니다. 같은 모델이 다른 지시를 받아 검토했을 뿐 독립 강사의 평가를 받은 것은 아니다. 실제 모델 실험은 이 정상 경로를 완주하지 못한 경우가 있으므로 마지막 장에서 나란히 비교한다.

**확인 질문**

1. 같은 모델을 세 번 부르면 언제나 역할 분리라고 할 수 있는가? 무엇을 달리해야 하는가?
2. Control에서 모델 5번·도구 2번인 이유는 무엇인가? Handoff도 모델 호출인가?
3. 답변 없이 일찍 끝나 호출이 줄었다면 효율이 개선됐다고 말할 수 있는가?

## 2. 전달할 ID와 실제 원문을 함께 확인하기

Handoff는 다음 역할이 사용할 실행 자료를 넘기는 과정이다. “찾아봤으니 알아서 답해”라는 자유 요약만 보내면 원문의 조건·버전·접근 범위를 잃기 쉽다. 이번 모델은 근거 ID와 정해진 부족 정보 코드를 요청하고, Runtime이 전달 기록과 원문을 만든다.

다음은 **Control의 검색 역할이 내는 고정 전달 요청 JSON**이다. 전체 Handoff 기록이 아니고 실행 코드도 아니다.

```json
{"kind":"handoff","evidence_ids":["A@v1:L1"],"missing_information":[]}
```

실행기는 이 ID를 실제 읽었는지, 받는 역할에게 허용됐는지, 현재 저장소에서 여전히 사용할 수 있는지 확인한다. 그 뒤 실행 ID·질문 ID·송신/수신 역할·저장소 변경 번호/설정 해시·근거 ID·실패 ID·예산 누적값 등을 기록한다. 모델이 예산 0이나 승인true를 썼다고 이 값이 바뀌지 않는다.

| 역할 | 실제로 볼 정보 | 허용 도구/행동의 범위 |
|---|---|---|
| 검색 담당 | 원 질문, 발견 ID·읽은 ID, 최근 관찰 | 검색·원문 읽기·근거 전달·되묻기·중단 |
| 작성 담당 | 원 질문, 전달 검증된 원문, 부족/보완 정보 | 받은 ID의 원문 읽기·초안·추가 근거 요청·되묻기·중단 |
| 검토 담당 | 원 질문, 초안, 전달된 원문, 기존 실패 | 받은 원문 읽기·인용 검사·판정·중단 |

작성자나 검토자에게 검색 도구를 자동으로 허용하지 않는다. 전달 ID 밖 원문도 읽을 수 없다. 검색자가 자료를 볼 수 있다는 사실은 작성자의 허용 범위를 넓혀 주지 않는다.

예를 들어 M01 실험에서는 검색자가 A@v1:L1을 실제 읽었지만 작성자 수신 허용 목록은 비워 뒀다. 전달 요청은 HANDOFF_SCOPE로 거부되고 작성 모델은 호출되지 않는다. 같은 잘못된 전달을 다시 요청하면 반복 실패로 중단한다. 잘못된 자료를 우선 넘기고 나중에 가리는 구조가 아니다.

ID만 거르고 자유 요약을 그대로 넘겨도 제한 내용이 요약에 섞일 수 있다. 이번 전달은 모델의 요약문 대신 ID로 확인한 원문을 저장소에서 다시 검사해 사용한다. 부족 정보도 NO_EVIDENCE(근거 없음), NEED_MORE_CONTEXT(추가 자료 필요), CONDITION_UNCLEAR(조건 불명확) 중에서 고른다. 전체 대화 로그나 이전 역할의 숨은 사고 과정을 전달하는 것은 아니다.

이것은 작은 로컬 실험의 정보 경계다. 실제 사용자 인증·조직 권한 서비스·분산 상태 보장까지 구현한 것은 아니다. 다음 모델 호출 전에도 전달된 자료의 현재성을 확인하며, 이전 Index 선택을 무조건 재사용하지 않는다.

**확인 질문**

1. 검색자가 읽은 실제 문서라도 작성자에게 전달할 수 없는 경우는 무엇인가?
2. Handoff 요청 JSON과 Runtime이 만든 전달 기록은 무엇이 다른가?
3. ID만 필터링하고 모델 요약을 그대로 넘기면 어떤 정보가 새어 나갈 수 있는가?

## 3. 한 번의 보완을 모든 역할이 공유하기

초안에 근거가 부족하면 작성자는 검색자에게 추가 근거를 요청할 수 있다. 검토자는 조건/인용 오류를 보고 작성자에게 보완을 요청할 수 있다. 둘을 각자 한 번씩 허용하면 보완이 두 번으로 늘어난다. 이번 구현은 출력/전달 오류 보완까지 **실행 전체 한 번의 같은 예산**을 사용한다.

M02의 고정 실험을 시간순으로 보자.

| 차례 | 행동 | 누적 모델/보완 |
|---|---|---|
| 검색자가 빈 근거와 추가 자료 필요 전달 | 작성자로 이동 | 1/0 |
| 작성자가 근거 추가 요청 | 검색자로 재진입 | 2/1 |
| 검색자가 검색·읽기·다시 전달 | 이전 검색 1회를 지우지 않음 | 5/1 |
| 작성자가 초안 제출 | 이전 작성 1회도 유지 | 6/1 |
| 검토자가 pass | 사람 검토용 초안 | 7/1 |

마지막 역할별 모델 호출은 검색 4·작성 2·검토 1이다. 도구 처리는 2회다. 역할을 재시작했다고 검색과 작성의 카운터를 0으로 만들지 않는다. 작성자의 요청은 허용된 추가 기회를 쓰는 것이며 무제한 작업 확장이 아니다.

M03은 검색→읽기→전달→초안 뒤 검토자가 UNSUPPORTED_CLAIM 보완을 요청한다. 작성자가 다시 제출했어도 검토에서 같은 실패가 반복되면 중단한다. 작성 중인 내용은 partial_draft에 남지만 사용자에게 정상 전달할 draft는 None이다. 부분 결과와 최종 결과를 구분하지 않으면 실패한 초안을 성공처럼 반환하게 된다.

검토자는 틀릴 수도 있다. pass는 모델의 의견이고 approval_granted는 실행기가 관리하는 별도 값이다. 원문에 인용이 존재해도 주장과 금액·조건·예외가 맞는지는 원문 대조가 필요하다. 검토 역할이 있다는 사실만으로 독립 검증이 완성되는 것은 아니다.

실제 기록에는 JSON을 Markdown 코드 블록으로 감싼 원응답이 있었다. 현재 파서는 **응답 전체가 하나의 json 블록**이면 포장만 제거하고 역할 Schema로 다시 검사한다. Python 블록·앞뒤 설명·JSON 여러 개에서 임의로 내용을 뽑거나 코드를 실행하지 않는다. Markdown 포장과 JSON 데이터, 실제 코드 실행은 다른 대상이다.

**확인 질문**

1. 작성자가 추가 근거 요청으로 보완을 썼다면 검토자에게 새 보완 한 번을 줄 수 있는가?
2. M02에서 재진입 후 검색 호출이 4회인 이유는 무엇인가?
3. 검토 반려 뒤 partial_draft가 남아 있으면 사용자에게 정상 결과로 돌려줘도 되는가?

## 4. 전체 예산·실패 전파·동일 조건 비교

역할별 허용량을 더한 값이 전체 허용량은 아니다. 기본 모델 전체 8회와 검색 4·작성 2·검토 3회 제한을 모두 검사한다. 역할 합은 9지만 전체는 8이다. 전체 또는 현재 역할 제한 중 먼저 닿은 곳에서 멈춘다. 도구 처리도 전체 6회, 일시 오류 재시도도 전체 1회다. 재시도는 실제 호출 예산을 소비한다.

| 고정 경계 시험 | 실제로 관찰할 동작 |
|---|---|
| 전체 모델 제한 4로 낮춤 | 검색 3·작성 1 뒤 검토 호출 전 model_budget. 작성 초안은 부분 결과만 |
| 역할 호출의 일시 오류 두 번 | 한 번 재시도 후 transient_budget으로 전체 중단 |
| 가짜 시계를 호출 중 241초로 바꿈 | 반환된 늦은 행동을 전달하지 않고 deadline 종료 |

가짜 시계 시험은 실제 240초를 기다린 성능 시험이 아니다. 이 동기 구현은 호출 전후 시간을 확인하므로 진행 중 모델을 정시에 강제 취소하지 못한다. 늦은 출력이 왔을 때 다음 역할로 넘어가지 않는 동작을 확인한 것이다.

### 실제 모델은 어디까지 도달했는가

과거 식비 C01은 검색 역할이 첫 호출에서 되묻기를 골랐다. 자료/초안 전달이 없고 작성·검토 호출도 0이다. Single의 반복 검색보다 호출/시간은 줄었지만 필요한 답을 못 냈으므로 품질/효율 향상으로 판단하지 않는다.

원문을 찾고 읽으라는 A02는 실제로 검색→읽기→전달→작성→검토에 도달했다. 그러나 작성자는 규정이 있는데도 ‘자료가 부족합니다.’라고 보류했고, 검토자는 기각했다. 최종 전달용 초안은 없다. 전달 제어가 실행됐다는 사실과 상한/조건을 설명하는 과제 완료는 다른 결과다.

| 과거 본 실험 18개 | 실제 관찰 |
|---|---|
| 역할 호출 | 검색 30·작성 6·검토 6, 총 42회 |
| 도구 함수 진입 | 검색 8·읽기 6, 총 14회 |
| 전체 종료 | 되묻기 11, 검토 기각 6, 공백 사전 거부 1 |
| 작성 부분 초안 / 최종 전달 초안 | 6개 / 0개 |

같은 L5 질문·자료·모델을 썼지만 Single은 모델 4/도구 3/180초, Multi는 모델 8/도구 6/240초다. 역할 지시도 달라졌다. 결과 차이를 역할 수 하나의 효과로 단정하지 않는다. 사실 6개·core 경계 6개·Agent 경계 6개의 분모를 유지하고, M01~M04를 새로운 품질 정답으로 더하지 않는다.

별도 writer/reviewer Probe는 Runtime이 검증된 근거를 준비한 뒤 역할 하나를 따로 호출한 기록이다. 입력이 실제 검색자의 Handoff에서 온 통합 성공과 다르다. 해당 모델이 형식상 유효한 응답을 냈더라도 전체 과제를 완수했다고 계산하지 않는다.

**확인 질문**

1. 역할 상한 4+2+3을 더해 전체 9회 실행해도 되는가? 어떤 제한을 함께 확인하는가?
2. A02가 검토까지 도달했으면 과제 성공인가? 무엇이 남았는가?

[실습](<../../../02. 실습/document-assistant/L6.md>)에서 Control·M01~M04·실제 C01/A02를 비교하고, 직접 코드로 전달 거부와 부분 초안을 관찰한다. [강사 해설](강사용.md)은 개념별 판단 이유와 활동 피드백을 제공한다. 다음 Fine-tuning에서는 데이터 설계·분리·검수와 학습을 다룬다. 이번 실패를 튜닝만 하면 해결된다고 가정하지 않고 같은 평가에서 입력/모델/데이터 중 무엇을 바꿀지 판단한다.
