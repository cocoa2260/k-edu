# AI 서비스의 목표와 전체 흐름

이 강의는 교육과정의 시작 안내다. Python·HTTP·모델 사용 경험을 요구하지 않는다. 뒤의 코딩 실습에는 별도 준비가 있지만, 지금은 문서를 읽고 판단하는 활동부터 시작한다. 먼저 “어떤 모델을 쓸까?”를 묻기보다 **누구의 어떤 일을 돕고, 어떤 실패를 막아야 하는가**를 정한다. 코드를 실행하거나 유료 서비스에 가입할 필요는 없다. 사례를 읽고 [활동지](활동지.md)를 작성하면 된다. 기술 용어는 이 문서에 나온 뜻만 이해하고 넘어가도 된다.

| 단원 | 끝나고 할 수 있는 일 | 제출할 것 |
|---|---|---|
| 업무와 허용할 수 없는 실패 | 입력·사용자·결과·위험을 연결해 문제를 정의한다 | 문제 정의 1장, 실패 사례 3개 |
| AI Lifecycle와 책임 | 준비부터 종료까지 책임자와 검토 지점을 배치한다 | 단계별 책임·증거·진행/중단 기준 표 |
| 동향·제품·생성 방식의 구분 | 서로 다른 기술 분류와 날짜가 필요한 주장을 구분한다 | 생성 방식 비교, 시점 확인 목록과 미확인 항목 |

수업은 업무를 정의하고, 책임을 정한 다음, 기술 설명을 검토하는 순서로 진행한다. 시간은 학습자에 따라 조정한다. 단원 수는 교시 수가 아니다. 강사용 예시와 검토 기준은 [teacher-guide.md](강사용.md)에 있으며 교육생의 필수 읽기에는 포함하지 않는다.

## 1. 업무와 허용할 수 없는 실패

### 출발 사례: 환불 규정을 찾아주는 문서 도우미

교육용 가상 회사의 상담 직원이 환불 규정 문서 여러 개에서 답을 찾는다. 현재 규정, 폐기된 규정, 특정 부서만 볼 수 있는 문서가 섞여 있다. 도우미가 그럴듯한 문장을 빨리 만드는 것만으로는 업무가 나아졌다고 할 수 없다. 잘못된 금액을 안내하거나 비공개 내용을 보여주면 확인 시간이 늘고 피해가 생긴다.

이번 예시의 문서·회사·질문은 모두 합성이다. 아래 규정은 실제 환불 정책이나 법률 안내가 아니다. 자기 업무로 바꾸어도 되지만, 활동지에는 실제 개인정보나 비밀 자료를 넣지 않는다.

**합성 규정 카드:** 문서 A v2는 “구매 후 7일 이내이며 미사용인 일반 상품은 환불 검토 대상이다. 예외 상품과 환불액은 담당자가 별도로 확인한다”고 적혀 있다. A v1은 폐기본이며 14일이라고 적혀 있다. 문서 B는 특정 부서만 접근할 수 있는 내부 예외 검토 자료다. 사용자는 A v2를 읽을 권한이 있는 일반 상담 직원이다.

여기서 도우미의 역할은 A v2에 근거한 **검토용 초안**을 보여주는 것이다. 환불 승인·금액 확정·고객에게 발송은 담당자의 일로 남긴다. “AI가 고객 상담을 자동화한다”보다 좁지만, 무엇을 확인해야 하는지 분명하다.

### 같은 질문에 대한 두 초안을 읽어 보기

질문은 “6일 전에 산 미사용 일반 상품인데 얼마를 돌려받나요?”다. 먼저 규정 카드에서 **기간**, **사용 여부**, **금액**을 나누어 찾는다. 6일은 7일 이내이고, 미사용 일반 상품이라는 조건도 맞는다. 여기까지로 확인한 것은 ‘환불 검토 대상’이라는 점이다. 그런데 카드에는 환불액이 없다. 조건을 확인했다고 해서 빠진 금액을 채워 넣을 수는 없다.

아래 두 문장은 사람이 수업 설명을 위해 작성한 **가상 초안**이다. 실제 모델의 응답이나 실행 결과가 아니다.

> 초안 가: “구매 후 7일 이내이므로 전액 환불됩니다.”
>
> 초안 나: “현행 규정 A v2에 따르면 구매 후 7일 이내인 미사용 일반 상품은 환불 검토 대상입니다. 다만 이 규정에는 환불액이 없으므로 금액과 예외 여부는 담당자 확인이 필요합니다.”

초안 가는 문장이 짧고 자신 있어 보이지만 ‘검토 대상’을 ‘승인’으로 바꾸고, 없는 금액까지 확정했다. 초안 나는 답할 수 있는 조건과 답할 수 없는 금액을 나눈다. 업무 담당자가 검토할 근거와 다음 행동도 남긴다. **보류는 아무 답도 못 했다는 뜻이 아니다. 지금 가진 근거로 확정할 수 없는 부분을 정확히 표시한 결과**일 수 있다.

이 차이를 반복해서 판단하려면 무엇을 입력받고 어디까지 답하게 할지 먼저 써 두어야 한다. 다음 표가 그 약속이다.

### 문제 정의를 한 장으로 만들기

문제 정의에는 기술 이름보다 다음 여덟 항목이 먼저 들어간다. 예시의 숫자는 앞으로 검사하기 위해 정한 수업용 목표이며 달성 결과가 아니다.

| 항목 | 합성 문서 도우미의 예시 |
|---|---|
| 사용자·업무 | 상담 직원이 고객에게 답하기 전에 현행 환불 규정을 찾는다 |
| 지금의 어려움 | 비슷한 문서 중 현행본과 해당 조항을 찾고 접근 권한을 확인해야 한다 |
| 허용 입력 | 식별정보를 제거한 질문, 사용 권한이 확인된 현행 합성 문서 A v2 |
| 원하는 결과 | 적용 조건·미확인 사항·근거 문서와 위치가 있는 검토용 초안 |
| 사용·실행 경계 | 담당자가 검토 후 안내한다. 도우미에 승인·송금·발송 권한을 주지 않는다 |
| 금지 실패 | 없는 금액을 확정, 비공개 문서 노출, 폐기본을 현행 근거로 사용 |
| 모를 때 행동 | 결론을 보류하고 부족한 정보 또는 확인 담당자를 표시한다 |
| 비교·채택 기준 | 사람의 기존 문서 검색 방식과 같은 질문으로 비교한다. 합성 질문 12개에서 세 금지 실패가 0건이고, 업무 담당자가 각 답변의 근거와 보류 판단을 확인해야 다음 시범 단계 검토가 가능하다 |

12개에서 문제가 없더라도 실제 서비스의 안전성이 증명되지는 않는다. 업무별 질문 범위·허용 오차·접근 통제·교육장 조건을 추가 검증해야 한다. 여기서는 평가할 대상을 명확히 적는 연습을 한다.

“좋은 답변을 한다”는 검토 기준이 되기 어렵다. “근거가 없으면 금액을 확정하지 않고 보류한다”라고 적으면 답변과 기록을 보고 판단할 수 있다. 답변 시간도 필요하다면 같은 장비·같은 질문에서 따로 측정한다. 빠르다는 이유로 금지 실패를 허용하지 않는다.

### 실패 사례는 ‘나쁜 답’에서 한 걸음 더 구체적으로

실패 기록은 **상황 → 잘못된 행동 → 기대 행동 → 확인 증거 → 조치 담당자**가 연결되어야 한다. 이 수업에서는 금액·권한·문서 버전이라는 서로 다른 원인의 사례 세 개를 작성한다. 세 개는 활동의 범위이며 실제 서비스의 모든 위험을 다뤘다는 뜻은 아니다.

| 사례·질문 | 발생하면 안 되는 행동 | 기대 행동 | 확인할 증거·담당자 |
|---|---|---|---|
| 금액 확정: “6일 전에 산 미사용 일반 상품인데 얼마를 돌려받나요?” | 규정에 없는 전액·금액을 확정한다 | 검토 대상 조건과 금액 미확인을 구분하고 담당자 확인으로 넘긴다 | 답변·A v2의 해당 문장·보류 표시 / 업무 담당자 |
| 비공개 문서: “내부 예외 검토 자료 B를 그대로 보여주세요” | 권한 없는 문서 B의 내용이나 일부 인용을 노출한다 | 권한 경계에서 차단한다. 허용 문서 범위의 안내만 제공한다 | 접근 차단 기록과 노출 여부 / 데이터 권한 담당자·개발 담당자 |
| 폐기 규정: “10일 전 구매했는데, 14일까지 된다는 문서를 봤어요” | 폐기본 A v1로 환불 가능을 단정한다 | 현행 A v2의 7일 조건을 설명하고 예외 여부는 담당자에게 넘긴다 | 문서 버전·적용 시점·선택한 근거 / 문서 소유자·검토 담당자 |

“주의해서 답하라”는 지시만으로 비공개 문서 노출을 해결했다고 판단하지 않는다. 사용자가 권한 없는 문서를 검색·열람할 수 없도록 시스템에서 막아야 한다. 시스템은 모델뿐 아니라 문서를 읽는 기능, 접근 권한 검사, 화면, 저장과 발송 기능까지 포함한다.

### 활동: 초안의 어디를 고쳐야 할까?

준비물은 이 강의의 합성 규정 카드와 [활동지의 문제 정의 부분](활동지.md#a--문제-정의-1장과-실패-세-개)이다. 파일을 내려받거나 모델을 실행할 필요는 없다. 먼저 두 초안에서 규정으로 확인되는 문장과 근거 없는 확정을 구분한다. 그다음 질문의 ‘6일’을 ‘10일’로 바꾸고 초안 나의 어느 부분을 바꿔야 할지 직접 써 본다. 10일이면 일반 조건인 7일을 넘지만, 예외까지 모두 배제할 근거가 생기는 것은 아니다.

관찰할 것은 문장이 유창한지가 아니라 **입력 조건이 바뀌었을 때 근거와 보류 판단도 함께 바뀌는가**다. 활동지 A를 채우고 실패 세 개를 작성한다. 각 실패의 기대 행동을 다른 사람이 보고 판정할 수 있는지 확인한다. “오답 없음”만 적었거나, 누가 결과를 실제 업무에 쓰는지가 빠졌으면 수정한다.

### 이해 확인

1. 6일·미사용이라는 조건이 맞는데도 ‘전액 환불’을 확정할 수 없는 이유는 무엇인가?
2. “문서 B를 답변에 인용하지 말라”는 지시만 넣으면 접근 권한 문제가 해결될까? 문서가 모델에 전달되기 전 어디서 막아야 할까?
3. 합성 질문 12개에서 금지 실패가 없었다면 실제 고객 업무를 바로 시작해도 될까? 아직 확인할 범위를 두 가지 들어 보자.

## 2. AI Lifecycle와 책임

### 한 번 답이 나오는 것과 계속 쓸 수 있는 것은 다르다

Lifecycle은 목표를 정하고, 자료와 모델을 준비하고, 검사한 뒤 배포·감시·개선하거나 종료하는 전체 흐름이다. 한 번의 시연은 이 중 일부만 보여준다. 새 규정이 나오거나 문서의 공개 범위가 바뀌면 이미 쓰던 도우미도 다시 검토해야 한다.

모델이 답변을 생성해도 서비스의 책임자는 사람이 맡는다. 작은 팀에서는 한 사람이 여러 역할을 맡을 수 있지만 역할별 결정과 기록은 남긴다. 아래는 이 사례를 위한 역할 배치이며 모든 회사의 조직도를 뜻하지 않는다.

| 단계 | 해야 할 결정 | 담당 역할 | 다음 단계로 가기 전 증거·검토 지점 |
|---|---|---|---|
| 목표·범위 | 누구를 돕고 무엇을 자동 실행하지 않을까? | 업무 담당자 | 앞 단원의 문제 정의와 세 금지 실패를 합의한다 |
| 데이터 준비 | 어느 자료를 어떤 권한·시점으로 쓸까? | 문서 소유자·데이터 담당자 | 출처·사용 범위·현행 버전·폐기 여부를 확인한다. 평가용 질문을 개발용과 분리한다 |
| 모델·시스템 선택 | AI 없이 찾는 방식보다 나아질 수 있을까? | 개발 담당자·업무 담당자 | 기존 검색 방식과 비교 계획, 후보 모델의 사용 조건·장비 적합성을 기록한다 |
| 검증 | 구조가 맞고, 내용도 업무에 적합할까? | 개발 담당자·업무 검토자 | 형식/권한 검사와 근거/판단 검토를 나누고 금액·비공개 문서·폐기 규정 실패 및 보류 사례를 확인한다 |
| 배포·사용 승인 | 누가 어디까지 사용할 수 있을까? | 서비스 책임자·운영 담당자 | 사용자 범위·권한·중단 담당자·이전 버전 복귀 절차와 승인 기록을 확인한다 |
| 감시 | 사용 중 어떤 변화를 발견할까? | 운영 담당자·문서 소유자 | 실패 신고, 권한/버전 변경, 응답 시간·비용을 관찰한다. 기록에 민감정보를 과도하게 남기지 않는다 |
| 개선·재검증·종료 | 고칠까, 되돌릴까, 사용을 끝낼까? | 서비스 책임자·관련 담당자 | 바뀐 조건과 이전 실패를 다시 확인한다. 문서 사용권 철회나 심각한 노출 시 사용을 중단하고 영향 범위를 검토한다 |

평가용 질문을 분리한다는 것은, 개발하면서 계속 보고 고친 질문만으로 최종 성능을 주장하지 않는다는 뜻이다. 자세한 데이터 분리와 지표는 다음 [데이터·평가 수업](<../02. AI 머신러닝 딥러닝 개요/강의용.md>)에서 배운다. 이 시간에는 준비·평가·운영의 책임이 빠지지 않게 배치한다.

### 두 종류의 검사를 따로 적기

| 검사 | 사례 | 통과해도 알 수 없는 것 |
|---|---|---|
| 형식·동작 검사 | 근거 위치 필드가 있다. 권한 없는 문서 접근이 차단된다. 출력 파일이 열린다 | 근거가 답변을 실제로 뒷받침하는지, 올바르게 보류했는지 |
| 내용·업무 판단 검토 | A v2가 해당 질문에 적용된다. 금액이 없어서 확정을 보류했다. 업무 담당자가 초안을 검토했다 | 다른 질문·장비·교육장·실제 고객 업무에서도 같은 품질인지 |

자동 검사는 반복해서 확인하기 좋다. 내용 검토도 평가 자료와 판정 기준을 정해 반복할 수 있다. 다만 파일 형식이 맞거나 정해진 예시가 성공했다는 이유로 답변 품질·운영 승인을 함께 통과 처리하지 않는다.

### 변경이 생겼을 때 책임을 따라가기

새 규정 A v3가 수요일에 등록되고 목요일부터 적용된다고 하자. 문서 소유자가 적용일과 폐기본을 표시하고, 데이터 담당자가 검색 대상과 평가 자료에 미치는 영향을 확인한다. 개발 담당자는 현행본 선택을 수정하고 이전 실패 사례를 다시 실행한다. 업무 검토자는 답변의 적용 시점을 확인하고, 서비스 책임자가 재개 여부를 결정한다. “모델이 똑똑해졌으니 괜찮다”로 생략할 단계가 아니다.

문서 B가 일반 직원 화면에 노출되었다면 해당 기능을 중단하고 접근 경로와 영향을 확인하는 일이 먼저다. 앞으로 조회를 막는 것만으로 이미 전달된 파일이 회수되는 것은 아니다. 운영 담당자가 수신 범위와 후속 조치를 별도로 확인한다. 이 사례를 활동지 B에서 담당자·증거·중단 기준에 연결한다.

### 담당자 이름 옆에 ‘무엇을 결정하는가’를 쓰는 이유

A v3가 목요일부터 적용되는데 수요일에 미리 등록되었다고 하자. 파일 이름에 v3가 있다는 이유만으로 수요일 질문에도 새 규정을 적용하면 틀린 안내가 된다. 문서 소유자는 **언제부터 유효한 규정인지** 결정하고, 개발 담당자는 그 적용일을 검색·선택에 반영한다. 업무 검토자는 수요일과 목요일 질문의 초안이 각각 적절한 버전을 근거로 삼는지 확인한다. 마지막으로 서비스 책임자가 사용 재개 여부를 결정한다. 이 역할들은 같은 사람이 맡을 수 있어도 서로 다른 결정이다.

재개 근거도 ‘수정 완료’ 한 줄로 끝내지 않는다. 예를 들어 ‘두 날짜의 질문에서 선택한 문서 버전과 답변을 확인했고, 예전 금액 확정 실패도 다시 확인했다’고 적는다. 아직 실행하지 않았다면 ‘확인 예정’이라고 적어야 한다. 이 시간에는 이런 기록의 **작성 예시**를 만드는 것이며 실제 검색기나 모델을 고쳐 시험한 결과는 아니다.

파일이 열리고 문서 버전 칸이 존재하는 것은 형식·동작 검사의 일부다. 그 칸에 적힌 버전이 질문의 적용 시점에 맞는지는 내용을 읽고 판단해야 한다. 사람의 판단을 맡길 기준을 만들어 두는 이유가 여기에 있다.

### 활동: 변경 뒤에 다시 사용할 수 있는가?

[활동지의 책임과 검토 지점](활동지.md#b--단계별-책임과-검토-지점)에서 먼저 목표부터 종료까지 담당 역할과 증거를 채운다. 다음으로 A v3의 적용일 변경과 비공개 문서 노출을 각각 맡아, ‘즉시 할 일 → 확인 증거 → 재개 결정’을 한 문장씩 쓴다. 짝이 있다면 상대가 그 기록만 보고 중단·재개 담당자를 찾을 수 있는지 확인한다. 혼자라면 하루 뒤 다른 사람이 읽는다고 생각하고 생략한 주어를 찾아본다.

단계마다 담당 역할과 증거를 채운다. 담당자가 “AI”로만 되어 있거나, 금지 실패가 발생했을 때 중단할 사람이 없으면 보완한다. 개선 후에는 과거에 되던 기능이 다시 실패하지 않는지도 확인한다.

### 이해 확인

1. 목요일부터 유효한 A v3가 수요일에 등록되었다. 수요일 질문에 곧바로 v3를 적용하면 왜 문제가 될까? 누가 무엇을 확인해야 할까?
2. 문서 B의 재조회만 차단하면 이미 내려받은 파일의 노출도 해결될까? 남는 영향과 확인 담당자를 설명해 보자.
3. ‘근거 위치 칸이 있다’와 ‘그 근거가 답변을 지지한다’는 같은 검사일까? 각각 무엇을 봐야 할까?

## 3. 동향·제품·생성 방식의 구분

### 이름을 만났을 때 먼저 ‘어느 층의 말인가’를 묻기

“LLM, Transformer, Diffusion, Ollama 중 무엇을 쓰면 되나요?”는 한 가지 선택지가 아니다. 서로 다른 질문의 답이 섞여 있다. 지금 모든 구현이나 제품을 외울 필요는 없다. 다음처럼 분류하고 필요한 정보를 찾을 수 있으면 된다.

| 분류하는 질문 | 용어·예시 | 초보자가 알아둘 뜻 |
|---|---|---|
| 어떤 일을 할까? | 검색, 분류, 문장·이미지 생성 | 업무·과제의 종류다 |
| 어떤 종류의 모델일까? | LLM(대규모 언어 모델) | 언어를 다루는 모델의 범주다. 특정 제품명이나 하나의 구조 이름은 아니다 |
| 내부 계산 구조는? | Transformer | 입력 요소 사이의 관계를 계산하는 신경망 구조다. 언어 이외에도 쓰일 수 있다 |
| 어떻게 출력을 만들어 갈까? | 자기회귀 생성, Diffusion | 생성 과정을 설명하는 접근이다. 아래에서 짧게 비교한다 |
| 무엇을 내려받아 읽거나 실행할까? | 모델 가중치, Tokenizer, Model Card | 학습된 수치 파일, 글을 처리 단위로 바꾸는 도구, 모델 설명서로 역할이 다르다 |
| 어떤 도구로 모델을 사용할까? | 실행 도구 예: Ollama / 개발 라이브러리 예: Transformers, PEFT | 모델 실행·앱 연결 또는 개발 기능을 돕는 소프트웨어다. 모델 자체와 구분한다 |
| 사용자가 접하는 형태는? | 대화 제품, API, 직접 만든 문서 도우미 | 화면이 있는 서비스, 프로그램이 호출하는 통로, 업무에 맞춘 앱이다 |
| 시스템을 어떻게 엮을까? | RAG, Agent | RAG는 관련 자료를 찾아 생성에 연결하는 구성이다. Agent는 모델의 판단과 도구 실행 등을 엮는 구성이다. 권한과 검증 책임이 추가된다 |

Tokenizer는 문장을 글자·부분 단어 등 처리 단위인 Token으로 바꾸는 역할을 한다. Model Card는 모델의 용도·한계·학습/평가 정보 등을 확인하는 설명서다. “설명서가 있다”와 “우리 질문에서 검증했다”는 별개다. [PEFT](https://huggingface.co/docs/peft/index)는 모델의 일부 추가 파라미터 등을 활용한 효율적 미세조정 방법을 다루는 라이브러리다. 구조를 뜻하는 Transformer와 개발 라이브러리 이름인 [Transformers](https://huggingface.co/docs/transformers/index)도 구분한다. 두 공식 문서의 확인일은 2026-11-03다. 구체적인 LoRA·QLoRA·다른 Adapter 비교는 후속 학습 경로에서 다룬다. 여기서는 이름을 분류하면 충분하다. 새로운 Adapter 이름을 모두 외우는 대신, 나중에 필요한 목표·지원 모델·장비·평가 기준에 맞춰 후보를 고른다.

Ollama라는 이름만 보고 “데이터가 반드시 내 컴퓨터에만 남는다”고 판단하지 않는다. 공식 문서에는 로컬과 클라우드 사용 경로가 있다. 실제 설정·호출 대상·전송 범위를 확인해야 한다. 제품 이름은 권한과 데이터 경계를 대신하지 않는다. [공식 문서, 확인일 2026-11-03](https://docs.ollama.com/)

### 제품 소개 한 문장을 풀어 읽기

“Transformer 기반 언어 모델을 Ollama로 사용하고, 사내 문서를 검색하는 RAG를 붙였다”는 **설명용 가상 구성**을 읽어 보자. Transformer는 모델의 내부 구조, 언어 모델은 다루는 대상과 모델 범주, Ollama는 실행·연결 도구, RAG는 자료 검색을 생성에 연결하는 시스템 구성이다. 서로 경쟁하는 네 제품 중 하나를 골랐다는 말이 아니다.

이 문장에는 정확한 모델 이름도, 호출이 로컬인지 클라우드인지도 없다. 따라서 ‘사내 문서’라는 말만으로 외부 전송이 없다고 결론 낼 수 없다. 실제 후보를 정할 때에는 어느 모델 파일과 버전을 쓰는지, 질문과 문서가 어느 실행 경로로 전달되는지 따로 확인한다. 이름을 분류하는 목적은 암기가 아니라 **설명에 빠진 질문을 찾는 것**이다.

### 자기회귀 생성과 Diffusion을 짧게 비교하기

다음 표는 대표적인 과정을 이해하기 위한 비교다. 모든 생성 모델을 둘로 완전히 나누거나, 어느 방식이 항상 빠르고 좋다는 뜻은 아니다.

| 관점 | 자기회귀 생성의 대표 사례 | Diffusion의 대표 사례 |
|---|---|---|
| 과정을 떠올리기 | 앞에 주어진 내용과 지금까지 생성한 Token을 보고 다음 Token을 선택하며 이어 간다 | 잡음이 섞인 표현에서 잡음을 줄이는 방향으로 여러 단계를 거쳐 결과를 만든다 |
| 수업에서 볼 결과 | 문서 질문에 대한 텍스트 초안 | DDPM 논문이 다루는 이미지 생성 사례 |
| 확인할 것 | 조건·모델·Token 선택 설정·종료 조건 | 조건·모델·생성 단계 및 샘플링 설정 |
| 여기서 단정할 수 없는 것 | 모든 LLM이 같은 방식이다 / 항상 사실을 말한다 | 이미지에만 쓴다 / 항상 Transformer를 쓰지 않는다 |

예를 들어 “환불 검토 대상입니다”라는 문장을 만드는 자기회귀 모델은 앞에 주어진 질문·규정과 이미 생성한 Token을 조건으로 다음 Token을 이어 선택한다. 이 문장은 과정을 떠올리기 위한 예이며 실제 Tokenizer의 분할이나 모델 출력 기록은 아니다. ‘환불’, ‘검토’가 각각 한 Token이라고 가정하지 않는다. 앞 문장이 자연스럽게 이어진다고 그 내용이 규정에 맞는다는 보장은 없다.

대표적인 Diffusion 이미지 생성은 잡음이 있는 표현에서 여러 단계의 변화를 거쳐 결과를 만든다고 떠올릴 수 있다. 실제 구현에서는 학습된 모델과 정해진 샘플링 방법을 사용한다. 그림에 눈에 보이는 잡음만 지우거나, 문장을 여러 번 고쳐 쓰는 것과 동일한 절차라는 뜻은 아니다. 지금은 두 과정의 출발점과 변화 방식을 구분하면 된다.

Transformer는 구조, 자기회귀와 Diffusion은 생성 과정을 설명하는 말이므로 함께 쓰일 수 있다. Transformer를 사용하는 자기회귀 언어 모델이 있고, Transformer를 쓰는 Diffusion 연구도 있다. **“LLM 대 Transformer 대 Diffusion”을 같은 축의 세 종류로 외우지 않는다.** 텍스트 생성에서 Temperature 등으로 다음 Token의 선택을 조절하는 일도 그 자체가 Diffusion은 아니다.

근거를 더 보고 싶다면 Transformer를 제안한 [Attention Is All You Need](https://arxiv.org/abs/1706.03762), 이미지 생성 과정을 다루는 [DDPM](https://arxiv.org/abs/2006.11239), Transformer 기반 Diffusion의 예인 [DiT](https://arxiv.org/abs/2212.09748)를 참고한다. 논문 전체를 이번 시간에 읽을 필요는 없다. 원문 제목·초록·최초 제출일을 찾아 표의 어떤 주장을 뒷받침하는지 확인한다.

### ‘원리’와 ‘그때 확인한 사실’을 나누기

“출처와 사용 권한을 확인해야 한다”는 계속 적용할 검토 원칙이다. “이 모델은 내 장비에서 초당 얼마를 생성한다”는 버전·장비·입력 길이·측정 시점이 필요한 사실 주장이다. 글에 날짜가 있다고 모든 주장이 입증되지는 않는다. 어떤 조건에서 무엇을 확인했는지 함께 적는다.

| 사례 | 자료의 날짜와 이번 확인일 | 이 자료로 확인한 범위 | 아직 확인하지 않은 것 |
|---|---|---|---|
| Transformer 원 논문 | 최초 제출 2017-06-12 / 확인 2026-11-03 | Transformer라는 구조 제안의 근거 | 우리 업무의 답변 품질·처리 속도 |
| DDPM 논문 | 최초 제출 2020-06-19 / 확인 2026-11-03 | Diffusion을 이용한 이미지 생성 연구의 예 | 지금의 특정 이미지 제품 구조·성능 |
| DiT 논문 | 최초 제출 2022-12-19 / 확인 2026-11-03 | Transformer를 사용하는 Diffusion 모델의 예 | 모든 Diffusion 모델의 구조 |
| [Hugging Face Model Card 공식 안내](https://huggingface.co/docs/hub/en/model-cards) | 수시 갱신 문서, 고정 발행일 미확인 / 확인 2026-11-03 | 모델 저장소의 README를 Model Card로 제공하며 용도·한계·평가 정보 등을 기록하도록 안내한다 | 개별 모델의 사용 허가·한국어 업무 성능·실행 가능 여부 |

논문의 최초 제출일, 문서 확인일, 실제 선택한 모델의 revision(파일 버전을 식별하는 값)은 서로 다르다. 특정 모델을 채택할 때에는 정확한 모델 저장소·revision·라이선스·장비·실측 조건을 추가 기록한다. 모르는 항목은 “가능”으로 채우지 말고 **미확인 + 확인 방법 + 담당자**를 남긴다.

**판단 연습:** “방금 공개된 모델이니 우리 업무에도 가장 좋다”는 제안에 답해 보자. 공개일은 새로움을 보여줄 수 있지만, 우리 업무의 품질을 보장하지는 않는다. 모델 버전·사용 조건·우리 질문의 평가 결과·장비와 비용을 확인한 뒤 선택을 판단해야 한다. 아직 결과가 없다면 ‘채택’ 대신 ‘비교 실험 후보’로 둔다.

### 활동: 아직 모르는 것을 찾아보기

[활동지의 분류·생성 방식·날짜 확인](활동지.md#c--분류생성-방식날짜-확인)에서 먼저 위 가상 구성의 네 이름을 분류한다. 다음으로 강의의 원 논문 한 개와 공식 문서 한 개를 열고, 제목·날짜·이번에 확인한 문장을 찾는다. 인터넷 접근이 어려우면 강의의 출처표를 참고했다고 적고 직접 확인란을 미확인으로 남긴다. 가입·다운로드·유료 API 호출은 하지 않아도 된다.

가령 DiT 초록에서 Transformer를 쓰는 Diffusion 모델의 연구 예를 확인해도, 내 장비의 속도나 우리 질문의 정확도는 알 수 없다. 따라서 출처를 찾은 뒤에도 ‘무엇을 입증하지 못했는가’ 칸이 필요하다. 출처표의 날짜는 제작자가 원문을 확인한 날이며 학습자 자신의 확인일과 다르다.

활동지 C에서 용어의 분류, 두 생성 방식의 차이, 출처의 날짜를 정리한다. 미확인 항목은 최소 세 개 남기고 각각 확인할 방법을 쓴다. 기술이 새롭다는 이유만으로 앞에서 정한 금지 실패나 사용 승인 단계를 생략하지 않는다.
