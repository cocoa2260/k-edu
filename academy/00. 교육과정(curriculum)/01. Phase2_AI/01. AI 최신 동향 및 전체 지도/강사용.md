# 강사용 안내 · 사례 검토와 피드백

교육생은 [강의](강의용.md)와 [활동지](활동지.md)만 사용하면 된다. 이 문서는 강사의 예시·진행·평가 참고다. 목표는 기술 이름 암기나 자동 채점이 아니라 업무의 목표·실패·책임·확인 범위를 설명하게 하는 것이다. 아직 실제 교육생 수업이나 독립 강사 검토를 수행한 자료는 아니다.

## 진행 방법

1. “환불 규정을 찾아 답하는 것”과 “환불을 승인하는 것”을 구분하게 한다. 강의의 합성 A v2·A v1·B 카드만 사용한다.
2. 문제 정의표를 쓴 뒤 세 실패 중 하나를 짝에게 설명하게 한다. 짝은 “어떤 답변이면 통과이고 어떤 증거를 볼 것인가”를 묻는다.
3. 책임 역할표에서 빠진 담당자와 중단 조건을 찾게 한다. AI 자체를 최종 책임자로 적으면 실제 결정을 맡을 사람/역할로 바꾸게 한다.
4. 기술 분류 단원에서는 이름을 분류하고 “Transformer를 쓰는 Diffusion”을 설명하게 한다. 논문 계산식이나 Adapter 전체 목록 암기를 요구하지 않는다.
5. 완료·미확인·미실행을 분리하여 제출하게 한다. 예상 소요 시간은 수업 시범 후 조정한다. 현재 측정한 학습 시간은 없다.

## 업무와 허용할 수 없는 실패 — 예시 해설

문제 정의의 결과는 “일반 상담 직원에게 권한 있는 현행 A v2의 근거와 미확인을 포함한 초안을 제공하고, 담당자가 검토하여 안내한다” 정도면 좋다. 업무가 다른 경우에도 입력·사용자·결과·금지 실패·보류·평가 범위가 연결되면 인정한다.

| 사례 | 가능한 적절한 응답·동작 | 잘못 판정하기 쉬운 점 |
|---|---|---|
| 금액 확정: 6일·미사용·금액 질문 | “일반 상품은 검토 대상 조건에 해당하지만 환불액은 이 규정으로 확정할 수 없다. 예외 상품과 금액은 담당자가 확인한다.” A v2 근거를 함께 표시한다 | ‘6일’이라는 숫자가 있다는 이유로 전액 환불을 확정하지 않는다. 금액 보류를 오답으로 처리하지 않는다 |
| 비공개 문서: B 요청 | B 접근을 차단하고 권한 있는 자료 범위에서만 안내한다. 노출 여부와 접근 검사 기록을 검토한다 | 출력에서 문구를 숨겼어도 권한 없는 본문이 모델에 넘어갔다면 경계를 해결한 것이 아니다 |
| 폐기 규정: 10일·14일 질문 | 폐기본 A v1을 현행 기준으로 쓰지 않고 A v2의 7일 조건을 밝힌다. 예외 여부는 담당자 확인으로 남긴다 | 7일이 지났다고 모든 예외까지 포함해 ‘무조건 환불 불가’라고 단정하지 않는다 |

활동지의 세 실패가 모두 단순 오타라면 권한·버전·내용 등 서로 다른 원인을 포함하도록 피드백한다. 다른 업무에서는 그 업무의 실제 영향에 맞게 바꾸어도 된다. 강의의 합성 12문항 기준은 설계 예시다. 12문항을 실행한 성적표로 평가하지 않는다.

## AI Lifecycle와 책임 — 변경 대응의 예시

| 변경 | 먼저 할 일 | 재개 조건과 남는 한계 |
|---|---|---|
| A v3 발행 | 문서 소유자가 발효일을 확인한다. 데이터 담당자는 현행본·폐기본 목록, 개발 담당자는 검색과 적용 시점 선택을 갱신한다 | 업무 검토자가 변경 질문과 과거 실패를 다시 검토하고 서비스 책임자가 재개를 승인한다. 아직 배포하지 않았다면 배포 보류로 표현해도 된다 |
| B 내용 노출 | 운영 담당자가 해당 기능을 중단하고 권한 담당자·개발 담당자가 접근 경로와 영향을 확인한다 | 권한 경계·재발 방지·영향 대응을 검토하고 책임자가 재개를 결정한다. 이미 전달된 파일의 수신·회수 가능성은 별도 확인한다 |

모든 단계가 한 방향으로 한 번만 흐르는 그림을 강요하지 않는다. 검증 실패는 데이터 준비·모델/시스템 선택으로 되돌아갈 수 있다. 개선과 재검증 후에도 사용권이 없거나 업무 기준을 만족하지 못하면 종료가 유효한 선택이다.

역할을 여러 사람이 나누거나 소규모 팀의 한 사람이 겸임해도 된다. ‘누가 결정하고 무엇을 남기는가’가 핵심이다. 실제 고위험 업무의 조직 정책·법적 검토는 별도다. 이 수업의 역할표만으로 운영 승인을 부여하지 않는다.

## 동향·제품·생성 방식 — 예시 해설

| 이름 | 예시 분류 | 여기서 알 수 없는 것 |
|---|---|---|
| LLM | 언어 모델의 범주 | 특정 구조·제품·우리 업무 성적 |
| Transformer | 신경망 구조 | 생성 방식·용도·안전성 전체 |
| Diffusion | 생성 모델링/생성 과정의 접근 | 모든 모델의 구조·제품별 성능 |
| Model Card | 모델 설명 자료 | 기재 내용의 완전성·실제 사용 허가·우리 환경 성적 |
| Ollama | 모델 실행·앱 연결을 돕는 소프트웨어 | 실제 호출이 로컬인지 클라우드인지·데이터 전송 범위 |
| RAG | 검색을 생성에 연결하는 시스템 구성 | 검색한 내용의 적합성·권한 보장·답변 정확성 |

자기회귀 예시는 앞의 Token을 조건으로 다음 Token을 이어 선택한다고 설명하면 된다. Diffusion 예시는 잡음이 있는 표현에서 잡음을 줄이며 생성한다고 설명하면 된다. Transformer는 이런 계산을 수행할 구조의 한 선택이므로 Diffusion과 함께 사용할 수 있다. DiT 원 논문이 반례가 된다. ‘Transformer는 LLM, Diffusion은 이미지 전용’이라는 양분은 보완한다.

날짜 예시: Transformer 원 논문의 최초 제출일 2017-06-12와 학습자가 확인한 날짜는 다른 칸에 쓴다. 논문 페이지의 개정일도 최초 제출일과 혼동하지 않는다. 수시 갱신 공식 문서의 고정 발행일을 못 찾았다면 ‘미확인’을 인정한다. 강의의 확인일을 학습자 자신의 직접 확인일로 복사하지 않게 한다.

후보 모델 미선정일 때 ‘revision 미확인, 후보 선정 뒤 저장소 커밋 식별값 확인, 개발 담당자, 채택 보류’처럼 쓰면 된다. 한국어 질문 품질·라이선스·장비/비용도 확인 방법과 담당자를 붙이면 된다. 최신이라는 주장만으로 채택하지 않고 비교 후보로 남기는 답을 인정한다.

## 제출물 검토 기준

항목별로 **충족 / 보완 / 미제출**을 기록하고 근거 문장을 남긴다. 점수 합계로 금지 실패를 상쇄하지 않는다. 다른 업무의 답은 아래 조건을 만족하면 인정하며, 정답 문구와 일치할 필요는 없다.

| 항목 | 충족 조건 | 보완이 필요한 사례 |
|---|---|---|
| 문제 정의 | 입력·사용자·출력·사용 경계·위험·보류·비교 기준이 한 업무로 연결됨 | ‘AI 자동화’만 쓰고 결과를 사용할 사람이 없음 |
| 실패 3개 | 서로 다른 원인, 기대 행동·증거·담당자가 있음 | ‘잘 답하기’만 적거나 세 사례가 모두 같은 오류 |
| 책임과 검토 | 준비·선택·검증·배포·감시·개선/종료에 역할과 증거·진행/중단 기준이 있음 | 모델에게 최종 책임을 맡기거나 중단/종료 역할이 없음 |
| 검사 구분·변경 | 형식 검사와 내용 검토를 구분하고 버전 변경·노출에 대응함 | 파일이 열렸으므로 업무 품질도 통과라고 주장함 |
| 분류·비교 | 범주·구조·생성 접근·도구·설명서·시스템 구성을 구분함 | LLM/Transformer/Diffusion을 같은 축의 배타적 종류로 나눔 |
| 출처·미확인 | 논문·공식 문서의 근거 범위와 날짜를 구분하고 미확인 3개 이상에 확인 계획이 있음 | 공개일만으로 최고 성능을 주장하거나 확인하지 않은 실행을 완료로 씀 |

**필수 보완 조건:** 권한 없는 자료 사용을 허용함, 사람의 검토 없이 환불 승인·송금·발송을 허용함, 금지 실패를 알면서 진행함, 단계별 사람 책임자가 없음, 날짜/조건 없이 ‘최신이므로 채택’을 주장함. 이 경우 관련 항목을 충족으로 표시하지 않고 수정 후 다시 검토한다. 실제 서비스 승인 여부는 이 제출물 평가와 별도다.

독립 수업에서는 이해가 막힌 용어, 활동지 작성 시간, 강사 도움 횟수, 판정이 갈린 사례와 보완 이유를 기록한다. 아직 이 검증은 수행하지 않았다. 제작 세션의 자체 검토와 구분하여 후속 결과에 남긴다.

## 새 활동을 설명하는 순서와 피드백

초안 가·나를 읽을 때는 먼저 학습자에게 ‘더 마음에 드는 문장’을 고르게 하지 않는다. 규정의 기간·사용 여부·금액 정보를 각각 찾아 표시한 뒤, 각 초안의 어느 문장이 그 정보로 뒷받침되는지 묻는다. 초안 나는 실제 실행 결과가 아니므로 모델이 정확해졌다고 설명하지 않는다.

10일로 바꾼 답은 ‘현행 A v2의 일반 조건인 구매 후 7일 이내를 넘습니다. 이 규정만으로 예외 적용이나 환불액을 확정할 수 없으니 담당자 확인이 필요합니다’처럼 쓸 수 있다. 초안을 똑같이 복사했거나 ‘무조건 불가’로 바꿨다면 각각 입력 변화·예외 범위의 근거를 다시 찾게 한다.

변경 활동의 v3는 목요일 발효라는 가정만 주어졌다. 새 환불 기간이나 금액을 만들어 채우면 보완한다. 수요일 질문은 그 시점에 유효한 v2, 목요일 질문은 v3의 실제 적용 범위를 확인해야 한다. v3 본문이 없으므로 새 답변 내용까지 확정할 수 없다. 등록일과 발효일이 다르다는 판단을 확인한다.

분류 활동에서는 가상 구성 한 문장에 정확한 모델·호출 경로가 빠졌음을 찾게 한다. ‘Ollama이므로 로컬’이라고 쓰면 실제 선택 경로와 전송 범위를 확인하도록 되묻는다. Model Card나 문서의 링크를 찾은 것과 모델 실행·권한·품질 확인을 구분한다. 이번 제작자는 2026-11-03에 강의의 일곱 원문 페이지를 확인했으며, 학습자는 자신의 확인 여부·날짜를 따로 기록한다.

## 단원별 이해 확인 — 해설과 판단 근거

### 업무와 허용할 수 없는 실패

1. **조건 충족과 금액 확정은 다른 판단이다.** 카드에는 검토 대상 조건만 있고 환불액은 없다. ‘검토 대상’에서 ‘전액 승인’으로 넘어가는 근거가 없음을 설명하면 된다.
2. **권한은 검색·읽기·모델 전달 전에 집행해야 한다.** 출력 지시는 우회·실패할 수 있고, 답변에 안 보여도 본문이 모델이나 외부 서비스에 전달되었을 수 있다. 실제 경계 검증은 후속 구현 과제이며 이 활동에서 구현했다고 보지 않는다.
3. **작은 합성 질문 집합의 성공은 그 범위의 관찰이다.** 실제 질문 분포·변경 규정·권한 조합·장비·운영 대응 등 추가 확인이 남는다. ‘무조건 안전’이라는 확대 해석을 하지 않으면 된다. 12개는 실행 성적이 아니라 설계 예시다.

### AI Lifecycle와 책임

1. **등록일은 발효일과 다르다.** 문서 소유자의 적용일 결정, 데이터/개발 담당자의 선택 반영, 업무 검토자의 날짜별 근거 확인, 책임자의 재개 결정을 나누어 말하면 된다. v3 본문을 추측한 답은 인정하지 않는다.
2. **향후 접근 차단과 이미 전달된 정보의 영향 대응은 다르다.** 운영·권한 담당자가 수신/노출 범위와 후속 대응을 확인하고 책임자가 재개를 결정한다. 파일 회수 가능성을 보장하거나 이번 표 작성으로 해결됐다고 하지 않는다.
3. **칸의 존재와 근거의 적합성은 다르다.** 전자는 필드·접근·파일 동작 등 검사를, 후자는 질문 조건과 원문이 주장에 맞는지 검토를 요구한다. 둘 다 필요하고 하나로 다른 하나를 대신하지 않는다.

### 동향·제품·생성 방식의 구분

1. **구조·도구·시스템 구성이 섞였다.** 같은 시스템 안에 함께 쓰일 수 있다. 명칭 분류만으로 정확한 모델·전송 범위·업무 성적을 알 수 없음을 덧붙이면 좋다.
2. **DiT는 Transformer 기반 Diffusion 연구의 예다.** ‘사용 불가’라는 일반 주장의 반례가 되지만 현재의 모든 이미지 제품 구조나 우리 장비 속도를 입증하지는 않는다. 논문 초록의 연구 범위와 제품 실측을 나누어야 한다.
3. **최초 제출일은 논문 공개 시점, 확인일은 내가 페이지를 읽은 시점, revision은 선택한 모델 파일 버전을 식별하는 값이다.** 셋 중 하나가 새롭다고 나머지 사용 조건·업무 품질이 확인되는 것은 아니다.
