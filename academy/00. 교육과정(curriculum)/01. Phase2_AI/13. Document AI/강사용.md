# 문서 등록과 근거 보고서 수업 해설

[문서 입력/상태](<01. 문서 등록.md>)와 [보고서](<02. 근거 보고서.md>), [실습](<../../02. 실습/document-assistant/L9.md>)의 질문과 활동을 해설한다. 아래 결정은 가상 자료와 로컬 검토자 시연이며 독립적인 업무 승인·실제 수업 검증이 아니다.

## 형식과 원본 연결

1. **IR은 공통 처리할 내용과 원본 위치를 담고, Chunk는 그중 검색에 넣을 부분, Locator는 원본으로 돌아갈 정보다.** 표 행렬을 IR에 저장했다고 행/열 조건을 이해하는 검색이 끝난 것은 아니다. PDF의 텍스트 줄에는 두 열의 문장이 섞여 있고, 표는 별도 Element로 남는 현재 예제를 짚는다.
2. **원본의 금액은 빈 줄을 포함한 3번째 줄이다.** 검색 문장이 두 개만 남아도 TXT Locator는 line=3이어야 한다. PDF는 물리 페이지/영역, DOCX는 본문 블록·표 셀의 구조 위치를 쓴다. 파일 형식이 다른데 가짜 페이지 좌표로 맞추면 원문 검토가 틀어진다.
3. **파일을 열었다는 사실은 모든 보이는 내용을 지원한다는 증거가 아니다.** 현재 DOCX는 단순 본문 문단과 병합 없는 직사각 표의 좁은 범위다. 그림/머리말·자동 번호·지원하지 않는 구조를 거부한다. 최초 PDF/TXT 기록의 미지원 표를 현재 코드의 사실로 복사하지 않는다. HWP/HWPX는 계속 미지원이며 확장자 변경은 변환이 아니다.

실습 intake 모드는 실제 저장된 디지털 PDF·단순 DOCX와 임시 TXT를 사용한다. 현재 고정 예제의 Element 수는 PDF 11, TXT 2, DOCX 16이다. 이를 외울 합격 기준으로 쓰지 말고 PDF 표 1개·TXT 빈 줄·DOCX 문단/셀 등 무엇을 센 것인지 설명하게 한다. 세 형식을 받는 것이 일반 문서 품질·모델 답변·전체 통합 채택을 증명하지 않는다.

## 상태와 재전송

1. **같은 키/같은 입력은 이전 요청의 재전송이므로 버전을 늘리지 않는다.** 같은 키로 바이트·제목 등 지문을 바꾸면 충돌이다. 새 키로 등록하면 같은 바이트라도 새 내부 버전이다. 바이트 중복 제거와 요청 중복 방지는 다른 정책이다. 오래된 요청이 현재 버전/권한/삭제 상태와 맞지 않으면 재전송도 거부한다.
2. **uploaded는 원본 보관, parsed는 추출, indexed는 검색 준비다.** parsed까지만 마치면 검색에 나오지 않는다. 새 버전 등록은 옛 Chunk를 제거하고 다시 uploaded에서 시작한다. review는 검토 대상으로 표시한 상태이며 특정 보고서 명세의 approve와 다르다. index/review 전이도 generation을 바꾸므로 이미 고른 선택은 다시 검색해야 할 수 있다.
3. **삭제/제한 뒤 옛 요청을 성공으로 돌려주면 자료가 부활할 수 있다.** 현재 저장소는 원본/IR/검색 내용·제목/해시를 비우고 ID/버전 삭제 흔적과 요청 지문을 남겨 재등록/재전송을 막는다. 사용자 PC 원본·외부 사본·백업까지 보안 삭제한 것은 아니다. 고정 staff도 실제 사용자 인증이 아니다.

PC 파일만 14일로 수정했을 때는 업로드 사본의 7일이 남는다. 자동 감시 서비스가 아니기 때문이다. 새 요청으로 등록한 뒤 기존 selection이 거부되고 새 버전을 parse/index/review한 다음 14일로 확인하는 흐름을 끝까지 따라가게 한다. 한 문서의 변경으로 이전 선택 전체를 거부하는 generation 정책은 보수적인 실습 선택이다.

## 주장과 검토·출력

1. **prepare는 출처와 인용 연결을 검사하고 의미 모순을 판정하지 않는다.** 실제 7일 원문 인용을 붙인 30일 주장도 명세로 만들어질 수 있다. 검토자가 이유를 적어 reject해야 한다. 반대로 모든 자동 검사를 통과했으니 approve를 주는 활동으로 바꾸면 수업 목적을 놓친다. PDF의 미사용/사용 이력 행을 혼동한 금액도 같은 기준으로 본다.
2. **검토는 ID가 아니라 내용 명세 해시에 묶인다.** 문장·인용·출처/버전·Locator·템플릿·generation이 바뀌면 현재 명세와 승인 대상이 달라진다. 같은 Claim ID만으로 승인을 재사용하지 않는다. 원본 14일 새 버전은 다시 추출/색인/검토하고 문장/인용·명세를 새로 만든다. 문서 review만으로 보고서 출력이 허용되는 것은 아니다.
3. **저장·텍스트·화면은 서로 다른 검사다.** DOCX XML에 한글이 있어도 렌더러 글꼴 문제로 화면에서 빠질 수 있다. 출력 전후 현재성/승인 검사도 필요하다. 삭제가 출력 도중 일어나면 최종 폴더를 남기지 않지만 이미 외부에 복사한 파일의 회수를 구현한 것은 아니다. 단일 로컬 staging 검사를 동시 발행/취소 전체 원자성으로 확대하지 않는다.

기존 두 Claim 파일은 템플릿 v1의 출력/검토 기록이다. 현재 코드는 DOCX Locator를 다루는 v2다. 과거 spec의 template 필드만 고쳐 검토를 재사용하지 말고 현재 원문에서 새 명세/검토를 준비한다. 기존 바이너리는 역사적 관찰 자료이며 현재 렌더링을 새로 검증했다고 쓰지 않는다.

## 활동 피드백

| 활동 | 충분한 설명 | 보완할 오해 |
|---|---|---|
| 원본/IR/Locator | PDF 영역·TXT 3번째 줄·DOCX 구조 위치와 검색 대상 차이 설명 | 파일 열기나 표 저장을 의미 이해 완료로 간주 |
| 같은 요청/새 버전 | 재전송/충돌/새 버전/권한 제한/삭제 뒤 결과와 이유 설명 | 같은 파일이면 항상 같은 버전이라고 가정 |
| 주장과 결정 | 7일 인용+30일 주장을 의미 불일치로 거부 | 출처가 있으면 사실이라고 자동 승인 |
| 변경 뒤 출력 | 승인한 내용과 현재 출처가 달라지면 차단 이유 설명 | review 상태·과거 approve만으로 계속 출력 |
| 저장 출력 관찰 | 내용/위치/해시와 화면·현재 템플릿 차이 구분 | 과거 파일을 새 실행/독립 승인으로 표시 |

실습 도구는 임시 SQLite와 TXT를 만들고 정리하며 DOCX/PDF를 생성하지 않는다. 실제 출력 선택 과제에는 글꼴과 별도 새 폴더가 필요하다. 실제 실행 여부를 제출물에서 나누고, 고정 검토자는 같은 Work 작성자가 정한 역할임을 명시한다.
