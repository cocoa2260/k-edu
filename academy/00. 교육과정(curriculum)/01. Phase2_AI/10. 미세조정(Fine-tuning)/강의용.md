# 무엇을 학습시킬지 정하고, 정답 데이터를 준비하기

자료에는 회의실 한도가 2시간이라고 있는데 모델은 늘 ‘자료가 부족합니다’라고 답한다. 최신 규정을 몰라서일까, 받은 자료를 활용하는 행동이 부족해서일까? 이 둘을 구분하지 않고 학습부터 시작하면 오래된 금액을 외우게 하거나 잘못된 거부를 반복해서 가르칠 수 있다.

**이번 수업은 바꾸려는 행동→교사 예제→데이터 분리/증강→학습할 Token 범위까지 연결한다.** 앞의 RAG·Agent 실패가 튜닝으로 해결된다는 결론은 아니다. 실제 훈련과 Adapter 저장/재로드는 [다음 강의](training.md)에서 다룬다. 기존 훈련 증거는 보존하며 이 준비 수업에서 새로 훈련했다고 표시하지 않는다.

예제는 [가상 시설 규정 데이터](../../practice/document-assistant/data/finetuning-v1/README.md)다. 실제 기관/개인 자료가 아니며 교사가 작성한 정답 초안이다. [연결 실습](../../practice/document-assistant/L7.md)에서는 필요한 예제를 골라 보고 현재 검수 함수를 실행한다.

## 1. 행동 목표와 Parameter 변경 방법은 다른 선택이다

Prompt는 지금 입력할 지시를 바꾸고, RAG는 지금 참조할 자료를 찾아 넣는다. Fine-tuning은 예제를 사용해 학습 가능한 Parameter를 갱신한다. 따라서 매일 바뀌는 규정은 현재 자료 제공/갱신부터 확인하고, 도구의 권한 검사는 실행기를 고쳐야 한다. 학습이 잘못된 접근을 막는 인증 시스템을 대신하지 않는다.

이번 가설은 ‘근거가 있으면 조건/예외와 함께 답하고, 사용자 조건이 없으면 묻고, 기준이 없으면 보류하며 권한이 없으면 거부하는 행동’을 연습시키는 것이다. 숫자를 기억시키는 것만이 목표가 아니다. 같은 질문에서 Base와 학습 후 응답을 비교해 행동이 바뀌었는지 확인해야 한다.

| 관찰한 실패 | 먼저 확인할 것 | 학습 전에 필요한 판단 |
|---|---|---|
| 최신 금액이 입력에 없음 | 검색·원본/Index·Context | 필요한 자료를 주지 않은 문제인가? |
| 근거가 있어도 반복 보류 | 실제 지시·응답·모델/설정 | 올바른 행동 예제를 만들 수 있는가? |
| JSON 필드 반복 누락 | 계약·파서·형식 예시 | 형식 학습 후보이나 의미 품질도 따로 확인 |
| 승인 없는 도구 실행 | Runtime 정책/권한 | Parameter 변경으로 대체할 검사가 아님 |

SFT는 교사 응답을 주어 그 응답을 예측하도록 학습하는 방식이다. Instruction tuning은 지시-응답 예제를 쓰는 SFT의 한 형태다. 선호 학습은 더 나은 응답 등의 비교 신호를 쓰는 별도 학습 방식이며 하나의 알고리즘 이름이 아니다. 이번에는 교사 응답을 사용하는 SFT 데이터를 준비한다.

LoRA는 SFT와 경쟁하는 목표 이름이 아니다. **SFT는 무엇을 정답으로 배우는가, LoRA는 어떤 Parameter를 바꾸는가**에 관한 선택이다. PEFT는 전체 Parameter보다 작은 부분을 학습하는 방법들을 묶은 계열/라이브러리다. LoRA도 잘못된 정답을 주면 잘못된 행동을 배울 수 있다.

| 변경 방법의 지도 | 주로 바꾸는 것 | 지금 알아둘 차이 |
|---|---|---|
| Full fine-tuning | Base 전체 Parameter | 학습/저장 자원 부담이 큼 |
| 일부 Layer/LayerNorm/Token 조정 | 선택한 기존 부분 | 전체를 바꾸는 것과 다름 |
| Prompt tuning/Soft Prompt | 입력에 붙이는 학습 가능한 연속 벡터 | 사람이 지시 문장을 고치는 Prompt engineering과 다름 |
| Prefix tuning/P-tuning | Prefix·Prompt 관련 학습 구조 | 같은 이름의 일반 텍스트 접두어와 구분 |
| LoRA | 동결 Weight에 더할 저랭크 갱신 | 다음 실제 훈련의 기준선 |
| IA3 | 내부 활성값을 조절하는 학습 벡터 | 갱신 구조가 LoRA와 다름 |
| AdaLoRA/DoRA 등 | 랭크 배분·갱신 표현의 변형 | 목적/지원 모델을 읽고 필요할 때 하나 비교 |
| QLoRA | 양자화한 동결 Base와 LoRA 학습 구성 | 양자화 추론만 돌린 것과 다름 |

Hugging Face의 Adapter 목록을 전부 외우고 시작할 필요는 없다. 먼저 목표·자원·호환 조건을 정하고 기준선 하나와 대안 하나를 같은 평가로 비교한다. 학습 Parameter가 적어도 Base·활성값·Gradient·Optimizer 메모리는 필요하다. 준비 코드가 CPU에서 실행됐다고 교육생 GPU에서 QLoRA 훈련도 가능하다는 뜻은 아니다.

**확인 질문**

1. SFT와 LoRA는 각각 어떤 결정을 나타내는가?
2. 규정이 검색 입력에 없거나 승인 검사가 빠진 문제를 바로 학습으로 해결하면 어떤 문제가 남는가?
3. Soft Prompt는 좋은 지시 문장을 자동 작성하는 기능인가? 양자화 추론 성공이 QLoRA 학습 성공인가?

## 2. 원문 하나에서 다섯 가지 정답 행동 만들기

원문은 ‘연구실 회의실의 이용 한도는 2시간이다. 사전 예약이 필요하며 음식 반입 금지 규칙이 적용된다.’다. 자료를 참조하는 RAG 원문과, 입력/바람직한 응답을 짝지은 훈련 예제, 학습 후 확인할 평가 문항은 역할이 다르다. 대화 로그를 통째로 넣는 것으로 정답 데이터 제작이 끝나지 않는다.

다음은 **같은 원문에서 교사가 작성한 예제들의 내용**이다. 모델이 생성해서 맞힌 답이 아니다.

| 사용자 질문의 상황 | 바람직한 행동/정답 내용 | 판단 이유 |
|---|---|---|
| 이용 한도와 조건 요청 | answer:2시간·예약·음식 반입 금지, 원문 인용 | 답할 근거가 있음 |
| 무제한으로 쓸 수 있지? | answer:무제한이 아니며 2시간, 조건/예외 교정 | 잘못된 전제를 그대로 학습하지 않음 |
| 지금 이용할 수 있어? 예약 상태 미제공 | clarify:사전 예약을 완료했는지 질문 | 자료 부족이 아니라 사용자 조건 불명확 |
| 분실 보상금은 얼마? | abstain:제공 규정에 기준 없음 | 수치를 만들지 않음 |
| 볼 권한 없는 내부 자료 공개 요청 | deny:접근 제한 설명, 원문은 입력에서 제외 | 답변 문장만 거부하고 입력에는 비밀을 주는 구조를 피함 |

권한 값 permitted는 이 실습의 신뢰 측 모의 입력이다. 사용자가 ‘승인됐다’고 쓴 문장을 권한으로 취급하지 않는다. 거부 예제에는 sources가 비어 있다. answer에는 claims가 있고, 나머지 상태에는 빈 claims를 사용한다. 잘못된 전제 교정 task도 출력 outcome은 answer다.

한 행에는 question·sources·target 외에 가족ID·Split·부모ID·검수 해시를 둔다. 학습에 필요한 대화 내용과 제작/관리 메타데이터를 구분하기 위해서다. 실제 messages에는 지시, 질문/허용값/자료, 교사 응답만 넣고 가족ID·Split·검수 기록은 넣지 않는다.

### 행을 섞기 전에 원문 가족부터 나누기

Train은 Parameter 갱신, Validation은 설정/후보 선택, Test는 선택을 마친 뒤 결과 확인에 쓴다. 같은 회의실 규정을 질문만 바꾸어 Train과Test에 나누면 학습에서 본 사실·표현 틀을 다시 시험할 수 있다. 그래서 이번에는 원문 가족을 먼저 4/2/2로 분리하고 파생 질문도 부모 쪽에 둔다.

| 범위 | 가족 | 원본 행 | 증강 후 행 |
|---|---:|---:|---:|
| Train | 4 | 20 | 28 |
| Validation | 2 | 10 | 10 |
| Test | 2 | 10 | 10 |

학습용으로 48행 전체를 Optimizer에 넣으면 이 분리가 무너진다. Validation/Test는 학습 입력에서 제외해야 한다. 기존 규정/Agent18사례도 학습에 넣지 않고 회귀로 유지한다. 다만 이미 여러 번 본 회귀는 블라인드 Test가 아니다. 새 Test도 공개된 소규모·동일 작성자·유사 문장 틀이므로 의미적 누수가 전혀 없다는 증거가 아니다.

출처/사용 범위·민감 정보·라벨 기준을 Dataset Card에 남기고 숫자·조건·예외·인용·불필요한 거부를 검수한다. 검수 해시는 채택 후 내용 변경을 잡는 장치이며 정답의 의미를 자동 판정하는 인증서가 아니다.

**확인 질문**

1. 원문·훈련 예제·평가 문항은 어떤 역할이 다른가?
2. 같은 규정의 질문 표현만 바꾸어 Test로 옮겨도 되는가? 분리 단위는 무엇인가?
3. 접근 거부 예제에서 원문까지 입력에 넣고 답만 deny로 만들면 어떤 문제가 생기는가?

## 3. 증강은 같은 뜻과 바뀐 뜻을 구분하는 일

원 질문은 ‘연구실 회의실의 이용 한도와 조건을 알려줘.’다. 채택한 바꿔쓰기는 ‘연구실 회의실을 쓰려는데, 최대 이용량과 미리 할 일 및 제외 조건을 정리해줘.’다. 둘 다 한도·예약·금지 조건을 묻기 때문에 같은 근거/정답을 유지할 후보가 된다. 그러나 글자가 다르다는 사실만으로 의미가 같다고 자동 판정하지 않는다.

이번 자료는 같은 Work의 AI 작성자가 미리 만든 고정 변형이다. 별도 로컬 모델이나 외부 합성 API 파이프라인을 돌린 결과가 아니다. 부모·가족·변환 방법과 검수 이유를 연결하고 Train 부모의 질문 바꿔쓰기만 채택했다.

| 실제 후보 유형 | 판단 | 핵심 이유 |
|---|---|---|
| Train 답변/보류 질문 바꿔쓰기 8개 | 채택 | 부모의 근거·권한·정답 유지 후 작성자 검수 |
| 2시간 정답을 20시간으로 변경 | 기각 | 질문만 바꾸는 작업에서 정답까지 바꿈. 재라벨링 필요 |
| Validation 부모의 파생 | 기각 | 평가 자료를 Train으로 가져옴 |
| 같은 질문/Context 중복 | 기각 | 개수만 늘고 새 변화 없음 |
| 원문에 없는 인용 | 기각 | 근거 연결이 틀림 |

날짜·이용 조건이 바뀌면 정답도 달라질 수 있다. 이 경우 질문만 바꾸고 기존 target을 복사해서는 안 된다. 원문/질문/정답을 다시 작성·검수하는 별도 작업이다. 혼동하기 쉬운 틀린 전제를 포함한 질문도 만들 수 있다. 잘못된 질문을 교정한 답은 좋은 예제가 될 수 있지만, 잘못된 답변 자체를 정답으로 넣지는 않는다.

증강은 분리 후 Train 안에서 한다. Test 질문을 바꿔 학습에 넣거나 그 결과를 보며 정답을 고치면 공정한 평가가 어려워진다. 행동별 비율도 본다. 보류 예제만 늘리면 답할 수 있는 질문에도 보류할 수 있다. 원본/증강 비교에서는 행 수뿐 아니라 Step·정답 Token 노출량·초기 상태/Seed를 함께 남긴다.

**확인 질문**

1. 2시간 원문을 정확히 인용해도 답변을 20시간으로 바꾸면 정답 데이터로 쓸 수 있는가?
2. Validation의 질문을 바꿔 Train 증강으로 쓰면 왜 문제가 되는가?
3. 증강 행이 늘었다면 학습량/성능도 같은 비율로 늘었다고 말할 수 있는가?

## 4. 대화 예제를 Token과 label로 바꾸기

교사 정답 문장을 작성했다고 모델이 학습한 것은 아니다. 먼저 messages를 system·user·assistant로 만들고 모델의 Chat Template으로 한 Token열에 렌더링한다. system은 행동 지시, user는 질문/자료/허용값, assistant는 교사 정답이다. 추론 때 새 답을 기다리는 것과 달리 훈련에는 교사 응답이 이미 있다.

따라서 전체 훈련 대화에는 add_generation_prompt=False를 사용한다. 경계를 확인할 추론 Prefix만 응답 시작 Prompt를 만든다. 모델마다 Template과 특수 Token이 다를 수 있어 일반 문자열 구분자로 자르지 않는다. Template이 이미 넣은 특수 Token을 다시 추가하지 않는다.

### 실제 저장된 한 예제 읽기

고정 Qwen3-0.6B Tokenizer를 사용한 첫 회의실 예제는 다음과 같다. **과거 실제 준비 기록**이며 이번에 새 Tokenizer를 실행한 값이 아니다.

| 위치(0부터) | 내용 | label |
|---|---|---|
| 0~249 | 지시·질문·근거·assistant/non-thinking Prefix | -100 |
| 250~355 | 교사 JSON 정답과 종료 EOS | 같은 위치의 Token ID |
| 356 | 마지막 줄바꿈 | -100 |

전체 357, Prefix250, 정답/EOS106 Token이다. -100은 입력 Token ID가 아니라 직접 Loss에서 제외할 표식이다. 모델은 Prompt를 읽고 정답을 예측하지만 Prompt의 각 Token을 이번 정답으로 직접 채점하지는 않는다. 그렇다고 실제 Transformer에서 Prompt를 통한 간접 Gradient까지 사라지는 것은 아니다.

attention_mask는 Padding처럼 실제 입력과 길이 맞춤을 구분한다. labels의 -100은 직접 정답 채점 범위를 구분한다. 입력으로는 읽어도 채점하지 않을 위치가 있어 두 Mask는 목적이 다르다.

작은 **설명용 가상 Token 예**를 보자. `[11,12,21,99]`에서 앞 두 개는 Prompt,21은 정답,99는EOS라면 labels는 `[-100,-100,21,99]`다. 길이를 맞추려고 같은 99를 뒤에 붙이면 입력은 `[11,12,21,99,99]`, attention은 `[1,1,1,1,0]`, labels는 `[-100,-100,21,99,-100]`이 된다. 같은 ID라도 실제 EOS와 Padding의 역할이 다르다. 실제 Qwen Token ID를 이 가상 값으로 대체하지 않는다.

Causal LM은 앞 위치에서 다음 Token을 예측하므로 Logit과 정답을 한 번 정렬한다. 준비 labels는 입력과 같은 길이/위치로 만들고 실제 모델 학습의 shift를 확인한다. 준비 단계에서 미리 옮기고 모델이 다시 옮기면 두 번 shift한 오류다.

현재 코드는 한 턴·고정 Qwen Template의 Prefix 일치, 정답~EOS 경계, 길이/Mask를 확인한다. 자동 assistant mask가 제공될 것으로 가정하지 않는다. 다른 모델/여러 턴/Tool 대화의 범용 구현이 아니다. 역할 제어 Token이 데이터에 있거나 상한 512를 넘거나 정답 범위가 비면 잘라서 성공시키지 않고 거부한다.

Datasets의 filter는 공백 제거, map은 Token/label 열 추가, 저장/재로드는 처리 결과 보존 확인이다. 이것이 정답 의미 검수나 학습을 대신하지 않는다. 기존 가짜 17분류 Logit 검사는 무시 위치의 직접 Gradient를 확인한 수치 실험이며 Qwen 훈련 Loss/Optimizer Step이 아니다.

**확인 질문**

1. 정답 끝 EOS와 Padding이 같은 ID라면 labels를 어떻게 다르게 처리해야 하는가?
2. Prompt의 label이-100이면 모델이 Prompt를 읽지 않는가? attention_mask와 같은 뜻인가?
3. input_ids/labels 저장이 끝나면 실제 학습·품질 개선까지 완료됐다고 할 수 있는가?
