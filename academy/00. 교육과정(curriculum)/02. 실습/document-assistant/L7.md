# 학습할 예제와 정답 범위 준비하기

앞서 만든 문서 도우미는 자료·권한·출력 계약을 실행기로 통제했다. 이제 ‘자료가 있으면 답하고, 조건이 빠지면 묻고, 기준이 없으면 보류하는 행동’을 교사 예제로 준비한다. **이번 필수 활동은 데이터·정답 범위 확인이며 새 모델 학습이 아니다.** [강의](<../../01. Phase2_AI/10. 미세조정(Fine-tuning)/강의용.md>)를 읽고 같은 회의실 예제를 따라간다.

원본 데이터와 기존 훈련 기록을 덮어쓰지 않는다. 아래 1~4는 로컬 JSON과 현재 검수 코드로 진행한다. 2의 읽기 도구는 Python 표준 라이브러리만, 3~4의 검수 코드는 backend의 Pydantic 의존성이 필요하다. Tokenizer·Datasets·Torch는 선택 실행에서 따로 준비한다. 모든 명령은 `practice/document-assistant/backend` 폴더에서 입력한다.

## 1. 학습 전에 실패 원인 고르기

‘최신 규정이 검색 입력에 없음’, ‘2시간·예약·음식 금지 근거가 있어도 보류’, ‘승인 없이 자료를 읽는 도구’ 중 하나를 고른다. 먼저 바꿀 대상을 각각 검색/자료, 지시·응답 확인 후 행동 학습 가설, 실행기 권한으로 나눠 본다.

두 번째 상황의 목표 문장을 “LoRA 사용” 대신 “근거가 있는 질문에는 한도와 조건을 포함해 답한다”로 적는다. 그 목표를 SFT로 배우게 할 때 Full fine-tuning과 LoRA 중 무엇을 갱신할지 따로 선택한다. 이번 후속 훈련의 기준선은 LoRA이며, 이 준비 활동에서 지원하지 않는 Adapter를 실행했다고 기록하지 않는다.

## 2. 회의실 원문 하나와 다섯 정답 읽기

아래는 **실행할 명령**이다. 첫 ID는 ‘회의실 한도와 조건을 묻는 원본 예제’를 찾는 실제 데이터 키다. 외울 관리 코드가 아니다.

```bash
python -m tools.training_data_steps --example FT-T01-S01
```

원문은 2시간·사전 예약·음식 반입 금지다. 출력의 question은 학습 입력의 질문이고 target은 교사가 작성한 바람직한 응답이다. 파생 후보는 아직 모두 채택된 것이 아니므로 3에서 결정을 확인한다. 모델이 생성한 답변이나 지금 학습한 결과가 아니다.

같은 명령 끝 ID를 `FT-T01-S02`, `FT-T01-S03`, `FT-T01-S04`, `FT-T01-S05`로 바꾸면 잘못된 무제한 전제 교정, 예약 상태 되묻기, 보상금 보류, 권한 거부를 읽는다. “지금 이용할 수 있어?”에는 예약 여부를 묻고, “보상금은 얼마?”에는 규정에 기준이 없다고 답하는 이유를 설명한다. 거부 예제는 sources가 없음을 확인한다.

원문 가족은 하나지만 질문/정답 행은 다섯 개다. 가족을 먼저 4/2/2로 나누어 원본은 Train 20/Validation 10/Test 10행이다. 원문·학습 대화·평가 문항의 역할을 적고, 같은 회의실 규정의 바꿔쓰기 한 개를 Test로 옮겨도 되는지 판단한다. 학습에는 Train만 사용한다.

## 3. 현재 검수 코드로 증강 결정 확인하기

현재 정책은 Train 부모의 질문 바꿔쓰기만 채택한다. 원본 질문의 한도·예약·금지 조건을 다른 말로 물어도 근거와 정답은 유지해야 한다. 실제 후보에는 2시간→20시간 정답 변경, 평가 부모, 중복, 없는 인용도 섞여 있다. 실행 전에 각각을 왜 기각할지 예상한다.

아래는 **완전한 실행 코드**다. backend에서 `python` 대화형 입력 대신 터미널에 블록 전체를 붙여 넣는다. 원본은 읽기만 하며 승인 기록을 새로 만들지 않는다.

```bash
python - <<'PY'
import json
from collections import Counter
from pathlib import Path
from app.training_data import validate_seeds, adopt_candidates
root = Path('..')
data = root / 'data/finetuning-v1'
def read(path):
    return json.loads(path.read_text())
manifest = read(data / 'split-manifest.json')
reviews = read(data / 'review-manifest.json')
regression = [case['question'] for name in ['core-v1.json', 'agent-v1.json']
              for case in read(root / 'data' / name)['cases']]
seeds = validate_seeds(read(data / 'seeds.json')['examples'], manifest, reviews, regression)
accepted, decisions = adopt_candidates(
    read(data / 'augmentation-candidates.json')['examples'], seeds, manifest, reviews, regression)
print('원본:', dict(Counter(row.split for row in seeds)))
print('채택:', len(accepted), '기각:', sum(not d['accepted'] for d in decisions))
print('준비 후:', dict(Counter(row.split for row in seeds + accepted)))
for decision in decisions:
    if not decision['accepted']:
        print(decision['id'], decision['rejection_id'])
PY
```

현재 고정 자료의 **예상 결과**는 원본 20/10/10, 채택 8·기각 4, 준비 후 28/10/10이다. `TARGET_CHANGED_REANNOTATION_REQUIRED`는 정답 변경, `TRAIN_ONLY_AUGMENTATION`은 평가 부모 사용, `DUPLICATE`는 중복, `QUOTE_NOT_IN_SOURCE`는 없는 인용을 뜻한다. 개수보다 각 이유를 확인한다.

코드는 Schema·원문 버전·가족 Split·계보·중복·검수 해시·인용 포함을 확인한다. 의미가 같은 질문인지, 답이 사실인지까지 모두 판정하지 않는다. 같은 작성자의 의미 검토를 거친 고정 예제라는 한계가 남는다. 오류를 없애려고 해시나 Split만 고치지 말고 어떤 규칙에 걸렸는지 원문·부모·정답을 함께 확인한다.

## 4. 교사 응답 중 어디를 채점할지 확인하기

아래 **실행 명령**은 과거 실제 Tokenizer로 만든 첫 회의실 예제를 읽는다. Tokenizer를 지금 실행하거나 ID를 새로 계산하지 않는다.

```bash
python -m tools.training_data_steps --mode labels
```

전체 357, Prefix 250, 교사 정답/EOS 106 Token이 저장되어 있다. 0부터 세면 labels의 250~355는 같은 위치 input_ids이고 나머지는 -100이다. Prompt도 입력으로 읽지만 직접 정답으로 채점하지 않는다. 마지막 줄바꿈은 제외한다. 출력의 정답 복원 문자열은 저장값이며 새 decode 실행값은 아니다.

다음은 **완전한 실행 코드와 설명용 가상 Token 입력**이다. 실제 Qwen ID가 아닌 11·12·21·99를 사용한다. 앞 둘은 Prompt, 21은 정답, 99는 EOS라고 정하고 두 번째 행을 더 길게 만든다. 실행 전 첫 행의 끝에 붙일 Padding 99가 채점될지 예상한다.

```bash
python - <<'PY'
from app.training_data import pad_batch
rows = [
    {'input_ids': [11,12,21,99], 'attention_mask': [1,1,1,1],
     'labels': [-100,-100,21,99]},
    {'input_ids': [11,12,21,22,99], 'attention_mask': [1,1,1,1,1],
     'labels': [-100,-100,21,22,99]},
]
batch = pad_batch(rows, pad_token_id=99)
print('입력:', batch['input_ids'][0])
print('Attention:', batch['attention_mask'][0])
print('정답:', batch['labels'][0])
PY
```

첫 행의 **예상 결과**는 입력 `[11,12,21,99,99]`, Attention `[1,1,1,1,0]`, 정답 `[-100,-100,21,99,-100]`이다. 네 번째 99는 EOS라 배우고 다섯 번째 99는 Padding이라 제외한다. 정답 ID를 한 칸 미리 옮기지 않는다. 실제 Causal LM에서 다음 Token 정렬을 한 번 적용할 때 이 같은 위치 labels를 사용한다.

실제 Qwen Template에는 역할 시작/종료와 non-thinking Prefix가 있으므로 가상 예제처럼 글자 수로 경계를 정하지 않는다. 현재 변환기는 고정 Template의 Token Prefix 일치·정답부터 EOS까지 범위·길이를 확인하고 상한 초과를 거부한다. 다른 모델/다중 턴까지 검증한 구현은 아니다.

## 선택 실행: 실제 Tokenizer·Datasets 변환하기

아래는 과거 준비 실행과 같은 고정 환경을 새로 만들 때의 안내다. 이번 설명 정비에서는 이 설치·변환을 재실행하지 않았다. 실제 실행하면 원본 검수→JSONL→Datasets 읽기→공백 filter→Token/label map→Arrow 저장/재로드를 진행한다. filter는 이번 자료에서 0행을 제거하며 의미 검수가 아니다.

### 환경과 명령

검증 환경은 Linux x86_64·Python 3.12 CPU다. L5의 고정 패키지를 유지하고 Datasets 4.4.1을 별도 환경에 추가했다. 이번 제작 환경에서는 큰 패키지를 다시 설치하지 않도록 L5 패키지를 읽기 전용으로 참조하는 별도 설치 계층을 사용했다. 아래 학생용 새 환경 설치 순서는 표준 pip 방식이다. 다른 OS·교육장 PC의 동시 실행은 별도 검증 대상이다.

backend 폴더에서 새 가상환경을 활성화한 뒤 실행한다. 표는 **입력할 명령**이며 관찰 결과 예시가 아니다.

| 목적 | 입력할 명령 |
|---|---|
| Linux CPU Torch 준비 | `python -m pip install torch==2.15.0+cpu --index-url https://download.pytorch.org/whl/cpu` |
| 고정 준비 의존성 설치 | `python -m pip install -r requirements-training-data.txt` |
| 최초 Tokenizer 준비와 Dataset 처리 | `python -m tools.training_data_lab --download --output l7-data-01` |
| 캐시만 사용하는 재실행 | `HF_HUB_OFFLINE=1 HF_DATASETS_OFFLINE=1 HF_HUB_DISABLE_TELEMETRY=1 python -m tools.training_data_lab --output l7-data-02` |
| 기존 회귀·데이터/Mask 경계 검사 | `python -m pytest -q` |

처음에는 같은 Qwen3-0.6B 리비전의 Tokenizer 파일을 받는다. Qwen 가중치는 필요하지 않다. 기존 L4/L5 모델 캐시와 HF_HOME을 따로 정했다면 같은 값을 유지한다. 원격 문서의 최신 API와 이 고정 실행 버전을 혼용하지 않는다.

출력 폴더가 있으면 덮어쓰지 않는다. 원본/검수/코드/Tokenizer 변경 후에는 새 폴더에 실행한다. 로컬 JSON을 읽어도 Datasets Library가 사용 횟수 통계용 HEAD 요청을 시도할 수 있어, 엄격한 캐시 재실행에서는 위 세 환경 값을 프로세스 시작 전에 지정했다. 실제 요청 가드 확인 범위는 결과 보고서에 있다.

### 출력과 제출물 해석

| 출력 | 확인할 내용 |
|---|---|
| observed.json | 수량·Features·후보 결정·길이·저장/재로드·환경/코드 해시 |
| train/validation/test.jsonl | 질문·근거·교사 정답과 Split; 학습에는 Train만 사용 |
| token-example.json | messages·Template·input_ids·labels·정답 복원 |
| batch-example.json | 길이가 다른 두 실제 행의 EOS와 Padding 구분 |
| arrow 폴더 | Datasets 저장·재로드 결과; Git에는 넣지 않음 |

현재 자료로 직접 실행했다면 첫 회의실 messages에서 가족ID·Split·검수 기록이 빠지고 질문·자료·교사 응답만 들어가는지 확인한다. 저장/재로드 동일성은 변환 결과가 보존됐다는 뜻이며 정답이 좋다는 의미는 아니다. Tokenizer 캐시가 없을 때 테스트의 skip은 실제 변환 성공으로 세지 않는다.

제출은 ① 실패 원인과 목표 행동, ② 한 가족의 다섯 질문/정답과 분리 이유, ③ 채택 하나·기각 네 유형의 이유, ④ EOS/Padding 정답 범위, ⑤ 자신이 실제 실행한 범위다. 전체 JSON을 하나씩 읽는 대신 선택한 행과 근거를 설명한다. 선택 변환을 안 했다면 저장 기록 관찰이라고 적는다. 가짜 17분류 Logit 검사는 Mask 수치 검사이며 Qwen 훈련 Loss가 아니다.

## 훈련 활동: 갱신·평가·재현을 나누어 확인하기

이제 [훈련 강의](<../../01. Phase2_AI/10. 미세조정(Fine-tuning)/LoRA 실습.md>)를 읽고 다음 네 활동을 진행한다. 1~4의 계산/기록 관찰은 Python 표준 라이브러리만 사용한다. 모델·Torch·GPU 없이 실행 가능하며 **새 훈련이나 새 프로세스 모델 재로드가 아니다.** 실제 재실행은 뒤의 별도 안내를 따른다. 명령은 계속 backend 폴더에서 입력한다.

### 1. 작은 갱신 계산과 실제 학습 로그

먼저 W=1, A=1, B=0, 입력=2, 정답=3, 배율=2로 시작한다. 출력은 W×입력+배율×B×A×입력이다. **설명용 가상 스칼라 계산**에서 제곱오차의 절반을 Loss로 쓰고 단순 SGD의 학습률을 0.1로 둔다. 실제 Qwen/AdamW/Token Loss와 구분한다. B=0일 때 A의 첫 Gradient가 0이어도 학습이 시작될 수 있을지 예상한다.

아래는 **실행할 명령**이다.

```bash
python -m tools.lora_steps --mode math
python -m tools.lora_steps --mode training
```

첫 출력의 예상값은 초기 예측 2·Loss 0.5, Gradient A=0/B=-4, 갱신 뒤 A=1/B=0.4·예측 3.6·Loss 약 0.18이다. 원래 W는 그대로다. 근사 오차로 0.180000…처럼 보이는 것은 정상이다. 이 수치를 실제 모델 Loss로 제출하지 않는다.

두 번째 명령은 **기존 전체 Train 실행**의 설정·Parameter 수·첫/마지막 Step을 읽는다. seed/augmented는 원본/증강 조건이며 난수 Seed 37과 다르다. 실제 573,440개가 학습 가능하고 전체는 596,623,360개다. 같은 초기 Adapter·28 Step에서 원본 고유행 20개와 증강 28개를 봤으며 정답 Token 노출은 1,727/1,947이다.

Forward의 Loss·Backward의 gradient_norm·Optimizer 이후 Adapter 변화가 각각 무엇을 증명하는지 적는다. 로그 norm은 clipping 전 값이므로 1을 넘는다고 clipping이 실패한 것은 아니다. 첫/마지막 Step이 다른 예제라 Loss 둘만으로 학습 곡선이나 수렴을 판정하지 않는다. 동결 확인도 전체 Weight 해시가 아닌 표본 검사다.

### 2. QLoRA가 줄이는 것과 남는 것 판단하기

6억 Weight의 float32 저장량 24억 바이트와 4-bit 코드 3억 바이트를 계산한다. 이 산술에서 빠진 양자화 상수·Adapter·Gradient·Optimizer·활성값·임시 메모리를 적는다. 이번 CPU float32 LoRA와 QLoRA의 Base 저장 형식·계산 dtype·학습 대상·필요 backend를 나란히 써 본다.

장비 이름/메모리, Python·Torch·양자화 backend 버전, 지원 연산/dtype, Sequence 길이·Microbatch·실제 실행 여부를 기록한다. 아직 측정하지 않은 칸은 미실행으로 둔다. 4-bit 추론만 성공했다면 훈련 성공으로 쓰지 않는다. 한 예제가 너무 길 때와 동시에 너무 많은 예제를 처리할 때의 조정 방향을 구분한다.

GTX 1060 3GB에서 가능하다고 미리 결론 내리지 않는다. [공식 설치/지원 안내](https://huggingface.co/docs/bitsandbytes/main/en/installation)도 확인하되 main 문서와 설치 버전은 구분한다. 이번 저장소의 고정 훈련 의존성은 QLoRA backend를 설치하지 않으며 실제 QLoRA 학습·저장·재로드는 미검증이다.

### 3. 지표를 확인하고 실제 반례 찾기

아래는 **실행할 명령**이다. 첫 명령은 저장된 예제 Loss를 평균하고 생성 기록의 계약/행동 개수를 다시 센다. 새 모델 평가가 아니다. 두 번째 ID는 ‘천체 관측실 보상금 질문’의 실제 데이터 키다.

```bash
python -m tools.lora_steps --mode evaluation
python -m tools.lora_steps --mode case --example FT-E01-S04
python -m tools.lora_steps --mode regression
```

Validation 기준으로 고른 후보는 seed다. Base/원본/증강의 Test 계약 통과는 0/8/8개, 계약+행동 이름 일치는 0/4/3개다. 이를 의미 정답률이라고 읽지 않는다. 보상금 질문의 seed 응답은 outcome=abstain인데 answer가 ‘0’이다. 원문에 보상 기준이 없는데도 왜 충분한 보류 설명이 아닌지 적는다.

ID를 `FT-E01-S01`로 바꿔 한도 질문도 본다. seed는 60분·신청·음료 금지를 말하지만 claims가 없어 계약에 실패했다. `FT-E02-S04`는 음성 녹음실 보상금 질문이다. 증강 응답의 근거 없는 5000원을 확인한다. 형식·행동 이름·사실/조건·원문 연결을 각 열로 나눠 실패를 기록한다.

Agent 회귀의 18개 사례에서 모델 생성은 60/42/40회, 최종 근거 초안은 모두 0개다. 호출 감소가 조기 실패일 수 있음을 종료 분포와 함께 설명한다. SFT 답변 작성과 Agent 도구 선택의 계약이 다르므로 이 결과로 공통 서비스 모델을 교체하지 않는다. 원본/증강을 다시 비교한다면 Step뿐 아니라 Token 노출·행동 비율·Seed와 평가를 어떻게 맞출지 가설을 적는다.

### 4. 저장 재현과 결과 Card

아래 **실행 명령**은 두 Adapter의 과거 새 프로세스 재로드 기록과 원래 생성 Token열을 비교한다. 실제 바이너리를 읽거나 지금 모델을 재로드하지 않는다.

```bash
python -m tools.lora_steps --mode reload
```

저장 Token열은 두 조건 모두 일치한다. 그런데 seed 첫 질문의 계약은 OUTPUT_CONTRACT 실패다. ‘같은 실패를 재현함’이 저장/추론 재현의 증거와 품질 판단에 각각 어떤 뜻인지 설명한다. 출력의 SHA256은 저장 기록에 적힌 값이며 현재 파일을 다시 해시한 값이 아니다.

결과 Card 초안에는 목표·Base/Revision·Adapter 설정·자료/Split/검수자·Step/Token/Seed·실제 평가와 실패·자원·재로드 범위·미실행을 쓴다. 예를 들어 “가상 규정 자료의 정답 작성 실험. 한 Seed 28 Step에서 Loss 감소를 관찰했으나 의미 오류와 Agent 실패가 남아 서비스 채택 보류. 첫 Test 사례의 재로드 Token 일치 확인. QLoRA·다른 Runtime·독립 수업/품질 검증은 미완료”처럼 근거 수준을 밝힌다. 본인이 기록만 읽었다면 그 사실도 적는다.

제출은 작은 계산과 실제 로그 차이, 자원 판단표, 실패 응답 두 개의 이유, 재현/재개 차이와 Card 초안이다. [강사용 해설](<../../01. Phase2_AI/10. 미세조정(Fine-tuning)/LoRA 실습 강사용.md>)에서 판단 근거를 확인한다.

## 선택 실행: 실제 LoRA 훈련과 새 프로세스 재로드

여기부터는 실제 모델 Weight·Tokenizer와 고정 훈련 의존성이 필요하다. 앞의 JSON 읽기 명령과 달리 모델을 로딩하고 훈련·생성하며 파일을 저장한다. 이번 교안 정비에서는 새로 실행하지 않았고 아래는 기존 실행 도구의 재실행 안내다. 다른 장비/동시 실행은 별도 확인이 필요하다.

### 준비와 초기 상태

1. backend에서 앞의 Linux CPU 가상환경과 고정 Torch·준비 의존성을 확인하고 `python -m pip install -r requirements-lora.txt`로 PEFT 0.17.1·Accelerate 1.10.1을 준비한다. 다른 버전을 섞지 않는다.
2. 같은 HF_HOME 캐시·Qwen3-0.6B의 고정 Revision `c1899de289a04d12100db370d81485cdf75e47ca`를 쓴다. 전체 회귀 실행에는 E5·문서 Index 준비도 필요하다. 기존 [Single-Agent 준비](L5.md)를 따른다.
3. 출력 폴더가 없는 이름을 고른다. 아래 폴더가 이미 있으면 접미사를 바꾸며 과거 관측/Adapter를 덮어쓰지 않는다. CPU RSS와 충분한 디스크를 확인하고 다른 모델 프로세스와 겹쳐 실행하지 않는다. 기록에 중복 프로세스의 메모리 종료가 있으므로 기존 시간/메모리는 실행 보장이 아니다.

아래 표는 **입력할 명령**이다. 재로드는 훈련 프로세스 종료 뒤 새 터미널 명령으로 실행한다. 준비/실제 생성/훈련의 시간을 섞어 비교하지 않는다.

| 목적 | backend에서 입력할 명령 | 범위 |
|---|---|---|
| 최초 작은 동작 확인 | `python -m tools.lora_lab --download --output l7-train-new` | 두 조건 각각 4개·4 Step, 전체 Train 아님 |
| 작은 실험 Adapter 재로드 | `python -m tools.lora_lab --reload l7-train-new/seed-adapter --output l7-reload-new` | 별도 프로세스 로딩/생성; 자동 Token 비교는 아래 전체 실행 도구와 구분 |
| 전체 Train 비교 | `python -m tools.lora_full_lab --download --output l7-full-new` | 원본 20/증강 28 전체 포함·각 28 Step·평가/18회귀 |
| 같은 조건 중단 재개 | `python -m tools.lora_full_lab --resume --output l7-full-new` | 같은 코드/환경/자료·캐시, 완료 기록은 건너뜀 |
| 전체 실험 원본 재로드 | `HF_HUB_OFFLINE=1 python -m tools.lora_full_reload --run l7-full-new --variant seed` | 캐시 전용·새 프로세스·첫 Test Token 비교 |
| 전체 실험 증강 재로드 | `HF_HUB_OFFLINE=1 python -m tools.lora_full_reload --run l7-full-new --variant augmented` | 같은 비교를 증강 Adapter에 수행 |

최초 실행 후 캐시만 쓴 새 전체 실험에서는 `--download`를 빼고 offline 환경을 프로세스 시작 전에 적용한다. `--resume`에서 캐시가 부족하면 새 다운로드 성공으로 바꾸어 기록하지 말고 필요한 파일을 확인한다. 설정/자료/코드/환경 변경 오류는 같은 중단 상태를 이어갈 수 없다는 뜻이다. 특히 Git에 보존된 과거 관측 폴더는 이전 소스로 실행되어 현행 Runner와 해시가 다르므로 그대로 재개하지 않는다. 새 실험 폴더를 사용한다.

### 실행 뒤 무엇을 볼까

| 실제 로컬 출력 | 관찰과 해석 |
|---|---|
| configuration.json | Base·환경/코드/자료 해시·r/alpha/대상·Step·생성 설정 |
| seed 또는 augmented/training.json | 실제 본 고유행·Step·정답 Token 노출·Gradient/Adapter 변화 |
| 각 조건의 validation.json, selection.json | Validation 평균과 Test 지표 확인 전 후보 선택 |
| test-loss.json, test/사례.json | Loss와 raw_output·Token·계약·행동을 따로 대조 |
| regression/사례.json | 도구 입력·종료·초안·상한·A05 오류 주입 도달 여부 |
| 각 조건의 adapter/ | Adapter 설정/Weight; Base 전체 파일이 아님 |
| progress.json, step별 폴더 | 훈련 재개용 완료 Step·Adapter·Optimizer/난수 상태 |
| reload-seed.json, reload-augmented.json | 새 프로세스 첫 Test Token 비교·HTTP 가드/Adapter 해시 |

위 경로의 ‘각 조건’은 `l7-full-new/seed`, `l7-full-new/augmented`다. Base에는 training.json/Adapter가 없다. Git의 기존 observed.json은 이 로컬 출력들을 모아 둔 과거 기록이며 새 로컬 실행 폴더와 구조가 다르다.
