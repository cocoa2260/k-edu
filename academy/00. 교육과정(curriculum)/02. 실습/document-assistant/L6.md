# 역할 사이에 근거를 넘기고 전체 작업을 멈추는 실습

[강의](../../lessons/multi-agent/lesson.md)의 정상 전달과 실패 경계를 직접 관찰한다. 고정 응답은 실행 경계를, 과거 실제 모델 기록은 역할 선택과 과제 완료 여부를 보여 준다. 두 근거를 섞지 않는다. [강사 해설](../../lessons/multi-agent/teacher-guide.md)은 별도로 있다.

저장소 최상위에서 터미널을 열고 다음 **이동 명령**을 실행한다. 이후 상대 경로는 backend 기준이다.

```bash
cd curriculum-work/practice/document-assistant/backend
```

기록 읽기는 Python 표준 라이브러리만 사용한다. 직접 코드/고정 실험에는 기존 Backend의 Pydantic 환경이 필요하다. E5/Qwen 실제 재실행은 뒤의 별도 환경을 따른다. 읽기 도구는 모델/도구를 호출하거나 기록을 수정하지 않는다.

## 활동 1. 정상 전달에서 정보와 예산 찾기

다음은 **과거 고정 응답의 Control**을 읽는 명령이다. 실제 모델의 계획 성공이 아니다.

```bash
python -m tools.multi_steps --record ../../../reports/KEDU-PRODUCTION-008/fixture-observed.json --case control
```

검색→읽기→전달→작성→검토를 따라간다. 모델 5/도구 2/보완 0, 역할별 검색 3·작성 1·검토 1이다. Handoff에서 실행ID·역할·질문ID·근거·예산이 Runtime 값으로 들어간다는 점을 본다. 최종 초안이 있어도 approval_granted와 semantic_grounding_verified는 False다. pass는 사용자 승인이나 의미 검증 완료가 아니다.

원문 cap 30000과 출처 A@v1:L1은 고정 실험의 가상 영어 자료다. 한국어 실제 모델 기록의 문서 ID나 숫자 벡터와 섞어 비교하지 않는다.

## 활동 2. 같은 ID라도 전달이 거부되는 이유

첫 명령의 `--case`를 M01로 바꾼다. 검색자는 원문을 읽었지만 작성자의 수신 허용 ID는 비어 있다. HANDOFF_SCOPE가 반복되고 작성자는 호출되지 않는다. 발견한 자료·읽은 자료·다음 역할이 받을 수 있는 자료가 서로 다른 집합임을 표로 정리한다.

아래는 **기존 경계 실험 함수를 현재 코드로 실행하는 전체 Python 코드**다. 의미 없는 고정 벡터와 정해 둔 응답, 실제 임시 SQLite를 쓴다. 모델 생성/학습·외부 작업은 없다. 도구 구현 전체를 교안에 다시 복사하지 않고 기존 probes를 호출한다.

```bash
python - <<'PY'
import tempfile
from pathlib import Path
from tools.multi_fixture_lab import probes
with tempfile.TemporaryDirectory() as folder:
    result = probes(Path(folder) / 'index.sqlite')
    rows = {'control': result['control']}
    rows.update({k: v for k, v in result['scenarios'].items() if k != 'M04'})
    rows.update({'M04/' + k: v for k, v in result['scenarios']['M04'].items()})
    for name, row in rows.items():
        print(name, row['stop_reason'], '예산', row['budget'],
              '전달 초안', row['draft'] is not None,
              '부분 초안', row['partial_draft'] is not None)
PY
```

Control은 전달 초안이 있고, M01은 없다. M01의 역할별 호출에 writer가 없는지 확인한다. 모델이 자유롭게 요약을 써 전달하게 바꾸면 ID 필터만으로 어떤 정보 누출을 놓칠지 설명한다. 실행기의 검증된 원문 조회와 모델 요약은 대체 가능한 증거가 아니다.

## 활동 3. 공통 보완 한 번과 부분 결과 구분

저장된 fixture 기록의 M02와 M03을 각각 읽고 위 현재 코드의 결과와 대조한다.

```bash
python -m tools.multi_steps --record ../../../reports/KEDU-PRODUCTION-008/fixture-observed.json --case M02
python -m tools.multi_steps --record ../../../reports/KEDU-PRODUCTION-008/fixture-observed.json --case M03
```

M02는 빈 근거 전달→작성자 추가 요청→검색/읽기/재전달→작성→검토다. 모델 7·도구 2·보완 1, 검색 4·작성 2·검토 1을 확인한다. 재진입하며 과거 역할 호출 수가 지워지지 않았다.

M03은 검토 보완 후 같은 UNSUPPORTED_CLAIM이 반복돼 최종 draft=None으로 중단한다. partial_draft는 남아 있어도 정상 전달 결과가 아니다. 작성자 추가 근거와 검토자 보완에 각각 새 예산을 주면 무엇이 달라질지 예상하되 현재 실행이 그런 정책이라고 표시하지 않는다.

M04 하위 결과는 다음 키로 읽는다. 모두 고정 오류/가짜 시계 시험이며 실제 모델 품질 또는 240초 장애 성능 시험이 아니다.

| `--case` 값 | 관찰할 것 |
|---|---|
| M04/model_budget | 전체 모델 4회 사용 뒤 검토 호출 전 중단, 부분 초안만 남음 |
| M04/transient_timeout | 전체 재시도 1회 소진, transient_budget으로 종료 |
| M04/deadline | 호출 중 가짜 시계 241초, 늦은 행동을 전달하지 않음 |

## 활동 4. 실제 모델의 도달 단계 비교

아래는 **저장된 실제 모델 통합 기록**을 읽는 명령이다. 지금 모델을 실행한 것이 아니다.

```bash
python -m tools.multi_steps --record ../../../reports/KEDU-PRODUCTION-008/observed.json --case C01
python -m tools.multi_steps --record ../../../reports/KEDU-PRODUCTION-008/observed.json --case A02
```

C01은 검색 역할의 첫 되묻기에서 끝나 작성·검토가 호출되지 않았다. A02는 검색/읽기/전달 후 작성자가 자료 부족 초안을 내고 검토자가 기각했다. 원문이 있었는지와 보류가 적절했는지를 확인한다. 검토까지 호출됐다는 이유로 과제 성공으로 채점하지 않는다.

실제 역할별 입력이 필요하면 단일 사례에 `--input`을 붙인다. 저장된 Chat Template 적용 전 메시지이며 내부 추론이나 새로운 Tokenizer 실행이 아니다. 작성자 입력에 검증된 근거와 필요한 보완 정보, 검토자 입력에 초안/근거/실패가 있는지 본다. 전체 대화 로그를 전달한다고 가정하지 않는다.

[기존 Single/Multi 비교](../../reports/KEDU-PRODUCTION-008/REVIEW.md)에서 같은 18개 질문을 대조한다. Single4/3/180초와 Multi8/6/240초, 역할별 지시 차이를 함께 기록한다. 첫 역할에서 일찍 끝난 실행의 짧은 지연을 성공적 비용 절감으로 표현하지 않는다. 모델 적재 시간과 질문 처리 시간, 미측정과 0도 구분한다.

## 활동 5. 별도 Role Probe를 통합 성공과 분리

writer-probe/reviewer-probe는 실행기가 근거를 준비해 해당 역할을 따로 부른 기록이다. 실제 검색자의 전달을 이어받은 전체 성공 수에 더하지 않는다. 원문을 읽고도 답을 못 쓴 것인지, 앞 역할에서 멈춰 작성자를 시험하지 못한 것인지 분리한다.

| 제출할 표 | 적을 내용 |
|---|---|
| 역할 계약 | 목표·볼 정보·허용 도구/행동·전달할 자료 |
| Handoff | 실제 읽은 ID·수신 범위·원문 버전/변경 번호·실패 ID |
| 전체 예산 | 역할별/전체 모델·도구·보완·재시도와 종료 지점 |
| 결과 | 부분 초안·최종 전달·검토 의견·의미/조건/예외의 미완료 |
| 비교 범위 | 고정실험/과거 실제통합/별도Probe/본인의 새 실행을 명시 |

사실 6개·core 경계 6개·Agent 경계 6개를 유지하고 M01~M04를 사실 정답률 분모에 더하지 않는다. 다른 역할이나 Fine-tuning을 추가한다는 계획을 실제 품질 개선 완료로 표시하지 않는다.

## 실제 모델을 새로 실행하려면

L5의 Linux x86_64 Python 3.12 CPU 환경과 모델 캐시를 그대로 사용한다. 새 패키지나 유료 API는 필요하지 않다. 아래는 backend 폴더에서 **입력할 명령**이며 관찰 결과 예시가 아니다.

| 목적 | 입력할 명령 |
|---|---|
| 기존·새 경계 검사 | `python -m pytest -q` |
| 고정 응답 M01~M04와 정상 경로 | `python -m tools.multi_fixture_lab --output l6-fixtures.json` |
| 실제 모델의 한 사례 | `python -m tools.multi_lab --output l6-multi --cases C01` |
| 같은 설정으로 18개·별도 역할 확인 이어가기 | `python -m tools.multi_lab --resume --output l6-multi --role-probes` |

기본 실행은 모델 캐시만 읽는다. 캐시가 없을 때만 최초 download 옵션을 사용한다. 이전 결과를 덮어쓰지 않고 완료 사례를 재사용한다. 기록한 코드·자료·모델 설정이 바뀌면 새 폴더를 쓴다.

모델은 입력 1536 Token·출력 최대 192 Token, 입력은 2000문자 제한도 적용한다. 중요한 원문을 몰래 자르지 않고 초과하면 중단한다. 교육생 GPU·다른 운영체제·동시 수업 실행은 검증하지 않았다.


위 명령은 본인의 새 모델 실행 준비이며 이번 교안 정비에서 실제 모델을 재실행한 기록이 아니다. 직접 활동 코드는 기존 Pydantic 앱 환경에서 모델 없이 실행할 수 있다. 고정 요구 2.14.2와 이번 보조 환경 2.14.1의 차이는 검증 기록에 남긴다.

재개는 완료 사례를 다시 생성하지 않고 재사용한다. 코드/자료/프로필의 기록 범위와 현재 환경을 대조하며 모든 패키지/소스의 완전한 Lock으로 취급하지 않는다. 이전 파일이 있으면 새 이름을 선택하고, 캐시·의존성·길이 오류는 미실행으로 남긴다. TLS 검증을 끄거나 고정 응답으로 몰래 바꾸지 않는다.

새 multi_lab 출력은 사례별 JSON이며 새 읽기 도구는 과거 합본/fixture 형식을 받는다. 개별 파일에서는 budget, handoffs, sources, draft/partial_draft, model_review, generation_observations와 trace를 직접 확인한다. 역할 Probe 파일도 통합 사례와 분리한다. 교육생 GPU·다른 운영체제·동시 수업·실제 인증/승인·독립 수업 검증은 미완료다.
