좋습니다. 14~17번은 사실 **하나의 이야기를 단계별로 쪼개 놓은 것**입니다.

핵심 흐름은 이겁니다.

```text
Python Function
      ↓
Tool로 등록
      ↓
Model에게 "사용 가능한 Tool"을 알려줌
      ↓
Model이 Tool 사용 여부를 판단
      ↓
Application이 실제 Function 실행
      ↓
결과를 다시 Model에게 전달
      ↓
필요하면 이 과정을 반복
      ↓
Agent
```

하나씩 연결해보겠습니다.

---

# 1. 출발점: 일반 LLM의 한계

먼저 Tool도 Agent도 없는 일반적인 LLM 호출입니다.

```text
User
 ↓
Model
 ↓
Answer
```

예를 들어 사용자가 질문합니다.

> "현재 서울 날씨 알려줘."

LLM은 기본적으로 현재 날씨를 직접 측정하거나 외부 시스템을 조회하는 프로그램이 아닙니다.

```text
User
"현재 서울 날씨 알려줘"
        ↓
       LLM
        ↓
자신이 가지고 있는 Context를 기반으로 답변
```

그런데 우리가 LLM에게 **외부 기능을 사용할 수 있는 방법**을 제공하면 상황이 달라집니다.

그게 Tool입니다.

---

# 2. 14번 - Tool

우리가 Python Function을 하나 만들었다고 해봅시다.

```python
def get_weather(city: str) -> str:
    # 실제로는 Weather API 호출
    return "서울: 맑음, 25도"
```

이건 아직 그냥 Python Function입니다.

```text
Python Application

get_weather("Seoul")
        ↓
Weather API
        ↓
"맑음, 25도"
```

LLM과 아무 관계가 없습니다.

그런데 LangChain 같은 Framework를 이용해서 이것을 **Tool로 등록**할 수 있습니다.

개념적으로:

```python
@tool
def get_weather(city: str) -> str:
    """지정한 도시의 현재 날씨를 조회한다."""
    ...
```

이제 Application은 Model에게 다음과 같은 정보를 제공할 수 있습니다.

```text
사용 가능한 Tool:

name:
    get_weather

description:
    지정한 도시의 현재 날씨를 조회한다.

arguments:
    city: str
```

여기서 아주 중요한 게 있습니다.

LLM에게 Python 소스코드 자체를 통째로 주면서

> "이 함수 실행해."

하는 개념으로 이해하면 안 됩니다.

Model이 알아야 하는 핵심은 대략:

```text
Tool 이름
Tool 설명
Parameter 구조
```

입니다.

---

# 3. Model 입장에서는 이렇게 보이는 것

Model에게:

```text
User:
현재 서울 날씨 알려줘.

Available Tools:

get_weather
- 지정한 도시의 현재 날씨를 조회합니다.
- city: string
```

같은 정보가 주어졌다고 생각해봅시다.

Model이 판단합니다.

```text
"현재 날씨는 내가 가지고 있는 지식만으로
정확하게 답변하기 어렵다."

        ↓

"get_weather라는 Tool이 있네."

        ↓

"이 Tool을 호출해야겠다."
```

그래서 Model이 일반적인 자연어 답변 대신 **Tool 호출 요청**을 생성할 수 있습니다.

개념적으로:

```json
{
  "tool": "get_weather",
  "arguments": {
    "city": "Seoul"
  }
}
```

여기까지가 **Model의 역할**입니다.

---

# 4. 15번의 핵심: Model이 Python을 실행한 게 아니다

이 부분이 가장 중요합니다.

Model이:

```text
get_weather(city="Seoul")
```

를 호출해야겠다고 **결정한 것**과 실제 Python Function이 **실행된 것**은 다른 일입니다.

Model은:

```text
"get_weather를
city=Seoul로 호출해주세요."
```

라는 요청을 출력한 것입니다.

그다음 Application 또는 Agent Runtime이 이 요청을 받아서 실제 함수를 실행합니다.

```text
Model

get_weather
city="Seoul"
     │
     │ Tool Call 요청
     ▼
Application / Agent Runtime
     │
     │ 실제 Python 실행
     ▼
get_weather("Seoul")
     │
     ▼
Weather API
     │
     ▼
"서울 맑음, 25도"
```

즉 역할을 정확히 나누면:

```text
Model
= 어떤 Tool을 사용할지 판단

Application / Runtime
= 실제 Tool 실행
```

입니다.

---

# 5. Tool 실행 결과를 다시 Model에게 줌

그런데 여기서 끝나면 안 됩니다.

Python Function은:

```text
서울: 맑음, 25도
```

라는 결과만 반환했습니다.

이걸 사용자에게 자연스럽게 설명해야 합니다.

그래서 Tool Result를 다시 Model에게 전달합니다.

```text
User
"현재 서울 날씨 알려줘."
        ↓
Model
        ↓
Tool Call 요청
get_weather("Seoul")
        ↓
Application
        ↓
Python Function 실행
        ↓
Tool Result
"서울: 맑음, 25도"
        ↓
Model
        ↓
"현재 서울은 맑고 기온은 25도입니다."
        ↓
User
```

이게 15번의 **Tool Calling Flow**입니다.

---

# 6. 그러면 Agent는 뭔가?

이제 16번으로 자연스럽게 연결됩니다.

Tool 하나를 한 번 호출하는 정도는 단순합니다.

그런데 사용자의 요청이 이렇게 복잡하다고 해봅시다.

> "오늘 서울 날씨 확인하고 비가 안 오면 내 일정 확인해서 오후에 비는 시간 알려줘."

사용 가능한 Tool이:

```text
get_weather
get_calendar
```

라고 합시다.

그러면 한 번의 Tool Call로 끝나지 않습니다.

Model이 먼저 판단합니다.

```text
Goal

"오늘 서울 날씨 확인하고
비가 안 오면
오후의 빈 일정 찾아줘."
```

첫 번째:

```text
Model
 ↓
날씨부터 확인해야겠다.
 ↓
get_weather("Seoul")
```

Application이 실행합니다.

```text
Tool Result
 ↓
"서울: 맑음"
```

이 결과가 다시 Model에게 갑니다.

Model이 다시 판단합니다.

```text
"비가 안 오는구나."

        ↓

"그러면 Calendar를 확인해야겠다."
```

두 번째 Tool을 요청합니다.

```text
get_calendar(...)
```

결과:

```text
13:00 회의
14:00 회의
16:00 미팅
```

Model이 최종적으로 판단합니다.

```text
"15:00~16:00이 비어있네."
```

그리고 답변합니다.

> "오늘 서울은 비가 오지 않을 예정이고, 오후 일정 중 3시부터 4시까지 시간이 비어 있습니다."

---

# 7. 이게 Agent의 핵심

Agent가 중요한 이유는 **한 번의 Model → Tool 호출로 끝나지 않을 수 있기 때문**입니다.

```text
             ┌───────────────┐
             │               │
             ▼               │
User → Model 판단            │
         ↓                   │
      Tool 필요? ── YES ─→ Tool
         │                   │
         │                Result
         │                   │
         │                   └─────┐
         │                         │
         └── NO                    │
             ↓                     │
        Final Answer               │
                                   │
                 Model ←───────────┘
```

즉 Model이 결과를 보고 **다시 판단할 수 있습니다.**

그래서 Agent의 핵심 중 하나가 **Loop**입니다.

```text
Think / Decide
      ↓
Tool Call
      ↓
Observation
      ↓
다시 Decide
      ↓
Tool Call
      ↓
Observation
      ↓
...
      ↓
Final Answer
```

여기서 `Think`는 개념적인 표현으로 이해하면 됩니다. 실제 시스템에서는 모델의 내부 추론 전체를 사용자에게 노출한다는 의미는 아닙니다.

---

# 8. 그래서 Tool과 Agent는 같은 게 아님

여기서 많이 헷갈립니다.

**Tool**은 기능입니다.

```text
Tool

get_weather()
search_document()
search_database()
send_email()
calculator()
```

**Agent**는 이런 Tool 중에서 **무엇을 언제 사용할지를 Model의 판단과 실행 Loop를 이용해 결정하는 시스템**입니다.

비유하면:

```text
Agent = 직원

Tool = 직원에게 주어진 도구
```

직원 책상에:

```text
🔨 망치
🔧 스패너
🪛 드라이버
```

가 있다고 해서 망치 자체가 직원은 아닙니다.

직원이:

```text
"이 작업에는 드라이버가 필요하겠군."

        ↓

드라이버 선택

        ↓

사용

        ↓

결과 확인

        ↓

"이번에는 스패너가 필요하겠군."
```

이라고 판단합니다.

LLM Agent도 비슷합니다.

```text
Agent
 │
 ├── Model ← 판단
 │
 ├── Tool A
 ├── Tool B
 ├── Tool C
 │
 └── Runtime ← 실제 실행
```

# 9. 14번의 search_document를 실제로 연결해보자

처음 질문에 나온 함수가:

```python
def search_document(query: str) -> str:
    ...
```

였죠.

이 함수가 Vector DB에서 사내 문서를 검색한다고 해봅시다.

```text
search_document
       ↓
Embedding
       ↓
Vector DB
       ↓
관련 Chunk 검색
       ↓
검색 결과 반환
```

Tool로 등록합니다.

```python
@tool
def search_document(query: str) -> str:
    """사내 문서에서 질문과 관련된 내용을 검색합니다."""
    ...
```

사용자가:

> "우리 회사 육아휴직 기간이 어떻게 돼?"

라고 물어봅니다.

그러면:

```text
User
 │
 │ "우리 회사 육아휴직 기간이 어떻게 돼?"
 ▼
Model
 │
 │
 │ "내 일반 지식이 아니라
 │  회사 내부 문서를 찾아야겠다."
 │
 ▼
Tool Call 요청

search_document(
    query="육아휴직 기간"
)
 │
 ▼
Agent Runtime
 │
 │ 실제 Python Function 실행
 ▼
Vector DB
 │
 ▼
관련 문서 반환

"취업규칙 제32조..."
 │
 ▼
Model
 │
 │ 검색된 내용을 이용하여 답변 생성
 ▼
Final Answer
```

여기서 `search_document()`는 사실상 **RAG의 Retrieval 부분을 Tool로 만든 것**이라고 볼 수도 있습니다.

---

# 10. RAG와 Agent가 여기서 연결됨

예전에 배웠던 일반적인 RAG는:

```text
User Question
      ↓
Retriever
      ↓
Vector DB
      ↓
Context
      ↓
LLM
      ↓
Answer
```

입니다.

이 경우 **항상 Retrieval을 수행하도록** 애플리케이션을 만들 수 있습니다.

그런데 Retrieval 자체를 Tool로 제공하면:

```text
User
 ↓
Agent
 ↓
Model 판단
 │
 ├── 검색 필요 없음
 │      ↓
 │    Answer
 │
 └── 검색 필요함
        ↓
 search_document Tool
        ↓
 Vector DB
        ↓
 Context
        ↓
 Model
        ↓
 Answer
```

처럼 만들 수 있습니다.

즉 모델이 **"이번 질문은 문서 검색이 필요한가?"**를 판단하도록 설계할 수도 있습니다.

# 11. Tool이 여러 개라면 Agent의 의미가 더 커짐

예를 들어 사내 AI Assistant를 만든다고 합시다.

사용 가능한 Tool:

```text
Tools
│
├── search_document()
│      └─ 사내 문서 RAG
│
├── search_employee()
│      └─ 직원 DB 조회
│
├── search_schedule()
│      └─ 일정 조회
│
├── calculator()
│      └─ 계산
│
└── web_search()
       └─ 인터넷 검색
```

사용자가:

> "우리 회사 육아휴직 규정을 찾아보고, 내가 10월 1일부터 6개월 사용하면 복귀일이 언제인지 계산해줘."

라고 요청합니다.

Agent는:

```text
Goal
 ↓
육아휴직 규정을 알아야 함
 ↓
search_document()
 ↓
Result
 ↓
6개월 사용 가능 확인
 ↓
날짜 계산 필요
 ↓
calculator()
 ↓
Result
 ↓
Model
 ↓
Final Answer
```

처럼 여러 Tool을 조합할 수 있습니다.

이게 **단순 Tool Calling보다 Agent라는 개념이 중요해지는 지점**입니다.

---

# 12. 단순 Model Call → Tool Calling → Agent

그래서 14~17번을 사실 세 단계로 정리하면 아주 깔끔합니다.

### Level 1 — Model Call

```text
User
 ↓
Model
 ↓
Answer
```

모델이 자신의 Context 안에서 답변합니다.

### Level 2 — Tool Calling

```text
User
 ↓
Model
 ↓
Tool Call 요청
 ↓
Application
 ↓
Tool 실행
 ↓
Result
 ↓
Model
 ↓
Answer
```

외부 기능을 사용할 수 있게 됐습니다.

### Level 3 — Agent

```text
                ┌──────────────┐
                │              │
                ▼              │
User → Model → 판단             │
          │                     │
          ├─ Tool A → Result ───┤
          │                     │
          ├─ Tool B → Result ───┤
          │                     │
          └─ 완료               │
              ↓                 │
         Final Answer           │
```

Model이 **목표를 달성할 때까지 어떤 Tool을 사용할지 판단하고, 결과를 보고 다음 행동을 결정하는 실행 구조**가 됩니다.

---

# 13. 한 가지 표현은 수정하는 게 좋음

17번의:

```text
Agent:

User
↓
Model
↓
Tool
↓
Model
↓
다른 Tool
↓
Model
↓
Answer
```

은 개념 설명으로는 괜찮지만, 엄밀하게 보면 중간의 **Application / Agent Runtime**이 빠져 있습니다.

학생들이 "LLM이 Python을 직접 실행한다"고 오해할 수 있으므로 다음처럼 쓰는 것을 추천합니다.

```text
User
 ↓
Model
 ↓
Tool Call 요청
 ↓
Agent Runtime
 ↓
Tool 실행
 ↓
Tool Result
 ↓
Model
 ↓
다음 행동 판단
 ↓
필요하면 Tool Call 반복
 ↓
Final Answer
```

이렇게 하면 14번에서 강조한:

> **Model이 Python Function 자체가 되는 것이 아니다.**

와 정확하게 연결됩니다.

---

## 14~17번 전체를 한 문장으로 연결하면

> **Tool은 LLM이 사용할 수 있도록 Application이 제공하는 외부 기능이고, Model은 필요할 때 Tool 호출을 요청하며, 실제 Function은 Application/Runtime이 실행합니다. Agent는 이러한 Model의 판단 → Tool 선택 → 실행 → 결과 확인 과정을 필요에 따라 반복하면서 사용자의 Goal을 해결하는 시스템입니다.**

결국 역할을 세 개로 분리해서 기억하면 가장 쉽습니다.

```text
Model
"무엇을 할지 판단"
        ↓
Agent Runtime
"판단에 따라 실행 흐름 관리"
        ↓
Tool
"실제 외부 작업 수행"
```

이 구분을 확실히 해두면 이후 **MCP, Function Calling, LangGraph Agent, ReAct Agent** 같은 개념을 배울 때도 훨씬 덜 헷갈립니다.
