좋습니다. 18~19번은 앞에서 배운 **Model → Tool → Agent**에서 한 단계 더 나아가,

> **"Agent의 복잡한 실행 흐름은 누가 관리하고, 그 흐름이 제대로 동작하는지는 어떻게 확인하는가?"**

를 설명하는 부분입니다.

먼저 전체 관계를 잡으면 쉽습니다.

```text
             AI Application
                    │
        ┌───────────┴───────────┐
        │                       │
    LangChain               LangSmith
        │                  관찰 / 평가
        │
      Agent
        │
        ▼
    LangGraph
  실행 흐름 / 상태 관리
        │
        ├── Model
        ├── Tool
        ├── Model
        └── Tool
```

# 1. 앞에서 만든 Agent부터 다시 보면

17번에서 Agent를 이렇게 설명했습니다.

```text
User
 ↓
Model
 ↓
Tool Call 요청
 ↓
Agent Runtime
 ↓
Tool 실행
 ↓
Result
 ↓
Model
 ↓
필요하면 반복
 ↓
Answer
```

그런데 실제 Agent가 복잡해지면 문제가 생깁니다.

예를 들어:

```text
사용자 질문
    ↓
질문 분석
    ↓
문서 검색 필요?
   ↙       ↘
 YES       NO
 ↓          ↓
RAG       Model
 ↓
검색 결과 충분?
 ↙       ↘
YES       NO
 ↓         ↓
Model    Web Search
 ↓         ↓
검증 ←─────┘
 ↓
답변
```

이제 단순한:

```text
Model → Tool → Model
```

수준이 아닙니다.

**분기, 반복, 상태 저장, 실패 처리** 등이 필요해집니다.

이걸 체계적으로 제어하는 것이 LangGraph의 핵심 역할입니다.

# 2. LangGraph란?

[LangGraph 공식 문서](https://docs.langchain.com/oss/python/langgraph/overview?utm_source=chatgpt.com)

LangGraph는 **상태(State)를 가지는 장시간 실행 Agent/Workflow를 구성하고 실행하기 위한 저수준 orchestration framework/runtime**입니다.

여기서 두 단어가 중요합니다.

```text
Stateful

Orchestration
```

---

# 3. Stateful이란?

State는 쉽게 말해서 **현재 작업 상태/중간 데이터**입니다.

예를 들어 Agent가 이런 작업을 하고 있다고 합시다.

> "사내 규정을 검색해서 질문에 답해."

처음에는:

```text
State

question:
"육아휴직 기간은?"

documents:
없음

answer:
없음
```

문서를 검색하고 나면:

```text
State

question:
"육아휴직 기간은?"

documents:
[
  "취업규칙 제32조...",
  "인사규정 제17조..."
]

answer:
없음
```

LLM이 답변을 생성하면:

```text
State

question:
"육아휴직 기간은?"

documents:
[...]

answer:
"육아휴직은..."
```

처럼 상태가 계속 변합니다.

즉:

```text
State ①
  ↓
Node 실행
  ↓
State ②
  ↓
Node 실행
  ↓
State ③
```

이러한 **State를 중심으로 Workflow를 실행**하는 것이 LangGraph의 중요한 특징입니다.

---

# 4. Graph라는 이름은 왜 붙었나?

LangGraph에서는 실행 단계를 **Node와 Edge**로 표현할 수 있습니다.

예를 들어:

```text
        ┌─────────────┐
        │   Router    │
        └──────┬──────┘
               │
        질문 종류 판단
          ↙          ↘
         /            \
        ▼              ▼
 ┌──────────┐    ┌──────────┐
 │ RAG Node │    │ SQL Node │
 └────┬─────┘    └────┬─────┘
      │               │
      └───────┬───────┘
              ▼
       ┌────────────┐
       │ Evaluator  │
       └─────┬──────┘
             │
             ▼
          Answer
```

여기서:

```text
Node
= 실제 작업

Edge
= 다음에 어디로 갈지
```

라고 이해하면 됩니다.

Node 안에서는:

```text
LLM 호출
Tool 실행
RAG 검색
DB 조회
결과 평가
```

등을 할 수 있습니다.

# 5. Orchestration이란?

이 단어가 처음 보면 어렵습니다.

Orchestration은 쉽게 말하면:

> **여러 작업을 어떤 순서와 조건으로 실행할지 조정하고 관리하는 것**

입니다.

오케스트라의 지휘자를 생각하면 됩니다.

```text
바이올린
첼로
피아노
트럼펫
드럼
```

각자 악기는 있지만 마음대로 연주하면 안 됩니다.

지휘자가:

```text
지금 바이올린
      ↓
다음 첼로
      ↓
여기서 모두 같이
```

처럼 전체 흐름을 조정합니다.

AI Application에서도:

```text
LLM
RAG
SQL
Web Search
Tool
Evaluator
```

가 있다면:

```text
어떤 것을 실행?
       ↓
다음에는 무엇?
       ↓
실패하면 어디로?
       ↓
결과가 부족하면 반복?
       ↓
언제 종료?
```

같은 실행 흐름을 관리해야 합니다.

이것이 **Orchestration**입니다.

---

# 6. 그러면 LangChain과 LangGraph의 차이는?

현재 LangChain의 고수준 Agent 기능은 LangGraph를 기반으로 동작합니다.

개념적으로:

```text
LangChain Agent

"Tool을 사용하는 Agent 만들어줘."
          ↓
높은 수준 API
          ↓
       LangGraph
          ↓
실제 상태/실행 흐름 관리
```

LangChain에서는 비교적 높은 수준으로 Agent를 구성할 수 있습니다.

```python
agent = create_agent(
    model=model,
    tools=tools
)
```

개발자는:

```text
Model
Tools
System Prompt
...
```

등을 설정하고 Agent를 사용할 수 있습니다.

반면 LangGraph로 직접 내려가면:

```text
Node를 어떻게 구성할까?

State에는 무엇을 넣을까?

어떤 조건에서 다음 Node로 갈까?

언제 반복할까?

어디에서 종료할까?
```

같은 것을 더 직접적으로 설계합니다.

# 7. 자동차로 비유하면

이렇게 생각하면 이해하기 좋습니다.

### LangChain Agent

```text
자동차 운전

D 넣고
가속페달 밟고
브레이크 밟고
운전
```

사용자는 높은 수준의 인터페이스를 사용합니다.

### LangGraph

```text
엔진
변속기
브레이크
전자제어장치
센서
상태 관리
```

등을 좀 더 직접적으로 다루는 쪽에 가깝습니다.

따라서:

> **LangChain Agent = 일반적인 Agent를 편하게 만드는 높은 수준 추상화**

> **LangGraph = 복잡한 Agent/Workflow의 실행 구조와 상태를 세밀하게 제어하는 낮은 수준 계층**

정도로 이해하면 됩니다.

단, LangGraph가 단순히 LangChain 내부의 "숨겨진 엔진"일 뿐이라고 이해하는 것도 정확하지 않습니다. **LangGraph를 독립적으로 직접 사용해서 Workflow를 만들 수도 있습니다.**

# 8. 언제 LangGraph가 필요할까?

아주 간단한 Agent:

```text
User
 ↓
Model
 ↓
Tool
 ↓
Model
 ↓
Answer
```

라면 굳이 처음부터 LangGraph를 직접 설계할 필요가 없습니다.

그런데 다음처럼 복잡해지면 이야기가 달라집니다.

```text
Question
 ↓
Router
 ↓
┌─────────┬──────────┬─────────┐
↓         ↓          ↓         ↓
RAG      CAG        SQL       Web
│         │          │         │
└─────────┴────┬─────┴─────────┘
               ↓
           Evaluator
               ↓
          결과 충분한가?
           ↙       ↘
         YES       NO
          ↓         ↓
       Answer      Retry
                    ↓
                  Router
```

이런 구조에서는:

```text
분기
반복
State
Error Handling
Checkpoint
Human-in-the-loop
```

같은 기능이 중요해집니다.

이런 경우 LangGraph의 의미가 커집니다.

이제 19번 LangSmith가 등장합니다.

Agent가:

```text
Model
 ↓
RAG
 ↓
Model
 ↓
SQL
 ↓
Model
 ↓
Tool
 ↓
Model
```

처럼 돌아갔다고 합시다.

사용자가 말합니다.

> "답변이 이상한데?"

그러면 개발자는 궁금합니다.

```text
어디서 잘못됐지?

Retriever가 이상한 문서를 찾았나?

Prompt가 문제인가?

어느 단계가 오래 걸렸지?
```

일반적인 로그만 가지고 분석하기가 상당히 어려워집니다.

그래서 **Observability**가 필요합니다.

# 10. LangSmith란?

[LangSmith 공식 사이트](https://www.langchain.com/langsmith?utm_source=chatgpt.com)

LangSmith는 LLM Application과 Agent를 **추적하고, 디버깅하고, 평가하고, 관찰하기 위한 플랫폼**입니다.

대표적으로:

```text
Tracing
Debugging
Evaluation
Observability
```

를 지원합니다.

LangGraph처럼 Workflow를 만드는 역할이 아닙니다.

**만들어진 AI Application이 어떻게 실행되고 있는지 들여다보고 평가하는 쪽**입니다.

---

# 11. Tracing

Tracing은 굉장히 중요합니다.

사용자 질문 하나가 들어왔습니다.

```text
"우리 회사 육아휴직 기간 알려줘."
```

Agent 내부에서:

```text
User
 ↓
Router
 ↓
RAG
 ↓
Retriever
 ↓
Vector DB
 ↓
LLM
 ↓
Answer
```

가 실행되었습니다.

LangSmith를 사용하면 이런 실행 과정을 **Trace**로 추적할 수 있습니다.

개념적으로:

```text
Trace #1234

User Input
 │
 ├─ Router
 │    └─ Result: RAG
 │
 ├─ Retriever
 │    ├─ Query: "육아휴직 기간"
 │    └─ Documents: 5
 │
 ├─ LLM
 │    ├─ Prompt
 │    ├─ Model
 │    ├─ Tokens
 │    └─ Response
 │
 └─ Final Answer
```

즉 Agent 내부에서 무슨 일이 일어났는지 볼 수 있게 됩니다.

---

# 12. Debugging

Tracing이 가능하면 문제가 생겼을 때 원인을 찾을 수 있습니다.

예를 들어 답변이 틀렸습니다.

Trace를 봅니다.

```text
User Question
     ↓
Router
     ↓
RAG 선택       ← 정상
     ↓
Retriever
     ↓
엉뚱한 문서 검색 ← 문제 발견
     ↓
LLM
     ↓
잘못된 Answer
```

그러면:

> "LLM 자체가 문제라기보다 Retrieval 단계가 문제구나."

라고 판단할 수 있습니다.

이게 Debugging입니다.

---

# 13. Evaluation

Evaluation은:

> **내 AI Application이 얼마나 잘 동작하는지 평가하는 것**

입니다.

예를 들어 테스트 Dataset을 만들어 놓습니다.

```text
Question 1
Expected Answer 1

Question 2
Expected Answer 2

Question 3
Expected Answer 3

...
```

그리고 새로운 Prompt나 Model을 적용합니다.

```text
Model A
 ↓
Evaluation
 ↓
Score

Model B
 ↓
Evaluation
 ↓
Score
```

또는:

```text
Prompt V1
vs
Prompt V2
```

를 비교할 수도 있습니다.

앞에서 배운 **Evaluation Result**를 이제 완성된 LLM Application 수준에서도 수행한다고 보면 됩니다.

---

# 14. Observability

Observability는 더 큰 개념입니다.

> **실제 시스템이 어떻게 동작하고 있는지 지속적으로 관찰할 수 있는 능력**

입니다.

예를 들어:

```text
어떤 요청이 들어왔는가?

어떤 Model을 호출했는가?

어떤 Tool을 호출했는가?

얼마나 오래 걸렸는가?

Token은 얼마나 사용했는가?

어디에서 Error가 발생했는가?

어떤 응답이 생성되었는가?
```

등을 확인합니다.

즉:

```text
Tracing
Debugging
Metrics
Monitoring
Evaluation
...
        ↓
Observability
```

라고 생각하면 됩니다.

# 16. 개발자 관점에서 한 문장씩

**LangChain**

> "AI Application을 어떻게 쉽게 만들까?"

```text
Model + Prompt + Tool + Retriever + Agent
```

**LangGraph**

> "복잡한 AI Workflow를 어떤 순서와 상태로 실행할까?"

```text
State + Node + Edge + Branch + Loop
```

**LangSmith**

> "그 AI Application이 제대로 돌아가고 있는지 어떻게 확인할까?"

```text
Trace + Debug + Evaluate + Observe
```

따라서 세 제품은 경쟁 관계가 아니라 **서로 다른 문제를 해결합니다.**

# 17. 지금 수업에서 LangGraph 구현을 안 하는 이유도 자연스러움

Phase 1에서 먼저:

```text
LLM이란?
 ↓
Model Call
 ↓
Prompt
 ↓
Tool
 ↓
Tool Calling
 ↓
Agent
```

를 이해해야 합니다.

그다음에야:

```text
Agent가 복잡해진다.
 ↓
상태가 필요하다.
 ↓
분기가 필요하다.
 ↓
반복이 필요하다.
 ↓
실행 흐름을 관리해야 한다.
 ↓
LangGraph
```

라는 필요성이 생깁니다.

그래서 현재 자료에서 **18번까지는 "LangGraph가 왜 존재하는지 개념만 이해하고 구현은 나중에 한다"**는 순서가 꽤 자연스럽습니다.

그리고 그 다음 19번에서:

```text
복잡한 Application을 만들었다.
        ↓
그런데 내부에서 뭘 하는지 어떻게 알지?
        ↓
LangSmith
```

가 등장하는 것도 자연스럽습니다.

결국 14~19번 전체가 하나의 흐름입니다.

```text
Python Function
      ↓
     Tool
      ↓
Tool Calling
      ↓
    Agent
      ↓
복잡한 Agent Workflow
      ↓
   LangGraph
      ↓
복잡해져서 내부 관찰 필요
      ↓
   LangSmith
```

이 흐름으로 학생들에게 설명하면 각각을 따로 외우는 것보다 **"왜 다음 기술이 등장했는가"**를 이해하기 훨씬 쉽습니다.
