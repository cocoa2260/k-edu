# Day 3 - 5교시. AI Model Selection과 운영 — Hugging Face Model Card 활용 (v0.2)

## 개요 — ‘모델을 아는 것’에서 ‘선택을 증명하는 것’으로

Day 2 - 4교시에서는 Hugging Face의 Model Repository와 Model Card에서 **선택에 필요한 근거를 찾는 방법**을 배웠습니다. Day 3 - 1~4교시에서는 Model Family와 Variant, Base/Instruction 차이, Quantization 및 실제 Hardware 조건을 다뤘습니다.

이번 교시에서는 해당 개념을 다시 정의하거나 같은 종류의 후보를 나열하지 않습니다. 이미 알고 있는 정보들을 **하나의 의사결정**으로 연결합니다.

> **“후보 모델 두 개 중 어느 것을 사용해야 하며, 왜 그렇게 판단했는가?”에 대해 다른 개발자도 검토할 수 있는 기록을 남길 수 있을까?**

오늘 완성할 산출물은 아래 세 가지입니다.

1. **요구사항·제외 조건표:** 사용할 수 없는 모델을 우선 걸러 내는 기준
2. **프로젝트 평가표:** 동일 조건으로 실행한 후보별 결과와 검증 상태
3. **Model Selection Record:** 선택·보류·제외 이유와 변경 시 재검증 기준을 담은 기록

Model Card는 1번과 2번에 필요한 자료를 찾는 출발점이지만, **Model Card를 읽었다는 사실만으로 모델 선정이 끝나지는 않습니다.**

### 이번 교시의 범위

- **이번 교시:** 요구사항 → 후보 자격 검토 → 공정한 평가 → 근거 기반 결정 → 운영 이력과 재검증
- **반복하지 않음:** Model Card의 기본 구조 및 항목별 사전식 설명(Day 2 - 4교시), Model Family/Quantization/CPU·GPU 기본 정의(Day 3 - 1~4교시)
- **다음 교시에 남김:** LangChain·LlamaIndex 등의 Framework 구조(Day 3 - 6교시), Provider 추상화 구현(Day 3 - 7교시), React–FastAPI 최종 연동(Day 3 - 8교시)

# 1. 학습 목표와 완료 기준

학생은 수업이 끝나면 다음 작업을 수행할 수 있어야 합니다.

1. 프로젝트 요구사항을 **필수 조건·품질 목표·보류 조건**으로 구분한다.
2. 정확한 Model ID, Revision, 사용 조건 및 실행 환경을 **근거와 함께 기록**한다.
3. Model Card에 적힌 값과 실제로 측정한 값을 구별한다.
4. 후보 모델의 비교 실험에서 **동일하게 유지해야 할 조건**을 정한다.
5. 대표 질문으로 구성한 간단한 평가 Dataset과 채점 기준을 작성한다.
6. 자동으로 검사할 수 있는 항목과 사람이 판단해야 하는 항목을 구분한다.
7. License·Runtime·Hardware·Quality 결과를 종합해 **선정/보류/제외**를 판정한다.
8. 선택한 모델이 변경될 때 어느 조건으로 재검증할지 기록한다.

**완료 기준:** 단순히 “A 모델이 더 좋다”라고 답하는 것이 아니라, **같은 자료를 받은 다른 사람이 판정의 근거와 미확인 항목을 확인할 수 있는 것**입니다.

# 2. 왜 이번에는 Model Card를 다시 ‘읽는 수업’으로 만들지 않을까?

이전에 이미 학습한 내용은 다음과 같습니다.

| 이미 배운 것 | 이번 교시에서 새로 수행할 일 |
|---|---|
| Hub에서 Model Card의 위치 찾기 | Card에서 확인한 사실을 **결정 증거**로 기록 |
| Task·Language·License·Limitation 항목 확인 | 요구사항에 비추어 **통과·실패·미확인** 판정 |
| Model Size·Quantization 해석 | 후보의 자원 제약을 **검증 항목**으로 전환 |
| Ollama·Transformers를 통한 실행 | 같은 기준으로 후보를 **시험·비교** |
| Base·Instruction Variant 구분 | 목적에 맞는 후보군을 제한한 뒤 **실측 결과**를 비교 |

이번 교시의 중요한 차이는 **‘정보가 무엇인가?’가 아니라 ‘그 정보로 어떤 결정을 내리고, 어떤 결론은 아직 내릴 수 없는가?’** 입니다.

# 3. 이번 교시에서 사용할 하나의 프로젝트 사례

가상의 교육 서비스에 다음 기능을 추가한다고 가정합니다.

**기능:** 교육생이 남긴 AI·개발 질문을 읽고 `초급 / 중급 / 고급` 중 하나로 분류하며, 분류 이유를 **한국어로 한 문장** 제공한다.

이 기능을 선택한 이유는 앞 강의에서 여러 번 등장한 ‘한국어 문서 요약’ 사례를 그대로 반복하지 않고, **분류 정확도·근거·응답 형식·실행 시간**을 분리해 평가하기 위해서입니다.

가정한 운영 조건은 다음과 같습니다.

| 구분 | 이번 수업의 프로젝트 요구사항(가정) |
|---|---|
| Input | 교육생이 작성한 한국어 질문 1개 |
| Output | 난이도 라벨 1개와 한국어 이유 1문장 |
| 허용 라벨 | `초급`, `중급`, `고급` |
| Deployment | 교육장 내부에서 실행하는 Local Model |
| 외부 전송 | 질문 내용을 외부 AI API로 전송하지 않음 |
| Hardware | 교육장 PC의 실제 사양을 수업 전에 기록해야 함 |
| 사용 조건 | 프로젝트에서 허용되는 사용·배포 조건 충족 |
| 품질 목표 | 라벨 오류가 적고 이유가 질문의 필요한 학습 수준을 설명해야 함 |
| 운영 목표 | 수업에서 정한 응답 대기 기준을 충족해야 함 |

**주의:** 여기의 프로젝트와 조건은 실습을 위해 만든 가정입니다. 특정 모델의 성능이나 교육장 장비를 실제로 검증했다는 뜻이 아닙니다.

학생에게 첫 질문을 던집니다.

> “어떤 Model Family를 사용할까?”보다 먼저, **이 요구사항에서 하나라도 충족하지 못하면 모델을 사용할 수 없는 조건**은 무엇일까요?

# 4. 조건을 세 부류로 구분하기

모든 기준을 같은 점수표에 넣으면 문제가 발생합니다. 예를 들어 성능이 아무리 좋아도 사용 조건이 맞지 않는 모델은 채택해서는 안 됩니다.

| 유형 | 뜻 | 예시 | 처리 |
|---|---|---|---|
| **필수 조건(Hard Gate)** | 만족하지 못하면 후보가 될 수 없는 조건 | 허용된 License/Terms, 외부 전송 금지, 필요한 Task 수행 및 Runtime 지원 | 실패 시 **제외** |
| **비교 조건(Trade-off)** | 후보 사이에서 상대적인 장단점을 비교하는 조건 | 한국어 이유의 정확성, 응답시간, 메모리 여유 | 조건별 점수·관찰 기록 |
| **증거 부족(Unknown)** | 맞는지 틀린지 아직 검증하지 못한 상태 | Terms 원문 미확인, 실제 장비 미측정, Revision 미기록 | **보류**, 추가 확인 |

여기서 **미확인과 불합격은 다릅니다.** 자료가 없다는 이유만으로 실패라고 단정하지 않지만, 확인되지 않은 필수 조건을 통과로 간주해서도 안 됩니다.

한 후보의 판정 흐름은 다음과 같습니다.

```text
후보 Model ID·Variant 확인
        ↓
필수 조건 확인
  ├─ 실패 확인 → 제외, 이유 기록
  ├─ 정보 부족 → 보류, 확인 담당·기한 기록
  └─ 모두 통과 → 프로젝트 평가 대상
                         ↓
                동일 조건으로 평가
                         ↓
                선정 / 추가 검증 / 제외
```

# 5. Model Card 정보는 ‘판정의 출처’이지 ‘검증 결과’는 아니다

Day 2에서 Card의 구조를 읽었습니다. 이번에는 **어디서 확인했는지와 어느 수준의 증거인지**를 기록합니다.

| 판단 질문 | 찾을 근거 | 기록 예시 |
|---|---|---|
| 어떤 작업용인가? | Task, Intended Use, Usage Example | `Card에 text-generation 명시` |
| 한국어를 지원한다고 주장하는가? | Language, Evaluation, Limitations | `다국어로 표기 / 한국어 실측 별도 필요` |
| 사용 가능한가? | License 원문, Terms, 제한 조건 | `Terms 확인 완료 또는 미확인` |
| 정확히 어떤 배포본인가? | Model ID, Revision, Variant | `저장소 ID와 사용한 Revision 기록` |
| 내 Runtime에서 실행 가능한가? | Library·Runtime 안내, 실제 로딩/실행 | `지원 주장`과 `실제 성공` 분리 |
| 성능을 믿을 근거가 있는가? | 평가 Dataset, Metric, 실행 설정 | `공개 Benchmark 참고 / 자체 평가 미수행` |

**근거의 신뢰 수준**도 구분합니다.

- **공식 명세 확인:** 해당 Model Card/공식 Terms에서 확인한 사양이나 조건
- **우리 환경에서 실측:** 대상 PC에서 실제 실행해 수집한 결과
- **추정:** Parameter 수, 정밀도 등을 바탕으로 계산한 근삿값
- **미확인:** 출처를 찾지 못했거나 실행 검증을 못한 항목

이 네 가지를 모두 ‘확인 완료’로 작성하면 안 됩니다. 예를 들어 `multilingual`이라는 표기는 한국어 품질의 **실측 결과**가 아닙니다.

# 6. 첫 번째 차단 조건 — 사용·배포 권한 확인

모델이 다운로드 가능한 것과 프로젝트에서 사용할 권한이 있는 것은 별개입니다. 이미 배운 License 정의를 다시 설명하지 않고, 이번에는 **승인 가능한 기록을 어떻게 남길지**를 다룹니다.

아래 사항은 현재 모델의 실제 Terms 원문을 읽고 확인해야 합니다.

| 검토 질문 | 확인 값 | 판정 |
|---|---|---|
| 현재 사용 목적에 적합한 사용 조건인가? | 근거 URL·문서명·확인일 | 통과/실패/미확인 |
| 필요 시 재배포 가능한가? | 해당 Terms 조항 | 통과/실패/해당 없음/미확인 |
| 부가적인 제한이나 의무가 있는가? | Attribution·Restricted Use 등 | 충족/미충족/미확인 |
| 파생 Model이면 관련 조건을 확인했는가? | Base Model과 해당 배포본의 조건 | 충족/미확인 |

Model Card의 `license` 필드만 보고 법적 검토가 끝났다고 기록하지 않습니다. Gated Repository의 경우 **접근 권한을 얻었는지**와 **사용 목적에 맞는 권한을 확보했는지**도 구분합니다.

**수업 판정 예:** “후보 A는 Model Card를 읽었지만 별도 Terms 확인이 필요하다.” → **선정 보류**. 이 예시는 가정이며 특정 실재 Model의 법적 상태를 말하지 않습니다.

# 7. 두 번째 차단 조건 — 실행 가능성의 ‘주장’과 ‘검증’ 분리

Day 3 - 3~4교시의 계산과 장비 진단을 오늘 다시 수행하지는 않습니다. 그 결과를 아래처럼 **판정 증거**로 사용합니다.

| 확인 항목 | 서류상 확인 | 실제 Target Hardware 검증 |
|---|---|---|
| 정확한 Model/Quantization | 모델 이름·배포 파일 확인 | 설치된 모델과 일치하는지 |
| 실행 Runtime | 문서의 지원 안내 | 실제 로딩·생성 성공 여부 |
| 저장 공간 | Repository에 표시된 파일 크기 | 다운로드와 여유 공간 확인 |
| Memory | 추정 또는 제공 사양 | 실행 도중 사용량·실패 여부 측정 |
| Context | 공식 지원 길이 | 실제 요구하는 입력 길이로 테스트 |
| Latency | 공개 Benchmarks 참고 | 교육장 PC에서 반복 측정 |

특히 **파일 크기가 RAM보다 작다 → 반드시 실행된다**라고 판단하면 안 됩니다. 그 이유와 메모리 배치는 앞 교시에서 배웠으므로 이번에는 추가 설명 대신 측정표에 남깁니다.

실행 결과를 기록하지 못한 상태에서는 `하드웨어 적합성: 미확인`으로 남겨야 합니다.

# 8. 후보를 두 개로 줄인 뒤에도 Model ID를 정확히 남긴다

오늘 사용할 후보 표입니다. 실제 교실에서는 강사가 확인한 Model을 넣습니다.

| 필드 | Candidate A | Candidate B |
|---|---|---|
| 정확한 Model ID | `<수업 후보 A>` | `<수업 후보 B>` |
| Revision / 배포 식별자 | 미입력 | 미입력 |
| Base / Instruction 여부 | 확인 필요 | 확인 필요 |
| 사용 Runtime | 확인 필요 | 확인 필요 |
| 사용 조건 검토 | 미확인 | 미확인 |
| Target Hardware 실측 | 미실시 | 미실시 |
| 이번 평가 참여 여부 | 보류 | 보류 |

후보의 **Family 이름만** 적거나 `latest`처럼 변경 가능한 이름만 기록하지 않습니다. Hub라면 Model ID와 가능한 경우 정확한 Revision을, 다른 배포 도구라면 해당 도구에서 확인할 수 있는 정확한 배포명·Version·Digest 등 식별자를 기록합니다.

이후 예제에 등장하는 `Candidate A/B`는 **특정 실제 Model을 가리키지 않는 실습용 가상 표기**입니다. 학생이 검증하지 않은 Model ID와 수치를 완성 답안처럼 채우지 않습니다.

# 9. 왜 공개 Benchmark 점수만으로 끝낼 수 없을까?

공개된 점수는 **어떤 데이터와 조건으로 측정된 결과인지**가 함께 있어야 의미가 있습니다.

예를 들어 다음 두 결과가 있다고 합시다. 이 수치는 **설명을 위한 가상 사례**입니다.

| 후보 | 공개 점수 | 실제 Project가 요구하는 작업 |
|---|---:|---|
| A | 90 | 교육생 질문의 난이도 분류 |
| B | 85 | 교육생 질문의 난이도 분류 |

여기서 A를 바로 선정할 수 있을까요? **아닙니다.** 점수 산출에 사용된 Dataset, Metric, Prompt, Model Revision 및 언어가 다를 수 있고, 해당 점수가 우리 분류 작업의 성능을 측정한 값인지 알 수 없기 때문입니다.

이번 교시의 새로운 작업은 **프로젝트 요구사항에 맞는 평가를 직접 정의**하는 것입니다.

# 10. 요구사항을 ‘시험 가능한 항목’으로 번역하기

| 요구사항 | 평가 질문 | 확인 방법 |
|---|---|---|
| 세 난이도 중 하나 반환 | 실제로 세 라벨 중 하나인가? | 출력 파싱 및 값 검사 |
| 질문 난이도 분류 | 강사가 정한 기준 라벨과 일치하는가? | 정답 대조 |
| 이유 한 문장 제공 | 왜 이 난이도인지 납득 가능한가? | 강사 판정 |
| 한국어 응답 | 이유가 한국어로 작성되었는가? | 직접 관찰 |
| 사실성 | 질문에 없는 조건을 지어내지 않았는가? | 근거 확인 |
| Local 실행 | 데이터가 요구 범위 밖으로 전송되지 않는가? | 실행 구조·환경 확인 |
| 사용자 대기 시간 | 요구하는 응답 시간 이내인가? | 동일 환경에서 측정 |
| 운영 가능성 | 실습에서 모델을 반복 로드·실행할 수 있는가? | 실패 및 재시도 기록 |

**모든 평가를 하나의 수치로 합치지는 않습니다.** `라벨 일치율`처럼 자동으로 셀 수 있는 것과 `설명 근거의 타당성`처럼 강사의 검토가 필요한 것을 구분합니다.

# 11. 평가 Dataset은 ‘많은 질문’보다 ‘구분 가능한 질문’부터

질문 난이도는 절대적인 정답이 저절로 존재하는 값이 아닙니다. 이 수업에서는 아래 운영 정의를 **강사가 사전에 합의한 분류 기준**으로 사용합니다.

| 라벨 | 이번 수업에서의 판정 기준 |
|---|---|
| 초급 | 한 개념의 뜻이나 단순 사실 확인을 묻는 질문 |
| 중급 | 이미 배운 기술을 적용하거나 한 단계 오류 원인을 확인하는 질문 |
| 고급 | 여러 조건을 종합하고 선택·트레이드오프·변경 영향을 판단해야 하는 질문 |

이 기준의 완성도를 검토하는 것도 평가 설계의 일부입니다. 같은 질문에 교사 두 명이 다른 라벨을 준다면 모델 오류로 단정하기 전에 **평가 기준이나 질문의 모호성**부터 확인해야 합니다.

실습용 평가 질문은 아래와 같습니다. **기준 라벨은 강사가 합의했다는 가정의 예시이며, 보편적으로 확정된 난이도 등급은 아닙니다.**

| Case ID | 질문 | 기준 라벨 | 이유의 핵심 |
|---|---|---|---|
| Q01 | “Token ID가 무엇인가요?” | 초급 | 단일 개념 설명 요청 |
| Q02 | “FastAPI에서 요청이 422로 끝나면 무엇을 확인하나요?” | 중급 | 한 API 문제의 진단 요청 |
| Q03 | “`ollama ls`에 보이는데 `ollama ps`가 비어 있어요. 무엇이 다른가요?” | 중급 | 실행 상태 확인 요청 |
| Q04 | “4-bit로 줄인 모델이 RAM 부족으로 중단됩니다. 추가로 어떤 요인을 점검하나요?” | 고급 | 여러 메모리 요인 종합 |
| Q05 | “GPU가 없으면 AI 모델을 실행할 수 없나요?” | 초급 | 단순 실행 가능성 확인 |
| Q06 | “모델 갱신 후 지연과 출력 형식 오류가 동시에 늘었습니다. 무엇을 비교해야 하나요?” | 고급 | 변경 원인과 회귀 검증 |

이 여섯 건은 **채점 방식을 이해하기 위한 극소형 실습 Dataset**일 뿐, 서비스 성능의 통계적 신뢰성을 확보한 평가 집합이 아닙니다. 실제 프로젝트에서는 더 다양한 길이·표현·모호한 질문·예외 입력을 포함하고, 기준 답안의 검토 이력도 남겨야 합니다.

# 12. 같은 조건으로 비교한다는 의미

A와 B에 서로 다른 조건을 주면 출력 차이를 모델 차이라고 단정할 수 없습니다.

| 통제할 항목 | 기록할 내용 |
|---|---|
| Dataset | 동일한 평가 질문, 같은 순서 또는 순서 차이를 기록 |
| Instruction | 같은 과제 설명과 라벨 기준 |
| Model ID/Revision | 정확한 배포본, Variant |
| Template | 각 Model이 공식적으로 요구하는 입력 형식을 준수했는지 |
| Generation 설정 | 가능한 한 비교 가능한 길이·샘플링 조건, 차이가 있다면 기록 |
| Runtime/Version | 사용한 Runtime과 Version |
| Hardware | CPU/GPU, Memory, 실행 위치 |
| 입력 길이 | 질문만 바꾸고 다른 Context가 유입되지 않도록 관리 |
| 측정 방식 | 처음 Load 시간을 포함하는지, 생성 시간만 재는지 명시 |
| 반복 횟수 | 같은 Case를 몇 번 실행했는지 기록 |

**주의:** 두 모델의 Chat Template이 다르면 문자열까지 억지로 똑같게 만드는 것이 공정한 비교는 아닙니다. 각 모델의 공식 입력 형식을 지키면서 **동일한 사용자 과제**를 수행시키고 형식 차이는 기록합니다.

샘플링 설정이나 환경이 달라지면 결과가 달라질 수 있으므로, **모델만 바뀌었다고 해석할 수 있는 범위**를 명확히 해야 합니다.

# 13. 평가용 Instruction을 먼저 고정한다

아래는 모델 평가를 위해 사용하는 **과제 정의 예시**입니다. Prompt Engineering이나 Chat Template의 내부 구현을 가르치기 위한 코드가 아닙니다.

```text
[과제]
사용자의 학습 질문을 초급, 중급, 고급 중 하나로 분류한다.

[판정 기준]
초급: 개념 하나의 뜻이나 단순 사실을 묻는다.
중급: 배운 기술의 적용이나 한 단계 오류 진단을 묻는다.
고급: 여러 조건을 종합하거나 선택·변경 영향을 판단한다.

[출력 계약]
level: 초급|중급|고급 중 하나
reason: 한국어 한 문장

[입력]
<평가 질문 한 개>
```

이것은 **평가 시 사용할 동일 과제 정의**입니다. 실제 모델별 Message 포맷에 어떻게 담는지는 해당 모델의 공식 사용법을 따릅니다.

모델이 이 계약을 반드시 지킨다고 보장할 수는 없습니다. 바로 그 **계약 준수 여부 자체를 평가 대상**으로 기록합니다. 한 후보에서 Prompt를 중간에 변경했다면 다른 후보도 동일 조건으로 다시 평가해야 합니다.

# 14. 평가 기록은 Case 단위로 남긴다

실제 평가 시 각 Case에 다음을 작성합니다.

| 기록 항목 | 설명 |
|---|---|
| Case ID | 평가 질문의 고유 번호 |
| Candidate / Revision | 평가에 사용한 정확한 Model 식별자 |
| Prompt Version | 사전에 정한 과제 정의의 버전 |
| Predicted Level | 실제로 출력된 난이도 |
| Reason | 실제 모델이 출력한 설명, 수정하지 않고 보존 |
| Ground Truth | 강사가 정한 기준 라벨 |
| Label Match | 라벨 일치 여부 |
| Reason Quality | 0~2점의 강사 평가 및 사유 |
| Format Valid | 약속한 출력 구조가 지켜졌는지 |
| Latency | 무엇을 포함한 시간인지와 단위 |
| Issue | 예외·누락·생성 중단·재시도 여부 |

**예상 결과는 실제 결과로 채우지 않습니다.** 강사가 실행 전 작성한 기대치와 모델 실행에서 나온 값은 별도 열로 보관합니다.

# 15. 단순한 평가 기준을 정하되, 점수의 한계를 명확히 한다

이번 교시의 예시 채점 규칙은 다음과 같습니다.

| 항목 | 판정 |
|---|---|
| 라벨 일치 | 기준 라벨과 동일하면 1점, 아니면 0점 |
| 이유의 타당성 | 2점: 질문이 요구하는 선수 수준을 설명 / 1점: 관련은 있지만 모호함 / 0점: 무관하거나 근거 없음 |
| 출력 형식 | `level` 유효 + `reason` 존재 시 통과, 아니면 실패 |
| 사실 왜곡·추측 | 문제 발견 여부와 사례 기록(필수 검토) |
| 실행 실패 | 실패 건수 및 원인 기록 |
| 실행 시간 | 동일하게 정한 측정 구간의 시간 기록 |

라벨 일치율의 예:

```text
라벨 일치율 = 일치한 Case 수 ÷ 전체 평가 Case 수 × 100
```

단, **라벨 일치율만으로 채택 여부를 결정하지 않습니다.** 이유가 틀리거나 외부 전송 금지·라이선스 조건을 위반하면 별도로 제외될 수 있습니다. 작은 Dataset에서 `5/6` 같은 숫자는 학생 활동용 참고값이지 실제 서비스의 품질 보증값이 아닙니다.

# 16. Python 실습 — 이미 얻은 분류 결과를 채점하기

이번 실습은 **모델을 다시 다운로드하거나 호출하지 않습니다.** Day 2에서 익힌 Python을 이용해, 평가 결과를 기록한 CSV 파일의 라벨 일치 여부만 집계합니다. 따라서 Model Selection의 **평가 단계**를 이해하는 데 집중할 수 있습니다.

아래 파일 3개를 같은 폴더에 저장합니다.

**① `cases.csv` — 강사가 합의한 기준 라벨**

```csv
case_id,expected_level
Q01,초급
Q02,중급
Q03,중급
Q04,고급
Q05,초급
Q06,고급
```

**② `candidate_sample.csv` — 채점기 검사용 가상 결과**

이 파일은 **실제 모델 출력이 아니라 채점 코드의 동작을 확인하기 위한 예시**입니다.

```csv
case_id,predicted_level
Q01,초급
Q02,초급
Q03,고급
Q04,고급
Q05,초급
Q06,고급
```

**③ `score_selection.py` — 채점 프로그램**

```python
import csv
from pathlib import Path

ALLOWED_LEVELS = {"초급", "중급", "고급"}


def load_rows(path: str, required_fields: set[str]) -> dict[str, dict[str, str]]:
    with Path(path).open("r", encoding="utf-8-sig", newline="") as file:
        reader = csv.DictReader(file)
        if not reader.fieldnames or not required_fields.issubset(reader.fieldnames):
            raise ValueError(f"필수 열 누락: {path}")
        records: dict[str, dict[str, str]] = {}
        for row in reader:
            case_id = (row.get("case_id") or "").strip()
            if not case_id or case_id in records:
                raise ValueError(f"Case ID 누락 또는 중복: {case_id!r}")
            records[case_id] = row
    if not records:
        raise ValueError(f"평가 행이 비어 있음: {path}")
    return records


def main() -> None:
    cases = load_rows("cases.csv", {"case_id", "expected_level"})
    results = load_rows("candidate_sample.csv", {"case_id", "predicted_level"})

    missing = sorted(set(cases) - set(results))
    extra = sorted(set(results) - set(cases))
    invalid = sorted(
        cid for cid, row in results.items()
        if (row.get("predicted_level") or "").strip() not in ALLOWED_LEVELS
    )
    correct = sum(
        (row["expected_level"].strip() ==
         (results[cid].get("predicted_level") or "").strip())
        for cid, row in cases.items()
        if cid in results
    )

    print(f"정답: {correct}/{len(cases)}")
    print(f"라벨 일치율: {correct / len(cases) * 100:.1f}%")
    print(f"누락 Case: {missing or '없음'}")
    print(f"예상 외 Case: {extra or '없음'}")
    print(f"허용되지 않은 라벨: {invalid or '없음'}")
    if missing or extra or invalid:
        print("주의: 데이터 불완전/형식 오류 — 모델 선정 근거로 사용 불가")
    else:
        print("형식 점검: 통과 (이유의 품질은 별도 수동 평가 필요)")


if __name__ == "__main__":
    main()
```

실행:

```bash
python score_selection.py
```

**예상 결과(가상의 CSV를 채점하는 경우):**

```text
정답: 4/6
라벨 일치율: 66.7%
누락 Case: 없음
예상 외 Case: 없음
허용되지 않은 라벨: 없음
형식 점검: 통과 (이유의 품질은 별도 수동 평가 필요)
```

이 코드가 확인하는 것은 **라벨 일치·누락·중복/형식의 일부**입니다. `reason` 품질, 실제 JSON 출력 유효성, 추론 속도, Runtime 메모리, 법적 사용 가능 여부는 확인하지 않습니다. **실제 모델에 대한 평가 결과라고 주장하면 안 됩니다.**

# 17. 학생 활동 A — 채점기는 무엇을 검증하지 못하는가?

1. `candidate_sample.csv`에서 Q04의 `고급`을 `중급`으로 바꾼 뒤 다시 실행합니다.

| 출력 계약 준수 | 미측정 | 미측정 | 실제 모델 출력 |
| 응답 지연 | 미측정 | 미측정 | 동일 측정 방식 |
| Memory 여유 | 미측정 | 미측정 | Target Hardware 실측 |
| Known Limitation | 미정리 | 미정리 | Model Card + 자체 사례 |
| 최종 판정 | 보류 | 보류 | 필수 정보가 없어 선정 불가 |

원본 자료에서 소개한 **Task·Language·License·Context·Size·Runtime·Evaluation 기준**은 모두 유지합니다. 다만 이번에는 같은 항목을 설명하기보다 **판정에 어떤 증거가 필요한지**를 학습합니다.

모든 Hard Gate가 통과된 후보끼리만 품질과 비용·속도를 비교합니다. 품질 차이가 작더라도 운영 환경 제약에 따라 결과가 달라질 수 있습니다.

# 20. 선정·보류·제외를 말로 설명하는 연습

아래는 특정 실재 Model의 사실이 아닌 **판정 방식 연습용 가상 사례**입니다.

**상황 A:** 모델이 한국어 분류를 잘 수행했으나 상업적 서비스 사용 조건을 확인하지 못했습니다.

- 판정: **보류**
- 이유: 품질 확인이 사용권 확인을 대신하지 못함
- 다음 행동: Terms 원문·사용 목적을 확인하고 결과를 기록

**상황 B:** 사용 조건은 충족하나 목표 Runtime에서 모델을 실행할 수 없습니다.

- 판정: 현재 실행 환경 기준 **제외**
- 이유: 필수 실행 조건 실패
- 다음 행동: 배포 방식 변경 여부는 별도 의사결정으로 관리

**상황 C:** 두 후보 모두 실행 가능하고 사용 조건도 충족합니다. A는 지연이 짧지만 이유 품질이 떨어지고, B는 느리지만 품질이 더 높습니다.

- 판정: **기준을 모르면 선정 불가**
- 이유: 지연/품질의 허용 한계가 정의되지 않음
- 다음 행동: 이해관계자와 품질·응답시간의 합격 기준을 확정하고 같은 Dataset으로 다시 검증

이 활동의 정답은 인기 Model 이름이 아니라 **왜 아직 판단할 수 없는지를 아는 능력**입니다.

# 22. Model Update가 발생하면 무엇을 다시 평가할까?

원본에는 Model Revision 관리와 Regression Evaluation의 필요성이 있습니다. 이를 **이번 프로젝트의 변경 기록**으로 연결합니다.

가정: 운영 중인 후보의 Weight 또는 Revision이 변경되었습니다. 코드가 정상 실행되어도 답변 내용은 달라질 수 있습니다.

| 변경된 것 | 다시 확인할 내용 |
|---|---|
| Model Revision / Weight | 기존 Case의 라벨·이유 품질·형식 준수 |
| Quantization Variant | 품질·메모리·지연 |
| Runtime Version | 로딩 성공, 요청/응답 호환, 자원·지연 |
| Prompt / Chat Template | 출력 형식, 누락·거절·오해 사례 |
| Hardware | 실행 가능성과 지연·메모리 실측 |
| 요구사항 / Dataset | 평가 기준과 합격 기준의 타당성 |

변경 관리는 다음 원칙을 따릅니다.

```text
변경 요청 및 변경 대상 기록
          ↓
기존 운영 기준·평가 결과 보존
          ↓
동일 핵심 Case로 회귀 평가
          ↓
새 요구사항 Case 추가 평가
          ↓
품질·자원·사용 조건 확인
          ↓
승인 또는 배포 보류
          ↓
배포 버전 기록 및 복귀 기준 보존
```

**Regression Evaluation:** 이전에 잘 동작하던 Case가 변경 후에도 요구조건을 충족하는지 다시 확인하는 것입니다. 단순히 새로운 Benchmark 수치가 올랐다고 기존 테스트를 생략하지 않습니다.

# 23. 운영에서 특히 구분할 네 가지 Version

운영 기록의 다음 항목은 서로 대체할 수 없습니다.

| Version | 예시로 답하는 질문 |
|---|---|
| **Model Revision** | 정확히 어떤 Weight/Config의 모델인가? |
| **Runtime Version** | 어떤 실행 도구 버전에서 사용했는가? |
| **Prompt/Contract Version** | 어떤 입력 조건과 출력 규칙으로 호출했는가? |
| **Evaluation Dataset Version** | 어떤 질문과 정답·채점 기준으로 검증했는가? |

예를 들어 모델만 바뀌었다고 기록했지만 Dataset도 바뀌었다면 **이전 점수와 새로운 점수를 그대로 비교하기 어려울 수 있습니다.** `4/6`과 `8/10`은 숫자로는 표현 가능하지만 Case 구성이 다르면 개선 여부를 단정할 수 없습니다.

**운영의 핵심은 ‘항상 최신을 사용한다’가 아니라 ‘어느 조합을 검증해 승인했는지 추적한다’는 것**입니다.

# 24. 강사 시연 운영안

수업 전에 강사가 할 일:

1. 앞 교시에서 사용한 **동일한 교육장 PC**와 실제 사양을 준비합니다.
2. 공식 Model Card와 현재 배포 식별자를 확인한 **서로 비교 가능한 후보**를 준비합니다.
3. 사용 조건을 검토합니다. 미확인 후보라면 시연 전에 선정 보류 예제로 구분합니다.
4. 평가 Dataset의 기준 라벨과 난이도 판정 기준을 검토합니다.
5. 학생에게 보여 줄 출력은 **실제 실행 로그**인지 **모의 CSV 결과**인지 화면에 명시합니다.
6. 모델 추론 실행이 불가능한 교육장에서는 본문의 CSV 채점과 선정 보류 판단만 진행합니다.

권장 수업 흐름:

| 순서 | 강사 활동 | 학생에게 요구할 결과 |
|---|---|---|
| ① | 실제 요구사항에서 Hard Gate 표시 | `탈락/보류/평가 대상` 구분 |
| ② | Candidate의 Model Card 근거 한두 항목 제시 | 출처와 확인 상태 기록 |
| ③ | 질문 6건과 기준 라벨 검토 | 모호한 Case 발견 |
| ④ | 가상 CSV 채점 도구 실행 | 수치와 실제 모델 성능의 차이 설명 |
| ⑤ | 실제 후보별 결과가 있으면 비교 | 조건 차이와 검증 누락 지적 |
| ⑥ | Selection Record 작성 | 선정/보류/제외 근거 제시 |
| ⑦ | Revision 변경 상황 질문 | 회귀 검증 목록 작성 |

**강사 주의:** 모델이 실제로 동작하지 않았는데 예상 결과를 실제 평가 점수로 제시하지 않습니다. 모델 다운로드·실행 시간이 수업을 초과하면 사전 검증한 로그를 **측정 환경과 함께** 사용합니다.

# 25. 학생 활동 C — Model Card의 누락 항목을 어떻게 다룰까?

다음 가상의 후보 서류가 주어졌습니다.

```text
Candidate X
- Text Generation 지원 표기
- Language: Multilingual 표기
- License/Terms: 링크 미확인
- 4B 계열로 소개됨
- Local Runtime 사용 여부: 문서에 설명 없음
- 자체 한국어 평가: 없음
```

**질문:** 다음 주장을 판별합니다.

1. “Multilingual이니까 한국어 분류 품질은 확인 완료다.”
2. “4B이므로 교육장 RAM에서 충분히 실행된다.”
3. “License 링크가 없으니 무조건 불법이다.”
4. “지금 당장은 선정하지 않되, 미확인 사항을 적고 조사할 수 있다.”

**해설:** 1·2는 확인되지 않은 사실을 확정한 주장입니다. 3은 사용 조건의 불확실성을 곧바로 위법으로 단정한 주장입니다. 4가 적절합니다. **미확인 필수 조건이 남아 있으므로 선정 보류**로 기록하고 원문·실측을 확보해야 합니다.

# 26. 학생 활동 D — Model Update 승인 회의

상황: 이전 버전은 6개 질문 중 5개의 라벨을 맞혔으며, 새 버전은 6개 중 6개를 맞혔습니다. 그런데 새 버전은 `reason`을 누락하는 경우가 있고, 응답 시간 측정 조건도 이전과 다릅니다. **이 수치는 가상의 회의 시나리오입니다.**

학생은 다음 세 가지를 작성합니다.

- **현재 판정:** 즉시 교체 승인 / 보류 / 제외 중 선택
- **누락된 증거:** 어떤 추가 평가가 필요한가?
- **재검증 조건:** 무엇을 같은 조건으로 다시 실행해야 하는가?

**해설:** 가용 정보만으로는 **보류**가 적절합니다. 라벨 일치만 개선되어도 출력 계약 위반이 생겼고, Latency 비교 조건도 다릅니다. 이전 버전과 동일 Dataset/조건으로 재평가하고 출력 계약과 운영 목표를 통과해야 합니다.

# 27. 수업 확인 질문과 예상 답안

**Q1. Model Card에서 ‘한국어 지원’이라고 적혀 있으면 선정할 수 있나요?**  
A. 한국어 지원 표기는 검토 근거일 뿐이며, 실제 한국어 Task 품질은 자체 평가해야 합니다.

**Q2. 어떤 모델이 공개 Benchmark 1등이라면 채택해야 하나요?**  
A. 아닙니다. Benchmark 조건이 우리의 Task·Language·환경과 맞는지 확인하고 필수 조건을 통과해야 합니다.

**Q3. License/Terms 확인이 안 되었지만 품질 평가에서 우수하면?**  
A. 선정 보류입니다. 우수한 품질이 사용 조건 확인을 대신하지 못합니다.

**Q4. 같은 Model Family의 두 Variant는 모델 이름만 기록하면 되나요?**  
A. 충분하지 않습니다. 정확한 배포본 및 Revision, 실행 Runtime, 평가 조건을 기록해야 합니다.

**Q5. 분류 정답률이 높으면 이유의 품질도 좋다고 볼 수 있나요?**  
A. 아닙니다. 라벨 일치와 설명의 타당성은 서로 다른 항목입니다.

**Q6. 모델이 업그레이드되었는데 기존 코드가 실행됩니다. 회귀 평가를 생략할 수 있나요?**  
A. 아닙니다. 실행 성공과 기존 기능·출력 품질 유지는 다른 문제입니다.

**Q7. Model Card에 RAM 요구량이 없으면 무엇이라고 기록하나요?**  
A. 미확인으로 두고 Target Hardware 실측 또는 추가 자료 확인을 요청합니다.

**Q8. 이번 Python 채점기에서 66.7%가 나왔으니 Candidate A의 실제 성능인가요?**  
A. 아닙니다. 인위적으로 작성한 CSV에서 계산된 모의 결과입니다.

**Q9. 후보 A/B 평가 중 한 모델에만 Prompt를 수정했으면 어떻게 하나요?**  
A. 동일 조건 비교로 해석하지 않습니다. 변경 조건을 기록하고 공정하게 다시 평가합니다.

**Q10. 모델의 현재 선정 결과가 ‘보류’여도 수업 산출물이 완성될 수 있나요?**  
A. 가능합니다. 무엇이 미확인인지, 어떤 근거와 검증이 있어야 결정 가능한지 명확히 남기는 것이 중요합니다.

# 28. 이번 교시 요약 — 모델을 ‘선정했다’고 말할 수 있는 조건

오늘 배운 절차는 다음입니다.

```text
Project Requirement
        ↓
Hard Gate / 품질 목표 분리
        ↓
정확한 Candidate·Revision 식별
        ↓
Model Card·Terms에서 근거 확보
        ↓
실제 환경 지원 여부 확인
        ↓
동일 Dataset과 비교 조건 고정
        ↓
자동 검사 + 사람의 품질 평가
        ↓
선정 / 보류 / 제외
        ↓
Selection Record 보존
        ↓
변경 시 동일 기준으로 회귀 검증
```

핵심은 세 가지입니다.

1. **Model Card는 판단 근거를 제공하고, 실제 Project Evaluation은 우리 환경의 결과를 제공합니다.** 두 정보는 다릅니다.
2. **License·데이터 정책·실행 가능성 등의 Hard Gate는 단순 품질 점수로 상쇄할 수 없습니다.**
3. **Model Selection은 Model ID 한 줄이 아니라 ‘결정 근거와 재현 조건’을 남기는 운영 행위**입니다.

> **이번 교시의 핵심 문장:** 가장 유명한 모델이 아니라, **요구사항을 만족한다는 증거를 남길 수 있는 모델**을 선택합니다. 증거가 부족하면 명확히 보류합니다.

# 29. 다음 교시 연결 — Model을 고른 다음 애플리케이션 구조를 어떻게 확장할까?

이번 교시까지는 **어떤 모델을 사용할지**와 **왜 그렇게 결정했는지**에 집중했습니다.

하지만 여러 기능이 연결된 AI Application에서는 Model 호출 이외에도 추가 작업이 생깁니다. 다음 Day 3 - 6교시에서는 이를 지원하는 **AI Application Framework 생태계**를 살펴봅니다.

이번 5교시는 **LangChain·LlamaIndex의 구조, Tool/Agent/Retrieval 설계 또는 Framework 구현 코드**를 먼저 가르치지 않습니다. 선택한 모델을 실제 Application의 구성 요소와 연결하는 방법은 뒤 교시에서 진행합니다.
