## 개요 — 모델은 실행했는데, 어느 모델을 사용했다고 말할 수 있을까?

Day2에서는 Ollama와 Transformers를 이용해 공개된 모델을 찾고 실행하거나, FastAPI를 통해 결과를 받았습니다. 그러나 실제 프로젝트에서 “Gemma를 사용했습니다”라는 말만으로는 다른 개발자가 **어떤 모델로 어떤 입력을 처리했는지** 알아낼 수 없습니다.

그 이유는 *Gemma*가 하나의 고정된 파일 이름이 아니라, 서로 관련된 여러 세대와 종류의 모델을 묶는 **Model Family** 이름이기 때문입니다. 같은 Family 안에서도 텍스트만 처리하는 모델과 이미지를 함께 입력받을 수 있는 모델이 나뉠 수 있고, 이름이 비슷하더라도 학습 목적이나 실행 조건이 다를 수 있습니다.

이번 교시에서는 설치 명령어를 반복하거나 특정 모델의 성능을 순위로 매기지 않습니다. 대신 하나의 제품 계열을 **어느 세대인가 → 어떤 갈래인가 → 정확히 어떤 Variant인가 → 그 Variant의 기능이 실제로 확인되는가**라는 질문으로 읽어 봅니다.

```text
“Gemma 사용”                    → Family만 기록한 상태
           ↓
“어느 Gemma 세대인가?”           → Generation 확인
           ↓
“그 안의 어느 모델인가?”         → Size · Type · Capability 구분
           ↓
“정확히 어떤 배포본인가?”        → Model ID · Variant 확인
           ↓
“무엇을 입력·출력할 수 있나?”     → 해당 모델의 공식 설명에서 확인
```

**이번 교시의 성과:** 모델 이름을 보고 기능을 *추측하는 학생*이 아니라, 모델 이름의 정보와 실제 확인한 사실을 **구분해서 기록하는 학생**이 되는 것입니다.

# 1. 학습 목표와 교시 경계

수업이 끝나면 학생은 다음을 수행할 수 있어야 합니다.

1. Model Family, Generation, Variant, 정확한 Model ID를 서로 구별한다.
2. Gemma가 Google에서 공개한 **Model Family**임을 설명하고, 한 Family 내부에 여러 갈래가 있다는 점을 이해한다.
3. 모델 이름에서 크기와 용도를 나타내는 **힌트**를 읽되, 그 이름만으로 기능을 단정하지 않는다.
4. Gemma의 서로 다른 Variant에 대해 **입력 Modality와 출력 Modality**를 별도로 정리한다.
5. 같은 세대·같은 Family라도 Variant마다 Capability가 달라질 수 있다는 것을 사례로 설명한다.
6. Model ID와 모델 기능에 관한 **확인된 사실 / 이름에서 추정한 내용 / 미확인 정보**를 구분한다.
7. 간단한 시나리오에 필요한 **모델 계열상의 정보**를 명시하되, 아직 결론을 낼 수 없는 조건을 기록한다.

**다루지 않을 내용:** Base Model과 Instruction-tuned Model의 실제 출력 비교·Post-training 원리(**Day3 2교시**), Parameter별 저장 공간 계산·Quantization(**3교시**), CPU·GPU·RAM·VRAM별 실행 환경 결정(**4교시**), 평가 지표를 이용한 최종 Model Selection과 변경 관리(**5교시**), Framework 및 Provider 구현(**6~8교시**).

Day1·Day2에서 Model, Parameter, Model Card, Ollama의 정의를 배웠으므로, 이번 교시에서 그 정의를 다시 여러 단계로 설명하지 않습니다. 새로운 작업은 **정확한 모델 계열을 식별하는 것**입니다.

# 2. ‘모델의 이름’은 어느 수준의 이름인가?

개발자가 모델을 언급할 때 같은 문장에서 서로 다른 수준의 이름을 사용할 수 있습니다. 아래는 **구분을 설명하기 위한 표현**이며, 모든 제조사가 이 계층을 동일하게 사용한다는 뜻은 아닙니다.

| 구분 | 답하는 질문 | 예시 관점 | 이 정보만으로 알 수 없는 것 |
|---|---|---|---|
| **Family** | 어느 계열인가? | Gemma | 정확한 입력 유형, 모델 크기, 버전 |
| **Generation** | 어느 세대인가? | Gemma 3 | 해당 세대 중 어느 Variant인지 |
| **Branch / Subfamily** | 특정 목적의 파생 계열인가? | Gemma 3n 같은 이름 | 다른 갈래와 완전히 같은 구조인지 |
| **Variant** | 세대·갈래 안의 어떤 개별 모델인가? | 크기, 학습 목적, 기능 구성이 다른 모델 | 배포 파일·리비전·호환성 전부 |
| **정확한 Model ID / 배포본** | 어느 저장소의 무엇을 사용하나? | 특정 Repository 식별자 | 실제 서비스 품질이 좋은지 |

핵심은 **세대와 Variant를 하나로 묶지 않는 것**입니다. Family 하나만 정해도 모델 선택이 끝나는 것이 아닙니다. 반대로 한 Model ID를 확인했다고 모델의 모든 기능이 검증된 것도 아닙니다.

### 같은 이름을 다르게 해석하면 생기는 문제

프로젝트 문서에 다음과 같이 적었다고 가정합니다.

```text
사용 모델: Gemma
```

이 기록만으로는 담당자에게 아래 질문이 남습니다.

- 어느 세대인가?
- 텍스트 전용인가, 이미지 입력도 받는가?
- 어떤 크기의 Variant인가?
- 사용자가 내린 지시를 따르는 용도로 배포된 모델인가?
- 정확히 어느 저장소·리비전·Runtime용 배포본인가?

이 교시에서는 이런 **누락된 식별 정보**를 찾아내는 능력을 먼저 기릅니다. 그 정보를 바탕으로 최종 채택 여부를 결정하는 과정은 5교시의 주제입니다.

# 3. Family와 Generation은 왜 1:1 관계가 아닐까?

하나의 Family는 시간이 흐르면서 새로운 세대가 공개될 수 있습니다. 새 세대는 이전 세대와 관련을 유지하면서도 Architecture, Tokenizer, 지원 입력 유형, 학습 방식, 공개된 크기 구성 등이 바뀔 수 있습니다.

```text
Model Family
   ├── Generation A
   │      ├── Variant A-1
   │      └── Variant A-2
   └── Generation B
          ├── Variant B-1
          ├── Variant B-2
          └── 별도 목적의 파생 갈래
```

위 그림은 모델 제품군을 이해하기 위한 **개념 구조**입니다. 모든 Family가 첫 세대부터 순서대로 출시되는 것도 아니고, 모든 세대가 동일한 크기·용도의 Variant를 제공하는 것도 아닙니다.

따라서 `이전 세대의 4B`와 `새 세대의 4B`는 숫자 표기가 같더라도 같은 모델이 아닙니다. 같은 세대 안의 `4B`와 `12B`도 단순히 파일 크기만 다른 복제본이라고 볼 수 없습니다. 두 모델은 지원 기능이나 권장 사용 방식이 달라질 수 있습니다.

학생에게 질문해 봅니다.

> “Gemma 3”이라고 정확하게 말했으니, 이제 이미지 입력을 지원하는지 알 수 있을까요?

**아직 알 수 없습니다.** 뒤에서 Gemma 3의 Variant별 사례를 비교하면 이유가 드러납니다.

# 4. Gemma는 정확히 무엇인가?

Gemma는 **Google이 공개한 Open Model Family**입니다. 하나의 이름 안에 여러 세대와 크기, 목적이 다른 모델이 포함됩니다.

여기서 중요한 것은 회사명이나 모델명 자체보다 **이름의 범위**를 이해하는 것입니다.

```text
Gemma                      Family
  └─ Gemma의 특정 세대      Generation
       ├─ 작은 Variant
       ├─ 큰 Variant
       ├─ Base 계열
       ├─ Instruction 계열
       └─ 특수한 기능·배포 목적의 갈래
```

원본 강의와 ZIP 내부 보충 Q&A에는 여러 Gemma 세대가 등장합니다. 보충 Q&A는 Gemma 3·Gemma 3n의 입력 유형이 Variant마다 다른 사례와 Gemma 4라는 후속 세대의 존재를 언급합니다. **이는 원본 자료 시점에 기록된 설명**으로 다루며, 배포 직전의 최신 모델 목록을 직접 검증한 결과로 오해하지 않습니다.

이 교시에서 Gemma를 배우는 목적은 “Gemma가 다른 모든 모델보다 낫다”고 결론을 내리려는 것이 아닙니다. **Gemma에서 연습한 구별 기준을 GPT, Llama, Qwen 등 다른 Family에도 적용**하기 위한 것입니다.

# 5. Gemma에서 한 Family 안의 차이를 직접 확인하기

원본 ZIP에 포함된 「Q - Day3 1교시 20」 보충자료는 **Gemma 3 계열도 Variant에 따라 입력 유형이 다르다**는 사실을 특히 강조합니다. 아래 표는 그 보충자료의 교육용 사례를 정리한 것입니다.

| 원본 보충자료에 등장한 계열·Variant | 입력 형태 | 출력 형태 | 이 교시에서 확인할 점 |
|---|---|---|---|
| Gemma 3 270M | Text | Text | 같은 세대의 작은 모델이 반드시 이미지 입력을 받지는 않음 |
| Gemma 3 1B | Text | Text | Gemma 3이라는 이름만으로 멀티모달을 단정할 수 없음 |
| Gemma 3 4B | Text + Image | Text | 같은 세대에서도 입력 유형이 다를 수 있음 |
| Gemma 3 12B | Text + Image | Text | Parameter 규모만으로 기능을 설명할 수 없음 |
| Gemma 3 27B | Text + Image | Text | 같은 세대 안에서도 기능 표를 Variant별로 확인 |
| Gemma 3n E2B / E4B | Text + Image + Audio | Text | 이름에 `3n`과 `E`가 있으므로 일반 3 계열 이름과 똑같이 해석하면 안 됨 |

> **자료의 검증 범위:** 이 표는 원본 교육과정 **보충 Q&A에 서술된 사례**입니다. 개별 모델의 실제 기능은 사용하려는 **정확한 Model ID와 버전의 공식 사양**을 수업 배포 전에 확인해야 합니다. 이 표를 모든 배포 형식과 Runtime에서 동일하게 작동한다는 보증으로 사용하지 않습니다.

### 여기에서 반드시 도출해야 할 결론

1. **같은 Family라도** 기능이 다를 수 있습니다.
2. **같은 Generation이라도** Variant별로 입력 형태가 다를 수 있습니다.
3. Text와 Image를 입력받는다고 해서 Image를 출력한다는 뜻은 아닙니다. **입력과 출력은 별도로 표기**해야 합니다.
4. 모델의 이름을 알아냈다면 다음은 **그 이름에 대응하는 실제 기능을 확인**하는 일입니다.

이것이 이번 교시에서 Gemma를 사례로 선택한 가장 중요한 이유입니다.

# 6. `Gemma 3`과 `Gemma 3n`을 동일한 표기처럼 읽지 않기

앞의 표에서 `3`과 `3n`처럼 이름이 달라지는 것을 확인했습니다. 두 이름 모두 Gemma 계열을 설명하지만, 이를 **숫자 3이 붙은 완전히 같은 구성의 모델**이라고 읽으면 안 됩니다.

```text
Gemma Family
   ├─ Gemma 3: 270M / 1B / 4B / 12B / 27B 등
   └─ Gemma 3n: E2B / E4B 등
```

위 표기는 원본 보충자료의 목록을 **학습용으로 분류한 것**입니다. 세부적인 공식 제품 계보 전체를 확정한 도식은 아닙니다.

특히 `E2B`, `E4B`에 포함된 `E`를 확인하지 않은 채 단순히 “전체 Parameter가 정확히 2B·4B다” 또는 “일반 Gemma 3의 2B·4B와 같다”고 말해서는 안 됩니다. **이름의 규칙은 해당 계열의 문서에서 확인**해야 합니다.

현재 단계의 판단은 간단합니다.

- `Gemma 3`과 `Gemma 3n`은 **동일한 Variant 명칭이 아니다.**
- 표기가 다르면 **같은 스펙이라고 가정하지 않는다.**
- 정확한 내부 구조와 Parameter 표현 방식은 **Day3 3교시**에서 Model Size를 학습할 때 연결한다.

# 7. 모델 이름에서 무엇을 읽고, 무엇은 읽지 말아야 할까?

모델 이름은 정보를 빠르게 찾게 해 주는 **힌트**이지만, 독립적인 사양 문서를 대신하지 않습니다.

개념적 이름의 형태를 살펴봅시다.

```text
example-family-4b-it
               │  └─ 문서에서 Instruction-tuned를 나타낸다고
               │     정의했을 때만 그 의미로 읽음
               └─ 문서에서 약 4B 규모를 뜻한다고 정의했을 때만 해석
```

이 문자열은 **명명 규칙을 설명하는 가상 예시**이지 실제 다운로드할 Model ID가 아닙니다.

| 이름에서 발견한 표시 | 예상할 수 있는 질문 | 이름만으로 확정할 수 없는 것 |
|---|---|---|
| 세대 번호 | “어느 출시 계열에 속하나?” | 성능·지원 입력 유형 전체 |
| `1B`, `4B`, `27B` | “Parameter 규모를 나타내는가?” | 실제 다운로드 크기·메모리 요구량 |
| `base`, `pt`, `it` 등 | “학습 목적을 구분한 표기인가?” | 실제 Instruction Following 품질 |
| `text`, `vision`, `multimodal` 등 | “어떤 Modality를 의도하나?” | 입력·출력 각각의 정확한 지원 범위 |
| 수치가 아닌 접미사 | “특수 배포 목적·파생 갈래인가?” | 해당 접미사의 공식 의미 |

예를 들어 `4B`를 봤다면 **약 40억 개 Parameter 수준이라는 표기인지** 확인할 수 있습니다. 그러나 4B 모델 파일이 4GB라는 뜻이 아니며, RAM 4GB면 반드시 실행된다는 뜻도 아닙니다. 여기에서 계산을 시작하지는 않습니다. **파일 크기·Quantization·메모리 계산은 Day3 3~4교시**의 고유 내용입니다.

# 8. Family · Generation · Variant · Revision은 서로 다른 질문이다

아래 네 질문에 모두 답하지 못했다면 실습 결과를 정확하게 재현할 준비가 충분하지 않을 수 있습니다.

1. **Family:** 어떤 모델 계열을 선택했는가?
2. **Generation:** 어느 세대 또는 파생 갈래를 선택했는가?
3. **Variant:** 같은 세대의 모델 가운데 어떤 크기·학습 목적·기능 구성을 선택했는가?
4. **Revision / 배포본:** 어떤 저장소의 어느 상태를 실제로 가져왔는가?

예시 기록:

```text
Family: Gemma
Generation / Branch: Gemma 3 계열
Variant: 4B 계열, 세부 학습 유형 확인 필요
Exact Model ID: 미확인
Revision: 미확인
Input Modality: Text + Image (원본 보충자료의 사례)
Output Modality: Text (원본 보충자료의 사례)
Local Runtime 호환 여부: 미확인
```

이 기록의 장점은 **아는 것과 모르는 것을 구분했다**는 점입니다. “Gemma 3 4B니까 Ollama에서 잘 실행되고 한국어 품질도 좋다”라고 주장하지 않았습니다.

원본의 Model Card 강의(Day2 4교시)에서는 저장소를 읽었습니다. 이번에는 해당 정보를 **모델 계열상의 위치를 식별하는 목적**으로 사용합니다. 저장소 메타데이터를 다시 처음부터 가르치지 않습니다.

---

# 9. Capability는 하나의 점수가 아니라 ‘기능의 구성’이다

“이 모델은 무엇을 할 수 있나요?”라는 질문은 한 문장으로 끝나지 않습니다. 원본은 Model Capability를 Text Generation, Instruction Following, Multilingual, Code, Reasoning, Multimodal, Function/Tool 지원 등의 항목으로 나누고 있습니다.

이번 교시에서는 이를 **어떤 종류의 정보를 확인해야 하는가**라는 판별 관점으로만 사용합니다.

| 구별 축 | 확인할 질문 | 쉽게 생기는 잘못된 판단 |
|---|---|---|
| 입력 Modality | 텍스트·이미지·음성 가운데 무엇을 받는가? | “Gemma니까 모두 가능하다.” |
| 출력 Modality | 결과가 텍스트인가, 다른 형태도 지원하는가? | “이미지 입력을 받으니 이미지도 생성한다.” |
| 사용 목적 | 생성·분류·요약 등 어떤 용도를 권장하는가? | “모든 언어 작업을 동일하게 잘한다.” |
| 지시 응답 | 사용자의 Instruction을 따르도록 준비됐는가? | “Base와 Instruction 모델의 결과는 동일하다.” |
| 언어 | 한국어 지원을 어떻게 설명하는가? | “Multilingual이라면 한국어 품질도 보장된다.” |
| 추가 인터페이스 | Tool 등 특정 사용 방식을 지원하는가? | “Family가 같으면 API 기능도 같다.” |

여기서 **Capability가 존재한다는 것과 품질이 충분하다는 것은 다릅니다.** 예를 들어 한국어 처리 가능이라는 설명만으로 교육용 문서를 충분히 잘 요약한다고 단정할 수 없습니다. 품질의 측정과 최종 선택은 **Day3 5교시**에서 구체화합니다.

---

# 10. 입력 Modality와 출력 Modality를 분리해서 읽기

다음 두 모델을 비교해 봅시다. 이는 앞서 본 **원본 보충 Q&A의 Gemma 3 사례**를 다시 설명하는 것이 아니라 **스펙을 읽는 연습**입니다.

```text
Variant A — Text → Text
사용자가 텍스트를 입력하고, 모델이 텍스트를 출력

Variant B — Text + Image → Text
사용자가 텍스트와 이미지를 입력할 수 있지만,
예시 사양에서 출력은 텍스트
```

**Variant B의 Image Input은 Image Output을 의미하지 않습니다.** 한 모델이 여러 형태의 입력을 이해하는 것과 여러 형태의 결과를 생성하는 것은 서로 다른 Capability입니다.

학생 활동의 출발 질문:

- 상품 사진을 보여 주며 “사진에 무엇이 보이는가?”라고 묻는 기능이 필요한가?
- 이미 추출한 텍스트만 받아 문장을 생성하면 되는가?
- 모델이 실제로 생성해야 하는 출력이 이미지인가, 텍스트인가?

위 질문은 특정 모델을 즉시 선택하라는 뜻이 아닙니다. **필요한 입력·출력 Capability부터 명확히 써 보라**는 뜻입니다.

### 문서 이미지와 OCR의 관계 — 여기서는 경계만 확인

원본에서는 “이미지를 입력받는 모델이 있다고 해서 OCR이 항상 불필요한 것은 아니다”라고 주의를 줍니다. 문서의 텍스트를 얼마나 정확히 추출해야 하는지, 표와 레이아웃을 보존해야 하는지 등은 별도의 요건입니다.

이번 교시에서는 이를 **입력 가능 여부와 프로젝트의 정확도 요구는 별개**라는 한 문장으로 연결하고, OCR 방식 비교나 구현으로 확장하지 않습니다.

---

# 11. Base / Pre-trained / Instruction 이름은 ‘계열 구분’까지만

같은 Family 안에 `Base`, `Pre-trained`, `Instruction-tuned`와 관련된 표시가 등장할 수 있습니다. 이 표기는 **이름이 비슷해도 서로 목적이 다른 Variant가 존재할 수 있다**는 신호입니다.

```text
같은 Family · 비슷한 크기
   ├─ Base / Pre-trained 계열
   └─ Instruction-tuned 계열
```

현재 학생이 할 일은 아래 두 가지입니다.

1. 모델 이름이나 문서에서 해당 **학습 목적 표시가 있는지** 찾는다.
2. 표시가 없다면 Base인지 Instruction인지 **임의로 단정하지 않는다.**

**왜 출력이 달라지는가**, 같은 Prompt에 어떤 응답 차이가 나타나는가, Conversation Format이 왜 필요한가는 **바로 다음 Day3 2교시**에서 충분히 다룹니다. 여기서 그 원리나 실습을 미리 진행하지 않습니다.

---

# 12. Size는 Model Family의 한 축이지 모델의 전부가 아니다

한 Family가 다양한 Parameter 규모로 제공되는 이유는 사용 목적이 서로 다르기 때문입니다. 원본의 Gemma 사례에는 작은 모델과 큰 모델이 함께 등장합니다.

- 작은 모델은 상대적으로 제약이 있는 환경에서 **후보로 고려할 여지**가 있습니다.
- 큰 모델은 일부 작업에서 더 높은 수행 능력을 **기대할 수 있는 후보**입니다.
- 그러나 **모델이 크다는 사실만으로** 특정 작업에 적합하다고 결론 낼 수는 없습니다.

여기서는 정확한 연산량·파일 크기·정밀도 환산표를 만들지 않습니다. Day3 3교시에서 Parameter 수와 Quantization을, 4교시에서 실제 하드웨어 제약을 따로 배울 예정입니다.

### sLLM이라는 표현을 보았다면

ZIP의 Day3 1교시 보충 Q&A에는 **sLLM(Small Large Language Model)**이라는 표현도 등장합니다. 비교적 작은 규모의 언어 모델을 가리키는 용법이지만, **‘몇 B 이하’처럼 보편적으로 합의된 절대 기준이 있는 정식 분류는 아닙니다.**

따라서 학생이 기록할 때에는 “sLLM”이라는 단어만 적기보다 **실제 Variant 이름·크기 표기·용도**를 남겨야 합니다. 모델 크기에 따라 실행이 어떻게 달라지는지는 이번 시간이 아니라 뒤의 Size·Hardware 교시에서 검토합니다.

---

# 13. Context, Language, 실행 방식은 무엇을 확인하는 항목일까?

원본은 모델을 설명할 때 Context Length, Language, Runtime Compatibility도 언급합니다. 하지만 모두 똑같은 종류의 정보는 아닙니다.

| 확인 정보 | 지금 확인하는 이유 | 이번 교시에서 확정하지 않는 것 |
|---|---|---|
| Context 관련 사양 | 같은 Family·세대 안에서도 사용 가능한 입력 범위가 달라질 수 있기 때문 | 긴 문서 성능·속도·메모리의 세부 분석 |
| Language 지원 | 한국어를 다루는 프로젝트에서 필요한 후보 정보를 얻기 때문 | 한국어 정확도·문체 평가 결과 |
| Runtime Compatibility | 같은 Family라도 배포본마다 사용할 수 있는 실행 방식이 다를 수 있기 때문 | CPU/GPU 설치·최적 설정 |
| 사용 조건 | 공개 모델이라는 이름만으로 자유롭게 사용한다고 단정하지 않기 위해 | 최종 법률 검토·배포 승인 |

`Context`의 Token 기반 의미는 Day2 1교시에서 이미 배웠습니다. 이번에는 **Model Variant에 따라 확인해야 하는 사양 항목**으로만 다시 활용합니다.

**중요한 구분:** *모델이 기능을 지원한다*와 *특정 Runtime에서 해당 기능을 사용할 수 있다*는 별도 확인 사항입니다. Gemma라는 Family 이름만으로 Ollama·Transformers의 모든 배포본에서 같은 기능이 된다고 가정해서는 안 됩니다.

# 14. ‘Open Model’이라고 적혀 있다면 확인할 것은?

Gemma가 Open Model Family라는 점은 이미 소개했습니다. 그러나 이 표현만으로 모델의 수정·재배포·상업적 사용 여부를 모두 결정할 수 없습니다.

```text
“Open Model”이라는 소개
        ↓
정확한 모델 · 배포본 확인
        ↓
해당 모델의 Terms / License / 사용 조건 확인 필요
```

Day2 4교시에서 라이선스와 모델 카드 내용을 이미 학습했으므로, 여기서 법적 용어를 다시 길게 설명하지 않습니다. 이번 교시에서 학생이 기억할 것은 **‘계열명은 사용 허가서가 아니다’**라는 원칙입니다.

교육자료의 모델 목록과 조건은 바뀔 수 있으므로 강사가 실제 배포 시점에 **정확한 공식 문서 및 해당 배포본**을 재확인해야 합니다. 이 문서는 그런 확인을 수행한 검증 보고서가 아닙니다.

---

# 15. 다른 Model Family에도 같은 읽기법 적용하기

Gemma에서 익힌 판별법은 GPT, Llama, Qwen처럼 다른 Family의 모델 이름을 볼 때에도 적용할 수 있습니다. 하지만 **이름 표기법은 Family별로 다르며**, 한 Family의 접미사가 다른 Family에서도 같은 뜻이라고 가정할 수는 없습니다.

여기서 학생에게 필요한 절차는 다음 정도입니다.

```text
Family 확인
  ↓
Generation · 파생 갈래 확인
  ↓
정확한 Variant / Model ID 확인
  ↓
그 Variant의 입력·출력·용도 확인
  ↓
확인하지 못한 정보는 미확인으로 표시
```

이 절차는 특정 모델의 **우열 판단**이 아닙니다. 먼저 같은 종류끼리 비교할 수 있도록 **대상을 정확하게 식별하는 절차**입니다.

예를 들어 모델 목록에 `GPT`라고만 적혀 있다면, 정확한 모델 및 그 모델의 입력·출력 지원 범위를 확인해야 합니다. `Gemma`라는 이름만 적혀 있을 때와 논리적으로 같은 문제입니다.

---

# 16. 모델을 설명할 때 사용할 ‘Variant 식별 카드’

Day2 4교시에서는 Model Card를 보며 모델 사용 가능 여부를 점검했습니다. 이번 교시의 기록 양식은 다릅니다. **Model Selection Matrix**가 아니라, 모델 계열상의 위치와 기능을 오해 없이 기록하는 **식별 카드**입니다.

| 항목 | 기록 내용 | 근거 수준 |
|---|---|---|
| Family | | 확인 / 추정 / 미확인 |
| Generation | | 확인 / 추정 / 미확인 |
| Branch / Subfamily | | 확인 / 해당 없음 / 미확인 |
| Variant 이름 | | 확인 / 추정 / 미확인 |
| Exact Model ID | | 확인 / 미확인 |
| Size 표기 | | 확인 / 의미 검증 필요 / 미확인 |
| Base / Instruction 표시 | | 확인 / 미확인 |
| Input Modality | | 확인 / 미확인 |
| Output Modality | | 확인 / 미확인 |
| Language 정보 | | 확인 / 미확인 |
| Context 관련 표시 | | 확인 / 미확인 |
| Runtime 호환성 | | 확인 / 미확인 |
| 공식 자료 위치 | | 기록함 / 미확인 |

**작성 규칙:** `확인`은 실제 자료에서 해당 사실을 찾았다는 뜻입니다. `추정`은 이름을 보고 그렇게 보인다는 뜻입니다. 출처가 없는 칸은 비워 두고 **미확인**이라고 적습니다.

아직 학생에게 “이 모델을 최종 채택할 것인가?”라고 묻지 않습니다. 후보 모델 사이의 평가 기준, License 심사 결과, 실제 실행 결과를 결합하는 판단은 Day3 5교시에 맡깁니다.

# 17. 강사 시연 — 같은 Gemma 이름으로 서로 다른 기능 찾기

강사가 아래 두 자료를 보여 줍니다. **인터넷 접속이 어렵다면 본문 5번 표를 사용**해도 됩니다.

- 자료 A: 원본 보충자료에 등장한 **Gemma 3 1B** 사례
- 자료 B: 원본 보충자료에 등장한 **Gemma 3 4B** 사례

학생과 함께 다음 질문에 답합니다.

**질문 1.** Family는 같은가?  
→ 둘 다 Gemma 계열입니다.

**질문 2.** Generation 표기는 같은가?  
→ 둘 다 Gemma 3이라는 세대 표기를 사용합니다.

**질문 3.** 같은 모델인가?  
→ 아닙니다. 크기 표기도, 원본 보충자료에 정리된 입력 Modality도 다릅니다.

**질문 4.** 이미지를 입력할 수 있다는 사실만으로 이미지 출력도 가능한가?  
→ 아닙니다. 표에서 두 Variant의 **출력은 Text**로 구분되어 있습니다.

**질문 5.** 두 Variant 가운데 무엇이 우리 프로젝트에 더 좋은가?  
→ 아직 확정할 수 없습니다. 실제 프로젝트 요구사항과 평가가 없기 때문입니다.

강사의 마지막 질문:

> “모델 Family가 같고 세대 표기도 같은데, 어째서 기능을 따로 확인해야 했을까요?”

학생이 **“Variant가 다르면 Capability가 달라질 수 있기 때문”**이라고 답하고 근거로 표를 가리킬 수 있다면 이번 교시의 중심 목표를 달성한 것입니다.

# 18. 학생 활동 1 — Family 계층 구분하기

다음 기록을 보고 어떤 정보가 부족한지 적어 봅니다. 여러 학생이 서로 다른 답을 낼 수 있지만, 근거가 명확해야 합니다.

| 기록 | 아직 확인해야 할 질문 |
|---|---|
| “Gemma” | 어느 세대·Variant·배포본인가? |
| “Gemma 3” | 같은 세대의 어느 크기·용도·입력 유형인가? |
| “Gemma 3 4B” | 정확한 Base/Instruction 표시·Model ID·리비전 등은? |
| “Gemma 3n E4B” | `3n`과 `E4B`의 의미가 해당 계열 문서에서 어떻게 정의되는가? |

**학생 제출:** 네 기록 각각에 대해 **이미 알 수 있는 것 1개**와 **아직 모르는 것 1개 이상**을 작성합니다.

**채점 관점:** 이름을 더 자세히 썼다고 무조건 정답이 아닙니다. **어느 수준까지 식별됐는지**와 **무엇이 남았는지**가 명확해야 합니다.

# 19. 학생 활동 2 — 입력·출력 Capability 분류하기

원본 보충자료의 예를 사용합니다.

| 사례 | 입력 가능한 형태 | 출력 형태 | Family·Generation만으로 확정 가능한가? |
|---|---|---|---|
| Gemma 3 1B | 학생 작성 | 학생 작성 | 학생 작성 |
| Gemma 3 4B | 학생 작성 | 학생 작성 | 학생 작성 |
| Gemma 3n E4B | 학생 작성 | 학생 작성 | 학생 작성 |

**정답 확인용:**

- Gemma 3 1B: Text 입력, Text 출력.
- Gemma 3 4B: Text + Image 입력, Text 출력.
- Gemma 3n E4B: Text + Image + Audio 입력, Text 출력.
- 어느 사례든 **Family만으로 해당 Variant의 기능을 확정할 수 없다.**

위 정답은 원본 ZIP 보충 Q&A가 기술한 사례를 재구성한 것입니다. 수업에서 특정 모델을 실제 실행할 때의 보증표는 아닙니다.

**추가 질문:** Gemma 3 4B에 이미지를 입력받는 기능이 있다고 설명한 자료만으로, “OCR 없이 모든 표를 정확히 추출한다”고 주장할 수 있을까요?  
→ **아닙니다.** 입력을 받을 수 있다는 사실과 실제 업무 정확도는 구분해야 합니다.

---

# 20. 학생 활동 3 — 사양으로 확정할 수 없는 주장 찾기

다음 문장을 **① 확인된 사실 ② 검증되지 않은 주장 ③ 추가 확인이 필요한 조건**으로 나눠 보세요.

> “Gemma 3라는 모델이 있으니 이미지를 받을 수 있다. 4B라서 파일도 4GB이고, 16GB RAM 노트북에서는 빠르게 실행된다. Gemma는 Open Model이므로 어떤 상용 앱에나 조건 없이 넣어도 된다.”

**해설:**

- Gemma 3라는 세대 이름만으로 이미지 입력 여부를 결정할 수 없습니다. **정확한 Variant가 필요**합니다.
- 4B가 Parameter 규모 표기라 해도 파일 크기 4GB를 뜻하지 않습니다. 실제 파일·정밀도·배포 형식을 별도로 확인해야 합니다.
- 16GB RAM 환경에서 빠른지, 실행 가능한지는 그 모델의 실제 파일과 Runtime·Hardware 사양 없이는 판단할 수 없습니다.
- Open Model이라는 분류가 모든 상업적 사용을 제한 없이 허용하는 것은 아닙니다. 해당 모델의 조건을 확인해야 합니다.

여기서 학생에게 계산식이나 법률 해석을 요구하지 않습니다. **이름에 들어 있는 정보의 한계**를 짚는 것이 이번 활동의 목표입니다.

---

# 21. 학생 활동 4 — 프로젝트 요구사항에서 ‘모델 기능 질문’만 도출하기

원본의 예시를 사용합니다.

```text
가상 프로젝트: 한국어 PDF 문서 요약 기능
- 입력: PDF에서 추출한 Text 또는 문서 이미지
- 결과: 한국어 요약 Text
- 외부 전송은 허용되지 않음
- 학생 실습 PC는 RAM 16GB
```

이번 교시에서는 최종 모델을 선택하지 않습니다. 대신 다음의 **사양 질문 5개**만 작성합니다.

1. 실제 입력이 **추출된 Text**인가, **문서 이미지**인가?
2. 모델이 반드시 받아야 하는 **Input Modality**는 무엇인가?
3. 모델의 **Output Modality**는 무엇인가?
4. Family·Generation·Variant 가운데 아직 **정확히 지정되지 않은 정보**는 무엇인가?
5. 기능이 맞는 Variant를 찾더라도 **뒤 교시에서 따로 확인해야 할 조건**은 무엇인가?

**해설 예시:**

- 추출된 텍스트만 처리한다면 Text Input이 우선 요구됩니다.
- 이미지를 직접 넣을 계획이라면 Image Input 지원 여부를 별도로 확인해야 합니다.
- 원하는 출력이 요약 문장이므로 Output은 Text입니다.
- 모델 이름이 Gemma라고만 정해져 있다면 Generation·Variant·Exact Model ID가 미정입니다.
- 실제 RAM 요구량, Runtime 호환성, 사용 조건, 한국어 품질은 **다른 검증 단계**가 필요합니다.

이 활동의 결과물은 **모델 채택서가 아니라 기능 요구를 분류한 메모**입니다. Day3 5교시에서 같은 프로젝트 요구사항을 바탕으로 평가·선정으로 발전시킵니다.

---

# 22. 흔히 생기는 오해 — 이번 교시에서 판정할 것만

| 오해 | 이 교시에서 설명할 수정 관점 |
|---|---|
| “Gemma는 모델 한 개를 뜻한다.” | Gemma는 여러 모델을 포함하는 Family입니다. |
| “같은 Generation이면 기능이 같다.” | 같은 세대 안에서도 Variant마다 Input Modality 등이 다를 수 있습니다. |
| “Family가 같으면 Tokenizer·설정·배포 형식도 전부 같다.” | 계열 이름만으로 동일성을 주장할 수 없습니다. |
| “4B라고 적혔으니 파일 크기는 4GB다.” | Parameter 규모 표기와 파일 크기는 다른 질문입니다. |
| “더 최근 세대이면 내 프로젝트에서 항상 더 낫다.” | 프로젝트 적합성은 별도 확인해야 합니다. |
| “Instruction 표기가 있으니 반드시 정확한 답변을 한다.” | 학습 목적 표시와 실제 정답률·업무 품질은 다릅니다. |
| “Open Model이면 사용 조건이 없다.” | 정확한 Model/배포본의 Terms를 확인해야 합니다. |
| “Gemma를 고르면 Ollama로 모든 기능을 사용할 수 있다.” | Model Capability와 Runtime·배포본의 지원 범위는 별도 확인이 필요합니다. |

오해 하나하나를 이미 배운 이론으로 다시 장황하게 설명할 필요는 없습니다. 이번 시간에는 공통적으로 **“Family 이름만으로 특정 Variant의 성질을 단정하는 오류”**를 잡아냅니다.

# 23. 수업 확인 질문

**Q1.** Model Family와 Variant의 차이는 무엇인가요?  
**A.** Family는 서로 관련된 모델들의 묶음이고, Variant는 그 안에서 크기·목적·기능 등이 특정된 개별 모델입니다.

**Q2.** “Gemma 3”이라고 했는데 이미지 입력을 지원하는지 확정할 수 있나요?  
**A.** 확정할 수 없습니다. 원본 보충자료의 사례처럼 같은 Gemma 3 계열에서도 Variant별로 입력 유형이 다를 수 있습니다.

**Q3.** Text + Image Input 모델은 Image Output 모델인가요?  
**A.** 그렇지 않습니다. 입력 가능 형태와 출력 형태를 따로 확인해야 합니다.

**Q4.** `4B`라고 적힌 모델이 4GB 파일이라는 뜻인가요?  
**A.** 아닙니다. 모델 이름의 크기 표기와 실제 파일 용량은 구분해야 합니다.

**Q5.** `base` 또는 `it`가 보이면 무엇을 해야 하나요?  
**A.** 해당 Family의 명명 규칙에서 그 표기가 어떤 학습 목적을 뜻하는지 확인해야 합니다. 두 계열의 학습 원리와 실제 응답 차이는 다음 교시에서 다룹니다.

**Q6.** Gemma 계열 중 하나를 고른 뒤 곧바로 개발을 시작해도 되나요?  
**A.** 기능 표시뿐 아니라 정확한 Model ID와 지원 환경, 사용 조건, 프로젝트 품질 요건을 별도로 확인해야 합니다. 최종 선정 과정은 5교시에서 수행합니다.

**Q7.** 같은 Model Family 안에 작은 모델과 큰 모델이 동시에 있는 이유는 무엇인가요?  
**A.** 사용 환경과 요구 기능이 다르기 때문입니다. 다만 크기별 실제 성능·실행 가능 여부는 이름만으로 보장되지 않습니다.

# 24. 이번 교시 핵심 정리

지금까지 배운 내용을 **단 하나의 확인 순서**로 묶어 봅니다.

```text
1. Model Family 확인
   “어느 모델 계열인가?”
            ↓
2. Generation · Branch 확인
   “같은 계열의 어느 세대/갈래인가?”
            ↓
3. Variant 확인
   “정확히 어떤 크기·종류·기능의 모델인가?”
            ↓
4. Exact Model ID 확인
   “어느 배포본을 말하는가?”
            ↓
5. Capability 구분
   “입력과 출력에서 무엇을 지원하는가?”
            ↓
6. 불확실성 표시
   “아는 것과 아직 검증하지 않은 것은 무엇인가?”
```

반드시 기억할 문장:

> **Model Family를 아는 것과 실제 사용할 Model Variant를 정확하게 아는 것은 다릅니다. 같은 Family·같은 세대라도 Variant에 따라 지원 기능이 달라지므로, 모델 이름을 읽은 뒤 해당 Variant의 사양을 확인해야 합니다.**

### 강의 마무리 점검

학생이 `Gemma`라는 이름 하나만 적힌 모델 기록을 보고 **“무엇이 누락되었는가?”를 세 가지 이상 말할 수 있는지**, 그리고 **Gemma 3 1B와 4B의 입력 형태를 정확히 구분하는지** 확인합니다. 이것이 이번 교시의 종료 기준입니다.
