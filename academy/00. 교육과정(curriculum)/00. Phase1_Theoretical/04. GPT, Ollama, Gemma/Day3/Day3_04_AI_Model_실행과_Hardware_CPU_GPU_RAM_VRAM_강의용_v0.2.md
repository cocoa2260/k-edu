## 개요 — 계산한 Weight 크기만으로 실행 가능 여부를 판단할 수 있을까?

앞 교시에서는 Parameter 수와 표현 정밀도를 이용해 **Weight만의 이론적인 크기**를 계산했습니다. 그러나 실제 Local Model을 실행할 때는 그 숫자 하나로 충분하지 않습니다.

예를 들어 어떤 모델의 Weight 계산값이 약 8GB이고, 컴퓨터에 메모리가 8GB 있다고 가정합니다. **이 조건만으로 실행 가능하다고 결론 내릴 수 없습니다.** 운영체제·프로그램·모델 계산용 메모리도 필요하며, GPU를 사용한다면 메모리 구조도 확인해야 하기 때문입니다.

이번 교시의 출발 질문은 세 가지입니다.

1. **어디에 저장되어 있는가?** — SSD의 파일과 실제 실행 중인 메모리는 어떻게 다른가?
2. **누가 계산하는가?** — CPU·GPU와 RAM·VRAM의 관계는 무엇인가?
3. **어디에서 막히는가?** — 실행이 불가능하거나 지나치게 느릴 때 무엇을 먼저 확인할까?

이번에는 같은 정의를 외우기보다 **실행 경로를 그려 보고, 컴퓨터의 상태를 관찰하고, 원인을 설명하는 것**을 목표로 합니다.

# 2. 저장된 모델과 실행 중인 모델은 무엇이 다른가?

Day 2의 Ollama 실습에서 `ollama ls`와 `ollama ps`를 이미 실행했습니다. 명령어의 뜻을 다시 설명하지 않고 **명령이 보여 주는 상태를 하드웨어 관점에서 해석**해 보겠습니다.

| 상황 | 저장 장치 | 실행용 메모리 | 현재 연산 |
|---|---|---|---|
| 모델 다운로드 직후 | 모델 데이터 존재 | 아직 로드되지 않았을 수 있음 | 없음 |
| 모델 로드 직후 | 모델 데이터 존재 | Weight 등이 배치됨 | 요청을 기다릴 수 있음 |
| Prompt 처리·생성 중 | 모델 데이터 존재 | Weight·계산용 데이터 사용 | CPU 또는 GPU 등이 연산 |
| 모델 언로드 후 | 파일은 남아 있을 수 있음 | 해당 실행 메모리 반환 가능 | 없음 |

**구별할 질문**

- 모델을 다운로드한 뒤 RAM 사용량이 거의 달라지지 않았다면 오류인가? → 다운로드와 메모리 로드는 별개이므로 반드시 오류라고 볼 수 없습니다.
- Chat 화면을 닫으면 모델 파일이 삭제되는가? → 삭제를 의미하지 않습니다.
- 실행 요청이 끝나면 모델이 언제나 즉시 메모리에서 사라지는가? → Runtime 정책에 따라 다릅니다.

수업 도중 실제 사용량이 서로 다를 수 있습니다. 상태표는 **개념적 가능성**을 구분하기 위한 것으로, 특정 Runtime이 매번 같은 방식으로 동작한다는 뜻은 아닙니다.

# 3. 실행을 담당하는 다섯 가지 자원

| 자원 | 이번 교시에서 볼 역할 | 학생이 관찰할 질문 |
|---|---|---|
| **Storage: SSD/HDD** | 다운로드한 모델 파일 저장 | 디스크에 파일이 남아 있는가? |
| **RAM** | 프로그램과 CPU 계산 등에 필요한 시스템 메모리 | 모델 실행 시 메모리 사용량이 변하는가? |
| **CPU** | 범용 연산과 시스템·프로그램 실행, 지원되는 AI 연산 | GPU 없이도 추론할 수 있는가? |
| **GPU** | 대량의 병렬 Tensor 연산에 적합한 처리 장치 | GPU로 계산할 때 무엇이 달라지는가? |
| **VRAM** | 독립형 GPU가 사용하는 전용 메모리 | GPU의 메모리 공간이 충분한가? |

단순히 'CPU는 제어, GPU는 AI'라고 나누면 잘못 이해할 수 있습니다. **CPU도 AI 계산을 수행할 수 있고, GPU도 연산 지원·메모리·호환성에 따라 제한**을 받습니다.

여기서 **장치가 계산한다**는 말과 **메모리에 데이터가 위치한다**는 말을 구분합니다. RAM은 연산 장치가 아니라 데이터를 보관하는 실행 메모리이며, GPU의 메모리 구조는 컴퓨터 종류에 따라 달라집니다.

# 4. CPU에서 추론할 때의 데이터 흐름

CPU 중심으로 실행하는 일반적인 상황을 단순화하면 다음과 같습니다.

```text
SSD / 모델 파일
      │  Load
      ▼
System RAM  ── 프로그램·Model Weight·연산 데이터
      │
      ▼
     CPU  ── Model 계산
      │
      ▼
Inference 결과
```

이 구조에서 학생이 확인할 점은 **CPU 실행에는 GPU 전용 VRAM이 필수조건이 아니라는 것**입니다. 모델과 Runtime이 CPU Inference를 지원하고 시스템 자원이 충분하다면 GPU가 없는 PC에서도 실행할 수 있습니다.

그러나 실행 *가능*과 사용하기에 *충분히 빠름*은 별개의 판단입니다. 대형 모델, 긴 입력, 생성 길이 등에 따라 처리 속도가 느릴 수 있습니다. 이번 교시에서는 결과를 미리 단정하지 않고 실제 실행을 관찰합니다.

**확인 질문:** CPU에서 추론하는 경우에도 SSD의 모델 파일이 매 Token 생성마다 그대로 실행된다고 이해하면 될까요? → 아닙니다. 실행에 필요한 모델 데이터가 메모리에 배치되고 계산에 사용된다는 점을 이해해야 합니다. 구체적인 읽기·캐시 방식은 Runtime에 따라 다를 수 있습니다.

# 5. 독립형 GPU에서 추론할 때의 데이터 흐름

전용 VRAM을 갖는 GPU를 사용하면 일반적으로 다음 요소가 필요합니다.

```text
SSD / 모델 파일
       │  Load
       ▼
System Memory (RAM)
       │  필요한 Data Transfer
       ▼
GPU Memory (VRAM) ── Weight·Input·중간 계산 데이터
       │
       ▼
      GPU ── 병렬 Tensor 계산
       │
       ▼
Inference 결과
```

이 그림은 대표적인 **개념도**입니다. 모든 프레임워크가 반드시 그림의 모든 단계를 동일한 방식과 횟수로 처리한다는 의미는 아닙니다. 일부 데이터는 RAM에 남고 일부만 VRAM에 배치될 수 있으며, Runtime이 메모리 이동을 관리합니다.

**중요한 차이:** GPU를 사용할 때는 모델을 저장한 디스크 공간뿐 아니라 **GPU가 실제 연산에 사용할 수 있는 메모리 공간**도 확인해야 합니다.

GPU가 장착되었다는 사실만으로 모델 전체를 해당 GPU에 올릴 수 있는 것은 아닙니다. Runtime·Model Format·지원 연산 및 여유 메모리 조건도 맞아야 합니다.

# 6. 독립형 GPU의 VRAM과 통합·공유 메모리는 다르다

앞의 GPU 구조를 모든 컴퓨터에 그대로 적용하면 오류가 발생합니다.

| 환경 | 일반적인 메모리 구조 | 주의할 점 |
|---|---|---|
| 전용 메모리를 가진 독립형 GPU | 시스템 RAM과 GPU 전용 VRAM을 구분 | VRAM 용량과 여유 공간을 확인 |
| 시스템 메모리를 공유하는 내장 GPU | CPU와 GPU가 시스템 메모리 일부를 공유 가능 | 별도 VRAM 용량만으로 판단하지 않음 |
| Apple Silicon의 Unified Memory | CPU와 GPU가 통합된 메모리 자원을 공유 | NVIDIA 독립형 GPU의 RAM/VRAM 구분을 그대로 적용하지 않음 |

예를 들어 **Unified Memory 24GB**라고 표기된 컴퓨터를 'RAM 24GB + 별도 VRAM 24GB'라고 해석하면 안 됩니다. CPU·GPU가 공유하는 자원이라는 점을 먼저 이해해야 합니다. 실제 어느 정도가 모델 실행에 이용 가능한지는 운영체제와 Runtime의 제약도 받습니다.

**강사 질문:** 컴퓨터 두 대에 모두 'GPU'가 있다고 할 때, 같은 방식으로 메모리 사용량을 비교해도 될까요? → 전용 VRAM을 가진 경우와 공유 메모리인 경우를 먼저 구별해야 합니다.

학생이 사용하는 장비가 서로 다르다면 **비교할 수 있는 숫자와 비교하면 안 되는 숫자**부터 표시합니다.

# 7. 모델을 로드하기 전·후에 어떤 메모리가 더 필요할까?

Day 3 - 3교시에서 계산한 Weight 크기를 다시 계산하지 않습니다. 이제 그 숫자가 **실제 메모리 구성의 일부**라는 사실을 확인합니다.

```text
실행 메모리에 영향을 줄 수 있는 요소

Model Weights
+ Input / Output Tensors
+ Intermediate Activations
+ Generation 중 사용하는 Cache
+ Runtime / Framework Buffers
+ 기타 Process / OS Memory
```

각 항목이 어느 메모리를 얼마나 사용하는지는 모델 구조·입력 길이·실행 장치·Runtime에 따라 달라집니다.

**상황 예시:** Weight만의 이론값이 8GB인 모델이 있다고 가정합니다.

- 시스템 RAM이 8GB라면 '정확히 들어간다'고 할 수 없습니다.
- 독립형 GPU의 VRAM이 8GB라면 '모든 계산을 GPU에서 수행한다'고 할 수 없습니다.
- 용량이 더 큰 컴퓨터라도 Runtime이 해당 모델이나 GPU를 지원하지 않으면 실행하지 못할 수 있습니다.

여기서는 *실행 가능 판정*보다 **어떤 정보가 부족한지 지적하는 능력**을 평가합니다. CPU/GPU별 자원 요구와 배치 원리를 익힌 뒤, 구체적인 모델 후보 판정은 다음 5교시에서 진행합니다.

# 8. 긴 입력이나 여러 요청을 처리하면 왜 상황이 달라질까?

같은 모델을 사용하더라도 실행 중 필요한 메모리는 일정한 한 숫자로 고정되지 않을 수 있습니다.

| 바뀌는 조건 | 메모리·처리 측면에서 관찰할 수 있는 변화 |
|---|---|
| Input/Context가 길어짐 | 계산과 생성 중 보관하는 데이터가 늘어날 수 있음 |
| 한 번에 처리하는 입력 묶음이 커짐 | 처리할 Tensor·중간 데이터가 늘어날 수 있음 |
| Runtime 설정·모델 배치 방식 변경 | RAM/VRAM 배치와 실행 속도가 달라질 수 있음 |

이전 교시의 KV Cache 정의나 Batch 계산을 다시 가르치지는 않습니다. 이번에는 **'모델 파일은 같은데 왜 실행 상태가 달라지는가?'**라는 하드웨어 질문으로 연결합니다.

예를 들어 짧은 입력에서는 동작하던 모델이 매우 긴 문서를 처리할 때 메모리 부족을 겪을 수 있습니다. 그 원인은 파일이 갑자기 커졌기 때문이 아니라 **실행 중 필요한 데이터가 달라졌기 때문일 수 있습니다.**

후속 Model Selection 수업에서 필요하면 이 관찰 결과를 후보 비교의 근거로 사용합니다.

# 9. CPU와 GPU는 어떤 계산에서 차이를 보일까?

CPU는 범용 처리를 담당하며, GPU는 대규모 병렬 연산에 적합하도록 설계된 장치입니다. AI 모델에서는 행렬과 Tensor를 대상으로 유사한 수학 연산을 대량으로 수행하는 경우가 많아 GPU가 유리할 수 있습니다.

하지만 아래 문장은 틀렸습니다.

> GPU가 있으므로 모든 연산과 전체 프로그램이 CPU보다 반드시 빠르다.

GPU 연산의 이점에는 조건이 있습니다. 실제 처리 시간은 **연산 규모, CPU·GPU 성능, 지원 Library, 데이터 이동, 메모리 읽기 속도** 등과 연결됩니다.

- 처리량이 큰 병렬 연산은 GPU가 유리할 수 있습니다.
- 매우 작은 작업은 GPU로 옮기는 비용이 이득보다 클 수 있습니다.
- GPU에서 지원하지 않는 연산이 있거나 호환 환경이 맞지 않으면 장점을 활용하지 못합니다.
- GPU가 빨라도 메모리 부족이나 CPU 측 준비 과정이 전체 실행을 제한할 수 있습니다.

이번 교시는 GPU의 작동 회로를 분석하는 시간이 아닙니다. **GPU 사용 여부만 확인하고 속도를 단정하지 않는 판단 원리**까지 학습합니다.

# 10. CPU↔GPU 데이터 이동도 실행 시간에 포함된다

GPU에서 계산하려는 Tensor가 시스템 RAM에 있을 경우 필요한 데이터를 GPU가 접근할 수 있는 위치로 옮겨야 할 수 있습니다.

```text
CPU 측 데이터 준비
        │
        ▼
필요한 데이터 이동 / 접근 준비
        │
        ▼
GPU 연산
        │
        ▼
결과 사용
```

따라서 GPU 처리 속도만 보고 전체 실행 속도를 비교하면 불완전할 수 있습니다. 특히 **작은 데이터에 대해 짧은 연산을 한 번 실행하는 경우** 이동·호출 등의 비용이 상대적으로 크게 나타날 수 있습니다.

이 때문에 실습에서 단일 시간을 기록했다면 반드시 '무슨 구간을 재었는가?'를 같이 적습니다.

- 모델 파일을 읽는 시간까지 포함했는가?
- Tensor를 Device에 준비하는 과정까지 포함했는가?
- 순수한 연산 구간만 측정했는가?
- CPU와 GPU의 측정 범위가 같은가?

아래 실습의 측정값은 **수업용 기초 관찰값**이며 모델 전체의 응답 성능을 보장하는 Benchmark가 아닙니다.

# 11. 속도 문제가 생기면 먼저 무엇을 구분할까?

학생에게 'AI가 느리다'고만 말하면 해결 단서를 찾기 어렵습니다. 다음과 같이 **느린 구간**을 먼저 구분합니다.

| 관찰 상황 | 먼저 확인할 질문 |
|---|---|
| 모델을 처음 불러올 때 오래 걸림 | 파일 접근·메모리 로드에 시간이 걸리는가? |
| 실행은 되지만 Token 생성이 느림 | CPU/GPU 실행 상태, 모델 규모, 메모리 사용 상황은 어떤가? |
| GPU 사용률이 낮음 | CPU 준비, 지원 연산, 데이터 이동, 작은 작업 규모 등이 원인일 수 있는가? |
| GPU 메모리는 사용하지만 프로그램은 멈춘 듯 보임 | 실제 연산 또는 입력 처리 중인지 추가 확인이 필요한가? |
| 입력 길이를 늘리자 오류가 발생 | 실행 중 메모리 증가가 관련될 수 있는가? |

**GPU Utilization**은 GPU 자원이 사용되는 정도를 나타내는 관찰값이지만, 값이 낮다고 무조건 고장이라고 결론 내릴 수는 없습니다. **Memory Bandwidth**는 메모리에서 데이터를 읽고 쓰는 능력과 관련된 하드웨어 특성입니다. 모델이 계산할 데이터를 충분히 빠르게 공급받지 못하면 연산 능력만 높여도 효과가 제한될 수 있습니다.

이번 교시에서는 두 용어의 의미와 관찰의 한계만 알고 넘어갑니다. 상세 성능 튜닝 및 최종 장비·모델 선정은 범위 밖입니다.

# 12. NVIDIA CUDA는 무엇을 확인하는 단계인가?

NVIDIA GPU 환경에서는 PyTorch가 GPU 연산을 사용할 때 **CUDA 소프트웨어 생태계**와 연결될 수 있습니다.

```text
PyTorch의 CUDA 지원
         │
CUDA 관련 Software / Driver 조건
         │
호환되는 NVIDIA GPU
```

이때 세 가지를 혼동하면 안 됩니다.

| 확인 대상 | 의미 |
|---|---|
| NVIDIA GPU 존재 | 컴퓨터에 해당 하드웨어가 있는가? |
| Driver / Framework 호환 | 사용하려는 도구가 해당 하드웨어를 지원하는가? |
| `torch.cuda.is_available()` | **현재 PyTorch 실행 환경**에서 CUDA 사용이 가능한가? |

따라서 `torch.cuda.is_available() == False`를 보고 **'이 컴퓨터에는 GPU가 전혀 없다'**고 해석하면 안 됩니다. CUDA가 아닌 GPU 환경도 있으며, NVIDIA GPU가 있어도 드라이버·PyTorch 빌드·환경 조건 때문에 `False`가 나올 수 있습니다.

Apple Silicon의 통합 GPU 역시 **NVIDIA CUDA GPU와 같은 검사 대상이 아닙니다.** 이번 실습의 자동 감지는 CPU와 CUDA를 대상으로 하며, 다른 GPU 경로의 지원 여부는 해당 환경을 따로 확인해야 합니다.

# 15. 통합 실습 B — 같은 계산을 CPU와 CUDA에서 관찰하기

이전 Tensor 수업에서는 연산의 **Shape와 결과**를 확인했습니다. 이번에는 같은 종류의 계산이 실행되는 **장치와 시간 측정 조건**을 확인합니다.

파일명: `hardware_compute_observe.py`

```python
from statistics import median
from time import perf_counter

import torch


def measure_matrix_calculation(device: torch.device, size: int = 256) -> float:
    # 같은 Shape과 dtype을 사용하되 각 장치에 별도로 Tensor 생성
    left = torch.ones((size, size), dtype=torch.float32, device=device)
    right = torch.ones((size, size), dtype=torch.float32, device=device)

    # 최초 호출 시 발생할 수 있는 준비 비용을 별도로 둔다.
    for _ in range(2):
        result = left @ right

    if device.type == "cuda":
        torch.cuda.synchronize(device)

    times = []
    with torch.inference_mode():
        for _ in range(5):
            if device.type == "cuda":
                torch.cuda.synchronize(device)
            start = perf_counter()
            result = left @ right
            if device.type == "cuda":
                torch.cuda.synchronize(device)
            times.append(perf_counter() - start)

    print(f"{device}: shape={tuple(result.shape)}, dtype={result.dtype}")
    print(f"{device}: median={median(times) * 1000:.3f} ms")
    return median(times)


def main() -> None:
    cpu_time = measure_matrix_calculation(torch.device("cpu"))

    if torch.cuda.is_available():
        gpu_time = measure_matrix_calculation(torch.device("cuda:0"))
        print("CPU/CUDA 관찰값:", cpu_time, gpu_time)
    else:
        print("CUDA를 사용할 수 없어 CPU 관찰만 진행했습니다.")


if __name__ == "__main__":
    main()
```

실행:

```bash
python hardware_compute_observe.py
```

**이 실습의 해석 원칙**

- 이 코드는 작은 행렬 연산의 관찰 예제입니다. **LLM의 전체 Token 생성 속도 Benchmark가 아닙니다.**
- 코드에서 Tensor를 장치별로 따로 생성하기 때문에 **디스크에서 모델을 읽는 시간이나 장치 간 입력 전송 시간은 측정하지 않습니다.**
- GPU 작업은 비동기로 처리되는 경우가 있으므로 CUDA 측정 구간 전후에 `synchronize`를 사용합니다.
- 장치·환경에 따라 출력 시간은 달라집니다. 예제에 고정된 '정답 시간'은 없습니다.
- CPU-only PC에서는 정상적으로 CPU 결과만 나타나야 합니다. 이는 실패가 아닙니다.
- Apple Silicon GPU를 이 코드에서 자동 측정하는 것은 아닙니다. Mac에서도 CPU 경로는 실행할 수 있습니다.

**학생 질문:** GPU 결과가 측정되더라도 왜 `GPU가 항상 더 빠르다`고 결론 내릴 수 없을까요? → 이번에 측정한 대상·규모·구간이 제한되어 있고, 실제 Local LLM 실행은 여러 단계와 자원 조건을 포함하기 때문입니다.

# 17. 실행 환경이 다를 때 관찰 결과가 달라지는 이유

다음 세 환경이 있다고 가정합니다.

| 환경 | 주어진 조건 | 지금 알 수 있는 것 | 아직 알 수 없는 것 |
|---|---|---|---|
| A | RAM 8GB, 독립형 GPU 없음 | CPU 중심 실행을 먼저 고려할 수 있음 | 실제 모델 실행 가능 여부·속도 |
| B | RAM 32GB, 전용 VRAM 8GB GPU | RAM과 VRAM을 구분해 관찰해야 함 | 모델 전체가 VRAM에 들어가는지 |
| C | Unified Memory 24GB | 공유 메모리 구조를 고려해야 함 | 특정 Model·Runtime의 실제 메모리 사용·속도 |

**잘못된 결론:** 'C는 24GB RAM에 24GB VRAM까지 있으므로 48GB를 쓸 수 있다.'  
**더 적절한 결론:** 'C는 공유 메모리 구조이므로 RAM/VRAM을 단순 합산할 수 없으며, 실제 사용 가능 범위를 확인해야 한다.'

**잘못된 결론:** 'B에는 GPU가 있으므로 VRAM보다 큰 모든 모델도 GPU에서 빠르게 실행된다.'  
**더 적절한 결론:** 'VRAM 및 추가 실행 메모리, Runtime의 분산·Offloading 지원 여부에 따라 결과가 달라질 수 있다.'

이 활동은 **특정 후보 모델을 선정하는 실습이 아닙니다.** 하드웨어 구조의 차이를 정확히 읽는 연습입니다.

# 18. VRAM이 부족할 때 가능한 실행 경로와 한계

GPU 메모리가 부족하다면 다음과 같은 선택지가 존재할 수 있습니다.

| 접근 | 이번 교시에서 이해할 의미 | 주의할 점 |
|---|---|---|
| 일부 데이터를 시스템 RAM 쪽에서 처리 | CPU Offloading 등 | 데이터 이동과 CPU 계산 때문에 속도가 낮아질 수 있음 |
| 지원되는 경우 여러 GPU에 배치 | Multi-GPU / 분산 처리 | GPU 간 통신과 Runtime 지원 필요 |
| 더 적은 Weight 메모리가 필요한 표현 사용 | Quantization과 연결 | Day3 3교시 내용 반복 없이 결과만 연결 |
| 모델 실행 요구량 자체를 낮춤 | 더 작은 규모의 Model 검토 | 실제 선정은 Day3 5교시에서 수행 |

여기서 **CPU Offloading**은 GPU 한 장의 VRAM만으로 부족할 때 일부 Weight나 계산을 CPU/시스템 메모리 측에 두는 접근입니다. 모델에 따라 구현 가능 여부가 다르고, 데이터를 나눠서 실행하는 만큼 성능상 손해가 있을 수 있습니다.

**Multi-GPU** 역시 GPU 숫자가 두 배라고 언제나 속도가 두 배가 되는 구조는 아닙니다. 데이터 배치와 GPU 사이의 통신 문제가 존재합니다.

이번 Phase 1에서는 이러한 방법의 **존재와 대가**까지만 이해하며, 실제 설정 코드·메모리 분산 구현은 하지 않습니다.

# 19. Training과 Inference를 실행 자원 관점에서만 비교하기

Training 과정과 Parameter 업데이트 방식은 Day 2 - 3교시에서 이미 학습했습니다. 이번에는 **필요한 하드웨어 자원의 차이**만 확인합니다.

Inference에서는 Model Weight 외에 입력·출력과 추론 중간 계산을 위한 메모리가 필요합니다. Training에서는 모델과 방법에 따라 **Gradient, Optimizer State, 학습 중간 데이터** 등 추가 자원이 요구될 수 있습니다.

따라서 같은 크기의 모델이라도 Training과 Inference를 **동일한 하드웨어 요구량으로 판단하면 안 됩니다.** 반면 Training이 언제나 특정 배수만큼 더 많은 메모리를 쓴다고 단정할 수도 없습니다. 학습 방식과 설정에 따라 다릅니다.

학생에게 필요한 결론은 하나입니다.

> 이전 교시에서 추론에 성공했다고 해서 같은 PC에서 대규모 Fine-tuning까지 바로 수행할 수 있다는 뜻은 아닙니다.

Fine-tuning, PEFT, LoRA, QLoRA의 실제 방법과 설정은 이 교시에서 다루지 않습니다.

# 20. 오류를 해석하는 순서 — 실행 실패가 모두 같은 이유는 아니다

아래 질문은 '무엇을 먼저 확인하겠는가'에 대한 안내입니다. 실제 오류의 원인은 로그와 실행 환경을 확인해야 확정할 수 있습니다.

| 증상 | 먼저 확인할 곳 | 바로 결론 내리지 말아야 할 내용 |
|---|---|---|
| `torch.cuda.is_available()`가 `False` | PyTorch CUDA 지원 환경·드라이버·GPU 종류 | GPU 하드웨어가 전혀 없음 |
| CPU 경로는 실행, GPU 경로만 실패 | VRAM·Device 설정·호환성·지원 연산 | Model 파일이 반드시 손상됨 |
| 실행 중 Memory 부족 오류 | 당시 사용 가능한 메모리·입력 크기·다른 프로세스 | Storage 크기만 늘리면 해결 |
| Model Load 시 지연 | 파일 읽기·메모리 배치·Runtime 초기 준비 | 이후 생성도 같은 속도로 느림 |
| 응답 생성이 느림 | CPU/GPU 사용, 데이터 이동, 메모리·Runtime | GPU가 없기 때문이라고 단정 |
| 모델 파일이 남았는데 `ollama ps`에 없음 | 런타임의 모델 로드 상태 | 모델이 다운로드되지 않았음 |

**단계별 진단 연습**

1. 실행 장치를 **CPU / 독립형 GPU / 통합·공유 메모리 GPU** 중 무엇으로 분류할지 정합니다.
2. **파일 존재**, **메모리 로드**, **연산 진행** 중 어느 단계의 문제인지 가릅니다.
3. 해당 환경에서 **GPU 사용 가능 여부**, **여유 메모리**, **입력 조건** 중 무엇을 먼저 확인할지 고릅니다.
4. 확인하지 못한 부분은 반드시 **미확인**이라고 적습니다.

원인을 가정한 뒤 무조건 재설치하기보다는 **현재 단계가 어디까지 동작했는지**를 먼저 확인합니다.

# 21. 학생 활동 1 — 실행 경로를 직접 그리기

다음 두 상황을 각각 도식화합니다.

**상황 A:** GPU가 없는 PC에서 CPU 추론이 가능한 Model을 실행합니다.  
**상황 B:** 독립형 GPU가 장착된 PC에서 Model과 계산용 Tensor가 GPU 전용 메모리를 사용합니다.

그림에는 다음 단어를 필요한 위치에 배치합니다.

`SSD / Model File / RAM / CPU / VRAM / GPU / Load / Inference`

**학생 답안에서 확인할 기준**

- Storage에 Model File이 존재하는 단계와 실행 메모리 단계가 구분되는가?
- CPU 경로에서 필요 없는 VRAM을 필수 요소로 넣지 않았는가?
- GPU 경로에 VRAM 또는 GPU가 접근하는 메모리의 역할을 설명했는가?
- 통합 메모리 구조가 위 독립형 GPU 그림과 반드시 동일하지 않음을 주석으로 표시했는가?

이전 교시에서 그린 단순 화살표를 다시 베끼기보다 **각 단계가 어떤 자원을 사용하는지 설명하는 문장**을 붙입니다.

# 22. 학생 활동 2 — 어떤 주장이 잘못되었는가?

다음 문장에서 사실이거나 단정 가능한 부분과 수정해야 할 부분을 구분합니다.

1. “GPU가 있는 PC라면 어떤 Local LLM이든 빠르게 실행할 수 있다.”
2. “CUDA 사용 가능 여부가 False이면 GPU가 한 개도 없다.”
3. “Ollama로 모델을 다운로드했으면 항상 RAM에 올라가 있다.”
4. “Unified Memory 24GB는 시스템 RAM 24GB와 VRAM 24GB의 합계다.”
5. “모델 파일이 6GB면 RAM이 8GB일 때 반드시 실행된다.”
6. “같은 모델도 Context와 Runtime 상태에 따라 메모리 사용량이 달라질 수 있다.”
7. “같은 계산이라도 CPU와 GPU의 연산 시간 외에 데이터 이동 시간이 발생할 수 있다.”

**강사용 해설**

- 1~5: 모두 지나치게 단정했거나 구조를 잘못 이해한 문장입니다. 각각 **지원 조건·GPU 종류·다운로드와 로드의 차이·공유 메모리·추가 실행 메모리**를 근거로 고쳐야 합니다.
- 6~7: 가능한 설명입니다. 다만 실제 변화량·속도는 모델·하드웨어·측정 조건에 따라 달라집니다.

# 23. 학생 활동 3 — 원인 분석표 작성

**사례 1**

> 모델 파일은 보이는데 모델을 아직 실행하지 않았습니다. 현재 RAM 사용량이 거의 변하지 않았습니다.

학생 질문: 이 사실만으로 설치 실패라고 판단할 수 있습니까? → **아닙니다.** 파일 존재와 실행 메모리 로드는 다른 상태입니다.

**사례 2**

> PyTorch에서 CUDA가 False입니다. 해당 컴퓨터는 Apple Silicon Mac입니다.

학생 질문: Mac에 GPU가 없다고 판단할 수 있습니까? → **아닙니다.** CUDA 검사는 NVIDIA CUDA 환경에 대한 판단이며, 통합 GPU 전체의 존재 여부를 뜻하지 않습니다.

**사례 3**

> 긴 입력으로 바꾸자 생성 중 메모리 문제가 나타났습니다.

학생 질문: 기존 모델 파일의 용량이 늘어난 것입니까? → **그렇게 결론 내릴 수 없습니다.** 입력 길이와 실행 중 중간 데이터의 메모리 요구가 연관되었을 가능성을 확인해야 합니다.

**사례 4**

> GPU 추론은 가능하지만 아주 작은 연산 하나는 CPU보다 빠르지 않았습니다.

학생 질문: GPU가 고장 났다고 판단할 수 있습니까? → **아닙니다.** 작업 크기·측정 조건·장치 사용에 드는 비용 등을 확인해야 합니다.

각 사례마다 `관찰 사실 / 가능한 원인 / 추가 확인 / 확정할 수 없는 것` 네 칸을 작성합니다.

# 24. 수업 확인 질문과 답안

**Q1. Model File이 SSD에 있는데 왜 RAM이 필요한가요?**  
A. 저장된 파일과 실제 계산 중 사용하는 데이터는 역할이 다릅니다. 프로그램과 모델 데이터가 실행 메모리를 사용해야 계산에 참여할 수 있습니다. 구체적 배치 방식은 Runtime에 따라 달라질 수 있습니다.

**Q2. CPU만 있는 컴퓨터에서도 Local LLM을 사용할 수 있나요?**  
A. CPU Inference를 지원하는 Model·Runtime이고 자원이 충분하다면 가능합니다. 다만 실행 속도는 별도로 확인해야 합니다.

**Q3. GPU에 VRAM이 8GB 있으면 Weight가 8GB인 Model을 바로 실행할 수 있나요?**  
A. 아닙니다. 실행 중간 데이터와 Runtime 메모리가 필요하며, 실제 호환성·여유 공간도 확인해야 합니다.

**Q4. Mac의 Unified Memory를 NVIDIA GPU의 VRAM과 동일하게 보면 되나요?**  
A. 아닙니다. 전용 메모리와 CPU/GPU가 공유하는 메모리 구조는 구분해야 합니다.

**Q5. CUDA가 False이면 무엇을 말할 수 있나요?**  
A. 해당 PyTorch 실행 환경에서 CUDA 사용이 가능하지 않다는 것을 말할 수 있습니다. 컴퓨터에 GPU가 전혀 없다는 의미는 아닙니다.

**Q6. GPU가 더 빠르다는 실험 결과가 나왔다면 모든 작업에서 GPU가 빠른가요?**  
A. 아닙니다. 작업 크기, 데이터 이동, Runtime 및 측정 구간을 함께 고려해야 합니다.

**Q7. VRAM이 부족할 때 어떤 방법을 검토할 수 있나요?**  
A. Runtime이 지원한다면 일부 CPU Offloading, GPU 분산, 더 작은 Weight 표현이나 모델 규모 등 가능한 경로를 검토할 수 있습니다. 항상 적용 가능한 해결책이라고 단정하면 안 됩니다.

**Q8. 같은 모델의 Input Length가 길어지면 메모리 요구가 달라질 수 있나요?**  
A. 그렇습니다. 실행 중 필요한 중간 데이터·Cache 등의 변화가 관련될 수 있습니다.

# 25. 강사 진행 순서와 검수 기준

| 순서 | 진행할 활동 | 강사가 확인할 점 |
|---|---|---|
| 도입 | 전 교시 Weight 크기 결과를 하드웨어 질문으로 연결 | 크기 수식·Quantization 정의 반복 없이 출발 |
| 원리 | Storage→Memory→Processor 경로 설명 | CPU·독립형 GPU·공유 메모리 차이 정확히 구분 |
| 조건 | CUDA·Driver·PyTorch Compatibility 확인 | CUDA False를 GPU 없음으로 가르치지 않음 |
| 코드 | `hardware_env_check.py` 실행 | CPU-only에서도 성공, 출력 의미 구분 |
| 코드 | `hardware_compute_observe.py` 실행 | 시간 단위·측정 범위·결과 한계 설명 |
| 관찰 | 기존 Local Model 실행 전후 자원 관찰 | Ollama CLI 강의 반복 없이 관찰 결과 기록 |
| 활동 | 세 환경·네 사례의 진단표 작성 | 단정과 미확인 구분 |
| 정리 | '무슨 하드웨어 정보가 필요한가' 설명 | 실제 Model Selection은 다음 교시로 넘김 |

**강사 판단 기준**

- 모든 학생이 GPU 실험을 해야 수업 완료인 것은 아닙니다. CPU-only 환경에서도 학습 목표를 충족할 수 있어야 합니다.
- 출력값이 서로 다른 경우 원인을 억지로 통일하지 않습니다. **환경 차이를 기록**하는 것도 학습 성과입니다.
- 실행하지 못한 코드나 확인하지 못한 장치 정보는 검증 완료로 표시하지 않습니다.
- 반드시 'Weight 크기 ≠ 전체 실행 메모리'라는 결론만 반복할 것이 아니라, **어느 장치에서 어떤 종류의 데이터가 사용되는가**를 설명하게 합니다.

**교육장 배포 전 확인**: 대상 OS 및 PyTorch 버전, CPU/GPU 환경, 이미 준비한 Ollama Model, 교육장 자원 관찰 도구, `torch.cuda` 이용 가능 여부를 강사가 직접 확인합니다.

# 26. 이번 교시 정리 — 실행 조건을 설명할 수 있어야 한다

이번 교시에서 새롭게 배우는 핵심은 다음과 같습니다.

```text
Model File: Storage에 있음
            │
            ▼
실행 Memory: RAM / VRAM / Unified Memory 등
            │
            ▼
계산 장치: CPU / GPU
            │
            ▼
Model Inference
            │
            ▼
실행 중 메모리·연산량·속도 관찰
```

**하나의 하드웨어 숫자만으로 Model 실행 가능 여부와 속도를 확정할 수는 없습니다.** 모델 데이터가 어느 메모리에 놓이고, 어떤 장치가 연산하며, 어떤 단계가 병목인지 확인해야 합니다.

학생은 다음 문장을 자신의 말로 설명할 수 있어야 합니다.

> **“Local AI가 실행된다는 것은 모델 파일을 보유했다는 뜻이 아니라, 실행에 필요한 데이터가 해당 하드웨어의 메모리에서 이용 가능하고 CPU 또는 GPU가 실제 계산할 수 있다는 뜻이다.”**
