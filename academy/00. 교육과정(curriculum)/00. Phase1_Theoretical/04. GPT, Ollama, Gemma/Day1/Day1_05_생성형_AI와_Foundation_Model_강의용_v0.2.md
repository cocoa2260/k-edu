## 2. 분류·예측과 생성은 어떻게 다른가?

2교시에서는 AI가 하는 작업을 분류·예측·추천·인식·생성으로 나눠 보았습니다. 여기서는 그 목록을 다시 외우기보다 **결과물이 어떤 형태인지**에 초점을 맞춥니다.

### 2-1. 작업의 차이

| 요구사항 | 입력 예시 | 기대 출력 | 대표 작업 |
|---|---|---|---|
| 고객 리뷰가 긍정인지 부정인지 판단 | 리뷰 문장 | 긍정 / 부정 | 분류(Classification) |
| 다음 주 판매량을 추정 | 과거 판매 정보 | 예상 수량 | 예측(Prediction) |
| 상품의 소개 문구를 새로 작성 | 상품 정보와 작성 지시 | 새로운 설명 문장 | 생성(Generation) |

상품 소개 문구를 만드는 경우를 살펴봅시다.

```text
사용자가 제공한 상품 정보
        +
"두 문장으로 소개문을 작성해 줘"라는 지시
        ↓
    Generative Model
        ↓
새롭게 구성된 상품 소개 문장
```

분류에서는 정해진 범주를 고르는 일이 중심이지만, 생성에서는 문장의 표현과 구성 자체가 출력의 일부입니다. 같은 상품 정보를 보고도 문장 길이, 어휘, 강조점이 다른 소개문이 나올 수 있습니다.

### 2-2. 이 둘을 완전히 반대되는 기술로 생각하면 안 된다

분류·예측은 **작업의 목적**이고, 생성형 모델은 **콘텐츠를 생성하는 모델의 성격**을 가리킵니다. 따라서 생성형 언어 모델에게도 다음과 같이 요청할 수 있습니다.

> “이 고객 리뷰를 읽고 `긍정` 또는 `부정`으로만 답해 줘.”

이 요청은 *분류 작업*이지만, 모델은 정해진 답변 형식으로 출력을 생성해 작업을 수행할 수 있습니다. 문장에서 정보를 추출하거나 기존 문장을 번역·변환하는 일도 마찬가지입니다.

**강사 확인 질문:** “분류를 수행하는 LLM은 더 이상 생성형 모델이 아닌가요?”  
**예상 답변:** 아닙니다. **모델의 종류**와 **모델에 맡긴 작업**은 구별해야 합니다.

## 3. 생성형 모델은 언제부터 있었을까?

생성 모델을 ChatGPT와 같은 대화형 서비스가 등장한 뒤에 처음 만들어진 기술로 생각하면 안 됩니다. 생성과 관련된 모델은 이전부터 연구되었으며, 서로 다른 유형의 데이터에 맞는 여러 접근이 발전해 왔습니다.

원본 교육자료에 나온 대표적인 계열은 다음과 같습니다.

| 모델 계열 | 이번 교시에서 기억할 역할 |
|---|---|
| Autoregressive Model | 앞서 주어진 내용에 이어 다음 부분을 생성하는 접근 |
| Variational Autoencoder(VAE) | 학습한 데이터의 잠재적인 표현을 이용해 생성하는 계열 |
| GAN | 생성 모델과 판별 모델의 경쟁적 학습을 활용하는 계열 |
| Diffusion Model | 잡음과 복원 과정을 활용하는 생성 모델 계열 |
| Transformer 기반 생성 모델 | Attention 중심의 구조를 이용하는 현대 생성 모델 계열 |

여기서 각 알고리즘의 수학이나 코드를 모두 배울 필요는 없습니다. **생성형 AI가 특정 제품이나 단 하나의 모델 구조를 뜻하는 말이 아니라는 것**이 핵심입니다.

또한 생성되는 결과는 텍스트에만 한정되지 않습니다.

```text
Generative AI가 만들 수 있는 콘텐츠
├─ Text: 설명문, 요약, 대화
├─ Code: 요구사항에 따른 코드 초안
├─ Image: 입력 설명에 따른 이미지
├─ Audio / Speech: 음향이나 음성
└─ Video: 영상 콘텐츠
```

이것은 **출력의 종류**를 보여 주는 목록입니다. 텍스트·이미지·음성을 함께 처리하는 모델의 개념은 뒤의 Multimodal 부분에서 별도로 다룹니다.

## 4. Language Model은 어떻게 문장을 만들까?

### 4-1. Language Model의 역할

**Language Model(언어 모델)**은 언어의 패턴을 모델링하는 모델입니다. 생성형 Language Model은 입력받은 문맥(Context)을 바탕으로 이어질 내용을 계산하여 텍스트를 만들어 낼 수 있습니다.

예를 들어 사용자가 다음과 같이 입력한다고 생각해 봅시다.

> “다음 상품 정보를 참고해 고객에게 보여 줄 소개 문구를 작성해 줘.”

모델은 이 지시와 함께 주어진 상품 정보를 입력으로 받고, 학습한 언어 패턴을 활용해 자연스러운 소개 문구를 생성합니다. 이 과정은 단순히 데이터베이스에서 이미 작성된 문장 한 줄을 찾아 복사해 오는 절차와 다릅니다.

### 4-2. Token은 무엇인가?

언어 모델이 텍스트를 처리할 때 사용하는 단위 중 하나가 **Token(토큰)** 입니다. Token을 무조건 하나의 단어로 생각하면 안 됩니다. 사용하는 모델과 Tokenizer에 따라 단어, 단어의 일부, 문자 조각, 기호나 공백을 포함한 조각처럼 나뉠 수 있습니다.

**Tokenizer(토크나이저)** 는 텍스트를 모델이 처리할 수 있는 토큰 단위로 나누고 이에 대응하는 표현으로 변환하는 구성 요소입니다.

```text
입력한 텍스트
      ↓
Tokenizer
      ↓
Token들의 순서
      ↓
Language Model
```

모델마다 Tokenizer가 다를 수 있으므로 “글자 수가 같으면 Token 수도 같다”라고 단정할 수 없습니다. 오늘은 구체적인 분할 결과를 암기하지 않고 **문장을 모델이 처리하는 단위가 필요하다**는 점을 이해합니다.

### 4-3. 한 번에 문장 전체가 정답처럼 저장되어 나오는 것일까?

많은 현대 생성형 언어 모델의 텍스트 생성은 **다음 Token의 가능성을 계산하고 하나를 선택하는 과정을 반복하는 방식**으로 이해할 수 있습니다.

```text
사용자 지시 + 제공된 정보
             ↓
        Tokenization
             ↓
        Language Model
             ↓
   다음 Token 후보들의 가능성 계산
             ↓
       다음 Token 선택
             ↓
    지금까지의 Context에 추가
             ↓
     다음 Token 계산을 반복
             ↓
         최종 텍스트
```

이해를 돕기 위해, 모델이 문장을 만들 때 매 단계마다 여러 후보를 검토한다고 생각해 봅시다. 예를 들어 상품 설명을 작성하는 상황에서 어떤 표현으로 이어 갈지는 한 가지로만 정해져 있지 않습니다. 모델은 지금까지의 문맥을 참고해 다음 출력의 후보를 계산합니다.

**주의:** 강의에서 화면에 보이는 완성된 단어나 문장 후보는 직관을 위한 예시입니다. 실제 모델은 해당 Tokenizer가 정의한 단위로 계산하며, **완성된 단어 하나가 항상 Token 하나인 것은 아닙니다.**

### 4-4. 왜 이 동작 방식을 알아야 할까?

이 원리는 네 가지 중요한 사실로 연결됩니다.

1. **출력이 자연스러워도 사실일지는 별도 문제입니다.** 모델은 언어 출력을 생성하는 것이지, 모든 문장의 진실을 자동 검증하는 것이 아닙니다.
2. **표현이 달라질 수 있습니다.** 출력 선택 방식에 따라 같은 요구사항에도 서로 다른 문장을 생성할 수 있습니다.
3. **입력 문맥이 중요합니다.** 어떤 상품 정보와 지시를 제공했는지가 생성 결과에 영향을 줍니다.
4. **입력과 출력에는 Token이라는 단위가 쓰입니다.** 따라서 모델이 처리할 수 있는 범위와 실행 조건에 연결됩니다.

다음에는 이런 언어 모델이 왜 여러 작업에 사용될 수 있게 되었는지 살펴봅니다.

## 5. Language Model, LLM, Foundation Model의 관계

### 5-1. LLM은 무엇인가?

**LLM(Large Language Model)**은 대규모 데이터와 많은 Parameter를 이용해 학습되어 다양한 언어 작업에 활용되는 **대규모 언어 모델**을 가리키는 말입니다.

LLM은 질문 답변만 수행하는 모델이 아닙니다. 원본 강의자료에 등장하는 대표 작업은 다음과 같습니다.

- 질문 답변, 대화, 요약
- 번역과 문서 변환
- 문장의 분류, 정보 추출
- 코드 생성과 언어 기반 문제 해결

예를 들어 하나의 모델에 고객 리뷰의 감정 분류를 요청할 수도 있고, 같은 모델에 상품 설명 초안을 작성하도록 요청할 수도 있습니다. **하나의 모델을 서로 다른 언어 작업에 활용할 수 있다는 점**이 중요한 변화입니다.

### 5-2. Foundation Model은 무엇인가?

**Foundation Model(기반 모델)**은 대규모 데이터 등을 활용해 사전학습되어, 여러 후속 작업(Downstream Task)이나 Application의 기반으로 사용할 수 있는 모델을 설명하는 개념입니다.

4교시에서는 왜 대규모 사전학습이 중요해졌는지를 배웠습니다. 이번에는 **사전학습된 모델을 실제로 어떻게 활용하는지**에 집중합니다.

```text
[특정 작업별 모델을 만드는 방식의 개념도]
작업 A → 그 작업에 맞는 Model A
작업 B → 그 작업에 맞는 Model B
작업 C → 그 작업에 맞는 Model C

[공통 기반 모델 활용의 개념도]
             ┌→ 요약
Foundation ──┼→ 질문 답변
   Model     ├→ 분류 / 정보 추출
             └→ 문장 생성
```

이 그림은 모든 작업을 언제나 하나의 모델로 해결하는 편이 우수하다는 뜻이 아닙니다. 각 작업에서 필요한 품질, 데이터, 비용, 검증 조건은 서로 다를 수 있습니다.

### 5-3. Foundation Model과 LLM은 같은 말인가?

아닙니다. 두 용어의 **기준이 다릅니다.**

- **LLM:** 언어를 중심으로 하는 *대규모 Language Model*이라는 성격에 초점을 둡니다.
- **Foundation Model:** 다양한 후속 작업의 *기반으로 활용할 수 있는 모델*이라는 성격에 초점을 둡니다.

Foundation Model이라는 개념은 Language뿐 아니라 Vision이나 Multimodal 영역에도 적용할 수 있습니다. 따라서 모든 Foundation Model이 LLM은 아니며, **LLM과 Foundation Model을 완전히 같은 의미로 쓰지 않습니다.**

```text
Foundation Model이 활용되는 영역의 예
├─ Language
├─ Vision
└─ Multimodal 등

LLM은 그중 언어를 중심으로 이해하는 모델 계열
```

**강사 포인트:** 이 구조는 개념 구분을 돕는 그림입니다. 모든 실제 모델을 배타적인 한 가지 범주에만 넣는 엄밀한 분류표는 아닙니다.

## 6. Base Model과 Instruction-tuned Model

같은 Model Family에 속한 모델을 받아 사용하더라도 **어떤 학습을 거친 Variant인지**에 따라 이용 방식이 달라질 수 있습니다.

### 6-1. Base Model

**Base Model**은 대규모 **Pre-training(사전학습)**을 통해 기본적인 패턴을 학습한 모델을 가리킵니다. Pre-training은 폭넓은 데이터를 이용해 모델이 여러 작업의 기반이 될 수 있는 표현이나 패턴을 학습하는 과정입니다.

### 6-2. Instruction-tuned Model

**Instruction-tuned Model**은 사용자의 지시를 따르는 데 더 적합하도록 추가 학습을 거친 모델을 말합니다. 흔히 `Instruct`, `Instruction`, `Chat`처럼 모델 이름에 들어가는 표현을 만날 수 있지만, **표기만으로 세부 학습 방식이 전부 같다고 단정할 수는 없습니다.**

```text
대규모 데이터
      ↓
 Pre-training
      ↓
   Base Model
      ↓
추가 지시 학습 등
      ↓
Instruction-following Model
```

예를 들어 사용자의 요청을 받아 대화형으로 답하는 Application을 만든다면, 지시 이행에 맞게 준비된 Variant가 더 적합할 수 있습니다. 반대로 같은 Family라 하더라도 Base Model에 원하는 형식의 지시를 주었을 때 기대한 답변이 나오지 않을 수 있습니다.

> **중요:** `Base Model`과 `Instruction-tuned Model`은 성격과 활용 목적을 구분하는 말입니다. 어느 쪽이 모든 상황에서 무조건 우수하다는 뜻이 아닙니다. 정확한 선택은 제공되는 모델 설명을 확인해야 합니다.

Fine-tuning의 학습 절차는 이후 과목에서 다루므로 여기서는 **“사전학습 후 추가 학습을 거친 모델이 존재하며, 그 차이가 사용 방식에 영향을 준다”**는 정도를 이해합니다.

## 7. Model Family와 개별 Model/Variant

### 7-1. 하나의 이름이 하나의 모델 파일만 의미할까?

모델을 공부하다 보면 **Model Family(모델 계열)**라는 표현을 만납니다. 이는 같은 계열에 속하는 여러 모델을 묶어 부르는 개념입니다.

```text
Model Family
│
├─ Model / Variant A
│  └─ 서로 다른 규모와 실행 조건
├─ Model / Variant B
│  └─ Instruction Tuning 여부가 다를 수 있음
└─ Model / Variant C
   └─ 지원 입력 형식과 목적이 다를 수 있음
```

같은 Family에 포함돼도 실제로는 다음 조건이 다를 수 있습니다.

| 비교 항목 | 무엇을 확인하는가? | 서비스 개발과의 연결 |
|---|---|---|
| Parameter Scale | 모델 내부 값의 규모 | 실행 자원 및 모델 선택에 영향 |
| Instruction Tuning | 지시를 따르도록 추가 학습되었는가 | 대화·지시 작업 적합성에 영향 |
| Context 지원 | 한 번에 처리할 수 있는 문맥의 범위 | 긴 입력 처리 가능 여부에 영향 |
| Modality | 텍스트·이미지 등 지원 입력/출력 | 구현 가능한 기능 범위에 영향 |
| Deployment 목적 | 어느 환경에서 운영하도록 준비되었는가 | Cloud/Local 운영 판단에 영향 |

원본 강의의 **Gemma** 사례로 연결하면, ‘Gemma’라는 Family 이름 하나만 보고 서비스용 모델 선택을 끝낼 수는 없습니다. 어떤 Variant를 사용하고 어떤 환경에서 실행할지 추가 판단이 필요합니다.

### 7-2. Parameter가 많으면 무조건 좋은 모델인가?

그렇지 않습니다. Parameter 규모만으로 업무 성능을 단정할 수 없습니다.

예를 들어 작은 규모의 모델이 필요한 업무에 충분한 품질을 제공하고, 원하는 장비에서 더 적절한 속도로 동작할 수도 있습니다. 반대로 큰 모델도 특정 언어나 업무에 필요한 조건을 충족하지 못할 수 있습니다.

모델 선택에는 다음을 함께 고려합니다.

- **업무 적합성:** 실제 작업의 품질을 충족하는가?
- **Latency(지연시간):** 결과를 받는 데 얼마나 걸리는가?
- **Memory / Hardware:** RAM·VRAM 등 사용 가능한 자원에서 실행 가능한가?
- **비용과 운영 조건:** 사용량에 따른 비용과 관리 부담은 적절한가?
- **언어·Context·Modality:** 필요한 입력과 출력 조건을 지원하는가?
- **License·Privacy:** 배포·사용 조건과 데이터 처리 요구사항에 맞는가?

실제 모델별 수치와 라이선스 확인은 이후 모델 선택 교시에서 다룹니다. **이번 교시에서는 비교 기준만 익힙니다.**

## 8. Multimodal Model은 무엇인가?

`Modality(모달리티)`는 정보가 표현되는 형태를 가리키는 용어입니다. 이 강의에서 주요 예시는 **Text, Image, Audio, Video**입니다.

**Multimodal Model**은 이처럼 서로 다른 형태의 정보를 함께 처리할 수 있는 모델입니다.

```text
Text(질문) + Image(영수증 사진)
               ↓
       Multimodal Model
               ↓
        Text(답변)
```

사용자가 영수증 사진을 제공하고 “총 결제 금액이 얼마야?”라고 질문하는 상황을 생각해 봅시다. 이런 입력을 처리할 수 있는 모델이라면 이미지의 시각 정보와 사용자의 질문을 함께 활용할 수 있습니다.

### 8-1. OCR과 무엇이 다른가?

**OCR(Optical Character Recognition, 광학 문자 인식)**은 이미지나 스캔 문서에 포함된 **문자를 인식해 텍스트로 변환**하는 기술입니다.

```text
영수증 이미지
     ↓
    OCR
     ↓
인식한 텍스트
```

한편 Multimodal Model은 모델이 지원하는 범위에서 이미지와 텍스트 등 **여러 형태의 입력을 함께 다룰 수 있다**는 점에 초점이 있습니다.

| 비교 | OCR | Multimodal Model |
|---|---|---|
| 중심 역할 | 이미지의 문자 인식 | 서로 다른 형태의 정보를 함께 처리 |
| 대표 입력 | 문서 이미지 | 이미지와 질문 등 |
| 대표 출력 | 인식된 문자 | 질문에 대한 텍스트 답변 등 |
| 실제 서비스 | 문서의 텍스트 추출 | 이미지 내용을 바탕으로 질문 응답 등 |

두 기술은 경쟁 관계로만 볼 필요가 없습니다. 실제 문서 서비스에서는 OCR로 추출한 텍스트를 언어 모델에 전달하거나, 지원되는 Multimodal Model을 직접 사용하는 등 구성 방식이 달라질 수 있습니다. **인식 결과의 정확성은 별도 확인이 필요**합니다.

더 자세한 OCR과 Multimodal 처리 흐름은 Phase 2에서 학습합니다.

## 9. LLM은 왜 Database나 Search Engine이 아닐까?

### 9-1. 저장된 사실 조회와 언어 생성의 차이

이전 교시에서 일반 프로그램과 AI 모델의 역할을 구분했습니다. 여기서는 한 단계 더 나아가 **정보의 출처를 어디에서 가져오는지** 살펴봅니다.

상품 설명 서비스를 만든다고 생각해 봅시다. 모델에게 다음과 같이 요청했습니다.

> “우리 쇼핑몰의 현재 재고가 몇 개인지 알려줘.”

LLM이 그 쇼핑몰의 실제 재고 시스템에 연결돼 있지 않다면 **오늘의 정확한 재고 수량을 자동으로 알 수 없습니다.** 자연스러운 숫자나 설명을 만들어 답해도 실제 기록을 조회한 결과로 취급해서는 안 됩니다.

```text
실제 재고를 확인해야 할 때
사용자 질문
    ↓
권한 확인 + 재고 시스템 / Database 조회
    ↓
실제 조회 결과
```

반면 LLM의 언어 출력은 다음 관점에서 이해합니다.

```text
사용자 입력 + Context
          ↓
    Language Model
          ↓
       언어 생성
          ↓
       Output
```

여기서 중요한 것은 **모델이 언제나 외부 정보를 못 쓴다는 뜻이 아니라**, **필요한 정보에 접근하는 별도 연결이 없는데도 실제 데이터를 안다고 가정하면 안 된다**는 것입니다.

### 9-2. Search Engine과도 역할이 다르다

**Search/Retrieval(검색·조회)**은 관련 문서나 정보를 찾는 역할을 합니다. 반면 LLM은 주어진 Context와 학습된 패턴을 활용해 언어 출력을 생성합니다.

둘을 결합할 수는 있습니다.

```text
사용자의 질문
      ↓
Search / Retrieval
      ↓
관련 문서나 기록 확보
      ↓
LLM에 필요한 정보 제공
      ↓
근거를 바탕으로 답변 생성
```

관련 문서를 찾아 제공하는 구조는 나중에 배우는 **RAG(Retrieval-Augmented Generation, 검색 증강 생성)**로 연결됩니다. 이번 교시는 RAG의 구현 과정을 배우는 시간이 아닙니다. **“검색해서 찾은 정보”와 “모델이 생성한 답변”의 책임이 서로 다르다**는 점을 기억합니다.

## 10. Hallucination: 그럴듯한 답변이 왜 위험할까?

**Hallucination(환각)**은 모델이 생성한 내용이 자연스럽고 그럴듯해 보이지만 **사실과 다르거나 뒷받침할 근거가 부족한 경우**를 설명할 때 쓰는 용어입니다.

### 10-1. 상품 설명 생성 예시

아래는 **강의용 가상 상품 정보**입니다.

> **제공한 정보:** 색상은 검정, 용량은 500mL, 소재는 스테인리스
>
> **사용자 요청:** “이 상품의 소개 문구를 두 문장으로 작성해 줘.”

모델이 다음과 같이 작성했다고 가정해 봅시다.

> “500mL 용량의 검정 스테인리스 제품입니다. **24시간 보온과 평생 무상 수리를 보장합니다.**”

첫 번째 문장은 제공한 정보와 연결됩니다. 그러나 두 번째 문장의 **보온 시간과 수리 보증 조건은 입력 자료에 없었습니다.** 그 문장이 실제로 맞는지 확인할 근거도 없습니다.

이것이 핵심입니다. **문장이 광고처럼 자연스럽게 읽힌다는 사실은 그 내용이 검증됐다는 증거가 아닙니다.**

### 10-2. ‘AI가 거짓말했다’로만 설명하면 부족하다

LLM은 주어진 입력과 학습된 패턴에 따라 출력을 생성합니다. 생성한 문장이 외부 세계의 실제 기록과 맞는지는 모델의 유창성만으로 보장되지 않습니다.

```text
자연스러운 표현
      ≠
검증된 사실
```

따라서 상품 소개처럼 실제 고객에게 노출되는 내용에는 **근거와 확인 절차**가 필요합니다. 특히 존재하지 않는 보증이나 재고를 사실로 표시하면 서비스 문제로 이어질 수 있습니다.

**강사 질문:** “틀린 문장을 만드는 것이 싫다면 LLM을 아예 사용하지 말아야 할까요?”  
**예상 답변:** 반드시 그렇지는 않습니다. 초안을 생성하는 데 활용하되, **확인 가능한 자료에 근거한 내용만 게시하도록 검토하는 방식**을 고려할 수 있습니다.

## 11. Non-determinism과 생성형 AI 테스트

### 11-1. 같은 질문에 왜 다른 답변이 나올까?

**Non-determinism(비결정성)**은 같은 입력이어도 실행 조건에 따라 결과가 달라질 수 있는 특성을 가리킵니다.

3교시에서는 명확한 코드 규칙과 통계적 모델의 차이를 설명했습니다. 이번에는 **생성형 언어 모델의 출력 선택 방식**에 집중합니다.

많은 생성형 모델은 다음 Token 후보들에 대한 가능성을 계산한 뒤, **Sampling(샘플링)** 등 설정된 방식에 따라 출력을 선택합니다. Sampling은 후보 중에서 확률적인 방식으로 선택하는 방법을 의미합니다.

```text
같은 Prompt
    ↓
Model이 후보 Token의 가능성 계산
    ↓
Sampling 등 출력 선택 방법
    ↓
이번 실행의 출력
```

따라서 같은 상품 정보로 소개문을 여러 번 요청하면 어휘나 문장 구성이 달라질 수 있습니다. 단, **같은 입력이면 반드시 매번 달라진다는 뜻은 아닙니다.** 생성 설정과 실행 조건에 따라 같은 결과가 나올 수도 있습니다.

### 11-2. 그럼 무엇을 테스트해야 할까?

상품 설명을 다음 두 방식으로 검사해 봅시다.

| 검사 방법 | 한계 또는 장점 |
|---|---|
| “지난번과 글자가 한 글자도 다르지 않은가?” | 의미가 같은 올바른 표현도 실패로 처리할 수 있음 |
| “필수 정보가 있고, 근거 없는 보증 조건은 없으며, 두 문장인가?” | 서비스 요구사항과 출력 품질을 직접 검사할 수 있음 |

이번 사례에 맞는 검사 질문은 다음과 같습니다.

1. **형식:** 소개문을 두 문장으로 작성했는가?
2. **사실성:** 용량·색상·소재가 제공된 정보와 일치하는가?
3. **금지 조건:** 주어지지 않은 보증·성능을 확정적으로 작성하지 않았는가?
4. **사용성:** 고객에게 보여 줄 수 있는 문장인가?

여기서 형식과 일부 데이터 유형은 코드로 확인할 수 있습니다. 하지만 **주장에 근거가 있는지**와 **정보가 정확한지**는 원본 데이터 대조나 별도의 검토가 필요할 수 있습니다. **형식이 맞는다고 내용까지 참인 것은 아닙니다.**

## 12. Context: 모델에 어떤 정보를 함께 전달할까?

**Context(문맥)**는 모델이 현재 입력을 처리할 때 참고하는 내용입니다. 질문뿐 아니라 지시사항, 이전 대화, 제공된 문서, 시스템이 전달한 다른 정보 등이 포함될 수 있습니다.

```text
지시사항
  +
사용자의 요청
  +
제공된 상품 정보
  +
필요한 경우 이전 대화나 조회 결과
          ↓
        Context
          ↓
     Language Model
```

### 12-1. Context가 왜 중요한가?

사용자가 “이 제품을 설명해 줘”라고만 말하면 **어떤 제품인지, 어떤 정보를 사실로 사용해야 하는지** 불분명합니다.

반면 색상·용량·소재 등 실제로 제공된 정보를 함께 주면 모델이 그 정보에 맞춰 문장을 만들도록 유도할 수 있습니다. 다만 정보를 제공했다는 이유만으로 모델이 언제나 이를 정확하게 사용한다고 보장할 수는 없습니다. **입력과 출력의 대조는 여전히 필요**합니다.

### 12-2. Context Window는 무한하지 않다

**Context Window(문맥 처리 범위)**는 모델이 한 번의 처리에서 다룰 수 있는 Token 범위와 관련된 개념입니다. 모델마다 지원 범위가 다를 수 있습니다.

문서나 대화가 길어지면 다음을 고려해야 합니다.

- 요청과 함께 전달해야 하는 정보가 얼마나 많은가?
- 모델이 현재 한 번에 다룰 수 있는 범위인가?
- 관련 없는 대화나 문서를 많이 추가해 중요한 정보가 흐려지지 않는가?
- 입력과 출력의 크기가 비용과 응답시간에 어떤 영향을 주는가?

정확한 Token 계산과 모델별 Context 제한은 이후 LLM 실습에서 확인합니다. 이번에는 **“많은 정보를 주기만 하면 무조건 정확해지는 것은 아니다”**라는 점을 기억합니다.

---

## 13. AI 출력을 프로그램에서 사용하려면: Structured Output

### 13-1. 사람이 읽기 좋은 문장과 프로그램이 처리하기 좋은 값

사용자에게는 자연스러운 소개 문구가 편할 수 있습니다. 하지만 프로그램은 그 결과에서 **상품명·설명문·검토 필요 여부**처럼 특정 값을 읽어야 할 수도 있습니다.

자연어 출력 예:

> “이 상품은 검정색 500mL 제품입니다. 출시 전에 설명 내용을 검토해 주세요.”

구조화된 출력 예:

```json
{
  "description": "검정색 500mL 제품의 소개 초안입니다.",
  "needs_review": true
}
```

이처럼 미리 약속한 구조로 결과를 받는 방식을 **Structured Output(구조화된 출력)**이라고 합니다. 위 JSON은 **형태를 설명하기 위한 예시**이며, 모델에서 실제로 생성·검증한 출력은 아닙니다.

### 13-2. JSON이라는 모양만 맞으면 충분할까?

아닙니다. 프로그램이 이 결과를 사용하려면 두 가지를 따로 확인해야 합니다.

1. **구조·자료형 검증:** `description`이 문자열인가? `needs_review`가 Boolean인가? 필수 필드가 존재하는가?
2. **내용·업무 규칙 검증:** 설명에 근거 없는 성능 주장이 들어 있지는 않은가? 공개 가능한 상태인가?

**Schema(스키마)**는 데이터가 따라야 하는 구조, 필드, 자료형 등의 규칙을 말합니다. **Validation(검증)**은 결과가 그 규칙이나 별도 업무 조건을 만족하는지 확인하는 절차입니다.

```text
Model이 결과 생성
        ↓
Structured Output
        ↓
Schema Validation
        ↓
원본 정보와 내용 대조 / 업무 규칙 검사
        ↓
필요하면 사람의 검토
        ↓
게시 또는 다음 단계 처리
```

실제 코드에서 Pydantic으로 자료형과 구조를 확인하는 방법은 Day 1 후반의 FastAPI·Structured Output 실습에서 학습합니다. **Pydantic 등으로 구조를 검사하는 것과 사실의 정확성을 입증하는 것은 다르다**는 점을 기억합시다.

## 14. 생성형 AI가 적합한 업무와 그렇지 않은 업무

생성형 AI로 작업을 수행할 수 있는지와 **그 업무를 AI에 맡기는 것이 적절한지**는 다른 질문입니다.

원본 강의에서 다루는 요구사항을 서로 비교해 봅시다.

| 업무 | 먼저 판단할 점 | 적절한 처리 방향의 예 |
|---|---|---|
| 상품 설명 초안 작성 | 정해진 상품 정보를 바탕으로 문장을 만들어야 함 | AI 초안 생성 + 사실 검토 |
| 고객 리뷰 감정 분류 | 입력 문장의 의미를 해석해야 함 | 분류 모델 또는 생성형 모델 활용 가능 |
| 현재 재고 수량 조회 | 최신의 실제 숫자가 필요함 | 재고 Database/API 조회 |
| 회사 내부 문서로 질문 답변 | 모델에 내부 문서의 내용이 제공되는가? | 권한 확인 + 문서 접근/검색 + 답변 생성 |
| 일정 금액 초과 시 승인 | 명확한 업무 규칙을 정확히 적용해야 함 | Application Code에서 규칙 검사 |

3교시에서 **명확한 규칙은 코드로 처리한다**는 원칙을 배웠습니다. 여기에서는 이를 다시 코딩하지 않고, 생성형 모델을 실제 서비스에 넣을 때 **입력의 근거와 출력의 책임을 분리해야 한다**는 점에 집중합니다.

**강사 포인트:** “AI가 잘하는 일”이라는 표현을 “AI가 무엇이든 맞게 처리하는 일”로 이해하지 않도록 합니다. 생성형 모델은 요약·분류·번역·정보 추출·초안 작성 등에 활용할 수 있지만, 정확성이 중요한 부분은 별도의 데이터 조회·업무 검증·사람 검토가 필요할 수 있습니다.

## 15. Cloud AI와 Local AI는 무엇이 다를까?

같은 생성 기능을 구현하더라도 모델을 **어디에서 실행하고 누가 운영하는지**가 다를 수 있습니다.

### 15-1. Cloud AI Service

**Cloud AI**는 일반적으로 외부 AI Provider가 운영하는 모델을 네트워크를 통해 이용하는 방식입니다. **Provider**는 모델 접근과 실행 서비스를 제공하는 사업자나 서비스 주체이고, **API**는 다른 프로그램이 그 기능을 요청하고 결과를 받을 수 있도록 마련된 인터페이스입니다.

```text
우리 Application
       ↓
   네트워크 요청
       ↓
AI Provider의 API
       ↓
Provider가 운영하는 모델
       ↓
응답을 Application으로 전달
```

**장점:** 직접 대규모 모델 실행 인프라를 준비·운영하지 않고도 기능을 연결할 수 있으며, API 기반 개발이 가능합니다.

**고려사항:** 네트워크 연결, 사용량별 비용, Rate Limit(요청 제한), 응답 지연, 전송 데이터의 처리 정책, Provider의 변경 사항 등을 확인해야 합니다.

### 15-2. Local / Self-managed Model

**Local AI**는 모델을 자신의 컴퓨터나 직접 관리하는 환경에서 실행하는 방식입니다. **Runtime / Serving 도구**는 모델 파일을 불러와 요청을 처리하고 결과를 제공하는 실행 환경을 말합니다.

```text
우리 Application
       ↓
직접 관리하는 실행 환경
       ↓
Model Runtime / Serving
       ↓
로컬 또는 자체 운영 모델
       ↓
응답을 Application으로 전달
```

**장점:** 데이터 처리 위치와 실행 환경을 직접 관리할 수 있고, 구성에 따라 외부 네트워크 없이 운영할 수 있습니다.

**고려사항:** CPU/GPU, RAM/VRAM, 모델 크기, 처리 속도, License, 업데이트, 운영과 보안 책임 등을 직접 관리해야 합니다.

### 15-3. 어느 방식이 더 좋을까?

| 관점 | Cloud AI | Local / Self-managed AI |
|---|---|---|
| 모델 운영 주체 | 주로 Provider | 주로 직접 관리하는 조직·개발자 |
| 초기 실행 준비 | API 연결 중심 | 모델·Runtime·장비 준비 필요 |
| 자원 문제 | 외부 서비스 조건에 영향 | 보유한 장비 성능과 메모리에 영향 |
| 데이터 처리 | 외부 전송 및 정책 검토 필요 | 자체 처리 위치·보안 운영 책임 중요 |
| 비용 | 사용량·서비스 정책에 따라 달라짐 | 장비·전력·운영 부담 등을 고려 |
| 통제 범위 | Provider의 공개 기능과 정책 내에서 사용 | 지원 범위 내에서 환경을 직접 조정 |

어느 쪽이 무조건 우수하다고 결론 내리지 않습니다. **품질·비용·자원·보안·운영 조건을 기준으로 선택**합니다. 실제 서비스별 가격과 제한은 이 강의자료에서 검증하지 않았습니다.

## 16. 강사 시연 — 하나의 생성 기능을 두 방식으로 설계하기

이번에는 이전 교시의 **PDF 요약 서비스 구조를 다시 그리지 않고**, 5교시에서 다룬 **상품 설명 초안 생성 기능**을 사용합니다.

### 16-1. 요구사항

> “관리자가 상품 정보를 입력하면 두 문장의 소개문 초안을 만들고, 확인 후 게시할 수 있도록 한다.”

관리자가 제공한 상품 정보만을 활용해 작성하며, 모델이 새로운 성능이나 보증 내용을 임의로 확정하지 않도록 검토합니다.

### 16-2. Cloud 방식의 개념적 흐름

```text
관리자가 상품 정보를 입력
           ↓
Application: 입력 정보·권한 확인
           ↓
Cloud AI API에 지시와 상품 정보 전달
           ↓
Provider의 모델이 설명 초안 생성
           ↓
Application: 형식·내용 검증
           ↓
관리자 확인 후 게시
```

### 16-3. Local 방식의 개념적 흐름

```text
관리자가 상품 정보를 입력
           ↓
Application: 입력 정보·권한 확인
           ↓
자체 Model Runtime에 요청 전달
           ↓
Local Model이 설명 초안 생성
           ↓
Application: 형식·내용 검증
           ↓
관리자 확인 후 게시
```

두 방식에서 **공통인 부분**은 상품 정보 준비, 입력 검증, 모델에 대한 지시, 출력 검증, 승인 절차입니다. **달라지는 부분**은 모델을 호출하는 위치와 실행·운영 책임입니다.

> **강사 질문:** “Local Model을 쓰면 근거 없는 문장이 생성되는 문제도 자동으로 사라질까요?”  
> **예상 답변:** 아닙니다. 어디에서 실행하는지와 생성한 내용의 사실성은 별도 문제입니다. Cloud와 Local 어느 방식이든 검증이 필요합니다.

이 시연은 **아키텍처를 구분하기 위한 개념 시연**입니다. 실제 Cloud API 호출이나 Local Model 실행은 뒤의 실습에서 진행합니다.

## 17. 학생 활동 — 생성형 AI의 결과를 평가해 보기

### 활동 A. 생성형 AI에 맡길 수 있는 부분 구분하기

원본 강의자료의 다섯 가지 요구사항을 보고, 무엇이 필요한지 이유까지 설명해 보세요.

| 사례 | 요구사항 | 핵심 판단 질문 |
|---|---|---|
| A | 고객 리뷰를 긍정/부정으로 나눈다 | 분류라는 작업을 어떤 모델이 수행할 수 있는가? |
| B | 상품 설명 초안을 작성한다 | 생성한 문장에서 무엇을 검증해야 하는가? |
| C | 현재 재고를 알려준다 | 최신 기록은 어디에서 조회해야 하는가? |
| D | 회사 내부 문서를 토대로 답한다 | 내부 문서에 접근하고 근거를 제공하는 절차가 있는가? |
| E | 결제 금액이 기준을 넘으면 승인을 요구한다 | 명확한 규칙을 코드로 처리할 수 있는가? |

**예상 답변:** A는 분류 작업으로 여러 모델 방식이 가능하고, B는 생성형 AI 초안을 검토해 사용할 수 있습니다. C는 실제 재고 조회, D는 허가된 내부 자료 접근과 검색, E는 명확한 비즈니스 규칙 검사가 중요합니다.

### 활동 B. 모델이 작성한 문장에서 근거 없는 주장 찾기

**10번 섹션의 가상 상품 정보**를 다시 봅시다.

- 입력에 있는 사실: 검정색, 500mL, 스테인리스
- 생성한 문장: “500mL 용량의 검정 스테인리스 제품입니다. 24시간 보온과 평생 무상 수리를 보장합니다.”

학생에게 다음을 질문합니다.

1. 두 문장 중 **제공된 정보로 뒷받침되는 내용**은 무엇인가요?
2. **자료에 없는 주장**은 무엇인가요?
3. 이런 문장을 고객에게 보여 주기 전에 **어떤 절차**가 필요할까요?
4. JSON 형식 검사가 통과했다면 **보온 시간까지 사실이라고 확정할 수 있나요?**

**예상 답변:** 색상·용량·소재는 입력에 있지만, 보온 시간·평생 보증은 주어지지 않았습니다. 원본 상품 데이터 확인과 관리자 검토가 필요하며, JSON 구조 검사는 그 주장의 진위를 보증하지 않습니다.

### 활동 C. 모델 선택 조건 생각하기

“고객 응답이 빠르고, 운영 비용이 제한되어 있으며, 상품 정보는 외부 전송 조건을 확인해야 한다”고 가정해 봅시다.

- 단순히 Parameter 수가 가장 큰 모델을 선택해도 될까요?
- Cloud와 Local 중 어느 쪽을 택하기 전에 무엇을 확인해야 할까요?

**예상 답변:** 작업 품질뿐 아니라 지연시간, 비용, 실행 장비, 데이터 처리 정책, 운영 부담을 함께 검토해야 합니다. 조건과 실측값 없이 한 방식을 정답으로 확정할 수는 없습니다.

## 18. 흔히 생기는 오해 정리

| 오해 | 어떻게 이해해야 할까? |
|---|---|
| “생성형 AI는 분류를 못 한다.” | 생성형 모델도 분류·추출·변환 작업에 활용할 수 있습니다. |
| “LLM과 Foundation Model은 같은 말이다.” | LLM은 언어 중심 대규모 모델, Foundation Model은 여러 작업의 기반이라는 성격을 나타냅니다. |
| “Base Model과 Chat/Instruct Model은 이름만 다르다.” | 추가 학습과 사용 목적이 다를 수 있으므로 Variant 설명을 확인해야 합니다. |
| “Multimodal이면 OCR과 완전히 같은 기능이다.” | OCR의 문자 인식과 여러 형태의 정보 처리라는 목적을 구분해야 합니다. |
| “모델의 답변은 현재 Database를 조회한 기록이다.” | 별도 데이터 연결이 없다면 실시간 내부 기록의 정확성을 보장하지 않습니다. |
| “답변이 자연스럽고 JSON도 맞으면 정확하다.” | 형식·자료형과 사실성 검증은 서로 다릅니다. |
| “같은 질문이면 매번 결과가 반드시 다르다.” | 생성 설정과 실행 조건에 따라 같을 수도, 다를 수도 있습니다. |
| “큰 모델은 모든 환경에서 더 적합하다.” | 업무 적합성·속도·메모리·비용·정책 등을 함께 판단해야 합니다. |

이 표는 앞서 배운 내용을 다시 길게 설명하는 용도가 아니라, **잘못된 결론을 빠르게 확인하는 용도**입니다. 학생이 설명하지 못하는 항목만 해당 본문으로 돌아가 확인합니다.

## 19. 수업 확인 질문

학생이 **정의뿐 아니라 그 이유**까지 말할 수 있는지 확인합니다.

**Q1. 생성형 AI는 어떤 결과를 만들 수 있나요?**  
텍스트, 코드, 이미지, 오디오·음성, 비디오 등 여러 콘텐츠를 생성할 수 있습니다. 단순히 ChatGPT 같은 대화형 서비스만 의미하지 않습니다.

**Q2. Token은 항상 단어 하나인가요?**  
아닙니다. Token은 모델이 처리하는 단위이고 Tokenizer에 따라 단어나 그 일부, 기호 등이 될 수 있습니다.

**Q3. LLM이 텍스트를 생성하는 기본 흐름은 무엇인가요?**  
Context를 참고해 다음 Token의 가능성을 계산하고 선택하는 과정을 반복하여 문장을 만들 수 있습니다.

**Q4. Foundation Model과 LLM은 동일한가요?**  
아닙니다. Foundation Model은 여러 작업의 기반으로 활용할 수 있는 모델이라는 성격을 말하며, 언어 외의 영역도 포함할 수 있습니다.

**Q5. Base Model과 Instruction-tuned Model은 무엇이 다른가요?**  
Base Model은 사전학습으로 기본 능력을 갖춘 모델이고, Instruction-tuned Model은 지시 수행에 적합하도록 추가 학습을 거친 모델입니다.

**Q6. 같은 Model Family에서 왜 Variant를 선택해야 하나요?**  
규모, 지시 학습 여부, Context, 지원 Modality, 배포 목적 등이 다를 수 있어 실제 서비스 요구사항과 맞춰야 하기 때문입니다.

**Q7. Hallucination이 서비스에서 왜 위험한가요?**  
모델이 근거 없는 내용을 자연스럽게 생성해도 사용자나 다음 시스템이 사실로 받아들일 수 있기 때문입니다.

**Q8. Structured Output의 Schema를 통과하면 내용도 정확한가요?**  
그렇지 않습니다. 구조·자료형 검증과 원본 사실 대조는 별도로 필요합니다.

**Q9. LLM에게 내부 재고를 물어보면 언제 정확한 답을 기대할 수 있나요?**  
권한 있는 실제 데이터 소스에서 필요한 정보를 조회·전달하고 결과를 검증하는 연결이 마련돼 있어야 합니다.

**Q10. Cloud와 Local AI의 가장 큰 운영 차이는 무엇인가요?**  
모델이 어디에서 실행되고 누가 운영하는지에 차이가 있습니다. 어떤 방식을 선택하든 비용·자원·보안·품질과 출력 검증을 함께 검토해야 합니다.

## 20. 이번 교시 핵심 정리

오늘 배운 내용을 서로 다른 질문으로 나누어 기억합시다.

| 질문 | 이번 교시의 답 |
|---|---|
| 무엇을 하는 모델인가? | 생성형 모델은 새로운 텍스트·이미지·오디오 등의 콘텐츠를 만들 수 있습니다. |
| 텍스트는 어떻게 만들어지는가? | Language Model은 Context와 Token을 바탕으로 다음 출력을 계산하며 텍스트를 이어 갈 수 있습니다. |
| 어떤 종류의 모델인가? | LLM은 언어 중심 대규모 모델이고, Foundation Model은 다양한 작업의 기반으로 활용되는 성격을 말합니다. |
| 어떤 모델을 선택하는가? | Family 이름뿐 아니라 Variant의 목적과 실행 조건을 확인해야 합니다. |
| 모델의 답변을 그대로 사용해도 되는가? | 자연스럽게 생성된 내용이라도 근거·정확성·업무 조건을 검증해야 합니다. |
| 어디에서 실행하는가? | Cloud와 Local은 모델 실행 위치와 운영 책임이 다릅니다. |

이 수업에서 가장 중요한 문장은 두 가지입니다.

> **생성형 AI는 학습한 패턴과 입력 Context를 활용해 콘텐츠를 생성합니다. 따라서 자연스러운 출력이 곧 검증된 사실은 아닙니다.**

> **실제 AI Application 개발에서는 모델이 무엇을 만들어 줄 수 있는지만 보지 않고, 필요한 데이터를 어디서 가져오고 결과를 누가 어떻게 검증할지도 함께 설계해야 합니다.**

## 21. 다음 교시 연결 — AI 개발 생태계와 핵심 라이브러리

이번 시간에는 생성형 AI를 사용할 때 알아야 할 **모델의 종류와 한계, 모델 선택·실행 방식**을 살펴보았습니다.

그런데 실제 개발을 시작하면 서로 다른 역할의 도구들이 등장합니다.

- **NumPy·pandas·scikit-learn·PyTorch:** 데이터를 다루거나 모델을 개발할 때 사용하는 도구
- **Hugging Face Hub·Transformers:** 사전학습 모델을 찾아 활용하는 생태계의 구성 요소
- **OpenAI SDK·Ollama:** Cloud API 또는 Local Model을 활용할 때 만나게 되는 도구
- **FastAPI·Pydantic:** 모델 호출을 서비스에 연결하고 결과를 처리하는 Backend 관련 도구
- **LangChain·LlamaIndex:** 여러 AI 기능과 데이터 처리를 연결할 때 쓰일 수 있는 도구

여기서 각 도구를 상세하게 다시 정의하거나 설치하지는 않습니다. 그 역할과 차이는 **6교시 ‘현대 AI 개발 생태계와 핵심 라이브러리’**에서 처음부터 체계적으로 비교합니다.
