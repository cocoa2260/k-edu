> 이번 교시의 핵심: **모델을 직접 실행하는 것과, 모델 실행 기능을 서비스로 제공하는 것의 차이**

## 개요 — 오늘 달라지는 질문

앞선 5교시에서는 Python 프로그램 안에서 Transformers를 이용해 Pre-trained Model을 불러오고, 생성한 Token ID를 텍스트로 복원했다. **어떻게 생성하는가**를 코드로 확인한 것이다.

이번에는 **다른 프로그램도 같은 모델을 사용하려면 어떻게 할 것인가?**를 생각한다. 모델을 실행하는 코드를 그대로 복사해 각 프로그램에 넣을 수도 있고, 실행을 맡는 별도의 프로그램을 만들어 다른 프로그램이 요청하도록 할 수도 있다. 이 차이가 오늘의 출발점이다.

```text
[방식 A: 직접 실행]
Python Application ─ Transformers / PyTorch ─ Model ─ CPU·GPU

[방식 B: 모델 실행을 서비스로 제공]
Application ─ HTTP Request ─ Model Server / Runtime ─ Model ─ CPU·GPU
                         └── HTTP Response ────────────┘
```

위의 화살표는 개념적인 책임 분담도다. 실제 모든 제품이 동일하게 구현된다는 뜻은 아니다.

**오늘은 Ollama를 설치하거나 실행하지 않는다.** Ollama의 실제 명령어·모델 다운로드·상태 확인은 7교시에서, FastAPI와 Ollama API를 연결하는 코드는 8교시에서 실습한다.

## 1. 학습 목표

수업 후 학생은 다음을 할 수 있어야 한다.

1. 동일한 모델 추론이라도 **어느 프로세스에서 실행하는지**에 따라 구조가 달라진다고 설명한다.
2. **Runtime**, **Model Server**, **Model Serving**, **API**, **Client**를 역할로 구분한다.
3. Transformers **직접 실행**과 Ollama를 통한 **별도 실행·Serving**을 비교한다.
4. Localhost를 통해 같은 컴퓨터의 서로 다른 프로세스가 HTTP로 통신하는 이유를 설명한다.
5. Cloud/Local을 서버 유무가 아니라 **실행 위치와 운영 주체** 관점에서 판단한다.
6. 여러 애플리케이션이 한 모델을 사용할 때 예상되는 메모리·프로세스 관리 문제를 찾는다.
7. Latency, Throughput, Concurrency, Streaming을 모델 서비스 **운영 관점의 관찰 항목**으로 구분한다.
8. 간단한 요구사항을 보고 직접 실행과 Serving 중 적절한 구조를 선택하고 이유를 제시한다.

> **학습 범위 구분:** Training/Inference의 상세 원리(Day2 3교시), Model Card·모델 파일 검토(Day2 4교시), Tokenizer·`generate()` 사용법(Day2 5교시)은 다시 강의하지 않는다. 이 교시에서는 **실행 위치·프로세스·요청 경계**를 새로 배운다.

## 2. 모델을 실행하는 위치와 역할을 구분하기

동일하게 텍스트를 생성하더라도 사용자가 보는 화면만으로 실제 모델의 실행 위치를 알 수는 없다.

| 구분 | 애플리케이션이 하는 일 | 모델을 계산하는 위치 | 실행 자원 관리 주체 |
|---|---|---|---|
| Day1 Cloud API | 외부 제공자에게 요청 전송 | 제공자가 운영하는 환경 | 주로 AI 제공자 |
| Day2 5교시 직접 실행 | Python 내부에서 모델 로드·추론 요청 | 직접 코드를 실행하는 환경 | 개발자/운영자 |
| 별도 Local Model Server | 서버에 요청을 전송 | 조직이나 개인이 관리하는 서버 환경 | 해당 서버 운영자 |

여기서 **직접 실행**이란 애플리케이션의 Python 프로세스 안에서 모델 라이브러리를 사용하여 모델 객체를 관리하고 추론한다는 의미다. 반면 **Serving**은 다른 프로그램이 요청을 보내 사용할 수 있게 추론 기능을 외부 인터페이스로 제공하는 방식이다.

같은 PC에서 서버를 실행해도 Serving일 수 있고, 원격 클라우드에서 Python이 직접 모델을 실행할 수도 있다. **직접 실행·Serving은 프로그램 구성의 차이이며, Cloud·Local은 실행 위치와 관리 책임에 관한 구분**이다.

## 3. Process를 알아야 Serving이 보인다

**Process(프로세스)**는 실행 중인 프로그램의 단위다. 이 수업에서는 서로 다른 Python 프로그램이나 서버가 별도의 프로세스로 동작할 수 있다고 이해하면 충분하다.

한 Python 프로그램 안에 모델을 넣으면:

```text
┌──────── Python Process A ────────┐
│ 업무 로직                         │
│   ↓                              │
│ Transformers                     │
│   ↓                              │
│ PyTorch / Tokenizer / Model      │
└──────────────┬───────────────────┘
               ↓
            CPU / GPU
```

반면 실행 프로세스를 분리하면:

```text
┌──── Application Process A ────┐
│ 요청 만들기 · 응답 사용        │
└──────────────┬───────────────┘
               │ HTTP
               ▼
┌──── Model Server Process B ───┐
│ 요청 받기 · Model 실행 · 응답   │
│                ↓              │
│          Model + CPU/GPU      │
└──────────────────────────────┘
```

이때 A가 B에 요청하기 위해 B의 Python 내부 함수를 직접 호출할 필요는 없다. 약속된 **API**를 통해 데이터를 전달할 수 있다. 프로그램 실행 단위를 분리했기 때문에 각 프로세스의 시작·종료, 오류, 사용 자원도 구분해 볼 수 있다.

## 4. Direct Model Execution — Transformers 방식

5교시에서 실행한 프로그램의 책임을 운영 관점에서 다시 표시하면 다음과 같다.

```text
Python Application
  ├─ 업무에서 처리할 입력 준비
  ├─ Model·Tokenizer 로드
  ├─ Tensor / Device 준비
  ├─ Model Generation 수행
  ├─ Token ID 해석
  └─ 결과를 애플리케이션에서 사용
```

여기서는 코드를 다시 작성하지 않는다. 위 각 항목은 **5교시 코드의 책임 목록**이다.

직접 실행의 강점은 애플리케이션이 Tokenizer, Tensor, Model Layer, Generation 동작 등을 세밀하게 다룰 수 있다는 점이다. 그래서 연구·모델 개발·사용자 정의 추론처럼 모델 내부에 접근해야 할 때 유용하다.

대신 운영자는 모델 파일 확인, 로드, 메모리, 장치 선택, 라이브러리 호환성, 프로세스 종료 등도 관리한다. 이는 모델을 제어할 수 있다는 장점과 함께 따라오는 책임이다.

**판단 질문:** “모델 내부 Tensor를 직접 관찰·수정해야 하는가?” 그럴 필요가 크다면 직접 실행 방식이 적합할 수 있다. 단순히 텍스트 생성 결과만 필요하다면 다른 선택지도 검토할 수 있다.

## 5. 애플리케이션이 세 개면 무슨 문제가 생길까?

아래 세 프로그램이 동일한 모델의 결과를 필요로 한다고 가정하자.

```text
문서 요약 프로그램 ─ 자체 Model Load
채팅 프로그램     ─ 자체 Model Load
분류 프로그램     ─ 자체 Model Load
```

각 프로그램을 서로 다른 프로세스에서 독립적으로 실행한다면, 각자가 모델을 로드하고 메모리를 사용하거나 라이브러리 환경을 관리해야 할 수 있다. 모델이 커질수록 문제가 눈에 띈다.

| 확인할 문제 | 각 프로그램이 직접 실행할 때의 가능성 |
|---|---|
| 메모리 | 별도 모델 로드로 사용량이 증가할 수 있음 |
| 초기 실행 | 프로그램별로 모델 준비 시간이 발생할 수 있음 |
| 모델 교체 | 여러 프로그램에서 설정을 바꿔야 할 수 있음 |
| 문제 분석 | 각 프로세스의 상태를 따로 확인해야 함 |
| 자원 경쟁 | 여러 실행이 같은 CPU·GPU 자원을 사용할 수 있음 |

단, **프로세스 분리 = 반드시 메모리가 정확히 세 배**라는 뜻은 아니다. 메모리 공유나 캐싱 등 실제 환경의 구현 방식에 따라 달라질 수 있다. 여기서는 모델 실행 책임이 중복될 **가능성**을 확인한다.

대안은 한 실행 지점에 요청을 모으는 것이다.

```text
문서 요약 App ─┐
채팅 App      ─┼──> Model Server ──> Loaded Model
분류 App      ─┘
```

이렇게 하면 모델 로드와 실행 상태를 한곳에서 관리하는 설계가 가능해진다. **다만** 모든 요청이 한 서버로 집중되므로 처리량과 장애 영향도 고려해야 한다. Serving을 도입한다고 자동으로 성능·확장성이 좋아지는 것은 아니다.

## 6. Runtime과 Model Serving

두 용어를 구별해 읽는다.

**Runtime**은 모델을 실제 실행하는 데 필요한 기능을 제공하는 환경·계층이다. 모델 로드, 메모리와 하드웨어 사용, 추론 및 생성 처리 등을 담당할 수 있다. 어떤 기능을 어느 정도 제공하는지는 도구에 따라 다르다.

**Model Serving**은 모델의 추론 기능을 애플리케이션이 *요청 가능한 서비스*로 이용하도록 제공하는 방식이다. 요청 수신·실행·응답 반환이라는 운영 경계가 생긴다.

```text
Client → API → [Serving 계층: 요청 수신 / 관리]
                         ↓
                [Runtime: Model 실행]
                         ↓
                       Model
                         ↓
Client ← API ← 실행 결과 반환
```

위처럼 구별하면 Model, Runtime, Serving, API가 모두 같은 용어가 아니라는 점이 보인다.

| 이름 | 질문 | 핵심 역할 |
|---|---|---|
| Model | 무엇으로 결과를 계산하나? | 학습된 Parameter 및 계산 구조 |
| Runtime | 어떻게 실행하나? | 모델 로드·추론 실행 환경 |
| Serving | 다른 프로그램이 어떻게 이용하나? | 요청 처리 및 추론 기능 제공 |
| API | 무엇을 주고받기로 약속했나? | 호출·응답 인터페이스 |
| Client | 누가 요청하나? | 서비스를 이용하는 프로그램 |

예를 들어 **모델 파일을 내려받은 상태**와 **프로그램에서 모델을 실행할 수 있는 상태**, **다른 프로그램이 요청할 수 있는 상태**는 구분해야 한다.

## 7. HTTP는 인터넷에서만 쓰는가?

아니다. HTTP는 같은 컴퓨터의 서로 다른 프로세스가 통신할 때도 사용할 수 있다.

```text
한 대의 컴퓨터
┌────────────────────────────┐
│ Application Process        │
│       │                    │
│       │ HTTP (localhost)   │
│       ▼                    │
│ Model Server Process       │
│       │                    │
│       ▼                    │
│ Model                      │
└────────────────────────────┘
```

`localhost` 또는 `127.0.0.1`은 이 수업에서 **같은 컴퓨터 안의 통신 상대**를 지칭할 때 사용한다. 인터넷의 외부 서버에 반드시 접속한다는 의미가 아니다.

프로세스가 분리되면 서로 다른 언어로 작성된 프로그램도 정해진 HTTP 인터페이스를 통해 요청을 주고받을 수 있다. 그 대신 요청·응답 구조와 연결 실패를 처리해야 한다.

**FastAPI와 비교하기:** FastAPI 프로그램을 Uvicorn으로 실행하면 Browser가 HTTP를 통해 API 기능을 사용한다. Model Server도 요청을 받아 결과를 내놓는다는 점에서 비교할 수 있다. 다만 Uvicorn이 AI 모델 실행 도구라는 뜻은 아니다.

## 8. Ollama는 이 그림에서 어디에 있을까?

Ollama는 Local Model을 실행하고 API 형태로 사용할 수 있도록 지원하는 **Runtime / Serving 도구**다. 모델 계열인 Gemma와 같은 개념이 아니며, Python용 Client가 Ollama 서버 그 자체도 아니다.

```text
[요청하는 프로그램]
        ↓
   Client / HTTP
        ↓
┌─ Ollama Runtime / Server ─┐
│ 요청 접수                 │
│ Model 실행 및 생성 처리   │
│ 결과 제공                 │
└──────────┬───────────────┘
           ↓
       Local Model
           ↓
        CPU / GPU
```

Transformers에서는 Python 코드가 모델과 Tokenizer를 직접 다루는 경우가 많다. Ollama에서는 실행과 제공에 관한 여러 과정을 Runtime이 대신 담당하므로, 애플리케이션은 API를 통해 모델을 사용하는 방식에 집중할 수 있다.

- **이번 교시:** 두 방식의 책임과 프로세스 구성을 비교한다.
- **7교시:** Ollama 설치·Model 다운로드·실행·상태 확인을 실제로 수행한다.
- **8교시:** Python/FastAPI에서 Ollama API를 호출하는 프로그램을 만든다.

이 범위를 지키기 위해 여기서는 Ollama CLI 명령어와 실제 API 요청 코드를 제시하지 않는다.

## 9. 직접 실행과 Serving은 무엇을 선택하는 문제인가?

| 판단 항목 | Transformers 직접 실행 | Ollama 중심 Serving |
|---|---|---|
| 코드가 모델을 다루는 방식 | Python 라이브러리와 모델 객체에 직접 접근 | Model Server에 요청 전송 |
| 모델 실행 프로세스 | 애플리케이션 프로세스 안에서 실행 가능 | 별도 Runtime/Server 중심 |
| Tokenizer·Tensor 접근 | 내부 데이터를 직접 확인·조정하기 쉬움 | 일반적인 API 사용 시 추상화됨 |
| Model Load 관리 | 실행 코드가 직접 다룸 | Runtime이 담당하는 부분이 많음 |
| HTTP 필요 여부 | 단독 스크립트라면 필수 아님 | API를 쓰면 HTTP 등 통신 사용 |
| 세밀한 제어 | 모델 내부에 접근하는 용도에 적합 | 제공하는 API 기능 범위에 따름 |
| 여러 App에서 이용 | 별도 서비스 계층 설계 필요 가능 | 공통 서버를 이용하는 구조 가능 |
| 적합한 출발점 | 연구·실험·Custom Inference | 애플리케이션에서 Local 추론 결과 사용 |

**어느 쪽이 항상 우월한 것은 아니다.** 요구사항에 따라 선택한다. 별도 Serving 구조를 만드는 것이 꼭 필요한 것은 아니며, 직접 실행을 사용하더라도 추후 별도의 API 서버를 구현할 수 있다.

### 간단한 선택 연습

A. “Python 코드에서 모델 Layer와 Tensor를 직접 살펴봐야 한다.”  
→ Transformers 직접 실행을 우선 검토한다.

B. “여러 사내 프로그램에서 하나의 모델 실행 기능을 요청해 사용한다.”  
→ 공통 Model Server 구조를 우선 검토한다.

C. “하나의 학습용 스크립트에서 단 한 번 텍스트를 생성한다.”  
→ 별도 Serving을 만들 이유가 크지 않다.

중요한 것은 제품 이름을 맞히는 것이 아니라 **필요한 실행 경계를 먼저 판단**하는 것이다.

## 10. Cloud / Local / Server / Private를 혼동하지 않기

Day1에서 Cloud와 Local의 개념을 배웠으므로 같은 정의를 길게 반복하지 않는다. 여기서는 **Server라는 단어가 Cloud를 뜻하지 않는다**는 점을 새로운 사례로 확인한다.

```text
[같은 노트북]
Application ─ localhost ─ Local Model Server

[사내 서버]
직원 PC ─ 사내 네트워크 ─ 조직 운영 Model Server

[외부 AI 서비스]
Application ─ 네트워크 ─ Provider API / Model
```

첫 번째도 서버 프로세스가 있고, 두 번째도 서버가 있지만 외부 AI 제공자가 모델을 대신 실행하는 것은 아니다.

또한 **Local AI = 항상 완전히 오프라인** 또는 **Local AI = 보안이 자동 해결**이라는 뜻은 아니다. 설치·다운로드 등에 네트워크가 필요할 수 있고, 내부 서버라도 사용자 권한과 전송·저장 정책을 따로 설계해야 한다.

다음 문장을 비교해 보자.

- “서버를 쓴다.” → **어디에서 운영하는 서버인지**가 빠져 있다.
- “Local AI를 쓴다.” → **누가 접근하고 어떤 데이터를 전송하는지**가 빠져 있다.
- “사내 서버를 쓴다.” → **보안 요구사항을 충족하는지**는 별도 확인이 필요하다.

## 11. Runtime을 정할 때 모델만 확인하면 충분할까?

그렇지 않다. Model이 있어도 선택한 Runtime과 호환되지 않으면 실행하지 못할 수 있다.

```text
Model의 Architecture / 배포 Format
                +
Runtime의 지원 범위
                +
실행 Hardware / Memory
                ↓
실행 가능 여부 판단
```

원본에서 예로 든 저장 형식은 `safetensors`, `GGUF` 등이다. **파일 이름이나 Parameter 수만으로 Runtime 호환성을 단정하지 않는다.** 이 수업에서는 *선택한 모델을 선택한 Runtime으로 실행할 수 있는지* 확인해야 한다는 수준까지만 다룬다. GGUF의 파일 구조나 Quantization 계산은 후속 학습 범위다.

모델 선택과 Runtime 선택은 서로 연결되지만 동일한 의사결정은 아니다. 필요한 경우 Model, Runtime, Hardware, API 접근 방식의 조합을 함께 검토한다.

## 12. 모델을 서비스할 때 새로 생기는 질문

Serving에서는 모델이 하나라도 **여러 요청을 받아야 하는 프로그램**이 된다. 따라서 단일 스크립트 실행과 다른 관찰 항목이 등장한다.

| 항목 | 학생이 이해할 질문 | 이 교시의 범위 |
|---|---|---|
| Request Handling | 요청을 누가 받고 결과를 돌려주는가? | 역할 확인 |
| Model Load / Warm 상태 | 요청 시 모델 준비가 필요한가? | 개념 구분 |
| Latency | 한 요청의 응답을 받는 데 얼마나 걸리는가? | 개념 구분 |
| Throughput | 일정 시간 동안 얼마나 많은 요청을 처리하는가? | 개념 구분 |
| Concurrency | 동시에 들어온 요청을 어떻게 처리하는가? | 요구 확인 |
| Streaming | 결과를 완성 후 반환할까, 생성 중 나누어 보낼까? | 차이 확인 |
| Logging / Monitoring | 실패와 운영 상태를 어떻게 알 것인가? | 필요성 확인 |
| Authentication | 누가 서버를 사용할 수 있는가? | 필요성 확인 |

### Model Load 상태

모델 파일을 저장장치에 **보관**한 것과 실행 메모리에 **로드**한 것은 다르다. 아직 로드하지 않은 상태에서 첫 요청을 처리하면 준비 시간이 추가될 수 있다. 이미 메모리에 로드된 상태에서는 그 준비 비용이 줄어들 수 있지만, 유지 정책은 Runtime에 따라 다르다.

### Latency와 Throughput

**Latency**는 한 요청이 응답을 얻는 데 걸리는 시간이고, **Throughput**은 일정 시간 동안 처리한 작업량이다. 한 번의 응답이 빠르더라도 다수 요청을 잘 처리한다고 보장할 수는 없다.

### Concurrency

동시에 여러 요청이 들어오는 상황이다. 예를 들어 세 직원이 동시에 문서 요약을 요청하면 Model Server가 이를 처리하는 방식이 중요해진다. 이 교시에서는 처리 정책을 구현하거나 성능 수치를 추측하지 않는다.

### Streaming

```text
일반 응답: Request ─ [전체 결과 생성] ─ Response
Streaming: Request ─ [일부 결과] ─ [추가 결과] ─ [완료]
```

Streaming은 사용자가 결과 일부를 더 일찍 받아볼 수 있게 할 수 있다. **모델의 총 계산 시간이 반드시 줄어든다는 의미는 아니다.** 여기서는 이런 차이가 서비스 설계에서 선택 사항이 될 수 있다는 것만 확인한다.

> 위 네 항목의 개념을 구별하는 것이 목표다. 구체적인 서버 설정, Streaming 코드, 동시성·성능 튜닝은 이번 교시에서 구현하지 않는다.

## 13. 실무 판단: 직접 실행과 Serving의 장단점만 외우지 말기

다음 조건을 보자.

> 회사 내부에만 보관해야 하는 PDF가 있다. 직원들의 PC는 성능이 낮지만 사내 GPU 서버 한 대를 사용할 수 있다. 여러 직원이 문서 처리 기능을 이용할 예정이다.

이때 모델을 직원 PC마다 별도 실행하기보다 **사내 Model Server를 두는 설계**가 후보가 될 수 있다.

```text
직원들의 Application
         ↓
     사내 Backend
         ↓ 사내 Network
     Model Server
         ↓
      GPU / Model
```

이 방안의 근거는 'Ollama라는 제품이 유명해서'가 아니다. **모델을 실행할 자원은 한곳에 있고, 여러 사용자가 기능을 요청해야 한다**는 요구 때문이다.

그러나 여기서 결정하지 못한 것도 남는다. 예를 들어 사내 데이터 접근 권한, 동시 요청 처리, 네트워크 연결, 장애 시 대체 방법, 실제 모델의 자원 요구량은 별도로 확인해야 한다. 따라서 **가능한 Architecture 후보**이지 검증 없이 바로 운영 가능한 완성 설계는 아니다.

## 16. 학생 활동 ③ — 요구사항에 따른 Architecture 선택

각 상황에서 직접 실행 또는 Model Serving을 제안하고 근거를 쓴다. 답은 한 가지일 필요가 없다.

| 상황 | 가장 먼저 확인할 질문 |
|---|---|
| 단일 Python 실험에서 모델의 중간 Tensor를 분석한다 | Model 내부를 직접 다뤄야 하는가? |
| 여러 사내 앱이 공통 생성 기능을 사용한다 | 실행 프로세스를 공유할 필요가 있는가? |
| 네트워크 연결이 어려운 독립 PC에서 AI를 사용한다 | 실행 자원과 모델 파일을 PC에 준비할 수 있는가? |
| 고객 요청이 동시에 증가하는 서비스에 적용한다 | 응답 시간과 처리량 요구는 무엇인가? |

**예상 판단:** 첫 상황은 직접 실행이 자연스럽고, 두 번째는 공통 Serving이 후보가 된다. 세 번째는 Local 실행을 검토하되 **직접 실행인지 Local Server인지** 추가 요구로 판단한다. 네 번째는 Serving 운영 요구를 반드시 검토해야 하며, 모델 선택만으로 결론을 내리지 않는다.

## 17. 학생 활동 ④ — 설계에 빠진 정보 찾기

다음 문장을 그대로 설계 확정안으로 사용할 수 있을까?

> “보안상 Local AI를 선택했다. 서버는 하나이고 빠를 것이다. 따라서 모든 직원이 문제없이 사용할 수 있다.”

문제점을 찾아보자.

- Local이라는 말만으로 접근 통제와 데이터 보호가 확인되는가?
- Server 한 대의 자원으로 동시 요청을 처리할 수 있는가?
- 모델 로드 시간, Latency, Throughput을 실제 측정했는가?
- 직원 PC와 서버의 통신 범위와 장애 상황을 정했는가?

**해설:** 모두 추가 확인이 필요하다. Architecture는 '어떤 도구를 쓴다'는 선언이 아니라, **어떤 요구를 어떤 실행 구조로 충족할지**를 설명해야 한다.

## 18. 헷갈리기 쉬운 질문과 답

**Q1. Ollama는 모델인가요?**  
아니다. 이 수업에서는 Local Model을 실행·제공하는 Runtime/Serving 도구로 구분한다.

**Q2. Transformers는 무조건 Model Server 없이만 사용할 수 있나요?**  
아니다. Python에서 직접 모델을 다루는 Library이며, 개발자가 그 실행 기능을 별도 서버로 제공하도록 구성할 수도 있다.

**Q3. Local AI라면 API를 사용하지 않나요?**  
아니다. 같은 컴퓨터 안의 localhost HTTP나 조직 내부 네트워크를 사용할 수 있다.

**Q4. Server가 있으면 Cloud인가요?**  
아니다. 서버는 다른 프로그램에 기능을 제공하는 역할을 뜻하며, 실행 위치는 별도로 확인한다.

**Q5. Model Serving을 도입하면 여러 요청이 항상 더 빨라지나요?**  
아니다. 공통 실행 지점은 관리상의 이점을 줄 수 있지만 자원 경쟁·대기 등도 생길 수 있다.

**Q6. Model Serving이 Training인가요?**  
아니다. 여기서는 이미 학습된 모델의 추론 기능을 요청 가능한 형태로 제공한다.

**Q7. Ollama Python Client와 Ollama Runtime은 같은가요?**  
아니다. Client는 API 요청을 보내는 쪽에, Runtime은 모델 실행을 맡는 쪽에 있다. 실제 설치나 호출은 다음 시간에 확인한다.

**Q8. GGUF나 Quantization을 지금 알아야 하나요?**  
이번 교시에서는 Runtime마다 지원하는 모델 형식이 다를 수 있다는 정도만 이해한다. 형식과 정밀도 조정의 상세 내용은 뒤 과정의 범위다.

## 20. 이번 교시 핵심 정리

오늘은 모델이 Token을 생성하는 방법이나 Training 수식을 다시 배우지 않았다. **그 추론 기능을 어느 실행 프로세스에서 관리하고, 다른 프로그램에 어떤 방식으로 제공할지**를 배웠다.

```text
Direct Execution: Application Process → Model Library → Model

Model Serving:    Application → API → Model Runtime / Server → Model
```

- **Transformers:** Python에서 모델을 직접 제어하고 실행하는 방식에 활용할 수 있다.
- **Ollama:** Local Model 실행과 API Serving을 별도 도구로 제공한다.
- **Local과 Cloud:** 서버 유무가 아니라 모델의 실행 위치·운영 주체와 관련된다.
- **Serving 설계:** 모델만이 아니라 Runtime, Hardware, 요청 처리, 운영 책임을 함께 고려해야 한다.

> **반드시 기억할 문장:** 모델을 직접 실행하는 것과 모델 실행 기능을 서비스로 제공하는 것은 다른 Architecture 선택이다.
