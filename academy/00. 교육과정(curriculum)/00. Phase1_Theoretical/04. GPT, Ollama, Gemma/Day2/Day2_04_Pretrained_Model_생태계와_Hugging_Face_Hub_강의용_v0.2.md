# Day 2 - 4교시. Pre-trained Model 생태계와 Hugging Face Hub

## 개요 — 이제 ‘모델을 만드는 사람’에서 ‘모델을 선택하는 개발자’로 시선을 옮긴다

앞선 3교시에서는 작은 PyTorch Model을 학습시키고, 같은 Source Code에서도 Weight와 Bias가 학습 전후 달라지는 것을 확인했습니다. 이번에는 **다른 사람이 이미 학습한 모델을 실제 프로젝트에 쓰고 싶을 때 무엇을 먼저 확인해야 하는가**에 집중합니다.

예를 들어 개발 환경이 다음과 같다고 가정합시다.

> 한국어 문서를 요약하는 기능이 필요하다. 실행 환경은 메모리 16GB인 교육용 PC이고, 외부로 문서 내용을 보내지 않는 구성을 검토하고 있다.

검색 결과에서 모델을 발견했다고 바로 다운로드하면 될까요? 아닙니다. 문서를 요약할 수 있는 모델인지, 한국어를 다루는지, 사용 조건에 문제가 없는지, 실제 PC에서 실행 가능한지, 안내된 성능을 어떻게 확인해야 할지 살펴봐야 합니다.

이번 시간은 **모델을 실행하는 시간**이 아니라 **모델 후보를 찾아 읽고 선택 근거를 기록하는 시간**입니다. 모델을 Python에 로드하여 텍스트를 생성하는 과정은 **다음 5교시**에서 다룹니다.

```text
프로젝트 요구사항
      ↓
모델 후보 탐색
      ↓
Model Repository 확인
      ↓
Model Card·Metadata·Files 검토
      ↓
사용 가능 / 추가 확인 / 부적합 판정
      ↓
다음 교시의 실제 실행 후보 확정
```

---

# 1. 학습 목표

수업을 마치면 학생은 다음을 할 수 있어야 합니다.

1. Pre-trained Model을 처음부터 학습하지 않고 가져다 쓰는 이유를 **실제 프로젝트의 의사결정**과 연결해 설명한다.
2. Hugging Face Hub에서 **Models·Datasets·Spaces**의 역할을 구분하고, Model Repository를 탐색하는 목적을 설명한다.
3. Model ID, Model Repository, Revision의 관계를 설명하고 자신이 확인한 후보를 식별할 정보를 기록한다.
4. Model Card에서 **Task·Language·License·Intended Use·Limitation·Evaluation**을 찾아 읽는다.
5. Model Card에 정보가 없을 때 추측으로 채우지 않고 **미확인 사항**으로 기록한다.
6. Repository의 `README.md`, `config.json`, `*.safetensors`, Tokenizer 관련 파일이 대체로 어떤 역할을 하는지 구분한다.
7. Architecture와 학습된 Weight의 관계를 파일 수준에서 이해하고, **Parameter 개수가 같다는 이유로 파일 호환성을 단정하지 않는다.**
8. 주어진 요구사항을 바탕으로 후보 모델을 비교하고 **선택·보류·제외 이유**를 작성한다.

> **교시 경계:** Day1의 Hub·Transformers 도구 소개를 다시 자세히 강의하지 않습니다. Day2 1교시 Tokenizer의 내부 처리, 2교시 Tensor 연산, 3교시 Training Loop도 반복하지 않습니다. 이번 교시는 **이미 공개된 모델을 읽는 법**이 중심입니다.

# 2. Pre-trained Model을 사용하는 상황

3교시에서 우리가 직접 만든 `nn.Linear(1, 1)`은 학습 구조를 관찰하기 위한 작은 실습 모델이었습니다. 하지만 한국어 요약이나 질문 답변처럼 훨씬 복잡한 작업에 사용할 모델을 매번 처음부터 학습시키는 것은 현실적인 선택이 아닐 수 있습니다.

Pre-trained Model은 **이미 데이터를 이용해 학습된 상태의 모델**입니다. 모델 개발자가 학습한 결과를 배포하면, 애플리케이션 개발자는 그 모델이 자신의 목적에 맞는지 검토한 후 사용할 수 있습니다.

```text
모델 개발자: 모델 설계·학습·평가·배포
                   ↓
              공개된 모델 자산
                   ↓
애플리케이션 개발자: 요구사항 대조·선택·검증·서비스 연결
```

여기서 이번 교시의 질문은 **“학습을 어떻게 수행했는가?”**가 아니라 **“이 모델을 가져다 사용해도 되는가?”**입니다. 모델 학습에 필요한 데이터·하드웨어·시간·비용이 크기 때문에 사전학습된 결과를 활용하는 방식이 실무적으로 중요합니다.

다만 Pre-trained Model을 사용한다는 이유만으로 다음이 보장되는 것은 아닙니다.

- 내 프로젝트에서 필요한 작업을 수행한다.
- 한국어를 충분히 잘 처리한다.
- 조직의 사용 목적과 라이선스에 맞는다.
- 내가 가진 CPU·GPU·메모리에서 실행된다.
- Model Card에 적힌 평가 점수가 내 데이터에서도 그대로 나온다.

이 다섯 가지는 **찾아서 확인해야 하는 조건**이지 Pre-trained라는 이름만으로 주어지는 성질이 아닙니다.

# 3. Hugging Face Hub에서 무엇을 찾는가?

Day1에는 Hugging Face가 단일 Python 라이브러리 이름이 아니라 여러 도구와 서비스를 제공하는 생태계라는 점을 배웠습니다. 여기서는 구분을 다시 외우지 않고 **Hub를 열었을 때 무엇을 조사해야 하는지** 살펴봅니다.

| 구분 | Hub에서 찾아보는 대상 | 개발자에게 필요한 질문 |
|---|---|---|
| **Models** | 배포된 모델과 관련 파일 | 이 모델이 내 작업에 적합한가? |
| **Datasets** | 학습·평가 등에 활용할 데이터 자산 | 자료의 목적과 이용 조건은 무엇인가? |
| **Spaces** | AI 애플리케이션·데모를 공유하는 공간 | 기능을 미리 체험하거나 동작을 확인할 수 있는가? |

이번 교시에서는 **Models의 Repository**를 중심으로 학습합니다. Dataset을 불러와 학습하거나 Spaces를 개발하는 실습은 하지 않습니다.

### Model Repository란?

Model Repository는 모델과 관련된 **설명 문서, 설정, Weight, Tokenizer 정보 및 기타 파일을 관리하는 저장소**입니다. 모델마다 실제 파일 구성은 다를 수 있습니다.

```text
Model Repository
├── 모델을 설명하는 문서 / Metadata
├── 모델 구조와 실행 조건을 나타내는 설정
├── 학습된 Weight 파일
├── 입력 처리에 필요한 Tokenizer 파일(해당하는 경우)
├── 기타 설정·예제·기록
└── Version / Revision 이력
```

하나의 저장소에 README만 있는 것이 아니고, 파일 목록에 Weight가 있다고 해서 실행 조건이 모두 설명된 것도 아닙니다. **문서·Metadata·파일 목록을 함께 확인**해야 합니다.

### GitHub와는 어떤 점에서 비슷한가?

Repository, Revision, Version History라는 구조는 GitHub의 소스 관리와 개념적으로 유사할 수 있습니다. 다만 Hugging Face Hub에서 주로 확인하려는 것은 **모델 및 AI 자산에 대한 정보와 파일**입니다.

학생이 기억할 점은 간단합니다. 같은 저장소 이름을 알고 있어도 **어느 버전의 파일과 정보를 확인했는지**에 따라 이후 실행 결과나 비교 조건이 달라질 수 있습니다. 그래서 후보 선정 기록에는 Model ID와 확인한 Revision 정보를 남길 수 있어야 합니다.

# 4. Model ID — 어떤 모델을 확인했는지 정확하게 남기기

Model Repository를 구분할 때 다음과 같은 형태의 ID를 사용합니다.

```text
owner/model-name
```

강의 원문에 등장한 Model ID의 예는 다음과 같습니다.

```text
google-bert/bert-base-cased
```

이 예시는 **Model ID가 어떤 모양인지** 보여주기 위한 것입니다. 해당 모델이 이번 한국어 요약 프로젝트에 적합하다거나 교육장 PC에서 실행 검증되었다는 뜻은 아닙니다.

일반적으로 `owner`는 모델을 게시한 계정이나 조직을, `model-name`은 그 안의 저장소 이름을 구분하는 데 사용됩니다. Model ID는 URL 전체와 동일한 개념이 아니라 **저장소를 지정하기 위한 식별자**입니다. 나중에 Library에서 사용할 후보를 지정할 때도 중요합니다.

### Model ID만 적으면 충분할까?

실제 작업에서는 다음 정보를 함께 기록하는 편이 좋습니다.

| 기록할 항목 | 기록하는 이유 |
|---|---|
| Model ID | 어떤 저장소인지 구분하기 위해 |
| 확인 날짜 | 언제 검토했는지 남기기 위해 |
| Revision / Version (확인 가능한 경우) | 같은 이름 아래 변경된 파일과 정보를 구분하기 위해 |
| Model Card 또는 Repository 위치 | 판단 근거를 다시 찾아보기 위해 |
| 확인 결과 | 선택·보류·제외 이유를 공유하기 위해 |

**강사 시연 질문:** 모델 이름은 같지만 Revision이 다른 두 파일을 비교한다면, 단순히 모델 이름만 적은 실험 기록으로 충분할까요? 충분하지 않을 수 있습니다. **어떤 상태를 사용했는지** 알아야 비교를 재현할 수 있기 때문입니다.

---

# 5. Model Card — ‘소개 글’이 아니라 선택 근거를 찾는 문서

Model Card는 모델의 목적, 사용법, 특징, 제한사항 등 모델 사용 판단에 필요한 정보를 설명하는 문서입니다. Hugging Face Hub에서는 Model Repository의 `README.md`를 바탕으로 제공될 수 있으며, 본문과 Metadata를 통해 정보를 찾습니다.

하지만 여기서 조심할 점이 있습니다.

> **모든 Model Card가 동일한 목차나 표를 갖고 있는 것은 아닙니다.**

예를 들어 하나의 Model Card에는 `Model Description`이 있고 다른 카드에는 `Model Details`가 있을 수 있습니다. Language나 License 정보는 Metadata에, 한계나 평가 결과는 본문에 적혀 있을 수도 있습니다. **원본 자료의 확인 항목 전체가 화면에서 같은 이름으로 보일 것이라고 기대하면 안 됩니다.**

그래서 읽는 방법은 다음과 같습니다.

1. 모델의 용도와 종류를 찾아본다.
2. 언어·라이선스·실행 조건을 확인한다.
3. 모델의 제한사항과 평가 조건을 읽는다.
4. 필요한 정보가 제공되지 않으면 **‘미기재 / 추가 확인 필요’**로 표시한다.
5. 검토 결과를 프로젝트 요구사항에 대조한다.

### 위치별로 어떤 근거를 찾을 수 있을까?

| 확인하는 위치 | 찾을 수 있는 정보의 예 | 주의할 점 |
|---|---|---|
| Repository의 Metadata | Task/Tag, Language, License, Library 등 | 모든 항목이 항상 제공되는 것은 아님 |
| Model Card 본문 (`README.md`) | Intended Use, Training, Limitation, Evaluation, Usage Example | 작성자가 어떤 정보를 제공했는지 확인해야 함 |
| Files / Versions | Configuration, Weight, Tokenizer, 파일 분할·버전 | 파일명만으로 내용·호환성·품질을 확정할 수 없음 |

**빈칸을 추측으로 채우지 않는 것**도 기술 검토 능력입니다. 특히 라이선스, 실행 메모리 요구량, 한국어 성능과 같은 항목을 추측으로 ‘가능’ 처리하면 실제 서비스 단계에서 문제가 생길 수 있습니다.

# 6. Model Card 첫 번째 검토 — 무엇을 하도록 만들어졌는가?

모델을 고를 때 가장 먼저 봐야 할 것은 인기도가 아니라 **Task와 Intended Use**입니다.

원본 강의에서 예시로 든 모델 작업은 다음과 같습니다.

| Task | 대표적인 결과의 성격 | 이번 시간의 확인 질문 |
|---|---|---|
| Text Generation | 새로운 텍스트 생성 | 필요한 형태의 답변을 만들 수 있는 모델인가? |
| Text Classification | 주어진 텍스트를 범주로 분류 | 생성이 아니라 분류를 위해 만들어진 모델인가? |
| Image Classification | 이미지 분류 | 내 입력인 문서 텍스트와 맞는가? |
| Automatic Speech Recognition | 음성을 텍스트로 인식 | 입력이 음성인가? |
| Text-to-Image | 설명을 바탕으로 이미지 생성 | 생성하려는 결과가 이미지인가? |
| Embedding | 입력을 수치 표현으로 변환 | 문장 생성 대신 검색 등에 사용할 표현이 필요한가? |

이름에 `AI`, `LLM`, `Transformer`가 들어 있어도 곧바로 **대화형 텍스트 생성 모델**이라고 판단할 수는 없습니다. 먼저 Model Card나 Metadata가 무엇을 위한 모델이라고 설명하는지 확인합니다.

### Model Type도 함께 확인한다

실제 후보에 따라 Base, Instruction-tuned, Chat 등과 같은 유형을 보게 될 수 있습니다. 이 용어의 정의는 Day1에서 배웠으므로 여기서는 반복하지 않습니다.

이번에는 **“사용자의 지시에 따라 한국어 요약을 생성하는 기능”**이라는 요구사항에 해당 모델의 유형이 맞는지 판단하는 데 사용합니다. 같은 Family의 Model이라도 Variant에 따라 목적이 다를 수 있으므로 **Family 이름만으로 선택하지 않습니다.**

#### 학생에게 묻기

> 한국어 문서의 요약문을 생성해야 하는데, 이미지 분류용 모델의 Model Card만 확인했습니다. 그 모델을 다운로드해 먼저 실행해 볼까요?

정답은 **먼저 Task가 맞는 후보를 찾아야 한다**입니다. 불필요한 다운로드와 실행 시간을 줄이는 것이 이 단계의 실무적 가치입니다.

# 7. Model Card 두 번째 검토 — 한국어와 사용 조건이 맞는가?

## 7.1 Language: 지원 언어와 실제 품질은 다르다

`English`, `Korean`, `Multilingual` 같은 표기나 설명을 발견할 수 있습니다. 하지만 `Multilingual`이라는 표시 하나가 **모든 언어에서 동일한 품질을 보장**하지 않습니다.

한국어 문서 요약을 위해 확인할 수 있는 질문은 다음과 같습니다.

- 한국어 지원이 명시되어 있는가?
- 한국어 성능 평가나 사용 예제가 있는가?
- 한국어를 지원한다고 하더라도 **요약이라는 작업**에 대한 근거가 있는가?
- 관련 설명이 없어서 자체 테스트가 필요한가?

예를 들어 Model Card에 영어 평가 결과만 있다면 그 점수를 한국어 요약의 근거로 그대로 쓰지 않습니다. **원문에 없는 수치를 추정해서 채우지 않습니다.**

## 7.2 License: 공개되어 있다는 사실과 사용 권한은 별개다

Model Repository가 공개되어 있거나 Model Weight를 내려받을 수 있다는 것만으로 **어떤 회사든 아무 조건 없이 상업적으로 활용하거나 재배포할 수 있다는 뜻은 아닙니다.**

원본 강의가 제시한 라이선스 점검 항목은 다음과 같습니다.

| 점검 항목 | 검토할 질문 |
|---|---|
| Commercial Use | 우리가 하려는 사용이 허용되는가? |
| Redistribution | 모델이나 관련 파일을 재배포할 수 있는가? |
| Attribution | 출처 표시 등 준수할 의무가 있는가? |
| Acceptable Use Policy | 제한되거나 금지된 사용 사례가 있는가? |
| Derivative Model | 변형하거나 조정한 모델에 조건이 있는가? |
| 기타 Restriction | 서비스 목적에 영향을 줄 별도 조건이 있는가? |

`Open Weight = 무제한 사용 가능`이라는 등식은 성립하지 않습니다. 라이선스가 없거나 불분명하면 **‘문제없음’으로 추측하지 않고 ‘확인 필요’**로 기록해야 합니다.

### 판정 예제

> 프로젝트는 상용 서비스를 목표로 하는데, 후보의 Model Card에서 License 항목을 찾지 못했습니다.

이때의 올바른 기록은 다음과 같습니다.

```text
Task 적합성: 추가 검토 가능
License 적합성: 미확인
결정: 즉시 도입 X / 라이선스 원문과 사용 조건 확인 전까지 보류
```

이 교시는 법률 판단을 연습하는 시간이 아닙니다. **결정할 수 없는 조건을 발견하고 조사를 멈추지 않는 습관**을 기르는 시간입니다.

# 8. Model Card 세 번째 검토 — 실제 환경에서 사용할 수 있는가?

이번 교시의 예시 조건은 **16GB RAM을 가진 교육용 PC에서 한국어 문서 요약을 실행하는 것**입니다. 모델의 크기만 확인해서는 충분하지 않습니다.

### 먼저 살펴볼 정보

| 항목 | 왜 살펴보는가? | 확인 가능한 근거의 예 |
|---|---|---|
| Parameter / Model Size | 규모를 가늠하기 위해 | Model Card, 파일 목록의 설명 |
| Hardware Requirement | 실행 환경에 맞는지 확인하기 위해 | 권장 하드웨어 및 메모리 설명 |
| Library / Runtime Compatibility | 사용할 도구와 맞는지 판단하기 위해 | 지원 Library·사용 예시 |
| Context / Sequence 제약 | 다룰 입력 분량에 영향이 있는지 판단하기 위해 | 지원 길이 및 입력 제한 설명 |
| dtype / Quantization 관련 정보 | 모델 배포 형태나 실행 요구 자원에 차이가 있는지 확인하기 위해 | Model Card나 Repository의 배포 설명 |

여기서는 **Memory 계산식이나 Quantization 방법을 실습하지 않습니다.** 원본은 해당 항목이 모델 선택에 영향을 준다고 소개하고 있으며, 이 교시에서는 Model Card에 해당 정보가 제공되는지만 판단합니다. 실행 속도·메모리 측정은 실제 환경에서 모델을 사용하면서 별도로 확인해야 합니다.

### 숫자의 의미를 구분하자

`1B`, `3B`, `7B` 등의 표기는 모델 규모를 나타내는 데 사용할 수 있습니다. `B`는 일반적으로 Billion을 뜻합니다. 이 표기를 본다고 해서 **정확한 다운로드 용량, 메모리 필요량, 응답 속도**를 곧바로 알 수 있는 것은 아닙니다.

예를 들어 둘 다 `7B`라는 표기가 있더라도 저장 형식이나 실행 조건이 다를 수 있습니다. 따라서 **Model Size라는 숫자와 내 PC에서 실제 실행 가능한지의 판정은 별개**입니다.

### 정보가 없는 Model Card는 어떻게 할까?

많은 Repository에서 모든 하드웨어 요구사항을 제공하지 않을 수 있습니다. 이때는 다음처럼 기록합니다.

```text
CPU 실행 가능 여부: 미확인
RAM 요구량: 미기재
GPU 필수 여부: 미확인
확인 필요: 모델 배포 설명 또는 실제 수업 환경에서의 실행 시험
```

**‘정보 없음’은 ‘문제없음’이 아닙니다.** 이 점은 뒤의 학생 활동에서도 채점 기준으로 사용합니다.

# 9. Model Card 네 번째 검토 — 한계와 평가 결과 읽기

## 9.1 Limitation은 모델이 ‘못하는 부분’을 찾는 항목

Model Card에서는 모델의 강점뿐 아니라 `Known Limitations`, `Bias`, `Unsupported Use`, `Safety Considerations`, 언어·도메인별 제한 같은 내용이 제공될 수 있습니다.

예를 들어 한국어 문서 요약에 모델을 쓰려는데 **영어 중심으로 학습되었고 한국어 성능에 제한이 있다**고 명시되어 있다면, 아무리 유명한 모델이라도 해당 프로젝트의 좋은 후보가 아닐 수 있습니다.

이 항목을 읽는 목적은 막연히 위험하다고 판단하는 것이 아닙니다. **우리 서비스 요구사항과 충돌하는 제한이 있는지 확인하는 것**입니다.

| 모델에 적힌 제한 또는 정보 부족 | 프로젝트에서의 판단 |
|---|---|
| 목표 언어에 대한 제한 | 한국어 성능을 별도로 확인해야 함 |
| 특정 용도는 권장하지 않음 | 해당 사용 목적과 충돌하는지 확인 |
| 일부 데이터 유형에서 성능 저하 | 실제 입력 자료와 유사한지 검토 |
| Limitation 항목이 없음 | 제한이 없다고 결론 내리지 말고 미확인으로 기록 |

## 9.2 Evaluation은 숫자보다 ‘무엇을 어떻게 측정했는가’를 본다

Model Card에 성능 점수나 Benchmark가 적혀 있다고 해도, 그 숫자만으로 최적 모델을 선정하면 안 됩니다.

원본 강의의 검토 질문을 **평가 근거 확인표**로 바꾸면 다음과 같습니다.

| 질문 | 왜 중요한가? |
|---|---|
| 어떤 Dataset을 사용했는가? | 평가 데이터와 우리 업무 데이터가 다를 수 있음 |
| 어떤 Metric인가? | 서로 다른 기준의 점수를 직접 비교하면 안 됨 |
| 어떤 Prompt 또는 Setting인가? | 실행 조건이 다르면 결과도 달라질 수 있음 |
| 어떤 Model Version인가? | 다른 Revision의 결과를 잘못 비교하지 않도록 |
| 우리 Task와 관련 있는가? | 다른 작업의 성능은 내 작업의 성능을 대신하지 못함 |

### 점수 비교 활동 — 가상 데이터

다음 숫자는 실제 모델 성능이 아니라 **평가 조건을 확인하기 위한 가상 예시**입니다.

```text
후보 A: 90점 — 영어 평가 데이터
후보 B: 86점 — 한국어 평가 데이터
요구사항: 한국어 문서 요약
```

A를 바로 선택할 수 있나요? **없습니다.** 점수를 매긴 작업·지표·설정·Version이 같은지부터 확인해야 합니다. B를 바로 선택할 수도 없습니다. 어떤 요약 평가인지, 우리 문서와 얼마나 유사한지, 사용 조건을 충족하는지도 필요합니다.

> **평가 결과가 좋다**는 사실과 **우리 프로젝트에 맞는다**는 판단은 연결되어야 하지만 같은 문장이 아닙니다.

# 10. Repository Files — 이름을 보고 역할을 구분하기

Model Card를 읽은 다음에는 Files 영역을 확인합니다. 파일을 실행하는 것이 아니라 **무슨 정보를 담고 있는지 분류**합니다.

원본 강의에서 예시로 든 Repository 구조는 다음과 같습니다.

```text
Model Repository (개념 예시)
├── README.md
├── config.json
├── tokenizer.json
├── tokenizer_config.json
├── model.safetensors
└── generation_config.json
```

모든 Repository가 이 목록을 그대로 갖는 것은 아닙니다. 이름이 다를 수 있고 일부 파일이 없거나 추가되어 있을 수 있습니다.

| 파일 예 | 이 교시에서 확인할 역할 | 학생이 해서는 안 되는 추측 |
|---|---|---|
| `README.md` | Model Card의 설명과 사용 조건 | 내용이 없으면 사용 조건도 없다고 판단 |
| `config.json` | 모델의 구조·설정 정보 | 파일 이름만으로 모든 설정이 확정됐다고 판단 |
| `model.safetensors` | 학습된 Weight Tensor를 저장하는 파일의 예 | 다른 모델의 파일로 마음대로 대체 |
| `tokenizer.json` | Tokenizer 관련 정보 | 모든 모델이 이 파일을 같은 방식으로 사용한다고 가정 |
| `tokenizer_config.json` | Tokenizer 설정 | Tokenizer가 항상 하나의 파일만으로 완성된다고 가정 |
| `generation_config.json` | 생성 관련 설정 | 이 파일만 보면 실행 결과를 정확히 예측할 수 있다고 판단 |

Day2 1교시에서 Tokenizer의 동작을 이미 확인했습니다. **이번에는 Tokenizer가 어떤 역할인지 다시 설명하지 않고, 배포 저장소에 관련 파일이 존재할 수 있다는 사실만 확인**합니다.

# 11. `config.json`, Architecture, Checkpoint를 연결하기

3교시에서 **Model의 계산 구조와 Parameter는 서로 다른 구성 요소**임을 배웠습니다. 이제 이 구분을 Repository의 파일에서 확인합니다.

- **Architecture:** 모델이 어떤 계산 구조를 가지는지 설명하는 개념
- **Configuration:** 구조를 구성할 때 필요한 설정 정보
- **Weights:** 학습을 통해 얻은 Parameter 값
- **Checkpoint:** 특정 시점의 학습된 Parameter 상태와 관련 정보를 저장한 결과물

이 용어들의 정의를 또 외우는 것이 목적은 아닙니다. **파일을 찾았을 때 어떤 질문을 할지**가 이번 교시의 새 학습입니다.

`config.json`에서 확인할 수 있는 구조 정보의 예는 다음과 같습니다.

```text
Architecture
Number of Layers
Hidden Size
Vocabulary Size
Special Token IDs
```

Model의 종류에 따라 실제 Field와 값은 다를 수 있습니다. 숫자 몇 개를 보고 성능이 좋다고 판단하는 것은 이 단계의 목표가 아닙니다.

### Checkpoint가 왜 여러 개 있을 수 있을까?

원본 강의에는 학습 중간이나 완료 시점의 Parameter를 각각 저장하는 예가 있습니다.

```text
어느 Training 시점의 Weight를 저장했는가?
         ↓
Checkpoint A / Checkpoint B / Final Checkpoint
```

Checkpoint라는 이름은 특정 시점의 학습 상태를 남기는 일과 연결됩니다. 따라서 Repository를 볼 때는 **같은 이름의 Model Family인지**뿐 아니라 **어떤 학습 결과를 배포한 파일인지** 살펴볼 필요가 있습니다.

# 12. `.safetensors` — Parameter 수가 같으면 교체해도 될까?

`*.safetensors`는 Tensor를 저장하는 형식이며 모델의 Weight를 배포할 때 사용할 수 있습니다. 원본 강의와 해당 교시의 보충 Q&A는 중요한 오해 하나를 다룹니다.

> **두 모델의 Parameter 수가 같다는 사실만으로 Weight 파일을 서로 바꿔 사용할 수는 없습니다.**

왜 그럴까요? Model의 구조에 따라 Parameter의 이름, Tensor Shape, Layer 구성 등이 달라질 수 있기 때문입니다.

```text
Model A
  구조 A + Weight A

Model B
  구조 B + Weight B

총 Parameter 수가 비슷하거나 같더라도
각 Weight가 들어갈 위치와 Shape가 다를 수 있음
```

예를 들어 `config.json`이 요구하는 Weight Shape와 실제 Weight 파일의 Tensor Shape가 일치하지 않는다면 호환 문제가 발생할 수 있습니다. `7B`와 같은 규모 표기는 호환성을 보장하는 조건이 아닙니다.

### 학생 활동 — 어떤 결론까지 가능한가?

**상황 1.** 두 Repository 모두 `7B`라고 설명합니다.

- 내릴 수 있는 결론: Parameter 규모를 비슷하게 설명하고 있다.
- 내릴 수 없는 결론: 서로의 `.safetensors`를 교체해도 반드시 실행된다.

**상황 2.** 동일한 Architecture를 사용한다고 설명합니다.

- 내릴 수 있는 결론: 구조가 같다는 근거가 하나 있다.
- 아직 확인할 것: 실제 Weight와 Configuration의 구조·이름·Shape 호환성 등.

여기서 파일을 직접 교체하거나 Weight를 로드해 보지는 않습니다. **이 교시는 저장소를 검토하고 문제를 예방하는 단계**입니다.

### Weight 파일이 여러 개라면?

큰 모델에서는 원본처럼 Weight가 여러 파일로 분할될 수 있습니다.

```text
model-00001-of-00004.safetensors
model-00002-of-00004.safetensors
...
```

여러 개의 파일이 보인다는 이유만으로 서로 다른 네 개의 모델이라고 판단하면 안 됩니다. **하나의 모델에 필요한 Weight가 분할되어 있는지** 파일 구성과 설명을 확인해야 합니다.

# 13. 실행 전 확인할 접근 제한 — Public, Private, Gated

Hub에서 Repository를 발견했다고 해서 누구나 같은 방식으로 바로 모든 파일을 사용할 수 있는 것은 아닙니다.

원본 강의에서 주의하라고 한 접근 형태는 다음과 같습니다.

| 상황 | 예상되는 확인 사항 | 4교시에서 할 일 |
|---|---|---|
| 공개 접근 가능 | 기본 설명과 파일 확인 | 후보 정보 기록 |
| Private Repository | 계정·접근 권한 등 | 접근 가능 여부 확인, 권한 없으면 보류 |
| Gated Model | 승인·사용 조건 동의 등 | 조건과 절차 확인, 완료 전 사용 가능 판정 금지 |

일부 모델은 Login, Access Request, 사용 조건 동의, License Agreement 등의 절차가 필요할 수 있습니다. **화면에서 이름이 검색되는 것과 Weight를 사용할 수 있는 권한은 구분**해야 합니다.

보안상 Hugging Face Access Token 등의 인증 정보를 실제 Source Code나 제출용 활동지에 적어서는 안 됩니다. 이번 교시에서는 계정 인증을 직접 구현하거나 다운로드 명령을 실습하지 않습니다.

접근 권한을 확인할 수 없다면 다음처럼 기록합니다.

```text
접근 상태: 확인 필요
원인: Gated Model / 승인 여부 미확인
결정: 실행 후보로 확정하지 않음
```

모델 선정에서 ‘보류’라는 판정도 정당한 결과입니다.

# 14. Library와 Model 파일의 관계 — 다음 교시를 위한 경계

Day1에서 Hub와 Transformers의 역할 구분을 배웠습니다. 여기서는 추가적인 도구 분류 문제를 내지 않고 **선택한 Repository가 나중에 Python에서 사용될 때 무엇을 확인해야 하는지**만 연결합니다.

```text
이번 교시: Model ID·Repository·Card·Files 확인
                         ↓
다음 교시: 선택한 모델을 Python에서 불러오고 실행
```

원본에는 `AutoTokenizer`, `AutoModel`, `AutoModelForCausalLM`, `from_pretrained()`라는 이름이 등장합니다. 이들은 **다음 5교시에서 실제 호출 코드와 연결**합니다.

지금 반드시 알아둘 내용은 두 가지뿐입니다.

1. Repository의 Model ID나 파일 경로가 다음 실습에서 모델 자원을 지정하는 데 사용될 수 있습니다.
2. 모든 Model을 모든 Task용 Library Class에 넣어 사용할 수 있는 것은 아니므로 **모델의 Task와 Library 호환성을 선택 단계에서 확인**해야 합니다.

**이번 교시에 실행하지 않는 것:** `from_pretrained()`로 모델 다운로드·로드하기, Tokenizer 실행하기, `generate()` 호출하기, 모델의 Device 변경, Cache 동작 시험. 모두 후속 실습의 학습 성과로 남겨둡니다.

# 15. 모델 선택 사례 — 한국어 문서 요약, 16GB RAM 환경

개요에서 제시한 상황으로 돌아갑니다. 이번 사례에서 할 일은 **가장 유명한 모델 이름을 맞히는 것**이 아닙니다. 후보 모델마다 필요한 정보를 찾아 ‘사용 가능성’을 판단하는 것입니다.

### 프로젝트 요구사항

```text
목표 기능: 한국어 문서 요약
입력: 한국어 문서 텍스트
출력: 한국어 요약문
실행 조건: RAM 16GB 교육용 PC
데이터 조건: 외부 전송을 피하는 실행 방식 검토
운영 조건: 모델의 사용 권한과 사용 목적이 명확해야 함
```

위 조건 중 `16GB`라는 숫자가 있다고 해서 어떤 모델이 무조건 실행된다고 판정할 수는 없습니다. **후보의 실제 실행 요구사항**을 별도로 확인해야 합니다.

### 후보 검토 순서

**1단계 — Task:** 텍스트 생성·요약 목적에 맞는 모델인가? 단순 분류·Embedding 전용 모델이면 요구사항과 다를 수 있습니다.

**2단계 — Language:** 한국어에 대한 지원 설명과 평가 근거가 있는가? 영어 성능만으로는 판단하지 않습니다.

**3단계 — Model Type:** 요청한 형식으로 요약문을 작성할 수 있는 유형인지 확인합니다.

**4단계 — License와 Access:** 해당 수업 및 향후 서비스의 사용 조건에 맞는가? 접근 승인이나 사용 제한은 없는가?

**5단계 — 실행 조건:** Model Size, Hardware 요구량, Library 호환성 등으로 교육용 PC에서 시험할 가치가 있는지 판단합니다.

**6단계 — Limitation과 Evaluation:** 한국어 문서 요약과 충돌하는 한계가 있는가? 성능 점수의 평가 조건은 우리 작업과 관련이 있는가?

**7단계 — 결론:** ‘선정’, ‘보류’, ‘제외’ 중 하나를 적고 근거와 미확인 사항을 함께 남깁니다.

### 선택 결과를 문장으로 설명하는 연습

좋지 않은 기록:

> 유명한 모델이고 Parameter도 많아서 선정했습니다.

개선된 기록 예시(특정 실모델에 대한 사실을 주장하는 문장이 아니라 작성 형식 예시입니다):

> 후보 A는 Model Card에 한국어 텍스트 생성 용도가 안내되어 있으므로 검토를 계속하겠습니다. 그러나 상업적 사용 조건과 16GB RAM 환경의 실행 가능성을 아직 확인하지 못했으므로, **실제 실행 후보 확정은 보류**합니다.

학생이 **좋은 후보와 확정 가능한 후보를 구분**할 수 있어야 이번 교시 목표에 도달한 것입니다.

# 16. 강사 시연 — 실제 Repository 한 곳을 함께 읽기

이 활동은 **Model Card를 정확하게 읽는 시연**입니다. 강사는 교육장 네트워크와 접근 권한을 확인하고, 원본 강의가 요구한 조건에 맞는 Repository 한 곳을 수업 전에 선택합니다.

### 시연 순서

1. Repository의 ID를 보여주고 학생이 그대로 기록하게 합니다.
2. Model Card를 찾아 설명 문서와 Metadata를 구분해 봅니다.

5. Files / Versions에서 문서·설정·Weight·Tokenizer 관련 파일을 분류합니다.
6. **표시되지 않은 항목**이 무엇인지 함께 체크합니다.
7. 모델을 지금 바로 사용할지, 추가 확인이 필요한지 결정합니다.

# 21. 학생이 자주 하는 질문

### Q1. Hugging Face에 있으면 누구나 바로 사용할 수 있나요?

아닙니다. Private 또는 Gated Model처럼 추가 권한·승인·사용 조건 확인이 필요한 경우가 있습니다. 공개 여부와 License 역시 별개입니다.

### Q2. Model Card의 모든 항목이 표로 완성되어 있나요?

아닙니다. Metadata와 본문에 흩어져 있거나 일부가 기재되지 않을 수 있습니다. **어디에서 어떤 근거를 찾았는지** 기록해야 합니다.

### Q3. Model Card에 RAM 요구량이 없는데 제 PC에서 실행된다고 가정해도 되나요?

안 됩니다. Model Size나 설명만으로 확정하지 않고 실제 하드웨어 요구사항을 추가로 검토해야 합니다.

### Q4. `model.safetensors`는 Python Source Code인가요?

아닙니다. 학습된 Parameter Tensor를 담을 수 있는 파일 형식입니다. Architecture나 Configuration과도 구분해야 합니다.

### Q5. 두 Model의 Parameter 수가 같으면 Weight 파일을 교환해도 되나요?

그렇지 않습니다. Model Architecture, Parameter 이름·구조·Shape와 설정이 호환되어야 하므로 **개수만 같다는 근거로 교환하면 안 됩니다.**

### Q6. Model Repository에서 점수가 가장 높은 모델을 고르면 되나요?

아닙니다. 평가 데이터·지표·설정·Model Version이 자신의 Task와 관련되는지 확인해야 합니다.

### Q7. `from_pretrained()`는 오늘 실행하나요?

아닙니다. 이번에는 Model ID와 Repository를 조사합니다. **다음 5교시에서 실제 모델 로딩과 추론 코드를 실행**합니다.

### Q8. Model Card에 Limitation이 없으면 한계가 없다는 뜻인가요?

아닙니다. **한계가 없다고 증명된 것이 아니라, 해당 정보를 찾지 못한 것**일 수 있습니다. 필요한 추가 평가를 계획합니다.

7. 후보를 ‘선정’하지 않고 ‘보류’하는 합리적인 상황을 하나 설명할 수 있나요?

---

# 23. 이번 교시 핵심 정리

오늘 가장 중요한 변화는 **용어를 아는 것에서 근거를 읽고 선택하는 것**으로 이동했다는 점입니다.

```text
Model을 찾는다
    ↓
Model ID / Revision 기록
    ↓
Model Card·Metadata 읽기
    ↓
Task·Language·License·실행 환경 확인
    ↓
Limitation·Evaluation 확인
    ↓
Repository Files 구성 확인
    ↓
선정 / 보류 / 제외 + 근거 작성
```

학생이 반드시 기억할 내용은 다음 네 가지입니다.

1. **Hugging Face Hub의 Model Repository**는 모델 설명과 관련 파일을 확인하는 장소입니다.
2. **Model Card는 고정된 완성형 스펙표가 아닙니다.** 누락된 정보는 추정하지 않습니다.
3. **모델의 크기·인기도·공개 여부는 곧바로 적합성이나 사용 허가를 뜻하지 않습니다.** Task와 사용 조건을 확인해야 합니다.
4. **Architecture와 Weight가 호환되어야 합니다.** 같은 Parameter 수나 파일 형식만으로 호환성을 판단하지 않습니다.

이번 수업에서 작성한 **모델 후보 검토표**는 다음 교시에서 실제로 실행해 볼 모델을 결정하는 데 활용합니다. 단, 문서 검토만 끝난 후보는 아직 ‘실행 검증 완료 모델’이 아닙니다.

# 24. 다음 교시 연결 — 선택한 모델을 실제로 실행하려면?

4교시는 **어떤 모델을 사용해 볼 것인지 결정하는 단계**였습니다. 이제 다음 질문으로 이동합니다.

> 저장소에서 확인한 Model ID와 Model 파일을 Python 프로그램에서 실제로 어떻게 사용할까요?

**Day2 5교시 — Transformers로 Pre-trained Model 직접 실행하기**에서는 이번 시간에 정리한 Model ID와 Model Card 확인 결과를 바탕으로 다음 과정을 실제 코드로 수행합니다.

```text
이번 교시의 결과: 후보 Model ID와 검토 기록
                   ↓
다음 교시에서 실습할 것:
Tokenizer / Model 로드
                   ↓
입력 준비
                   ↓
Inference / Generation
                   ↓
출력 확인
```

따라서 **이 교시에서는 모델 다운로드, `from_pretrained()` 호출, `generate()` 실행을 미리 실습하지 않습니다.** 모델이 검색되는지, 문서와 파일을 읽고 사용 조건을 설명할 수 있는지까지가 4교시의 완료 기준입니다.
